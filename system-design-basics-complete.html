The words everyone uses and nobody defines

Latency vs. throughput
Latency is how long one request takes; throughput is how many you finish per second. They trade against each other, and improving one often degrades the other — batching is the classic example.
p50, p99, p99.9
Percentiles of response time. p99 = 1% of requests are slower than this. Averages hide outages; percentiles don't. At scale, p99 is somebody's whole experience.
Horizontal vs. vertical scaling
Vertical is a bigger box — simple, instant, and it runs out. Horizontal is more boxes — unlimited in principle, and it makes everything else in this series necessary.
Stateless
A server that keeps nothing between requests that it couldn't reconstruct. It's what makes servers interchangeable, which is what makes load balancing, autoscaling and rolling deploys possible.
Idempotent
Doing it twice has the same effect as doing it once. The property that makes retries safe, and therefore the property that makes distributed systems tolerable.
Backpressure
A system under strain telling its callers to slow down, rather than silently queueing until it dies. The opposite of an unbounded buffer.
Hot key / hot shard
One key or one partition receiving wildly more traffic than its peers. Adding capacity doesn't help, because the routing sends it all to the same place regardless.
Eventual consistency
If writes stop, all replicas converge on the same value — eventually. It says nothing about how long that takes, which is the part that bites.

Understanding Caching

What a cache really is, where caches live, the read/write patterns worth knowing, and the parts that quietly break in production — explained for developers.

The opener to Scaling Databases, Load Balancing, Message Queues, Reliability, and Consistency & CAP.

◇ the ninety seconds after the key expired

19:42 on a Tuesday, the busiest hour of the week. One key — the homepage feed, cached for an hour, requested about 8,000 times a second — reaches the end of its TTL. Every one of those 8,000 requests looks in the cache, finds nothing, and does the obvious thing: asks the database. The query takes 40 ms when the database is idle. It is not idle; it is now running 8,000 of them at once, so it takes four seconds, then twelve. Clients time out at two seconds and retry, which adds a second wave on top of the first. Nobody deployed anything. Nobody's disk failed. A timer ran out, and by 19:44 the site is down.

1. What a cache actually is

A cache is a small, fast store that keeps copies of data close to where it's needed, so you don't have to redo expensive work — a database query, an API call, a heavy computation, a network round-trip. You spend a little memory and some added complexity to buy a lot of speed and a much lighter load on the systems behind it.

The reason it matters is a gap in speed. Reading from an in-memory cache is measured in microseconds (local) to well under a millisecond (a Redis hop); the same request that falls through to a database and back can take tens of milliseconds — often orders of magnitude slower. When most requests are answered by the cache, average latency collapses and the origin barely notices the traffic.

The whole tension in one line "There are only two hard things in Computer Science: cache invalidation and naming things." — attributed to Phil Karlton. Caching is easy to add and hard to keep correct. That's the real subject of this guide.

These layers compound: one page load might be served partly from the browser, partly from the CDN, and partly computed fresh. Each layer needs its own story for staying correct.

Local vs. distributed An in-process cache is fastest (no network hop) but every server has its own copy — they can disagree, and you multiply memory use. A distributed cache (Redis/Memcached) adds a network hop but gives every instance one shared, consistent view. Once you have more than one server, distributed is usually the answer.

3. Read/write strategies

Each pattern answers two questions: who talks to the cache, and when does the cache get written. The read patterns decide how misses get filled; the write patterns decide how the cache stays in step with the source of truth.

Cache-aside (lazy loading) — the default

The application manages the cache. On a read: check cache → hit returns it → miss reads the DB, writes the value into the cache, then returns it. On a write: update the DB and invalidate the cached entry.

  • + Only requested data is cached (lean, cheap). If the cache disappears, reads still return — they fall through to the database instead of erroring.
  • − The first request for any key always misses (cold start). The app carries the caching logic. A small window exists where DB and cache can disagree.
"Resilient to cache failure" has an asterisk on it You will read that cache-aside means "if the cache dies, the app still works." What it actually means is that the app degrades rather than throwing errors — which is not the same thing as surviving. If your cache was absorbing 95% of reads, then the moment it goes away cold your database receives twenty times its normal read load, all at once, with no ramp. Databases do not politely queue; they fall over. Losing a cache cold is one of the best-documented ways to take a service down, and it is why cache warmup, request coalescing and load shedding exist at all. Cache-aside buys you a failure mode you can survive if you built for it — see the Reliability guide for the machinery.

Read-through

Like cache-aside, but the cache knows how to load from the DB on a miss (via a library/provider), so the app only ever talks to the cache. Cleaner app code; loading logic moves into the caching layer.

Write-through

Every write updates the cache and the DB synchronously, together.

  • + Cache and DB stay consistent; any key that's been written is served warm (unwritten or evicted keys still miss).
  • − Every write pays to write both; you cache data that may never be read (bloat). Often paired with cache-aside reads.

Write-back (write-behind)

Write to the cache immediately and return; flush to the DB asynchronously later, in batches.

  • + Very fast writes; absorbs bursts; fewer DB writes.
  • − Data loss risk if the cache node dies before the flush. More complex.

Write-around

Writes go straight to the DB, bypassing the cache; the cache fills later on a read miss.

  • + Avoids flooding the cache with write-heavy data that isn't read soon.
  • − Recently written data is a guaranteed miss on first read.

Read replicas move the same reads to a different machine without introducing a second copy of the truth with its own lifetime — see the Database Scaling guide. Caching wins when the work is expensive to compute, not merely expensive to fetch.

4. Cache-aside in code — and four bugs in it

Everything above is vocabulary. Here is what cache-aside looks like when you actually write it, and it is worth staring at, because this exact function is in production somewhere near you right now.

def get_user(user_id):
    key = f"user:{user_id}"
    cached = redis.get(key)
    if cached:
        return json.loads(cached)

    user = db.query_one("SELECT * FROM users WHERE id = %s", user_id)
    redis.setex(key, 3600, json.dumps(user))
    return user

def update_user(user_id, fields):
    db.update("users", user_id, fields)
    redis.delete(f"user:{user_id}")

Thirteen lines, textbook-correct in shape, and wrong in at least four ways.

1. Nothing coalesces the misses

Ten thousand concurrent requests for the same missing key run this function ten thousand times. Each one sees an empty cache, and each one issues its own SELECT. The cache does not queue them; it does not know they are related. You have built a mechanism that converts a single expiry event into ten thousand simultaneous database queries — the cold open of this guide, in thirteen lines. The fix is single-flight: the first caller to miss takes a short lock and does the load, and everyone else waits for its answer.

2. The TTL is a constant

3600, exactly, for every key. If you warm the cache after a deploy, or a batch job populates ten thousand keys in one loop, all of those keys were written within the same second and will therefore expire within the same second — an hour later, at a time nobody chose. Constant TTLs manufacture synchronised expiry. Randomise it.

3. The stale-forever race

This one is subtle and it is the reason people lose faith in their cache. Follow two threads:

reader GET user:42 → miss reader SELECT ... id = 42 → returns name = "Ada" reader ...descheduled. GC pause, slow network, whatever. writer UPDATE users SET name = "Grace" WHERE id = 42 writer DEL user:42 → key isn't there; no-op reader ...wakes up reader SETEX user:42 3600 {"name": "Ada"} cache = "Ada" db = "Grace" for the next 60 minutes

The invalidation happened before the poisoning write, so it invalidated nothing. No subsequent write will fix this either — the next update_user deletes a key that now holds the stale value, sure, but until someone writes again the cache confidently serves "Ada". Nothing in the system knows it is wrong.

This is why invalidation-on-write alone is not sufficient, no matter how carefully you find every call site. The window is small, but "small" times "a million writes a day" is a support ticket. Narrowing it is possible — Facebook's leases hand the missing reader a token that the writer's delete invalidates, so the late fill is simply rejected; a "delayed double delete" removes the key again a second after the write. Eliminating it needs versioned compare-and-set on the fill.

And it is why a bounded TTL is a safety net rather than a nicety. The TTL is the only thing in the buggy version above that ever repairs this. Every key you cache without an expiry is a key that can be silently wrong forever. If you find yourself writing SET with no TTL, you are betting that your invalidation logic is perfect. It is not.

4. Misses and empty results are the same thing

db.query_one returns None for a user that doesn't exist. json.dumps(None) is the string "null", which gets cached for a full hour and is indistinguishable from a real value. So a user created one second after somebody looked them up stays invisible for an hour. Flip the code the other way — only cache when user is not None — and you get the opposite failure, cache penetration: every request for a non-existent ID misses the cache and hits the database, forever, which is a free denial-of-service for anyone who can guess URLs.

The answer is to cache negatives deliberately, with their own short TTL and a sentinel you can tell apart from real data. (While you are in there: if cached: is also wrong — an empty cached value is falsy, so a legitimately-empty entry is treated as a miss on every read. Test is not None.)

The version that survives contact

MISS = b"\x00none"                  # sentinel: cached "does not exist"

def jitter(ttl):
    return ttl + random.randint(0, ttl // 10)

def get_user(user_id):
    key = f"v3:user:{user_id}"      # v3 = serialisation version
    hit = redis.get(key)
    if hit is not None:
        return None if hit == MISS else json.loads(hit)

    with single_flight(key):        # only one loader per key
        hit = redis.get(key)        # someone may have filled it while we waited
        if hit is not None:
            return None if hit == MISS else json.loads(hit)

        user = db.query_one("SELECT * FROM users WHERE id = %s", user_id)
        if user is None:
            redis.set(key, MISS, ex=jitter(60), nx=True)
        else:
            redis.set(key, json.dumps(user), ex=jitter(3600), nx=True)
        return user

def update_user(user_id, fields):
    db.update("users", user_id, fields)
    redis.delete(f"v3:user:{user_id}")   # delete, don't write the new value in

What changed: misses collapse to one query, TTLs no longer synchronise, non-existent users get a short negative entry instead of either an hour of invisibility or an open channel to the database, and the key carries a schema version. nx=True means a slow reader can never clobber a value someone else has already refreshed — it does not close the stale-forever race, because after the writer's DEL the slot is empty and the stale SET succeeds. Only the bounded TTL saves you there, which is the whole point.

Note also the last line: the writer deletes rather than writing the new value. Two concurrent writers who both write their value into the cache can land in the opposite order they landed in the database. Delete-on-write has one outcome — the next reader goes and finds out — and one outcome is much easier to reason about than two.

Validation & 304s

Instead of re-sending a whole resource, the client revalidates cheaply. The server sends an ETag (a content fingerprint); the browser later sends If-None-Match. If nothing changed, the server replies 304 Not Modified with no body. (Last-Modified + If-Modified-Since is the timestamp-based equivalent.) Big bandwidth savings, still fresh.

CDNs apply these same rules at the edge — which is exactly why the s-maxage (edge lifetime) vs max-age (browser lifetime) split is so useful.

Vary — the header that leaks other people's data

A shared cache keys entries on the URL. That is the whole model. If two different responses can come back from the same URL, the cache needs to be told which request headers made them different, and that is what Vary is for: Vary: Accept-Encoding means "store gzip and brotli separately," Vary: Accept-Language means "store per language."

Now consider GET /dashboard, which renders the logged-in user's name, and which your framework marks Cache-Control: public, max-age=60 because someone was tuning performance. The response varies by the session cookie. The header does not say so. The CDN stores Alice's dashboard under the URL alone and serves it to Bob for the next sixty seconds. This is not a hypothetical class of bug; it has shipped, repeatedly, at companies you have heard of, and it usually surfaces as a support ticket that reads "I'm logged in as someone else."

The blunt instrument, and why you want it Cache-Control: private tells shared caches not to store the response at all — only the end user's own browser may. For anything personalised, reach for private (or no-store if it's sensitive) rather than trying to get Vary exactly right. Vary: Cookie is technically correct and practically useless: if your site sets any cookie at all, every visitor has a unique key and your hit rate goes to roughly zero. The real fix for a page that is mostly public is to cache the public shell and fetch the personalised fragment separately.

6. Eviction & TTL: keeping the cache lean

A cache has finite memory, so it must decide what to drop.

Expiration (TTL) gives every entry a time-to-live; after it lapses, the entry is refetched. TTL is the simplest correctness tool — it bounds how stale data can get without any explicit invalidation. Short TTL = fresher but more misses; long TTL = faster but staler.

Eviction policies decide what to drop when memory is full:

  • LRU (Least Recently Used) — drop what's gone unused longest. The default sweet spot for most workloads.
  • LFU (Least Frequently Used) — drop the least-often accessed; better when popularity is stable.
  • FIFO — drop the oldest inserted, regardless of use.
  • Random / TTL-based — simpler, occasionally the right call.
Eviction ≠ invalidation Eviction is the cache freeing space on its own terms. Invalidation is you deciding a value is now wrong. Conflating the two is a common source of confusion.

7. The hard parts

This is what separates "I added a cache" from "I run a cache in production."

Cache invalidation

The cache holds a copy. The moment the source of truth changes, that copy might be wrong. Three broad approaches:

  • TTL / expiry — let entries lapse. Simple, eventually consistent, but stale within the window.
  • Write-time invalidation — when you update the DB, delete/update the cache entry in the same flow. Fresher, but you must find every place a value is cached, and the DB-write + cache-delete pair isn't atomic (a failure between them leaves you inconsistent).
  • Event-driven invalidation — publish change events (pub/sub, a CDC stream, Redis Pub/Sub) that fan out and purge keys. Scales well, more moving parts, and you inherit every delivery guarantee question the transport has — see the Message Queues guide, because "at-least-once purge" and "at-most-once purge" are very different promises about your cache.
Ask this before caching anything How stale can this specific data safely be? A product catalog tolerates minutes. An account balance tolerates nothing. The answer picks your strategy. Most caches give eventual consistency — for a window, readers may see old data. If that phrase is doing more work than you're comfortable with, the Consistency & CAP guide unpacks exactly what you are and aren't promised.

Cache key versioning

Prefix every key with a schema version: v3:user:123. You will not appreciate why until the deploy where you add a field to the serialised shape, and every instance running the old code starts reading objects that have it while every instance running the new code reads objects that don't. Without a version prefix your options are (a) flush the cache, which is the cold-start outage described below, or (b) write defensive deserialisation forever. With one, you bump v3 to v4, the new code writes and reads new keys, the old keys are read by nobody and quietly age out under their own TTL or get evicted by LRU. It costs six characters per key.

Cache stampede — two different problems that people merge into one

These get taught together and they have different fixes. Getting them confused is why people add jitter to a hot-key problem and are baffled when nothing improves.

Synchronised mass expiry. Many different keys were written at roughly the same moment — a deploy warmed them, a batch job populated them, the cache restarted and refilled in a burst — and because they all got the same fixed TTL, they all expire at roughly the same moment too. One second you're at a 95% hit rate; the next you're at nothing, and the database gets the whole read load.

  • The fix is TTL jitter. Randomise expiry per key — 3600 seconds plus 0–360 random — so the cliff becomes a slope. This is the entire fix, it's three lines, and there's no reason not to do it by default.

A single hot key expiring. One key, requested thousands of times a second. Whenever its TTL lands, every in-flight request misses simultaneously and every one of them queries the database. Note what jitter does here: nothing. There is only one key. It has one expiry time. Randomising when the cliff happens does not stop it happening, and it does not reduce the height of the drop by one request.

  • Request coalescing / single-flight — the first request to miss takes a lock and recomputes; the rest wait for its result. N misses become one query. This is the actual fix.
  • Probabilistic early expiration (XFetch) — see below.
  • Serve-stale-while-revalidate — keep the old value past its nominal freshness and hand it back instantly while one background task refreshes it. Nobody waits, nobody misses.

Probabilistic early expiration (XFetch)

The elegant answer to the hot-key case, and it needs no locks. On every read, alongside the value you store how long the last recompute took (delta) and when the key expires. Then each reader independently rolls a die: recompute early if

now - delta * beta * ln(random())  >=  expiry_time

Because ln(random()) is negative, that left-hand side sits ahead of now, and the further ahead the closer you are to expiry — so the probability of any given reader deciding to refresh climbs smoothly as the deadline approaches. In practice one request somewhere in the last few seconds volunteers, refreshes the value in the background, and every other request keeps getting hits. The key never actually expires under load. beta (default 1) tunes eagerness; the delta term makes expensive values start refreshing earlier, which is exactly what you want.

Metastable failure — why the outage outlives its cause

This is the failure mode that surprises people, because the trigger is gone and the system is still down.

Start from the cold open. The cache empties, the database saturates, requests take longer than the client timeout, clients retry. Now count the load: every user request has become two or three database queries, so the offered load has tripled at the exact moment capacity collapsed. And the cache cannot refill, because filling it requires successful database reads and the database is not completing any. The system has entered a state where the load it is generating is sufficient to keep itself in that state. Restore the cache node, fix the config, undo whatever you did — none of it matters. It is now self-sustaining.

The only exit is to remove load. Shed traffic at the edge, drop the retry budget to zero, disable the expensive endpoint, take a fraction of users offline deliberately. Give the database enough headroom to answer some queries, let those answers populate the cache, watch the hit rate climb, and only then ramp traffic back. Engineers hate this because it means choosing to fail requests during an outage, which feels like making it worse. Waiting feels like the safe option and is the one that keeps you down for an hour. The Reliability guide covers load shedding, retry budgets and circuit breakers in detail — a cache is one of the systems that most needs them.

Hot keys don't get fixed by more cache nodes

Worth being explicit, because it's the first thing everyone tries. A cache cluster distributes keys by hashing them — consistent hashing, usually — which means user:celebrity maps to exactly one node. Adding nodes changes which node. It does not change how many. You can triple your cluster and that one node is still absorbing 100% of the traffic for that key while the other nodes idle. The fixes are different in kind:

  • Key splitting — write the same value under user:celebrity#0 … #7, and have readers pick a suffix at random. Eight keys hash to (probably) eight nodes and the load divides. You pay for it in invalidation: a write now has to clear all eight.
  • A client-local tier — a small in-process cache in front of the shared one, holding the top few hundred keys for a second or two. A one-second local TTL on a key read 8,000 times a second turns 8,000 remote reads into one. The cost is a second of extra staleness and the fact that every instance can now disagree.

8. Operational reality: Redis and Memcached

The patterns above are portable. These are the specific ways the two boxes you'll actually run will embarrass you.

Redis: maxmemory-policy defaults to noeviction

This one catches almost everybody. Redis is a database that people use as a cache, and its defaults are a database's defaults. Set maxmemory, leave maxmemory-policy alone, and when the cache fills up Redis does not evict anything — it starts returning OOM command not allowed when used memory > 'maxmemory' on every write. Your cache stops accepting new entries, which means every miss stays a miss, which means the database takes the full load. A full cache has become a total cache outage, quietly, without a single alarm firing.

  • For a pure cache you want allkeys-lru or allkeys-lfu. Then a full cache does what you expect: makes room.
  • volatile-lru and friends only consider keys that have a TTL set. Forget the TTL on one code path and those keys become permanently un-evictable — and if enough of them accumulate, Redis runs out of eviction candidates and falls back to erroring anyway.
  • Don't leave maxmemory at its default of 0 (unlimited) either. That just moves the failure from Redis to the kernel's OOM killer, which is a worse place for it.
  • Redis's LRU is approximate — it samples a handful of keys (maxmemory-samples, default 5) and evicts the best candidate among them, rather than tracking a true global ordering. Close enough for caching, but don't reason as if it's exact.

Memcached: slab calcification

Memcached carves memory into pages and assigns each page to a slab class — a bucket for items of a particular size range. Once a page belongs to the 1 KB class, it stays there. So if your workload shifts — you start storing bigger serialised objects, or a new feature caches small counters — the new size class runs out of pages and starts evicting aggressively while another class sits half-empty holding memory it no longer needs. Your hit rate drops and your memory graph shows plenty free. That's calcification. Modern versions can rebalance (slab_reassign / slab_automove), but it is not something to discover during an incident: watch per-slab eviction counts, not just the total.

The numbers may not mean what you think

Redis reports mem_fragmentation_ratio in INFO memory — resident memory divided by the memory Redis thinks it's using. Meaningfully above 1 (say 1.5) means the allocator is holding memory it isn't handing back, so your 8 GB instance is really using 12 and your capacity planning is fiction. Below 1 is worse: it means part of your in-memory cache has been swapped to disk, and a cache that reads from disk is just a slow database with extra steps. Check it before you conclude anything from a memory graph. Likewise, keyspace_hits and keyspace_misses are server-wide counters since boot — if three services share the instance, that ratio is nobody's hit rate. Instrument hit rate in your own client, per cache.

9. Real-world examples

Every concept above is running, right now, in systems you use daily. Here's where each one shows up in the wild.

DNS — TTL and eventual consistency, everywhere

Every domain name lookup is cached with a TTL, from your browser down through your OS and ISP resolvers. It's why changing a website's DNS record "takes a while to propagate" — old answers sit in caches until their TTL expires. DNS is the world's largest example of expiration-based invalidation: nobody actively purges those caches, they just lapse. It's also the everyday illustration of eventual consistency — for a window, different people genuinely get different answers.

Your frontend build — immutable caching via content hashing

When Webpack, Vite, or Next.js builds your site, it names files by a hash of their contents: app.9f2a1c.js. Because the filename changes whenever the content changes, the server can safely send Cache-Control: public, max-age=31536000, immutable — cache it for a year. A deploy produces new filenames, so browsers fetch the new files and never serve a stale bundle. This is the fingerprinted asset recipe from section 5, and it's why modern web apps load so fast on repeat visits.

Netflix Open Connect — a CDN with pre-warming

Netflix places its own caching appliances (Open Connect) inside ISP networks, as close to viewers as possible. The clever part is proactive prepositioning: during off-peak hours they push the shows likely to be watched tomorrow onto those edge caches, so the popular content is already there before anyone presses play. That's edge caching plus proactive cache warming at continental scale.

Facebook & Memcached — taming the stampede at scale

Facebook runs one of the largest Memcached deployments in the world (cache-aside in front of their databases). Their well-known "Scaling Memcache at Facebook" work describes a mechanism called leases to tackle exactly the thundering herd problem from section 7: when a hot key misses, only the first request gets a "lease" to recompute it, while others are told to wait briefly and retry (and may be served a slightly stale value) — a coalescing-style throttle, in production, at enormous scale.

Twitter/X timelines — precompute and cache the answer

Rather than assemble your home timeline from scratch on every load, Twitter historically precomputes it: when someone you follow tweets, that tweet is fanned out and written into your cached timeline in Redis ahead of time — a fan-out-on-write approach that materializes each timeline in advance. Reads are then just "fetch the ready-made list." It also shows off the hot key problem — a celebrity with 100M followers can't be fanned out to everyone cheaply, so those accounts are handled differently (merged in at read time). One product, two strategies, chosen by the shape of the data.

E-commerce product pages — different data, different rules

On a large store, the product description and images barely change, so they're cached aggressively at the CDN. But the price and stock count must be near-real-time — you can't sell something you don't have — so those are cached for only seconds, or written through on every change, or fetched live. It's the clearest illustration of the section 7 question: how stale can this specific data safely be? — answered differently for two things on the same page.

The takeaway Notice the pattern: nobody picks one strategy. Netflix pre-warms, Facebook coalesces, Twitter precomputes, a shop mixes long and near-zero TTLs on the same page. Real systems layer these techniques and choose per-data-type based on how fresh it must be.

10. When not to cache

Caching isn't free — it adds a whole new class of bugs (stale reads, invalidation races). Skip or minimize it when:

  • Data changes constantly and must be exact — financial ledgers, inventory at checkout.
  • Data is user-specific and rarely re-read — a low hit rate is pure overhead.
  • Correctness beats latency and you can't tolerate any staleness.
  • The added complexity outweighs a modest speedup.

A cache you can't reason about is a liability, not an optimization. Measure the hit rate — a cache with a low hit rate is often worse than none.

11. Metrics that matter

Hit / miss rate

The headline number. A low hit rate means the cache isn't earning its keep.

Latency (p50 / p99)

The actual user-facing win — watch the tail, not just the average.

Eviction rate

High evictions suggest the cache is too small for the working set.

Origin load reduction

How much traffic the cache absorbs before it reaches the DB/API.

12. Where to start

If you're adding caching to something real, resist the urge to reach for the fanciest pattern. A reliable progression:

  1. Start with cache-aside + a TTL. It's simple, resilient, and covers most read-heavy workloads.
  2. Measure the hit rate. If it's low, you're caching the wrong things — fix that before adding machinery.
  3. Add TTL jitter from the start — it is three lines and it prevents keys written together from expiring together. Note that it does nothing for a single hot key; that one needs single-flight.
  4. Reach for write-through, event-driven invalidation, or coalescing only when the numbers actually ask for them.

Add complexity in response to evidence, not anticipation. The best caching setup is the simplest one that hits your latency and freshness targets.

13. Recap in 60 seconds

  • A cache trades memory and a new class of bugs for latency and origin load. The bugs are the price, not a defect.
  • Cache-aside is the default: read cache, miss, read DB, fill, return; on write, update DB and delete the key. Deleting beats writing the new value, because two concurrent writers can land in either order.
  • "The app still works without the cache" means it degrades rather than errors. A cache absorbing 95% of reads leaves the database facing 20× its normal load the instant it goes cold.
  • Always set a TTL. It is the only mechanism that repairs an invalidation you got wrong, and you will get one wrong.
  • Jitter fixes synchronised mass expiry (many keys written together). Single-flight fixes a hot key expiring (one key, many concurrent misses). They are different problems; jitter does nothing for the second.
  • The stale-forever race: a slow reader writes its pre-update value into a slot the writer just cleared. Invalidation-on-write alone can't prevent it; the TTL is what eventually cleans it up.
  • Cache negative results deliberately, with a short TTL and a distinguishable sentinel. Not caching them at all is an open channel to your database.
  • A hot key is not fixed by more cache nodes — consistent hashing sends it all to one node anyway. Split the key, or add a client-local tier with a one-second TTL.
  • Personalised responses need Cache-Control: private. A shared cache keys on URL; getting Vary subtly wrong serves one user's page to another.
  • Version your keys (v3:user:123) so a serialisation change never forces you to choose between a flush and reading garbage.
  • Redis's maxmemory-policy defaults to noeviction: a full cache returns write errors instead of making room. Set allkeys-lru.
  • Once retries are amplifying, the outage is self-sustaining. Recovery is shedding load, not waiting.

14. Check yourself

Six situations. Think before you open them — the answers are where the guide stops being vocabulary.

Your hit rate is 94% and p99 latency got worse after you added the cache. What's the likely cause?
p99 is made of the 6% that miss, and a miss now costs a cache round trip plus the database query it always cost — you added latency to exactly the requests that were already slowest. Averages improved, the tail didn't. Look also for serialisation cost on large objects, connection-pool contention against the cache, and one slow node in the cache cluster dragging a slice of traffic. Instrument hit latency and miss latency as separate metrics; a single blended number will hide this forever.
You invalidate on every write, you've checked every call site, and users still report stale data — for almost exactly your TTL duration. What happened?
The stale-forever race. A reader missed, read the old value from the database, got descheduled; your writer updated the row and deleted a key that wasn't there; the reader woke up and wrote its stale value into the empty slot. Your invalidation ran before the poisoning write, so it invalidated nothing. The giveaway is the duration: it's the TTL, because the TTL is the only thing that ever clears it. Narrow the window with leases or a delayed second delete, and never remove the TTL.
Which of these must never be cached in a shared CDN, and why: (a) the logged-in dashboard HTML, (b) app.9f2a1c.js, (c) /api/me, (d) a public product image?
(a) and (c). A shared cache keys on the URL plus whatever Vary declares, and both of those return different bytes to different people at the same URL — so the first response gets stored and handed to the next visitor. Mark them Cache-Control: private, or no-store if they carry anything sensitive. Don't rely on Vary: Cookie to save you: it's correct in theory and gives you a ~0% hit rate in practice, so someone will eventually "optimise" it away.
You flush the cache during a 3am deploy every week and it's fine. You do it at peak and the site is down for 40 minutes, even though you reverted the change within seconds. Why didn't reverting help?
At 3am the database has enough headroom to serve 100% of reads while the cache refills. At peak it doesn't, so it saturates, requests exceed the client timeout, clients retry, and offered load doubles or triples at the worst possible moment. That's a metastable failure: the load keeping you down is now being generated by the outage itself, so removing the original trigger changes nothing. You have to shed traffic until the database can answer enough queries to repopulate the cache, then ramp back. Also: version your keys instead of flushing.
You added jitter to every TTL and your hot-key stampede is exactly as bad as before. What did you misunderstand?
Jitter desynchronises different keys that were written at the same moment. A hot key is one key with one expiry time — randomising when that moment arrives doesn't reduce the number of requests that miss when it does. You need single-flight so only one request rebuilds the value, or probabilistic early expiration so one request refreshes it slightly early and nobody ever sees the miss, or stale-while-revalidate so the old value is served during the rebuild.
Your Redis is at its memory limit. Instead of evicting anything, it started returning errors on SET — and your database load quietly tripled. What's the setting?
maxmemory-policy, which defaults to noeviction because Redis is a database first and a cache second. A full cache that refuses writes can never fill a miss, so every miss stays a miss and the whole read load lands on the origin. Set allkeys-lru or allkeys-lfu for a pure cache. Avoid volatile-* unless you're certain every key has a TTL — those policies only consider keys that have one, and can run out of candidates and start erroring anyway.
The one-liner to remember A cache is a second copy of the truth with its own lifetime, and every hard problem in caching is a consequence of that sentence. Give every entry a TTL, delete on write rather than overwriting, collapse concurrent misses into one query, and remember that the cache is now load-bearing — losing it is an outage you have to design for, not a graceful fallback you get for free.

1. Why the database breaks first

You can add app servers behind a load balancer almost endlessly — they're stateless and interchangeable. The database is different: it holds state, and there's usually one authoritative copy that every write must go through. That makes it the natural bottleneck.

Two pressures build up, and they need different fixes:

  • Read pressure — too many queries reading data. Usually the easier problem; you can serve reads from copies.
  • Write pressure — too many inserts/updates, or simply too much data to fit and index on one machine. The harder problem, because all writes contend for the one source of truth.
The golden rule of scaling Every rung up this ladder adds complexity and new failure modes. So climb it only as far as your load actually forces you to — and no further. Most applications never need sharding. Diagnose whether you're read-bound or write-bound first; it decides which rung you need. The next section is how you actually do that.

2. Diagnose first: read-bound or write-bound?

"The database is slow" is not a diagnosis, and the two pressures send you to completely different rungs. Worse, the wrong answer is expensive in a specific way: if you're write-bound and you add read replicas, you have not just failed to help — you've added machines that each replay every single write, plus a replication stream to monitor and a new failure mode. You made it worse and you paid for the privilege.

Here is a triage you can genuinely run on a Monday morning. Five signals, in order of how quickly they answer the question.

1. The read/write mix, from the database's own counters

Every engine counts this for you. In Postgres, pg_stat_database gives you tup_returned / tup_fetched against tup_inserted + tup_updated + tup_deleted; pg_stat_user_tables breaks it down per table. In MySQL, SHOW GLOBAL STATUS gives you Com_select versus Com_insert/Com_update/Com_delete, and Innodb_rows_read versus Innodb_rows_inserted. These are cumulative since restart, so take two samples an hour apart and subtract — the absolute numbers are meaningless, the delta is the answer. They're row counters, not statement counters, so treat them as order-of-magnitude signal, not gospel.

2. Which p99 actually moved

This is the one that settles arguments. Split your latency percentiles by statement type and look at what degraded when the trouble started, not what is slowest in absolute terms. Writes are often slower than reads on a healthy system; that's normal and tells you nothing. If SELECT p99 went from 40 ms to 600 ms while INSERT p99 barely moved, you are read-bound. If your writes are the ones climbing while reads hold steady, you are write-bound. pg_stat_statements (ordered by total_exec_time, not mean_exec_time — the query that costs you most is usually a fast one run absurdly often) or the MySQL slow query log will point at the specific statements.

3. Replication lag climbing vs. lock wait time climbing

These two are near-perfect discriminators. Replication lag rising means the primary is generating write-ahead log faster than replicas can apply it — that is a write-volume problem by definition, and it is a leading indicator you'll hit the write ceiling. Lock wait time rising means writes are contending with each other or with long-running readers: check pg_stat_activity for wait_event_type = 'Lock', or SHOW ENGINE INNODB STATUS for row-lock waits. Contention is a write-shaped problem too, but it's usually fixed by shortening transactions rather than by buying hardware.

4. Buffer cache hit ratio

From pg_stat_database: blks_hit / (blks_hit + blks_read), or InnoDB's buffer pool hit rate. For an OLTP workload you want this above about 99%. When it starts falling, your working set has outgrown RAM and reads that used to be memory hits are now disk reads — a read-side problem that vertical scaling (more RAM) fixes instantly and cheaply. One honest caveat: Postgres counts a "miss" whenever it goes to the operating system, and the OS page cache may still serve it from memory, so the true disk-read count is lower than this ratio suggests. Use the trend, not the value.

5. Rows examined per row returned

The single most diagnostic number in this entire guide. For each expensive query, divide the rows the database touched by the rows it gave back — Rows_examined vs. Rows_sent in the MySQL slow log, or Rows Removed by Filter in EXPLAIN (ANALYZE, BUFFERS). Near 1 is healthy. Above 100 means the database is doing a hundred times more work than the answer requires, and the fix is an index or a rewritten query — not a bigger machine, not replicas, and absolutely not sharding.

$ triage — pg_stat_database delta, 09:00 → 10:00 rows returned by reads .............. 4,120,000,000 rows inserted + updated + deleted ... 3,900,000 ≈ 1000:1 $ which p99 moved (pg_stat_statements) SELECT p99 .......... 42 ms → 610 ms ◀ this one INSERT p99 .......... 6 ms → 7 ms unchanged $ supporting signals buffer cache hit .... 99.6% → 91.2% working set left RAM rows examined/returned 1.2 → 3,400 a plan went sequential replication lag ..... 40 ms (flat) writes are fine lock wait time ...... flat nothing is blocking verdict: READ-BOUND → index the query, then cache, then replicas

What each answer sends you to

  • Read-bound → indexes, then cache, then replicas. In that order, and the order is not negotiable. Indexing is free and can be 100×. Caching removes the query entirely and needs no new database. Replicas are last because they're the first move that adds a distributed system, replication lag, and a whole class of read-your-writes bugs to your life.
  • Write-bound → batching, then vertical, then partitioning, then sharding. Batching first, because the cheapest write is the one that shares a transaction and an fsync with 999 others — a queue in front of the database turns a spiky per-request write into a steady batched one. Then vertical: faster NVMe and more RAM move the write ceiling further than people expect. Then partitioning, which fixes size and maintenance but not throughput. Then sharding, which is the only thing on this list that actually multiplies write capacity. Read replicas do nothing for you here — every replica applies every write, so they add write work rather than absorbing it.
The third answer nobody expects Sometimes you are neither. If the database's own CPU, I/O, and lock waits are all unremarkable but your application's latency is terrible, the bottleneck is in front of the database — connection-pool queueing, an N+1 loop issuing 400 tiny queries per request, or a missing timeout letting one slow endpoint hold every connection. That's the cold open at the top of this page, and no rung of this ladder fixes it. See the gotchas.

3. Rule zero: make one box faster before you add boxes

Before any distributed anything, exhaust the cheap wins on a single database. They routinely buy 10–100× and cost a fraction of the complexity.

Indexing

The single biggest lever. An index lets the DB jump to the rows it needs instead of scanning the whole table. Most "the database is slow" problems are really "this query has no usable index."

Query & schema tuning

Fix N+1 queries, avoid SELECT *, read the query plan (EXPLAIN), remove accidental full scans. Free performance hiding in plain sight.

Vertical scaling (scale up)

Move to a bigger machine — more CPU, RAM, faster NVMe. Zero code change. The ceiling is real (and pricey at the top), but it buys you time.

Connection pooling

Each DB connection costs memory; thousands of app instances can exhaust the server. A pooler (PgBouncer, RDS Proxy) multiplexes many clients onto few connections.

Do this first, always A well-indexed query on a single beefy box beats a poorly-designed sharded cluster every time. Sharding a slow query just gives you many slow queries.

4. Worked example: the index that isn't used

"We have an index on that" is one of the most confidently wrong sentences in software. Having an index and using an index are separate facts, and only one of them makes queries fast. Here are the two ways it goes wrong, both of which look completely fine in code review.

Case 1: the composite index and the leftmost prefix

You have an events table, 40 million rows, and an index that was created for a dashboard query:

CREATE INDEX idx_events_org_created ON events (org_id, created_at);

-- Fast. Filters on the leading column.
SELECT * FROM events
WHERE  org_id = 42
  AND  created_at > now() - interval '7 days';

-- Slow. Same index, same table, no predicate on org_id.
SELECT * FROM events
WHERE  created_at > now() - interval '7 days';

A composite B-tree index is sorted by its columns in order: first by org_id, and only within each org_id by created_at. Think of a phone book sorted by last name, then first name. Ask it for everyone called Okafor and it's instant. Ask it for everyone called James, with no last name, and the sort order is worthless — the Jameses are scattered across every page, so you may as well read the whole book. That's the leftmost-prefix rule: an index on (a, b, c) can serve predicates on a, on a AND b, and on a AND b AND c, but not on b alone or c alone. Some engines can partially work around this with a skip scan when the leading column has very few distinct values — MySQL 8.0, Oracle, and PostgreSQL 18 all have one — but it's a consolation prize, not a design you should rely on. The fix is a second index on (created_at), or reordering the columns if the single-column query is the important one.

Here's what the arbiter says. Before:

Seq Scan on events (cost=0.00..982431.00 rows=1204 width=88) (actual time=0.031..4128.774 rows=1187 loops=1) Filter: (created_at > (now() - '7 days'::interval)) Rows Removed by Filter: 39998813 Execution Time: 4131.006 ms

Forty million rows touched to return 1,187. After CREATE INDEX idx_events_created ON events (created_at);:

Index Scan using idx_events_created on events (cost=0.44..421.90 rows=1204 width=88) (actual time=0.028..1.902 rows=1187 loops=1) Index Cond: (created_at > (now() - '7 days'::interval)) Execution Time: 2.140 ms

Case 2: the function that hides the column

This one is subtler, because the index is on exactly the column you're filtering on:

CREATE INDEX idx_users_email ON users (email);

-- Sequential scan. Every time.
SELECT * FROM users WHERE lower(email) = 'ada@example.com';

The index stores the values of email, verbatim. It has never seen lower(email) — as far as the planner is concerned that's a different expression, computed per row, and the only way to compute it for every row is to read every row. Same bug, different costumes: WHERE created_at::date = '2026-01-01', WHERE substr(sku, 1, 3) = 'ABC', and the classic WHERE account_number = 12345 where account_number is a varchar and the implicit cast quietly wraps the column. The fix is to index the expression you actually query, or to stop applying the function:

CREATE INDEX idx_users_email_lower ON users (lower(email));
-- or normalise on write, or use a case-insensitive column type (citext)
EXPLAIN is the arbiter, and dev data will lie to you Never reason about index usage from first principles — run EXPLAIN (ANALYZE, BUFFERS) and read what the planner actually chose. Two things to watch for. First, EXPLAIN alone gives estimates; ANALYZE executes the query and gives you real row counts and timings (it also really runs the statement, so wrap writes in a transaction you roll back). Second, on a 5,000-row development table the planner will correctly choose a sequential scan no matter how perfect your index is, because reading the whole thing is genuinely cheaper. Index decisions have to be validated against production-shaped data volumes, or you're testing the wrong database.

5. Read replicas & replication

The first distributed move, and the answer to read pressure. You keep one primary (a.k.a. leader) that takes all writes, and add replicas (followers) that receive a stream of those changes and serve read-only queries. Point your reporting, search, and read-heavy traffic at the replicas; the primary breathes easier.

Synchronous vs. asynchronous replication

How the primary waits for replicas defines the core trade-off:

  • Asynchronous (the common default) — the primary commits and replies immediately, then ships changes to replicas after the fact. Fast, but replicas trail slightly.
  • Synchronous — the primary waits for a replica to confirm before acknowledging the write. Little to no data loss on failover (depending on quorum config), but every write is slower.
The gotcha: replication lag With async replication, a replica is a few milliseconds (sometimes seconds, under load) behind the primary. So a user who writes a comment and immediately reloads from a replica may not see it — a "read-your-own-writes" bug. Fixes: route reads that need freshness to the primary, "stick" a user to the primary briefly after they write, or wait for the replica to catch up. This is the same eventual consistency trade-off as cache staleness, one layer down — and the same dial the Consistency & CAP guide turns. There's more to this than the usual one-paragraph treatment; see the gotchas for why this bug only ever appears in production.

Replicas scale reads, add read capacity cheaply, and give you a failover target — but they do nothing for write throughput or total data size. When those are the problem, you have to split the data itself.

6. Partitioning: splitting a table

Partitioning breaks one big table into smaller pieces. Two flavors, often confused:

  • Vertical partitioning — split by columns / tables: move different groups of tables (or rarely-used wide columns) onto separate databases. E.g. put "billing" tables on one DB and "content" tables on another. Figma started here.
  • Horizontal partitioning — split by rows: keep the same columns but divide rows across partitions by a key (e.g. by month, or by a hash). Within a single database engine this is just called "partitioning"; the app still queries one logical table and the engine prunes to the relevant partition.

Horizontal partitioning within one server helps with table size, index bloat, and lifecycle management (drop last year's partition instantly). But it's still one machine's CPU and IOPS. When you need to spread rows across separate machines, horizontal partitioning becomes sharding.

7. Sharding: splitting across machines

Sharding is horizontal partitioning taken across independent database servers. Each shard holds a slice of the rows and runs on its own hardware, so writes, storage, and IOPS all scale out. It's the most powerful move — and by far the most complex. This is the top of the ladder for a reason.

The shard key is everything

You pick a shard key (user ID, org ID, channel ID…) and a function that maps each row's key to a shard. Every design decision flows from this choice, because it determines how evenly load spreads and which queries stay cheap.

Why sharding is hard — the four taxes you pay

  • Hot shards / hot keys — if one tenant, channel, or celebrity dominates, their shard melts while others idle. Hashing helps distribute keys, but a single hot key still lands on one shard. (This is the DB-level twin of the "hot key" cache problem.)
  • Cross-shard queries & joins — a query spanning shards must fan out and merge results; joins across shards are painful or impossible. Every accidental cross-shard join becomes an app-level problem.
  • Distributed transactions — an atomic change touching two shards needs two-phase commit or careful redesign. Most teams avoid cross-shard transactions entirely by choosing the key so related data lives together. What that atomicity really costs you across a network is the subject of the Consistency & CAP guide.
  • Rebalancing & resharding — adding shards means moving live data without downtime. Consistent hashing and logical-vs-physical shard separation exist largely to make this survivable.
The pro move: logical vs. physical shards Create many logical shards up front (say 1,000) and pack them onto a few physical machines. To grow, you move logical shards to new machines — no re-hashing of keys. Instagram and Figma both lean on this split; it's what makes resharding a data-move instead of a rewrite.

One assumption underneath all of this deserves saying out loud: sharding presumes your application tier is stateless, so that any app server can talk to any shard and be replaced at will. If your app servers are still holding per-user state in local memory, fix that first — see the Load Balancing guide. A sharded database behind sticky, stateful app servers is two hard problems wearing one trench coat.

This is the part that gets skipped, so here it is with numbers attached.

  • One workspace can outgrow a shard. Workspace sizes follow a power law: the median workspace has a dozen people, and your largest customer has 200,000 seats generating 2 million messages a day. That's 800 MB/day, roughly 290 GB/year — survivable on storage, but it is 6.7% of all your writes on a single shard, when an even split across 16 shards would be 6.25%.   • Cross-workspace search becomes a fan-out. The usual answer isn't to make that fast on the shards; it's to stop asking the shards. Push those into a dedicated search index or an analytics warehouse fed by change-data-capture, and let the sharded store answer only the workspace-scoped questions it's shaped for.
  • Rebalancing is now a real activity. Because the distribution is uneven and changes as customers grow, you will move logical shards between machines on purpose, periodically, forever. The rule underneath the arithmetic Pick the shard key that matches the boundary your product already draws around data. If almost every request is scoped to one workspace, one tenant, or one account, then that is your shard key — because it turns "distributed database" back into "a lot of small ordinary databases" for the 99% of queries that stay inside the boundary. Even distribution is a nice-to-have. Keeping the hot query on one shard is the requirement. Slack's own move onto Vitess used workspace as the dominant sharding key for exactly this reason.

9. Avoiding the query entirely

The cheapest query is the one you never run. Several techniques reduce database load without splitting it:

  • Caching — put Redis/Memcached in front of the DB so hot reads never reach it. Often the highest-leverage move before you shard, and the rung immediately before replicas — see the Caching guide.
  • Denormalization — store data pre-joined/pre-computed so reads are a single lookup, trading write complexity and some redundancy for read speed. Standard in NoSQL data modeling.
  • Materialized views — precompute an expensive aggregate/report and refresh it periodically, instead of recomputing per request.
  • CQRS (read models) — separate the write model from purpose-built read models (often kept fresh via events), so reads and writes scale independently. The event stream that keeps them fresh is a message queue.
  • Write buffering — put a queue between the request and the database so bursts are absorbed and writes arrive batched and steady instead of spiky. It converts a peak-throughput problem into a latency-budget problem, which is a much easier problem. Again: the Message Queues guide.

10. CAP & consistency: the trade-off underneath

The moment your data lives on more than one node, the CAP theorem applies: when a network partition splits your nodes, you must choose between Consistency (every read sees the latest write) and Availability (every request still gets an answer). You can't have both during a partition.

In practice this shows up as a spectrum you tune per workload:

  • Strong consistency — always read the latest value. Simplest to reason about; costs latency and availability. Right for money, inventory, auth.
  • Eventual consistency — reads may be briefly stale but the system stays fast and available. Right for feeds, counts, timelines — the same call you made with cache TTLs and replication lag.

Replication lag, quorum reads/writes, and "tunable consistency" in databases like Cassandra are all just knobs on this one dial. The Consistency & CAP guide takes this apart properly, including why "CP" and "AP" are less binary than the theorem makes them sound.

11. Distributed SQL & NoSQL: scaling as a built-in

Instead of bolting sharding onto a single-node database, you can adopt an engine designed to scale horizontally from the start:

Distributed / NewSQL

Spanner, CockroachDB, TiDB, YugabyteDB — SQL and transactions, but data auto-shards and replicates across nodes. You get horizontal scale without hand-rolling a shard router.

Sharding middleware

Vitess (born at YouTube for MySQL) and Citus (for Postgres) add sharding on top of engines you already know, transparently routing queries.

Wide-column NoSQL

Cassandra, ScyllaDB, DynamoDB, Bigtable — built for massive write throughput and horizontal scale, at the cost of flexible queries and (often) strong consistency.

The trade-off

These solve distribution for you, but impose their data model and consistency rules. You trade freedom and familiarity for scale that "just works."

12. The gotchas that bite later

None of these appear in the architecture diagram. All of them show up in the incident channel.

Connection pool sizing is Little's Law, not a vibe

Pool sizes get chosen by doubling until the errors stop. There is an actual formula, and it's the one queueing theory has been quietly holding out the whole time: concurrency = throughput × latency. If you serve 2,000 queries per second and the average query takes 4 ms, then 2,000 × 0.004 = 8 queries are in flight at any instant. Eight. A pool of 20 is comfortable headroom; a pool of 200 is 192 connections that will never be simultaneously useful.

And an oversized pool isn't merely wasteful, it's actively harmful. A database can only do so much genuine parallel work — bounded by cores, by disk queue depth, by lock contention on the hot rows. Beyond that point, extra concurrent queries don't get executed in parallel, they get interleaved: the same total work, sliced into more pieces, with context switches and cache-line thrash between the slices. In Postgres each connection is a separate OS process with its own memory; 200 of them on a 16-core box means the scheduler spends real time deciding who runs next. Throughput stays flat while every individual query gets slower, so your p99 climbs even though nothing about the workload changed. The widely used rule of thumb (from HikariCP) is (cores × 2) + effective_spindle_count — a folk formula, not physics, but it lands in the right order of magnitude, which is tens, not hundreds.

The part people miss: a small pool is a feature. When the pool is full, requests queue in your application, where you can see the queue, put a timeout on it, and shed load. When the pool is huge, the queue moves inside the database, where you can do none of those things.

Idle-in-transaction is a slow leak

A connection sitting in state idle in transaction has begun a transaction, read something, and then gone quiet — usually because the code made an HTTP call, or hit a breakpoint, or threw an exception on a path that forgot to roll back. It looks harmless in the connection list. It is not. That transaction holds a snapshot, and while it does, VACUUM cannot reclaim any row version that became dead after it started — not just in that table, anywhere in the database. So the dead tuples accumulate, the table and its indexes bloat, and every sequential scan against them now reads pages of garbage. Queries get slower with no code change and no traffic change, which makes it a genuinely awful thing to debug.

Long-running read-only transactions do the same thing, and so does a replica running a long analytical query with hot_standby_feedback on — that pins the primary's vacuum horizon from another machine. Defences: set idle_in_transaction_session_timeout and statement_timeout, never perform network I/O inside a transaction, and alert on pg_stat_activity rows where state = 'idle in transaction' and xact_start is older than a minute.

Online schema migration: ALTER TABLE is an outage waiting for a big enough table

On a small table, ALTER TABLE is instant and you learn nothing. On a hot 40-million-row table it can take an exclusive lock for minutes while it rewrites the file — and in Postgres the failure mode is worse than the wait. The lock request queues, and because it's an ACCESS EXCLUSIVE lock, every query that arrives after it queues behind it. So a migration that spends 30 seconds waiting politely for one slow SELECT to finish has blocked every read and write on that table for those 30 seconds. Your migration didn't need to run slowly to cause an outage; it only needed to wait.

What to do. Set a short lock_timeout on migrations and retry, so a blocked migration fails fast instead of building a queue behind it. Prefer the operations your engine has made cheap: modern Postgres adds a column with a constant default as a metadata-only change, MySQL 8 has ALGORITHM=INSTANT for some changes, and both support building indexes without blocking writes (CREATE INDEX CONCURRENTLY in Postgres, online DDL in InnoDB). Add constraints as NOT VALID and VALIDATE them separately. And for the genuinely heavy changes on MySQL, use the tools built for precisely this — gh-ost and pt-online-schema-change, both of which build a shadow copy of the table, keep it in sync while it fills, and swap it in with a brief atomic rename.

OFFSET pagination degrades linearly, and it is everywhere

This is the single most common cause of a slow endpoint in a maturing product, and it ships in every tutorial:

-- Page 5,000 at 20 per page.
SELECT * FROM messages
ORDER BY created_at DESC
LIMIT 20 OFFSET 100000;

OFFSET is not a seek. The database has to produce the first 100,000 rows in sorted order and throw every one of them away before it can return the 20 you asked for. Page 1 is instant, page 100 is fine, page 5,000 does 5,000× the work of page 1 for an identical-looking response. Nobody notices during development because nobody clicks to page 5,000 — and then a crawler does, repeatedly, in parallel.

Keyset (or "seek") pagination fixes it by remembering where you stopped instead of counting from the beginning:

-- Simple case: a monotonic id.
SELECT * FROM messages
WHERE  id > :last_seen_id
ORDER BY id
LIMIT  20;

-- Sorting by a non-unique column needs a tiebreaker for a total order.
SELECT * FROM messages
WHERE  (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT  20;

That's an index seek straight to the right position: constant cost regardless of depth, and it doesn't skip or duplicate rows when the underlying data changes mid-scroll, which OFFSET quietly does. The price is that you lose "jump to page 5,000" — you get next/previous, not random access. For infinite scroll, feeds, exports, and APIs, that's not a loss at all. For a UI that genuinely needs numbered pages, keep OFFSET but cap the depth.

Secondary indexes under sharding: pick your poison

Once data is sharded, "add an index on email" stops being a one-line decision, because there are two completely different things that sentence could mean.

  • Local index — each shard indexes only its own rows. Cheap, and consistent for free because the index update happens in the same transaction as the write. But it can only be searched shard by shard, so any lookup that isn't on the shard key becomes scatter-gather: 16 shards, 16 queries, latency equal to the slowest of the 16, and 16× the total cluster work for one user's login-by-email. It works fine until that query gets popular, at which point a single lookup pattern is consuming the whole cluster.
  • Global index — a separate structure keyed by the indexed column, mapping value → shard and primary key. One lookup, no fan-out. But it lives on different machines than the data it points at, which means every insert is now a distributed write. You get two options and no third: update the index asynchronously and accept that it's briefly wrong (so a just-created user isn't findable by email for a moment, and you now own that bug class), or run two-phase commit on every write and pay the latency plus a coordinator that can fail mid-commit. DynamoDB makes this trade in the open — global secondary indexes are eventually consistent by design, and local secondary indexes are strongly consistent but must share the partition key.

A global index is not a feature you enable. It is a distributed system you now operate.

Replication lag is not a constant

The mental model that causes the bugs is "replicas are about 50 ms behind." They aren't. Lag is near zero, and near zero, and near zero — and then it is eleven seconds. It spikes when a backfill or bulk delete floods the write-ahead log; when a long query on the replica blocks log replay; when a vacuum generates a burst of changes; during failover; and generally whenever write volume exceeds what the replica's apply process can keep up with, which is often more single-threaded than the primary's write path.

Combine those triggers and you get the defining property: lag is worst exactly when load is highest. Which means read-after-write bugs are invisible in development, invisible in staging, invisible in production at 4 AM — and appear for a fraction of users at peak, unreproducibly, in the exact window when you have the least attention to spare.

Two real fixes. The simple one is a sticky primary window: after a user writes, route that user's reads to the primary for a few seconds. Cheap to implement, costs a little primary capacity, and covers the overwhelming majority of cases. The precise one is a version token: capture the write's position in the log at commit time — an LSN from pg_current_wal_lsn(), or a GTID in MySQL — carry it in the session or a cookie, and have the read path either wait for the replica to reach that position (WAIT_FOR_EXECUTED_GTID_SET, or comparing against pg_last_wal_replay_lsn()) or fall back to the primary if it hasn't. One more operational note: monitor lag in bytes of log distance as well as seconds. "Seconds behind" reports a cheerful zero on an idle system and is a lagging indicator on a busy one.

The bills that arrive later

The decision to shard gets modelled as an engineering cost paid once. It is mostly a set of recurring costs paid by people who weren't in the room. None of these are hypothetical; all of them are boring.

  • Data transfer. Shards spread across availability zones for durability means cross-AZ traffic, which is billed per gigabyte, in a line item that grows with every fan-out query you add. Cross-region replication is the same charge, continuously, forever. A scatter-gather query is no longer just slow — it has a price per execution.
  • Backup and restore multiply by shard count. Sixteen shards is sixteen backup jobs, sixteen restore procedures, and a point-in-time recovery that has to be coordinated across all of them or you restore a cluster that's internally inconsistent. Your recovery time objective is now "the slowest shard's restore," and rehearsing it is a sixteen-fold exercise that nobody schedules.
  • Every schema migration becomes N migrations. And they can be half-applied: shard 7 has the new column, shard 8 doesn't, and your application must tolerate both states for as long as the rollout takes. That constraint never goes away — it changes how you write every migration from now on.
  • Resharding is a project, not a task. Going from 16 shards to 32 needs a plan, a backfill, a dual-write period, a cutover, and a rollback story. Weeks, with a named owner. Logical shards make it a data move rather than a rewrite — they do not make it free.
  • Cross-shard transactions are either unavailable or a trap. Where two-phase commit exists it's slow and it introduces a coordinator whose failure mid-commit leaves locks held on multiple machines. So in practice you design around it: sagas, idempotency keys, compensating actions, reconciliation jobs. That is permanent application complexity you now maintain, and it's the real reason the shard key matters so much — see Consistency & CAP for what you're actually buying, and the Reliability toolkit for the retry and timeout machinery you'll need around it.
  • On-call surface. One database with a replica is two things that can page you. Sixteen shards with replicas is thirty-two, each with its own failover, its own disk, and its own capacity to be the one that's different.

13. Real-world examples

How real teams actually climbed this ladder — including where they stopped.

Figma — vertical partitioning, then in-house sharding

Figma ran a single Postgres instance on AWS's largest box in 2020. They first scaled by vertical partitioning — splitting tables like "Files" and "Organizations" onto separate databases — reaching about a dozen databases with replicas and caching by late 2022. But some tables hit terabytes and billions of rows, bumping into RDS IOPS limits and Postgres vacuum problems that partitioning couldn't fix. So they built horizontal sharding in-house: multiple shard keys (UserID, FileID, OrgID) rather than one, hashed for even distribution, with "colos" grouping related tables so joins stay within a shard — and a routing service, DBProxy. They deliberately chose this over CockroachDB or Vitess to stay on their known Postgres. First table sharded in September 2023 with ~10 seconds of partial impact. (Figma Engineering)

Discord — MongoDB → Cassandra → ScyllaDB

Discord outgrew MongoDB and moved to Cassandra in 2017, partitioning messages by channel_id plus a time bucket. By early 2022 it was trillions of messages across 177 nodes — and struggling: popular channels became hot partitions, and Java garbage-collection pauses caused latency spikes and heavy on-call toil. They migrated to ScyllaDB (a C++ reimplementation of Cassandra) and added a Rust data-services layer that coalesces concurrent requests for the same hot channel — the exact request-coalescing trick from the Caching guide, at the database tier. Result: 177 nodes down to 72, and p99 message reads from 40–125 ms to ~15 ms. (Discord Engineering)

Instagram — thousands of logical shards on few machines

Instagram sharded Postgres early by creating thousands of logical shards mapped onto a smaller number of physical servers, and encoded the shard ID directly inside their 64-bit primary keys. Growing capacity meant moving logical shards to new hardware — no re-hashing. It's the textbook logical-vs-physical split from section 7.

The pattern across all three Every team climbed the ladder in order — one box, then partitioning/replicas, then sharding — and only sharded when size or write load genuinely forced it. None reached for the most complex tool first. That restraint is the strategy.

  • Rung 1 — Index and fix queries. Most "slow database" is one missing or unusable index. Climb when EXPLAIN shows an index scan and it's still not fast enough.
  • Rung 2 — Scale up, and right-size the pool. More RAM fixes a falling cache hit ratio outright; the pool should be tens, not hundreds. Climb when you're near the largest sensible instance or its IOPS ceiling.
  • Rung 3 — Cache. The cheapest query is the one you never send. Climb when the hit rate is already high and the remaining reads still saturate the box.

16. Check yourself

If you can answer these without scrolling up, you have the guide.

Reads are slow. You add three read replicas. Nothing improves. What did you get wrong?
Almost certainly the diagnosis. A replica runs the same schema and the same query plan as the primary, so if the query is doing a sequential scan over 40 million rows, you have just bought three more machines to do that badly in parallel. Replicas add read capacity; they do nothing about work per query. Check rows examined per row returned before you check anything else. The other common answer is duller: the reads never moved. Traffic still goes to the primary because nothing routes it, or the queries sit inside transactions, which most routers pin to the primary by default.
You shard by user_id. One customer's shared service account generates most of their API traffic and melts the shard it lands on. What should you have done?
Hashing distributes keys evenly, not load per key — a single hot key always lands on exactly one shard no matter how good your hash is, so no hashing scheme was ever going to save you here. Hot keys need their own mechanism: a directory-style mapping so that key can be pinned to a dedicated shard, a second-level key to split it, or request coalescing and caching in front so the shard sees one query instead of a thousand. And there's a second mistake underneath: in a tenant-scoped product, user_id scatters each customer's data across every shard, so all your tenant-scoped queries were already fanning out. The tenant boundary was the shard key.
Your p99 doubled after you raised the connection pool from 20 to 200. Throughput didn't change. Why?
Because 20 was already more than enough, and 200 doesn't create parallelism the database can use. Concurrency = throughput × latency, so 2,000 queries/second at 4 ms each is only 8 queries genuinely in flight. Past the point where the database can execute work in parallel — bounded by cores, disk queue depth, and lock contention — extra connections just interleave the same work into more slices, adding context switches and (in Postgres, where each connection is a process) real scheduler overhead. Total throughput stays flat while every individual query takes longer, which is exactly the shape of a p99 that doubles for no visible reason. The bigger loss is that the queue moved from your application, where you can time it out and shed it, into the database, where you can't.
A read-your-writes bug affects about 2% of users, only at peak, and has never once reproduced in staging. Where do you look?
Replication lag, and the reason it hides is that lag isn't a constant — it's near zero until it spikes, and it spikes under exactly the conditions you can't recreate: heavy write volume, a backfill flooding the log, a long analytical query on the replica blocking replay. Staging has no load, so staging has no lag, so staging has no bug. Fix it structurally rather than by chasing it: give each user a sticky window that routes their reads to the primary for a few seconds after they write, or carry a version token (a Postgres LSN, a MySQL GTID) captured at commit and make the read path wait for the replica to reach it or fall back to the primary.
A migration adding one nullable column ran in 200 ms in staging and made the table unavailable for 30 seconds in production. The migration itself wasn't slow. What happened?
The migration spent 30 seconds waiting, not working. It requested an exclusive lock, a long-running query was already holding a conflicting one, and while the migration sat in the lock queue every subsequent query on that table queued behind it — because a pending exclusive lock blocks the readers arriving after it, not just the migration. So one slow report plus one polite ALTER TABLE equals a table-wide stall. The defence is a short lock_timeout on migrations with retry, so a blocked migration fails immediately instead of building a queue, plus using the non-blocking variants (concurrent index builds, NOT VALID constraints validated separately) or a shadow-table tool like gh-ost for the heavy changes.
One customer's list endpoint has been getting steadily slower for six months. No deploys, no schema changes, and it's fast for everyone else. What's your first guess?
They have the most rows, and something in that endpoint costs more as their row count grows — most often OFFSET pagination, where page depth makes the database produce and discard everything before the page you want, so the customer with ten times the data pays ten times the cost on the same click. Keyset pagination makes it flat. If it isn't pagination, the same shape shows up as an unbounded query whose result set grows with the tenant, or an index that stopped being selective for them specifically. The general lesson: in a multi-tenant system, "slow for one customer" is usually not a customer-specific bug, it's your largest tenant arriving at a limit ahead of everyone else — and telling you where the whole product will be in a year.
The one-liner to remember Every rung of this ladder trades a simple problem for a harder one, so make each rung earn its place with a measurement. In practice, most "we need to shard" turns out to be one missing index, one unbounded query, and a connection pool sized by superstition.

1. Why one server isn't enough

A single server has a ceiling: finite CPU, memory, and network. You can buy a bigger one (vertical scaling), but that ladder runs out — and a single anything is a single point of failure. The moment it reboots, your whole product is offline.

The alternative is horizontal scaling: run many identical servers and split the work between them. It scales almost linearly and survives individual deaths. But it raises one immediate question — when a request arrives, which server should handle it? Answering that, well and instantly, millions of times a second, is the entire job of a load balancer.

2. The load balancer, explained

A load balancer sits in front of your fleet of servers. Clients connect to it; it picks a healthy server and forwards the request. To the outside world there's one address; behind it, a crowd. Think of a restaurant host: diners don't wander in and fight over tables — the host seats them, keeps things even, and quietly skips the table with a broken chair.

3. L4 vs L7: two places to make the decision

Load balancers come in two broad flavors, named after layers of the networking stack. The difference is how much of the request they bother to read.

Layer 4 (transport)

Routes by IP and port only. It doesn't open the envelope — just forwards packets. Blazing fast, protocol-agnostic, but can't make smart decisions based on content.

Layer 7 (application)

Reads the actual HTTP request — URL, headers, cookies. Can route /api to one pool and /images to another, do TLS termination, rewrite, and inspect. Smarter, slightly slower.

Most modern web setups use L7 (Nginx, HAProxy, Envoy, AWS ALB) because content-aware routing is worth the tiny overhead. Reach for L4 (AWS NLB) when you need raw throughput or you're balancing non-HTTP traffic.

6. Health checks & failover

A load balancer is only as good as its ability to notice a server has died. It constantly pokes each backend — "you alive? GET /health" — and the instant one stops answering, it's pulled from rotation. Traffic silently reroutes to healthy servers; users never see the corpse.

This is the quiet superpower: failover for free. A server can crash at 3 AM and, if you've got spare capacity, nobody wakes up. The subtlety is designing the health check well — a shallow "is the port open?" check will happily send traffic to a server whose database connection is dead but whose web process is technically running. Good health checks test the thing that actually matters.

The gotcha: don't health-check yourself to death Health checks that are too aggressive, or that hit a shared dependency, can cause the overload they're meant to detect — thousands of checks hammering one database. And if a check flaps, servers yo-yo in and out of rotation. Tune the interval and thresholds.

7. Sticky sessions & the case for statelessness

Here's a trap. Say a user logs in and their session lives in that specific server's memory. Now the load balancer's next request from them lands on a different server, which has never heard of them. Suddenly they're logged out. Rude.

Two ways out:

  • Sticky sessions — pin each user to the same server (via a cookie or IP hash). Works, but it's a band-aid: that server now can't be replaced without logging people out, and load gets lumpy.
  • Statelessness — the real fix. Keep no per-user state on the app server. Push sessions into a shared store — Redis, a signed cookie, a database. See the Caching guide for how that shared store is built and what happens when it's cold. Now every server is truly interchangeable and any of them can serve any request.
The thread that connects every guide Statelessness is why caching and horizontal scaling exist as a pair. Move session state into a shared cache (Caching guide) and your app servers become disposable clones a load balancer can shuffle freely. It also cashes out one layer down: every sharding and read-replica scheme in the Database Scaling guide quietly assumes the app tier is stateless, because a shard map only works if any app server can be pointed at any shard. Fast, scalable, resilient — all unlocked by refusing to remember anything locally.

8. Autoscaling: the fleet that breathes

Once servers are stateless and disposable, you can add and remove them automatically based on load. Traffic climbs at lunchtime → spin up five more servers → the load balancer folds them into rotation as their health checks pass. Traffic drops at 2 AM → scale back down and stop paying for idle machines.

The catch is cold starts (new servers boot with empty caches and briefly run slow — see the Caching guide) and the lag between "we're overloaded" and "new capacity is ready." Good autoscaling scales up early on a leading signal, and down slowly so a brief dip doesn't kill servers you'll want back in five minutes.

And be clear-eyed about what autoscaling is for. It absorbs the shape of a normal day — the lunchtime ramp, the Monday morning wall, the marketing email. It does not save you from a fleet collapsing in real time, because a new instance needs minutes and a collapse needs seconds. That's a different tool, and it's in the death spiral below.

9. The gotchas nobody diagrams

Everything above is the version that fits on a slide. What follows is the version that pages you. Each of these is a real production failure mode with a specific setting attached to it.

Connection draining, or: why every deploy has an error spike

You remove an instance — a rolling deploy, a scale-in, a health check that flipped. The naive implementation cuts it out of rotation and stops the process. Every request that was already in flight on that box dies mid-sentence. The client gets a reset or a 502, and because a rolling deploy does this to each instance in turn, the spike is proportional to your fleet size and it happens on every single release. Teams live with this for years and call it "deploy noise."

The correct sequence has three steps, in order. The instance starts failing its readiness check (or is explicitly marked draining), so the load balancer stops sending it new requests. It keeps serving the connections it already has. Only when those finish — or a drain timeout expires — does the process exit.

The knob has a different name everywhere: deregistration delay on an AWS target group (default 300s), drain timeout in HAProxy and Envoy, terminationGracePeriodSeconds plus a preStop hook in Kubernetes. Set it longer than your slowest normal request and shorter than your patience for a deploy. And note the ordering trap: the pod must fail readiness before it gets SIGTERM, or the load balancer is still sending it traffic while it's shutting down — which is the same error spike with more steps.

Liveness and readiness are different questions

Liveness asks: should I be restarted? Readiness asks: should I get traffic right now? These are not the same question and wiring them to the same handler produces two distinct outages.

Conflate them one way and an instance that is merely warming up — filling a connection pool, loading a model, JIT-compiling — gets killed by the liveness probe before it ever serves a request. Deploy, crash-loop, repeat. Conflate them the other way and a saturated instance keeps receiving requests because the process is technically alive, which is exactly the failure the cascade below is built on.

A readiness handler that returns a static 200 from a constant string tells you the process is running and the port is open. That's it. It cannot tell you whether a request would succeed, because it doesn't do anything a request does. A useful readiness check touches what the request path touches: can I take a connection from the pool, is config loaded, is the cache client connected, is my in-flight count below the line where I stop being useful.

…but not too deep If every instance's readiness check queries the same database, and that database has a bad ten seconds, every instance fails readiness at the same moment and the load balancer has nothing left to send traffic to. A shared dependency turns a dependency blip into a total outage. Check the dependency, cache the result for a few seconds so you're not hammering it, and don't fail readiness for anything you can serve degraded.

Fail-open and the panic threshold

If health checks are the only thing standing between you and an outage, then a bug in the health check is an outage. A config push that changes the health path. A certificate that expires on the health port. A probe timeout tuned for an idle box, now being evaluated on a busy one. Any of these can mark one hundred percent of your fleet unhealthy inside a single check interval, and a strictly correct load balancer will then dutifully send traffic to nobody.

Real proxies refuse to be that correct. Envoy has a panic threshold, default 50%: once fewer than half the hosts in a cluster are healthy, it stops honouring health status and load balances across all hosts, sick ones included. The reasoning is blunt and right — if most of your fleet appears dead, the likelier explanation is that your health checking is broken, and a degraded backend beats no backend. Whatever proxy you run, find out what it does when zero hosts are healthy, and find out before the day it matters.

Slow start: don't hand a cold instance the firehose

A freshly added instance has empty caches, empty connection pools, and a JIT that hasn't compiled anything hot. It is the slowest machine in your fleet and it is also, to a least-connections balancer, the emptiest one. So the balancer points the firehose at it. It falls over, fails its health check, restarts, comes back cold, and does it again — a loop you can watch on a graph for hours.

The fix is slow start: ramp the new instance's share from near-zero to full over a window — thirty seconds to a couple of minutes is the usual range. Nginx Plus, Envoy, and AWS ALB target groups all have a setting for it. The complementary fix is on the instance itself: warm your caches and pools before you report ready. Readiness is a promise. Don't make it early.

Keepalive and HTTP/2 quietly defeat L4 round robin

An L4 balancer distributes connections, not requests. It makes one decision, at connection setup, and every byte on that connection goes to the same backend for as long as it lives.

With HTTP/1.1 keepalive that's already thousands of requests riding a single decision. With HTTP/2 or gRPC it's far worse: one connection multiplexes many concurrent streams, so a client that connected at 03:00 keeps hammering the one backend it was assigned, indefinitely. Add capacity and the new instance gets nothing at all — nobody is opening new connections, so there is nothing to balance.

The tell is a dashboard that lies to you in a very specific way: connections per backend are beautifully even, and CPU is 90% on one box and 8% on the others. Three fixes, roughly in order of preference. Balance at L7, so the decision is made per request (or per HTTP/2 stream) rather than per connection. Set a maximum connection age or max requests per connection, so clients are periodically forced to reconnect and get re-balanced. Or move the decision to the client — a service mesh sidecar or a client-side balancer that knows about streams.

The client's IP disappears at L7

Once an L7 proxy terminates the client connection, your backend's socket shows the proxy's address. Every access log, every rate limit, every geo-block is now pointed at your own load balancer. The standard fix is X-Forwarded-For: the proxy appends the client's address to the header as the request passes through.

Now the trap. X-Forwarded-For is a header, and headers are whatever the sender says they are. If you read it naively on a request that arrived from the internet, anyone can send X-Forwarded-For: 203.0.113.9 and your rate limiter, your geo-block, and your audit log all believe them — which is to say your rate limiting is now optional. Your edge proxy must overwrite or normalise the header, and everything behind it must count from the trusted end and trust only the number of hops you actually operate. Nginx expresses this as set_real_ip_from plus real_ip_recursive; Envoy as xff_num_trusted_hops. Get the hop count wrong and you are trusting an attacker-supplied value again, just with more configuration.

At L4 the equivalent is the PROXY protocol: the balancer prepends a small fixed header to the TCP stream carrying the original source and destination addresses, before any application bytes. Because it sits underneath the application protocol it works for anything — SMTP, Postgres, raw TCP — but the backend must be configured to expect it, and must accept it only from the proxy, for exactly the same spoofing reason.

Retry amplification

Retries are individually reasonable and collectively catastrophic. The mobile SDK retries. The CDN retries. The API gateway retries. The service client retries. The database driver retries. Three layers that each make three attempts is 3³ = 27 requests for one user action — and they arrive during precisely the window when the system is already failing, which is when a 27× multiplier is least survivable.

They're also correlated. Everyone's timeout fires at roughly the same moment, so the retries land as a synchronised wave rather than a smear. That's a retry storm, and it is how a five-second dependency blip becomes a twenty-minute outage.

Three fixes, and you want all of them. Retry at exactly one layer and make every other layer fail fast — pick the layer with the most context, usually the one closest to the caller who can actually do something about it. Put a retry budget on that layer: cap retries as a fraction of successful traffic, so a total outage multiplies load by nothing at all rather than by three (Envoy's default budget is 20% of active requests; Finagle popularised the idea). And add jitter to your backoff so the wave spreads out instead of arriving as a spike. The full treatment — circuit breakers, budgets, shedding — is in the Reliability guide.

Least connections doesn't scale — use the power of two choices

True least-connections needs to know every backend's current load at the instant of the decision. That's easy with one load balancer and impossible with a tier of them: each has only its own view, and if they all independently spot the same emptiest server, they all stampede it simultaneously. It's the same mechanism that makes least-connections dogpile a just-restarted instance, only now with a multiplier.

Power of two random choices is the fix, and it is almost insultingly simple: pick two backends uniformly at random, compare only those two, send the request to whichever has fewer outstanding requests. No global state, no coordination, no single "best" server for everyone to converge on. The theoretical result (Azar, Broder, Karlin and Upfal, 1994) is that this is not a small improvement over pure random — it's an exponential one. Throwing n requests at n servers uniformly at random leaves the worst-loaded server with roughly log n / log log n of them; sampling two and taking the lighter drops that to roughly log log n. A second sample buys you most of the distance to perfect balance. A third buys almost nothing.

This is what large systems actually run: Nginx (random two least_conn), HAProxy (balance random), Envoy (its LEAST_REQUEST policy samples two hosts by default), and most client-side balancers in a service mesh. If you're picking an algorithm and you don't have a specific reason for something else, pick this one.

The capacity death spiral

Ten instances, each at 70% CPU. One dies. The other nine now carry its share and sit at 78%. Latency rises; requests queue; queued requests hold memory, connections, and thread slots, so the next instance saturates and drops out too. Now eight are at 87%. Then seven, at 100% — and there is no seven-instance configuration that serves this traffic. Every removal makes the next removal more likely, and sooner. The load balancer's failover, which is genuinely the right behaviour when one box dies in a healthy fleet, becomes the transmission mechanism.

Autoscaling cannot save you here and it's worth being precise about why. A scale-up needs a metric window (tens of seconds), then an instance boot, then application start, then cache warm, then enough consecutive passing health checks to be added. Minutes, at best. The collapse runs in seconds. By the time the new capacity is ready there's nothing left to relieve.

The only thing that operates on the right timescale is refusing work. Load shedding: when the queue is longer than you can serve inside your latency budget, return 503 to the excess immediately rather than accepting everything and serving none of it. Per-instance concurrency limits: a hard cap on in-flight requests, so an instance degrades predictably instead of falling over. Both trade visible errors for a surviving fleet, which is a trade people resist right up until the first time they watch the alternative. Details in the Reliability guide.

11. Real-world examples

War story · the doorman who quit A load balancer's health checks assume a dead server stops answering. The nastier failure is the server that keeps answering but returns garbage or hangs at 30 seconds — "brownout," not blackout. Netflix engineered around exactly this with adaptive concurrency limits and circuit breakers, because a slow server that a load balancer keeps feeding is more dangerous than one that cleanly dies. (More in the Reliability guide.)

Google's Maglev — Google runs software L4 load balancers on commodity machines, using consistent hashing so that even when the fleet changes, existing connections mostly stay put. It's how a single virtual IP fronts an ungodly amount of traffic.

Anycast + DNS at the edge — before a request even reaches a traditional load balancer, providers like Cloudflare announce the same IP address from data centers worldwide (anycast), so the network itself routes you to the nearest one. Load balancing that starts at the level of the internet's routing tables.

The humble /health endpoint — almost every service you've ever used has an unglamorous URL that a load balancer hits every few seconds, forever. It is the most-visited page in your entire system and no human will ever look at it. Pour one out.

The one-liner to remember A load balancer turns a fragile single server into a resilient herd — but only if those servers are stateless clones. Make your servers boring and interchangeable, and scaling becomes a slider you drag.

12. Recap in 60 seconds

  • The job is to answer "which backend?" correctly, instantly, millions of times a second — and to notice when the answer stops being a backend at all.
  • L4 forwards packets, L7 reads requests. Content routing, TLS termination, header rewrites, per-route limits and cross-backend retries are all L7. Protocol neutrality, source-IP fidelity and minimum latency are all L4. Edge L4 in front of a tier of L7 proxies is a very common shape.
  • Round robin is blind to work. A backend taking 100× longer gets the same number of requests. Prefer least-connections, and implement it as power of two random choices so it survives a tier of load balancers.
  • Consistent hashing is what stops a fleet size change from invalidating every cache key at once.
  • Sticky sessions are a band-aid. Push session state into a shared cache and every server becomes interchangeable — which is also what sharding in the Database guide assumes.
  • Liveness ≠ readiness. "Restart me?" and "send me traffic?" are different questions. A static 200 answers neither.
  • Removal is not free. Drain first, or every deploy is an error spike. And the traffic you remove lands on instances that may not have room for it.
  • Health checks can fail open. If every host looks unhealthy, the likeliest bug is in the checker. Know what your proxy does at zero healthy hosts.
  • Retries multiply. Retry at one layer, cap it with a budget, jitter the backoff.
  • Only refusal is fast enough. Autoscaling takes minutes; a cascade takes seconds. Shed load and cap concurrency per instance.

13. Check yourself

Six situations. Answer before you open them — the useful part is noticing which ones you can't.

Your dashboard shows connections evenly spread across ten backends. One of them is at 90% CPU and the others are idle. What's happening?
You're balancing connections, not requests — an L4 hop in front of long-lived clients, and almost certainly HTTP/2 or gRPC, where one connection carries many concurrent streams. The connection counts are even and meaningless; the work behind them is not. Balance at L7 so the decision happens per request, or cap connection age so clients are periodically forced to reconnect and re-balance. Watch requests and in-flight count per backend, never connection count.
Every deploy produces a spike of 502s. Name the two settings you'd check first.
Deregistration delay (drain timeout) and the ordering between failing readiness and receiving SIGTERM. The 502s are in-flight requests being cut off on instances that were removed without draining. The instance has to stop being eligible for new traffic first, then keep serving what it already has until it finishes or the drain timeout expires, and only then exit. If your platform sends SIGTERM before the load balancer has noticed the readiness change, no drain timeout will save you — you need a preStop delay to cover the propagation gap.
A config push marks all backends unhealthy. What should the load balancer do, and why is "send no traffic" the wrong answer?
It should fail open — ignore health status and distribute across every host it knows about. "Send no traffic" is a 100% outage, and it's chosen on the basis of information that has just proven itself unreliable: if every single host reports unhealthy simultaneously, the overwhelmingly likelier explanation is a broken health check than a fleet that died in unison. Envoy formalises this as the panic threshold, defaulting to 50% healthy. A degraded backend beats no backend, and the failure mode you're guarding against is your own tooling.
Least-connections is dogpiling instances the moment they come back from a restart. Two fixes — one on the balancer, one on the instance.
On the balancer: slow start, ramping the returning instance's share from near zero to full over 30 seconds or more, so "emptiest" doesn't mean "gets everything". On the instance: don't report ready until you actually are — warm your connection pools and caches before passing the readiness check, so the balancer never sees an empty, cold, willing target in the first place. The underlying bug is that in-flight count is a proxy for capacity, and a cold instance has almost no capacity and no in-flight requests at all.
A dependency is down for eight seconds. Your service is down for twenty minutes. Where did the extra nineteen minutes come from?
Retries, mostly your own. Every layer retried, the multiplication compounded, and because all the timeouts fired at nearly the same instant the retries arrived as a synchronised wave rather than a smear. That wave kept the system saturated well after the dependency recovered, which caused more timeouts, which caused more retries. Retry budgets break the loop by making retry volume a bounded fraction of real traffic; jitter breaks the synchronisation; retrying at exactly one layer stops the multiplication at the source.
You're rate limiting by client IP behind an L7 load balancer, and a single abusive client is sailing straight through it. Why?
Either every request looks like it comes from the load balancer — because the proxy terminated the connection and your app is reading the socket's peer address — or you're reading X-Forwarded-For without normalising it, and the client is simply sending its own. Both are the same underlying mistake: treating an attacker-controlled value as identity. Overwrite or normalise X-Forwarded-For at the trusted edge, count hops from the trusted end only, and if you're at L4 use the PROXY protocol, accepted exclusively from the proxy's addresses. A third possibility worth ruling out: your limits are enforced per load-balancer instance, so the real limit is your configured value times the number of proxies.

1. Synchronous vs. asynchronous

Synchronous is a phone call: you both have to be on the line at the same time, and you wait for the answer. Asynchronous is a text message: you send it and get on with your life; the other side handles it when they can.

Lots of work has no business being synchronous. The user doesn't need to watch their receipt email get sent — they just need to know the order went through. So do the essential bit inline (record the order, take the money), drop everything else onto a queue, and return "success" immediately. The slow, non-urgent work happens in the background.

2. The queue as a shock absorber

A message queue is a durable line that work waits in. Producers add messages to one end; consumers take them off the other and do the work. Its magic trick is decoupling in both time and speed.

When a traffic spike hits, the queue simply gets longer — it doesn't fall over. Consumers chew through the backlog at a steady rate the downstream systems can survive. That's the shock absorber: bursty input, smooth output. A queue turns "everything at once" into "a steady, controlled rate."

This is load-leveling — and where backpressure comes in Absorbing a spike by buffering it (letting the queue grow) is load-leveling: the database sips at its own pace instead of getting knocked over. This is the cheapest thing you can put in front of a write-bound database — writes are the hard half to scale, as the Database Scaling guide gets into, and a queue lets you cap the write rate without dropping the writes. True backpressure is the next step — a bounded queue that, when full, pushes back on or sheds producers, so an unbounded backlog can't itself become the outage (runaway memory, ever-staler messages). Buffer for smoothness; bound the queue so the buffer can't sink you.

3. Producers, consumers, and two shapes of delivery

Beyond the basic queue, there are two classic patterns, and knowing which you want saves a lot of confusion:

Work queue (point-to-point)

Each message goes to exactly one consumer. Ten workers share the load; a receipt gets emailed once. This is task distribution.

Pub/sub (publish–subscribe)

Each message is broadcast to every interested subscriber. "Order placed" fans out to billing, shipping, and analytics — each gets its own copy. This is event notification.

Pub/sub is the backbone of event-driven architecture: services announce that something happened and don't care who's listening. New feature? Subscribe to the existing event stream — no need to touch the producer. It's how big systems add capabilities without everything having to know about everything.

4. Delivery guarantees: the three honesties

Networks fail, consumers crash mid-task. So every queue has to answer: if things go wrong, how hard do we try to deliver? There are three honest answers, and physics won't let you have a perfect fourth.

GuaranteeMeaningRiskUse when
At-most-onceFire and forget. Deliver 0 or 1 times.Messages can be lost.Metrics, logs — a dropped one won't hurt.
At-least-onceRetry until confirmed. Deliver 1 or more times.Messages can be duplicated.Almost everything — the common default.
Exactly-onceDeliver precisely once. The holy grail.Expensive, complex, and often a comforting fiction.Rarely truly needed; usually faked with at-least-once + idempotency.
The dirty secret End-to-end "exactly-once delivery" — across systems with real side effects — is famously close to impossible. The obstacle is the same one the CAP & Consistency guide circles: two independent systems can't agree on "this happened" in one indivisible step over an unreliable network, so somebody always has to choose between retrying (maybe twice) and giving up (maybe never). What people actually build is at-least-once delivery + idempotent processing: deliver possibly twice, but make processing a duplicate a harmless no-op. The result looks exactly-once from the outside, which is all anyone wanted. (Kafka's exactly-once processing within its own ecosystem — idempotent producer + transactions — is the real exception, but it doesn't extend to arbitrary external side effects.)

5. Idempotency: the survival skill

Idempotent means: doing it twice has the same effect as doing it once. Pressing an elevator button five times doesn't summon five elevators. This single property is what makes at-least-once delivery safe, and it's worth internalizing because it shows up everywhere in distributed systems.

The classic horror is a payment consumer that gets the same "charge $50" message twice (because the first ack got lost) and charges the customer $100. The fix: give each message a unique ID and record which IDs you've already processed. See a repeat? Skip it. Now the retry that would've double-charged is a shrug.

That's the idea. The obvious way to write it is wrong.

The version everybody writes first — and it's broken

on message(id, action):
    if already_processed(id):   # seen this one?
        return ok               # harmless no-op
    do(action)
    mark_processed(id)

Read it as a single thread and it's flawless. Read it as two consumers — which is the entire point of a queue — and there's a gap between the check and the mark that is wide enough to drive a double charge through. Duplicates don't politely arrive one after the other; they arrive at the same moment, on two machines.

t1 C1 gets msg #7847 (charge $50) t1 C2 gets msg #7847 — a duplicate t2 C1 already_processed(7847)? → no t3 C2 already_processed(7847)? → no t4 C1 do(charge $50) → card charged t5 C2 do(charge $50) → charged again t6 C1 mark_processed(7847) t7 C2 mark_processed(7847) (no-op) result: $100 taken for a $50 order

Both consumers looked before either wrote. The guard did nothing. Note that no line of that trace is unusual — it's just two ordinary executions overlapping by a few milliseconds, which is the normal condition of any system with more than one worker.

The fix: claim the ID before doing the work

Don't ask whether you've processed the message. Claim it — in one statement that the database is obliged to arbitrate, because a uniqueness constraint on message_id means only one of the two inserts can possibly succeed. If yours didn't insert a row, someone else owns this message and you go home.

on message(id, action):
    # one atomic claim; the DB picks a winner
    rows = execute("""
        INSERT INTO processed (message_id)
        VALUES (:id)
        ON CONFLICT (message_id) DO NOTHING
    """, id)

    if rows == 0:        # lost the race
        return ok        # the winner is handling it

    do(action)           # only the winner gets here

The check and the write are now the same operation, so there is no gap to lose. This is the general shape of the trick, not a Postgres detail: any store with a uniqueness constraint or a conditional write will do — a unique index, DynamoDB's attribute_not_exists, Redis SET NX. What you need is one operation that both tests and takes.

What this still doesn't solve

The winner can crash between claiming and finishing. Now the ID is marked and the work never happened, and every redelivery bounces off a claim row belonging to a process that no longer exists — a permanently lost message that looks, from the outside, exactly like a successfully processed one. That's why the claim row shouldn't be a bare marker. Give it a status (claimed / done) and a lease — a claim timestamp plus an expiry — so a claim that has gone stale can be taken over rather than blocking the message forever. Then "already claimed" and "claimed by a corpse" stop being the same state.

The genuinely robust version doesn't need a lease at all, because it puts the work and the claim in the same transaction: insert the claim row and write the business change together, commit once. Either both land or neither does, and a crash rolls the claim back along with everything else. Do this whenever the side effect lives in the same database as the claim — and notice how often it does.

When the work isn't in your database Charging a card is the case that breaks the pattern: you cannot enrol someone else's payment API in your transaction. The answer is to push idempotency across the boundary — send an idempotency key (your message ID, or something derived from it) with the charge request, and the provider dedupes on their side, returning the original result instead of charging again. This is exactly what Stripe's and every other payment provider's idempotency keys are for. When you can't make the operation idempotent, make the API call idempotent and let the system that owns the money enforce it.
The table you'll forget about A processed table grows by one row per message forever, and nobody notices until it's the biggest table in the database and the unique index no longer fits in memory. Give it a retention policy from day one — delete rows older than your maximum redelivery window (hours or days, not years), with a partitioned table or a scheduled purge. You only need to remember an ID for as long as the queue could plausibly resend it.

6. Visibility timeouts: the bug that duplicates your work

This is the most common queue bug in production, and it hides because nothing in your code is wrong.

When a consumer takes a message, the broker doesn't delete it — it makes it invisible for N seconds (SQS calls this the visibility timeout; other brokers call it an ack deadline or ack timeout). If your ack arrives within N, the message is removed. If it doesn't, the broker assumes you died and hands the same message to another consumer. It has no way to tell "crashed" from "still working."

So if a job takes longer than N, the queue delivers it again while the first consumer is still running it. That is not a stray duplicate from a lost ack; it is genuine, guaranteed concurrent processing of the same message, and it's the scenario the race in section 5 was drawn for. Worse: if the job is slow for everyone, every redelivery also times out, and the message loops forever — redelivered, re-processed, never completed, burning capacity that the rest of the queue needed. A backlog that grows while your consumers are visibly busy is usually this.

  • Set the timeout above your real p99 processing time, with headroom — not above the average, which is the mistake. The tail is what times out.
  • Heartbeat long jobs. Most brokers let a consumer extend the timeout while it works (SQS ChangeMessageVisibility, RabbitMQ's consumer timeout tuning, Kafka's max.poll.interval.ms and background heartbeats). A job of genuinely unpredictable length should extend its own lease, not be given a huge fixed one — a huge fixed timeout means a real crash goes unnoticed for just as long.
  • Cap redelivery. A maximum receive count turns the infinite loop into a DLQ entry, which is a problem you can see.

7. Ordering & the dead-letter queue

Ordering. Many queues don't guarantee messages come out in the order they went in — especially once you have multiple consumers racing. If order matters ("account created" must precede "account updated"), you either use a queue that preserves order within a partition (Kafka does, keyed by e.g. user ID) or design so order doesn't matter. Assuming global ordering you don't have is a top-tier source of Heisenbugs.

Dead-letter queue (DLQ). What about a message that can't be processed — malformed data, a bug, a permanent failure? Without a plan, your consumer retries it forever, blocking everything behind it (a "poison message"). The fix is a DLQ: after N failed attempts, shunt the message to a separate queue for humans to inspect later. It's the inbox of things that went wrong, and checking it occasionally will teach you a lot about your own system.

8. The dual-write problem and the transactional outbox

Here's a line of code that appears in almost every service that uses a queue, and it's a bug:

db.insert(order)               # write 1
queue.publish(order_placed)    # write 2
                               # ...and nothing binds them

Two writes, two systems, no transaction spanning them. Crash between them and you get one of two bad outcomes, and which one you get depends on the order you chose. Write the database first and die: you have taken the order and told nobody, so no receipt, no warehouse pick, no fraud check — a paid order that silently doesn't exist downstream. Publish first and die: you have announced an order you never recorded, and the shipping service is now confidently picking stock for a row that isn't there. Wrapping it in a try/catch doesn't help, because the failure you're worried about is the process dying between the two lines, and dead processes don't run catch blocks.

The transactional outbox removes the second system from the critical path. You write the event into an outbox table in the same transaction as the business data — one commit, one database, atomic by construction. A separate relay process then reads unsent rows from that table and publishes them to the broker, marking them sent.

BEGIN;
  INSERT INTO orders (...)  VALUES (...);
  INSERT INTO outbox (topic, payload)
         VALUES ('order_placed', :json);
COMMIT;
-- a relay polls outbox and publishes,
-- then marks the row sent

Now the only question is when the event gets published, never whether — if the order committed, the event is in the table, and the relay will get to it. The other route to the same guarantee is change data capture: instead of a table you write yourself, a tool tails the database's own replication log (Postgres WAL, MySQL binlog) and turns committed rows into messages. Debezium is the usual name here. Less application code, more infrastructure to run; same property.

Outbox gives at-least-once, not exactly-once The relay can publish a message and crash before marking the row sent — so it publishes it again on restart. That's not a flaw to be engineered away; it's the same wall from section 4, moved one step. The outbox guarantees the event is never lost. Making a duplicate harmless is still the consumer's job, which is why the idempotent claim in section 5 doesn't become optional just because you adopted an outbox.

9. Operational gotchas that bite in year two

None of these show up in the tutorial. All of them show up in the incident review.

Head-of-line blocking

Ordering guarantees are always per-partition — Kafka orders within a partition, SQS FIFO within a message group, and nobody orders across them. And a partition is, for ordering purposes, a queue of one: to keep messages in order you must finish message N before starting N+1. So one slow message, or one that keeps failing and retrying, blocks every message behind it in that partition — and if you keyed by customer ID, "that partition" is a specific set of customers having a very bad day while your overall queue depth looks fine.

The trade is unavoidable: concurrency within a partition and strict ordering are mutually exclusive. You pick. Usually you pick more partitions (finer keys, so a blockage is narrower), a fast path to the DLQ so a poison message stops blocking quickly, and ordering only where it genuinely matters rather than as a default.

Alert on consumer lag, not queue depth

Depth tells you how much is waiting. Lag tells you whether you're falling behind — arrivals minus completions, or in Kafka terms the distance between the producer's offset and your committed one. They're different questions and only one of them is urgent. A deep queue that's draining is a system doing its job after a spike; a shallow queue that's growing is a system that will be a deep queue by morning. Alert on lag and on its derivative — is it increasing? — and treat depth as context, not as a page.

Claim check: don't put the payload in the message

A 40 MB video, a giant CSV, a base64'd PDF — none of these belong in a message. Brokers enforce size limits precisely because of this (SQS caps a message at 256 KB; Kafka's default max message size is around 1 MB), and even below the limit a fat queue is a slow queue: more bytes per message means less throughput, longer replication, worse memory behaviour on the broker. The claim check pattern is the fix and it's exactly what it sounds like — put the payload in object storage, send a message containing the key, let the consumer fetch it. The message describes the work; it isn't the work.

Schema evolution across a rolling deploy

Producers and consumers are separate deployments, so they never change at the same instant. For a window — minutes, or hours if a deploy stalls — the new producer is emitting messages that the old consumer has to survive. And messages already sitting in the queue were written by yesterday's code, so the reverse is true too: a message in flight during a deploy is a message from the past.

  • Additive only. Add optional fields; don't remove or rename in the same release as you stop writing them. Removal is a second deploy, after nothing reads it.
  • Tolerant readers. Ignore fields you don't recognise instead of rejecting the message. Strict parsers turn a harmless producer change into a DLQ flood.
  • Never repurpose a field. Changing what status: 2 means is the change that can't be rolled back, because the messages already in flight carry the old meaning and nothing distinguishes them. New meaning, new field.

The DLQ that nobody reads

A dead-letter queue you don't monitor is not a safety net — it's a slower, quieter way to lose data, with the added insult that you'll discover it during a customer complaint about an order from three weeks ago. A DLQ needs two things to actually be a safety net: an alert on arrival rate (non-zero should be interesting; a spike should page someone), and a documented, rehearsed replay path — how a human moves messages back to the main queue after the bug is fixed, and what happens if the replayed message is a duplicate. If the answer to that last part is "we've never tried," you don't have a DLQ, you have a landfill.

10. Four numbers that describe any queue

Every queue's health fits in four numbers. Learn what each one means when it moves and you can debug most queue incidents from the dashboard.

  • Consumer lag — are we falling behind? The one that matters. Rising lag means arrival rate has overtaken drain rate; nothing else on this list is urgent while this one is flat.
  • Oldest message age — how stale is the worst case? This catches what lag averages away: one partition with no live consumer, or a message stuck at the head. It's also the number your users actually feel, because it's the wait time of the unluckiest request.
  • Processing time p99 — how close are we to the cliff? This must sit comfortably below the visibility timeout. When p99 drifts up toward it, you get redelivery and concurrent duplicates before you get a single alert about latency.
  • DLQ arrival rate — what are we losing? The rate, not the count — a count is a number nobody looks at twice, a rate has a shape and you can see it change after a deploy.

Starting points, not benchmarks — every one of these depends on what the queue does, and a nightly batch pipeline has no business being held to a checkout queue's numbers. Use them as the values you set on day one and then argue with:

The arithmetic worth doing once Messages arrive at rate A. Each consumer processes at rate C. With N consumers you need N > A / C just to hold steady — at exactly A/C you never fall behind and you never catch up either. Only the surplus eats a backlog: a backlog of B messages drains in roughly B / (N·C − A). Push N·C toward A and that denominator goes to zero and the drain time goes to infinity. Which is the whole lesson: a queue provisioned with no headroom above its arrival rate never recovers from a spike. It doesn't recover slowly — it doesn't recover. Size consumers for the backlog you want to be able to clear, not for the average day.

11. Kafka vs. RabbitMQ vs. SQS

Three tools you'll hear constantly. They're less interchangeable than they look:

Apache Kafka

A distributed log, not a traditional queue. Messages are kept (even after reading) and replayed. Insane throughput; great for event streaming, analytics pipelines, and "many consumers, same stream." Heavier to operate.

RabbitMQ

A classic, flexible message broker with rich routing. Smart about getting this message to the right consumer. Great for task queues and complex routing. Messages typically vanish once acked.

AWS SQS

A fully-managed queue — no servers to babysit. Dead simple, scales itself, at-least-once by default (plus a FIFO mode). The boring, correct choice on AWS.

Rule of thumb

Streaming/replay/high volume → Kafka. Complex routing of discrete tasks → RabbitMQ. "I just want a queue and no ops" → SQS.

12. Real-world examples

War story · the retry storm At-least-once retries have a dark side. When a downstream service slows down, naive consumers retry immediately — piling more load onto the thing that's already struggling, guaranteeing it never recovers. This is a retry storm, and it has caused real outages at companies you've heard of. The fix (from the Reliability guide): exponential backoff + jitter, so retries spread out instead of stampeding. Retries are a fire; backoff is not throwing gasoline.

LinkedIn & Kafka — Kafka was born at LinkedIn to move billions of events a day (clicks, profile views, messages) between systems without every service calling every other service. It got so central they open-sourced it, and now half the industry runs on it.

Uber's dispatch & every food-delivery app — "your driver is 3 minutes away" is a river of location events flowing through streaming queues. The order you place, the restaurant's ticket, the courier assignment, the push notification — each is a message handed between services asynchronously so no single slow step freezes the app.

Your last online order — the instant "Order confirmed!" you saw was almost certainly a lie of omission: the receipt, the warehouse pick, the fraud check, and the loyalty points were all still sitting in queues, being handled by background workers while you closed the tab. And that's exactly how it should be.

The one-liner to remember Do the urgent bit now, queue the rest, and make every consumer idempotent so retries are harmless. Async isn't about doing less work — it's about not making the user wait for work they don't care about.

13. Recap in 60 seconds

  • Async is a choice about waiting, not about work. Do the essential bit inline, queue the rest, answer the user now.
  • A queue is a shock absorber. Bursty in, smooth out. Bound it, or the buffer becomes the outage.
  • Work queue = one consumer gets it. Pub/sub = everyone does. Task distribution vs. event notification.
  • At-least-once is the real default. Exactly-once end-to-end is a story; at-least-once plus idempotency is the implementation.
  • Check-then-act is a race. Claim the message ID with one atomic conditional insert, and only the winner does the work.
  • A claim needs a status and a lease, or a crash mid-work turns a message into a permanent silent loss.
  • External side effects need the provider's idempotency key. If you can't put the work in your transaction, push dedup to whoever owns it.
  • Visibility timeout below your p99 = guaranteed duplicate processing, and if it's slow for everyone, infinite redelivery. Heartbeat long jobs; cap receive count.
  • Ordering is per-partition, and a partition is a queue of one. Concurrency and strict ordering are mutually exclusive — pick.
  • Never write to the DB and the broker as two steps. Outbox table in the same transaction, or CDC off the replication log.
  • Send a pointer, not a payload. Claim check keeps the queue thin and inside broker size limits.
  • Deploys are rolling, so schemas must be additive. Tolerant readers, optional fields, never repurpose a field's meaning.
  • Alert on lag and its slope, not depth. Deep and draining is fine; shallow and growing is not.
  • An unmonitored DLQ is a landfill. Alert on arrival rate, rehearse the replay.
  • N > A / C, always. No headroom above arrival rate means a spike never drains.

14. Check yourself

Six situations. Answer before you open them — the point is the diagnosis, not the vocabulary.

The same job runs three times. The logs show no errors and no retries. What's the first setting you check?
The visibility timeout (or ack deadline) against your actual p99 processing time. No errors is the tell: nothing failed, the broker simply decided you'd died because you hadn't acked in time and gave the message to someone else — twice. Three executions of a job that takes just over the timeout is the classic signature. Fix the timeout, then heartbeat the job so its length stops being a guess, and check the receive count on the message to confirm — it's the number nobody thinks to look at.
Your service records the order correctly, but roughly once a week the confirmation email never sends. No exception, no DLQ entry. What's the architectural fix?
This is the dual-write problem: the database commit and the queue publish are two separate writes, and once a week the process dies or the broker call fails in the gap between them. There's no exception because there's nobody left to catch it, and no DLQ entry because the message was never published. The fix is the transactional outbox — write the event to an outbox table inside the same transaction as the order, and let a relay publish it. Retrying the publish in a catch block only shrinks the window; it doesn't close it.
Kafka guarantees ordering, so why did your "account created" and "account updated" events arrive backwards?
Because the guarantee is per-partition, and those two events almost certainly landed in different partitions — either they were produced with no key (round-robin) or with different keys. Ordering only holds for messages that share a partition, so anything that must be ordered relative to each other has to share a partition key: here, the account ID. The corollary is that your key choice is your ordering design, and it also decides your blast radius when one message gets stuck.
Consumers are healthy, CPU is low, lag is basically zero — but one customer's exports have been pending for two hours. Which number would have caught it?
Oldest message age. Lag and depth are aggregates, and an aggregate over dozens of partitions will happily average away one partition that is completely stuck — a consumer that died without rebalancing, or a poison message at the head blocking everything behind it. Oldest message age is the only one of the four that can't be diluted by healthy traffic, which is exactly why it's worth paging on separately. High age with low lag is nearly always head-of-line blocking in one partition.
You doubled your consumers to clear a 2-million-message backlog. Six hours later it's barely moved. What's the arithmetic?
Only the capacity above the arrival rate does any draining: the backlog falls at N·C − A, not at N·C. If you were previously right at the edge, doubling might take you from "keeping up" to "keeping up plus a little," and a little divided into two million is a very long time. Work out the surplus explicitly before you scale — and check that C itself hasn't dropped, because a saturated downstream dependency means the extra consumers are just queueing somewhere else.
You add a processed-IDs table and the double charges stop. A month later, a handful of payments silently never happen at all. What did the fix introduce?
A claim with no way to expire. The consumer inserted the ID, then crashed before completing the charge, so the row now says "handled" for work that never ran — and every redelivery bounces off it and acks. You traded a loud failure for a silent one. The claim row needs a status and a lease so a stale claim can be taken over, or the claim and the work need to commit in one transaction; where the side effect is external, the provider's idempotency key is what lets you safely retry instead of guessing.

The Reliability Toolkit

Everything fails, all the time. Reliability isn't preventing failure — it's making sure one thing breaking doesn't take the whole cathedral down with it.

1. The uncomfortable truth

At scale, something is always broken. A disk somewhere is dying, a network link is flapping, a deploy is misbehaving, a dependency is having a bad day. You cannot engineer failure away — with enough machines, the rare becomes the constant. So the goal shifts from "don't fail" to "fail small, fail contained, and keep serving what you still can." This is resilience, and it's a set of specific, learnable moves.

Two numbers worth knowing Availability is often quoted in nines. "Three nines" (99.9%) is ~8.76 hours of downtime a year (about 8h 46m); "four nines" (99.99%) is ~52 minutes; "five nines" is ~5 minutes. Each extra nine costs roughly an order of magnitude more effort — which is why "how many nines do we actually need?" is a business question, not just an engineering one.

2. Redundancy & failover

The foundation: never have exactly one of anything critical. Two servers, replicated databases, multiple availability zones. When one dies, another takes over — failover. The load balancing guide covered the mechanism and the database scaling guide covered the replica side of it; the principle here is broader: a single point of failure is a scheduled outage you haven't been told the date of yet.

The subtlety is that failover itself must be tested. A backup that has never been failed-over to is not a backup — it's a hope. Plenty of outages are made worse by a standby that turned out to be misconfigured, out of date, or, memorably, also on fire.

3. Timeouts: the first and cheapest defense

Go back to the cold open. The root sin was waiting forever for a slow service. A call with no timeout is a promise to hang indefinitely — and hung threads are the fuel of every cascade.

A timeout says: "if you haven't answered in 2 seconds, I'm giving up and moving on." It converts an unbounded hang into a fast, catchable failure you can handle. It's one line of code and it's the highest-value cheap habit in this whole guide. The catch is picking the number: too short and you kill healthy-but-busy calls; too long and you're back to hanging. Base it on real latency percentiles (p99), not vibes.

4. Retries — and the storm they can summon

Transient failures (a blip, a brief network drop) often succeed on a second try, so retrying is smart. Retrying naively is how you turn a small problem into an outage.

War story · the retry storm A service slows down. Every client immediately retries. Those retries double the load on the already-struggling service, so it slows further, so more calls fail, so more retries fire… a self-reinforcing avalanche that keeps the service down long after the original blip is gone. Naive retries don't help a struggling system recover — they hold its head underwater.

The fix is exponential backoff with jitter: wait 1s, then 2s, then 4s before each retry (back off), and add a random wobble (jitter) so a thousand clients don't all retry in lockstep and re-synchronize the stampede. Also cap the number of retries, and don't retry things that aren't retryable (a 400 Bad Request will be just as wrong the second time). Notice this only works because of idempotency from the queues guide — retrying a non-idempotent action is how you double-charge someone.

Backoff and jitter fix retry timing. They do nothing about retry volume, which is the half that actually kills you — see retry budgets below.

6. Bulkheads & load shedding

Bulkheads — named after a ship's watertight compartments. Isolate resources so a flood in one area can't sink the whole vessel. If calls to the flaky recommendations service get their own limited thread pool, they can exhaust that pool without stealing threads from checkout. One feature browns out; the ship stays afloat.

Load shedding — when you're truly overwhelmed, it's better to serve most requests well than all requests badly. So deliberately reject some traffic at the door (return a quick "try again in a moment") to keep the system from collapsing entirely. Counterintuitive but vital: sometimes saying "no" fast is the most reliable thing you can do. Shedding lives next door to the health checks and connection draining in the load balancing guide — same idea, applied at the door rather than at the pool.

7. Graceful degradation

When a non-essential dependency fails, don't take the whole page with it — shed the feature, keep the core. The recommendations engine is down? Show a generic "popular items" list, or nothing, but still let people check out. The search ranking service died? Fall back to plain results. Users forgive a missing sidebar; they don't forgive a white screen.

The mindset Ask of every feature: "if this dependency vanishes, what's the least-bad thing we can show?" Design that fallback on purpose, before the incident. A system that degrades gracefully feels far more reliable than one that's binary — perfect or dead.

Notice what you're actually doing when you serve stale prices from a cache because the pricing service is down: you're trading correctness for availability, one feature at a time. That's the choice from the consistency and CAP guide, made concrete. Graceful degradation isn't a separate topic from consistency — it's the AP branch, chosen deliberately and scoped to the parts of the product where slightly-wrong beats not-there. Checkout totals get the other answer.

You get a graph that's the wrong shape and four minutes to decide. The question that matters is narrower: which flood am I looking at, and which wall stops that one? 9. Do the arithmetic

Cascading failure gets described in metaphors — dominoes, floods, avalanches — which makes it feel like weather. It isn't. It's a multiplication you can do on a napkin, and the reason a cascade is so fast is that the multiplier is large.

Little's Law, and why a slow dependency kills every endpoint

One formula does most of the work here: concurrency = throughput × latency. If you serve 400 requests a second and each takes 50 ms, then at any instant about 20 requests are in flight. That's it. That's the law. Now watch what happens when only the latency term moves.

concurrency = throughput × latency healthy throughput 400 req/s p99 latency 50 ms (0.05 s) concurrency 400 × 0.05 = 20 slots in use thread pool 200 slots → 10× headroom, feels generous the downstream call slows to 5 s throughput 400 req/s (unchanged — callers don't know yet) latency 5000 ms (5 s) → 100× worse concurrency 400 × 5 = 2000 slots needed thread pool 200 slots → short by 1800 time from "slow" to "down" free slots at t=0 180 arrival rate 400 req/s completions none for 5 s 180 ÷ 400 = 0.45 seconds

Latency went up 100×, so required concurrency went up 100×, and the pool you thought had ten times the headroom you'd ever need was gone in under half a second. Note that nothing crashed and no error was logged by the thing that caused it. The dependency is still returning 200 OK, just eventually.

Now the part that turns a feature problem into an outage: the pool is shared. Every request that arrives after those 180 slots are gone gets nothing — the login page, the health check, the status endpoint, the one endpoint in your service that has never once called recommendations. That's the cold open, in numbers. A slow dependency doesn't degrade the feature that uses it; it takes the whole process, because threads and connections are the currency all your endpoints spend.

The line worth memorising A timeout is a concurrency budget. Rearranged, the law says the most concurrency a dependency can ever consume is throughput × timeout. Setting a timeout of 5 seconds on a call that takes 400 requests a second isn't a latency decision — it's you authorising that call to occupy 2000 slots. Nobody would sign that if it were written down. It usually is, in a config file, as timeout: 5000.

Redo it for your own service and you'll see why timeouts alone don't save you. Drop the timeout from 5 s to 1 s and the arithmetic gives 400 × 1 = 400 slots — still double the pool. A tight timeout buys you time; it doesn't buy you a bound, because the throughput term is set by your users and not by you.

The bound is what a bulkhead is for, and the same formula sizes it. Give recommendations its own pool of 20 connections and the answer stops depending on how fast the dependency is: 20 is the most it can ever take, and everything else fails instantly at the bulkhead instead of queuing inside your process. Run it the other way — throughput = concurrency ÷ latency — and you get the shape of the degraded state: 20 ÷ 5 = 4 requests a second still get real recommendations, the other 396 get the fallback, and checkout never notices. That's the whole toolkit in one line of arithmetic: the outage became a slightly worse sidebar.

The nines multiply, and that's the problem

The other arithmetic people skip is what a chain of dependencies does to an availability figure. Availability composes by multiplication, not by averaging, and multiplication of numbers below 1 only goes one direction.

ten hard dependencies, each at three nines (99.9%) 0.99910 = 0.99004 → 99.0% , about 87 hours of downtime a year compare: three nines on its own 0.999 = 99.9% → about 8.8 hours a year

A service that depends on ten things each at three nines cannot itself be at three nines. It starts its life at 99.0% and then subtracts whatever its own bugs cost. You don't get to promise your users an availability number better than the product of everything you hard-depend on, and no amount of care in your own code changes that — you'd be trying to be more reliable than your inputs.

Two honest caveats, both of which matter. First, this assumes failures are independent, and they usually aren't: shared availability zones, a shared config push, a shared identity service. Correlated failure makes the real number worse than the arithmetic, not better. Second, it assumes every dependency failure becomes your failure — and breaking that assumption is precisely what this entire guide is about. A timeout with a designed fallback converts a dependency's outage into a degraded response instead of an outage of your own, which takes that dependency out of the product entirely.

The number actually worth tracking Not "how many dependencies do I have" but "how many hard dependencies do I have" — the ones with no fallback, where their bad day is definitionally your bad day. Count them. That count is your availability ceiling, and the useful reliability work is nearly always moving items off that list rather than making each one slightly better.

10. The gotchas that actually bite

The five walls are the part that fits on a slide. What follows is the part that shows up in postmortems.

Retry budgets: backoff controls timing, not volume

Exponential backoff and jitter decide when retries happen. Nothing in either decides how many. During a broad outage, every client is failing, so every client is retrying, and politely staggered retries are still a multiplied traffic load arriving at a service that is already on the floor. Backoff spreads the stampede over a few seconds; it does not make it smaller.

The volume control is a retry budget: a token bucket, refilled by successful requests, that permits retries only up to a small fraction of live traffic — on the order of 10%. The property this gives you is the one you want: when a few calls fail, retries are free and they work. When everything fails, there are no successes refilling the bucket, the budget empties, and retries simply stop. The system loses its ability to amplify its own outage at exactly the moment that ability would be most destructive.

Pair it with the other rule: retry at exactly one layer. Three retries in the client SDK, three in the API gateway, and three in the service is not nine attempts — it's 3 × 3 × 3 = 27 requests hitting the bottom of the stack for one user action, generated by three teams who each individually did the responsible thing. Pick the layer that knows enough to judge whether a retry is safe, retry there, and make every other layer fail fast. The queues guide has the other half of this: retries are only safe on operations that are idempotent.

Deadline propagation: a timeout set per hop is a lie

Every service in the chain sets its own timeout, independently, based on its own sensible reasoning. The caller waits 1 second. The service it calls waits 3. So one second in, the caller has given up, returned an error to the user, and moved on — while the callee is still working, still holding a connection, still hammering the database, producing an answer that will be written to a socket nobody is reading. Under load, a meaningful share of your capacity goes to computing responses that are already garbage.

The fix is to pass the remaining deadline down with the request — a header, a context object, whatever your stack calls it — and have each hop check it before starting work and refuse anything it can't plausibly finish in time.

POST /checkout           deadline = now + 1000ms
  └─ POST /inventory     remaining: 940ms   → ok, proceed
       └─ SELECT ...     remaining: 780ms   → ok, proceed
  └─ POST /recommend     remaining: 120ms   → p99 is 300ms
                                            → refuse now, return fallback
                                            (don't start work nobody will wait for)

This is what makes timeouts compose. Without it you have a pile of unrelated numbers that happen to be in the same request path; with it you have one budget, spent down the stack, with every hop able to see how much is left.

Metastable failure: the outage that outlives its cause

This is the most important idea missing from most reliability writing, and it's the one that produces the 3 a.m. phone call nobody can explain. Some systems, once pushed past a threshold, stay collapsed after the original trigger is gone. The deploy was rolled back twenty minutes ago. The slow query was killed. The dependency has been green for a while now. The service is still down.

The reason is that the outage manufactured its own new load. The queued retries from every client that failed during the incident are still arriving. The caches went cold while the service was unavailable, so every request that does get through is now a full cache miss and costs ten times what it used to. Connection pools are churning. That combination — retry backlog plus cold cache — is, by itself, more load than the system can serve, which produces more failures, which produces more retries. The trigger is long gone; the feedback loop it created is self-sustaining.

The counter-intuitive part You cannot wait a metastable failure out. Patience is the wrong instinct and it is the instinct everyone has. Recovery requires actively removing load — aggressive shedding, flushing retry queues, sometimes turning traffic off entirely and reintroducing it in slices while caches refill. You will be deliberately taking down a service that is already down, in front of an audience, at 3 a.m. Nobody makes that call well under those conditions, which is exactly why it has to be decided, written down, and rehearsed in advance. A 2021 HotOS paper gave this failure mode its name — metastable failure — and naming it is most of the battle, because a team that has the word will recognise the shape in minutes instead of hours.

Gray failure: nothing is ever cleanly dead

Every diagram in this guide implies a binary — up or down, healthy or failed, closed or open. Real outages are almost never that considerate. A node that is slow. A node failing 5% of requests. A node that answers GET /health perfectly and cannot serve a single real query because the connection pool to its database is exhausted. A node that looks healthy to the load balancer sitting next to it in the same rack, and unreachable to the clients in another region.

Each of these evades a binary health check, which is why gray failures last so much longer than clean ones: your automation sees nothing wrong and does nothing, while your users see everything wrong. The defences are behavioural rather than binary — health checks that exercise the real dependency path rather than returning a constant, latency-based ejection rather than error-based, breakers that count slow responses as failures, and outlier detection that compares a node against its peers instead of against a threshold.

The line to keep Every network partition is, in practice, a timeout you configured. No packet ever arrives announcing a partition. There is only silence, and a number you chose that decides how long silence is allowed to last before it counts as failure. Which means the boundary between "slow" and "dead" isn't a property of the network — it's a product of your config file.

Fail open or fail closed is a product decision

The auth service is down. Does the door open, or does it stay shut? Fail open and you're serving users you can no longer authenticate. Fail closed and you're locking out every legitimate customer over a dependency they've never heard of. The fraud checker is down — do you take the payment, or refuse the money? There is no engineering answer to either. There is a revenue answer, a legal answer, and a trust answer, and they don't all point the same way.

Two things follow. First, someone with the authority to make that trade-off must decide before the incident, because during the incident the decision falls to whoever is on call, who does not have that authority and is guessing. Second, the right answer differs per feature within the same system: the session-validity check on a "recently viewed" widget can fail open without anyone caring, and the same check on the admin panel absolutely cannot. Treating fail-open as a system-wide switch is how you end up with one setting that's wrong somewhere important.

Circuit breaker tuning is where breakers go wrong

The state machine is the easy part; nobody gets that wrong. The thresholds are where breakers earn their reputation for being more trouble than they're worth.

Set them too tight — trip on 3 failures, or on a 10% error rate — and the breaker opens on ordinary background noise. You've now cut yourself off from a dependency that was fine, and you'll do it repeatedly, converting a service that was 99.5% available into one you refuse to call. Set them too loose — 90% errors over a five-minute window — and it never opens at all during the incident it existed for. Anything with a 5% error rate, which is most gray failures, will never cross a threshold set on error rate alone. And a breaker evaluated over too few requests trips on statistical noise: require a minimum volume in the window, or a quiet endpoint will open a circuit on the strength of two unlucky calls.

Then half-open, which is the state people forget to tune. When the cooldown expires, the recovering service must be probed by a trickle — a handful of requests, one at a time. If every instance in your fleet resumes full traffic at the same moment the cooldown ends, you have built a synchronised stampede aimed at a service with cold caches and empty pools, and you will knock it straight back down. The same jitter that fixes retry timing belongs on breaker cooldowns for exactly the same reason.

And then the human factors, which cause more downtime than any of this

Every mechanism in this guide is executed by tired people reading a screen at 3 a.m. That's the actual runtime environment, and it's the one least often designed for.

The runbook nobody has run

Written once, at the end of a project, by someone who has since left. It references a dashboard that was renamed and a script that requires permissions the on-call doesn't have. A runbook is a hypothesis until someone has followed it start to finish.

The dashboard nobody can read

Sixty panels, no ordering, and nothing that answers "is it us or is it them?" in the first five seconds. At 3 a.m. you get one glance. If the top of the page doesn't say what's broken, the dashboard is decoration.

Alerts too noisy to hear

Every page that didn't need a human trains the next one to be ignored. Alert fatigue isn't laziness — it's a correctly learned response to a channel with a bad signal rate, and the real alert dies in that noise.

The unrehearsed rollback

"We can always roll back" is a claim about a procedure nobody has performed under pressure. Then it turns out the migration wasn't backward-compatible, and you discover this during the incident rather than during a Tuesday.

Recovery paths that only run in emergencies

Code that executes exclusively during disasters gets tested exclusively during disasters. Failover, fallback, restore, shed — anything on that list which hasn't run this month should be assumed broken.

The fix: make them routine

The most reliable systems aren't the ones with the best failure handling. They're the ones whose failure handling runs constantly — failover as a weekly exercise, restores on a schedule, breakers that trip in normal operation and nobody notices.

Which is the honest argument for the next section. Chaos engineering isn't about breaking things for sport — it's the mechanism that moves a recovery path from the "only runs in emergencies" column to the "runs every Tuesday" column. That's the entire value proposition.

11. Testing with chaos

Here's the punchline to all of the above: a failure path you've never triggered probably doesn't work. Backups you don't restore, failovers you don't rehearse, circuit breakers you've never watched trip — they're all theories until tested. So the boldest teams break things on purpose, in production, during business hours, to prove the safety nets hold.

Netflix pioneered this with Chaos Monkey, a tool that randomly kills live servers to force engineers to build systems that don't care when a server dies. If a random instance vanishing is a non-event, then a real one dying at 3 AM is also a non-event — and everyone sleeps. Chaos engineering is just the discipline of finding your weaknesses before they find you.

12. Real-world examples

War story · $440 million in 45 minutes In 2012, trading firm Knight Capital deployed new code to its servers — but one of eight servers didn't get the update and started running old, repurposed logic. In about 45 minutes, it fired millions of unintended orders into the market and lost roughly $440 million, near-fatally wounding the company. The killers weren't exotic: an inconsistent deploy, no kill switch, and no fast way to detect and stop a misbehaving node. Reliability isn't only about staying up — it's about being able to stop fast when something goes wrong.
War story · the typo that broke the internet On February 28, 2017, an AWS engineer debugging S3 in the us-east-1 region ran a command with a typo, accidentally removing far more capacity than intended. S3 went down for hours and took a huge slice of the internet with it — sites, smart-home gadgets, even other AWS services that secretly depended on it. Lessons the industry absorbed: guardrails on dangerous commands, blast-radius limits, and not letting one region become a single point of failure for everyone.

Netflix, the reliability obsessives — beyond Chaos Monkey, Netflix built Hystrix (circuit breakers + bulkheads) precisely because their service depends on hundreds of others. (Hystrix is now in maintenance mode — today teams reach for resilience4j or adaptive concurrency limits — but the patterns it popularized are everywhere.) Their whole architecture assumes dependencies will fail and degrades around them, which is why a struggling microservice usually means a slightly worse row of recommendations, not a dead app.

The one-liner to remember You can't stop things from failing — you can only stop failures from spreading. Timeouts, retries-with-backoff, circuit breakers, bulkheads, and graceful degradation are the five walls that keep one crack from sinking the ship. Then test them by breaking things on purpose.

13. Recap in 60 seconds

  • Redundancy — answers "one machine died." Useless until you've actually failed over to the spare.
  • Timeout — answers "it's slow." Bounds the wait, and by doing so bounds the concurrency: throughput × timeout.
  • Retry with backoff + jitter — answers "it blipped." Fixes retry timing only.
  • Retry budget — answers "everything blipped at once." Fixes retry volume, which is the half that causes outages.
  • Circuit breaker — answers "it's down." Stops paying for calls you know will fail, and gives the sick service room. Says nothing about overload.
  • Bulkhead — answers "one thing is eating everything." The only tool that gives you a hard bound rather than a smaller number.
  • Load shedding — answers "there's more work than machine." Says nothing about a slow dependency.
  • Graceful degradation — answers "this part is optional." Decide the least-bad fallback before the incident, per feature.
  • Deadline propagation — makes the timeouts above compose instead of contradicting each other.
  • Chaos engineering — the only evidence that any of the above works.
  • Metastable failure — the outage that survives its own cause. Shed load to escape; you cannot wait it out.

14. Check yourself

If you can answer these without scrolling up, you own the material.

The dependency recovered ten minutes ago and your service is still down. What's happening, and what do you do?
This is a metastable failure: the outage created its own load — a backlog of client retries plus caches that went cold while you were unavailable — and that load alone is now enough to keep you down. The original trigger is irrelevant; you're stuck in a feedback loop it started. Waiting will not fix it, because nothing in the loop decays on its own. You escape by actively removing load: shed aggressively, drop or drain the retry backlog, and if necessary take traffic to zero and reintroduce it in slices so caches can refill against a survivable request rate. Yes, that means deliberately taking down something already down — which is why it should be a written, pre-approved procedure rather than a judgement call at 3 a.m.
You add retries and the outage gets worse. Why?
Because retries are a load multiplier, and you applied one to a system whose problem was load. If the dependency is saturated rather than blipping, every retry is extra work aimed at the thing that's already failing to keep up. Two specific traps: retries configured at several layers multiply rather than add — three at the client, gateway and service is 27 attempts at the bottom — and backoff with jitter only spreads that volume over time, it doesn't reduce it. The missing piece is a retry budget that caps retries at a small fraction of live traffic and empties itself when there are no successes to refill it, so retries switch themselves off during exactly the broad outage where they'd do the most damage.
"Our service is 99.99% available and it depends on four services that are each 99.9%." What's wrong with that sentence?
Availability composes by multiplication, so four hard dependencies at three nines put your ceiling at 0.999⁴ ≈ 99.6% — around 35 hours a year — before your own code contributes a single bug. You cannot be an order of magnitude more available than your inputs. The sentence is only rescuable if those four aren't hard dependencies: if each one has a timeout and a designed fallback, its outage becomes a degraded response rather than yours, and it drops out of the product entirely. That's the real point — the fix isn't making four services better, it's moving them off the hard-dependency list.
Recommendations has slowed to 4 seconds and your whole site is now failing, including endpoints that never call it. Do you shed load?
No — you'd be treating the wrong flood. Shedding helps when there's more work than machine; here there's plenty of machine, and it's all parked on blocked threads waiting for an outbound call. Rejecting your own callers frees nothing. The right walls are a tight timeout (the concurrency you're spending on that call is throughput × timeout), a bulkhead so recommendations can only ever occupy its own small pool, a breaker that counts timeouts — not just errors — as failures, and a fallback so the page still renders. The general tell: threads blocked on outbound calls means dependency trouble, threads blocked on inbound queue depth means overload.
There was clearly a dependency outage, but your circuit breaker never tripped. Name two plausible reasons.
Most likely it was a gray failure — a 5% error rate, or responses that were slow but successful — and a breaker watching for a 50% error rate on explicit errors will never see it. That's the fix too: count timeouts and slow responses as failures, not just non-2xx. The other common causes are a threshold or window set too loose to trigger inside the incident's duration, and a breaker scoped per-instance across a large fleet, where each instance sees too few failures individually to cross its own threshold even though the aggregate picture is obvious. Breakers fail silently in the wrong direction, which is why "did it trip?" belongs on the postmortem checklist.
The auth service is down. Do you fail open or fail closed?
There is no engineering answer — it's a product decision about which risk the business prefers, and it must be made per feature rather than per system. Failing open on a session check for a "recently viewed" widget costs nothing; failing open on the admin panel or a payment authorisation is how you end up explaining yourself to a regulator. Failing closed on everything is safer and may still be the wrong answer if it means zero revenue for the duration. The engineering obligation is to surface the choice to someone with the authority to make it, in advance, and to build the switch so it can actually be flipped per feature during an incident — not to guess at 3 a.m.

Consistency & the CAP Theorem

When your data lives in more than one place, "what is the current value?" stops being a simple question — and physics forces you to choose what you're willing to give up.

The capstone to Caching, Scaling Databases, Load Balancing, Message Queues, and Reliability.

1. What "consistency" actually means

On one machine, this is trivial: you write a value, you read it back, you get the value. The trouble starts the moment data is copied — to a replica, a cache, another region — which, as every other guide in this series showed, is exactly what you do to scale.

Consistency, in the distributed sense, asks: when I read, am I guaranteed to see the most recent write, no matter which copy I hit? If yes, the system is strongly consistent — it behaves as if there were one copy. If reads can be briefly stale, it's eventually consistent. You've met this exact trade-off already as cache staleness and replication lag. This guide is the theory that unifies them.

Two different words, spelled the same The C in CAP is not the C in ACID, and almost every circular argument about consistency starts right here. CAP's C is linearizability: the system behaves as though there were exactly one copy of the data, and operations appear to take effect in an order that respects real time — if your write returned before my read started, I see your write. ACID's C is a completely different promise: the database won't let you violate your own constraints — foreign keys hold, CHECK passes, the balance doesn't go negative because you said it mustn't. One is about copies agreeing with each other; the other is about rules holding within one copy. A single-node Postgres gives you ACID's C in full and has nothing whatsoever to say about CAP's. When someone says "we need consistency," find out which word they're using before you design anything, because the two answers share no code.

2. The CAP theorem

The CAP theorem is the closest thing distributed systems has to a law of physics. It says a system can offer at most two of three guarantees:

C — Consistency

Every read sees the latest write. All copies agree.

A — Availability

Every request gets a (non-error) response, even if some nodes are down.

P — Partition tolerance

The system keeps working even when the network splits and nodes can't talk to each other.

The part everyone gets wrong "Pick two" is misleading. In any real distributed system, P is not optional — networks will partition, and you don't get to opt out of reality. So the real choice is only ever between C and A, and only during a partition. That's it. That's the whole theorem, stripped of its mystique: when the network breaks, do you return possibly-stale data (choose A) or refuse to answer (choose C)?
The test that shows how little CAP tells you A single node on a single machine is trivially CP. It never disagrees with itself, so every read sees the latest write; and when you can't reach it, it's simply unavailable. Perfect consistency, achieved by doing nothing. That should be a useful embarrassment: "we're CP" describes what a system does in one rare situation and tells you nothing about its latency, throughput, durability, isolation level, or behaviour on an ordinary day. CAP is a constraint on the design space, not a description of a design. PACELC exists because people kept treating it as one.

3. Why partitions aren't optional

A network partition is any moment your nodes can't reliably reach each other — a cut cable, a bad switch, an overwhelmed link, a whole region going dark. Over enough machines and enough time, this is not a maybe. So every distributed database has already, quietly, made a CAP choice on your behalf:

  • CP systems (choose Consistency) — during a partition, refuse reads/writes that can't be made safely. Correct, but some requests fail. Think: HBase, ZooKeeper, etcd, and RDBMS clusters run in CP mode.
  • AP systems (choose Availability) — during a partition, keep answering with whatever each node has, and reconcile later. Always up, sometimes stale. Think: Cassandra, DynamoDB, most caches and DNS.

The ATM in the cold open chose AP — stay available, sort out the mess later. For a bank balance that's terrifying; for a shopping cart or a like-count it's exactly right. There is no universally correct answer, only a correct answer for this data. (A system that degrades to a cached or approximate answer instead of erroring is choosing A over C on purpose — that's the graceful degradation pattern wearing its CAP hat.)

Every partition is a timeout you configured

Here's the part the textbook diagrams skip. You never actually observe a partition. No packet arrives announcing that the network has split. What you observe is that a node didn't answer inside a window — and you chose that window. Set the failure detector to 500 ms and a long GC pause becomes a partition. Set it to 30 s and the same event becomes "a slow request," while a genuinely dead node keeps taking traffic for half a minute. Same network, same hardware, different config file, different number of partitions per week.

This is gray failure: nodes are rarely up or down, they're slow, and from the outside "slow" and "gone" are the same observation. A node answering in four seconds is in some ways worse than a crashed one, because a crashed node is at least unambiguous. The consequence for CAP is worth sitting with — the P is not a natural phenomenon you detect, it's a threshold you set, usually by copying a default. Shorten it and you get more partitions, each resolved faster. Lengthen it and you get fewer partitions, each of which hurts for longer. There is no setting that gives you zero.

4. PACELC: the sequel that tells the whole truth

CAP has a blind spot: it only describes behavior during a partition, which is rare. What about the 99.9% of the time the network is fine? PACELC extends it with a brutally honest addendum:

If Partition, choose A or C — Else (normal operation), choose Latency or Consistency.

In plain terms: even when everything is healthy, keeping all your copies perfectly in sync costs time — you have to wait for the other nodes to confirm. So there's a permanent, everyday trade-off between being fast and being perfectly consistent, partition or not. This is why strongly-consistent databases feel slower: they're paying the coordination tax on every write. Latency vs. consistency is the tax you pay all day; availability vs. consistency is the bill that comes due during a partition.

The branch that actually runs Read PACELC again and notice which half of it fires more often. A partition is an incident — a handful of minutes a year if you're unlucky, and someone writes a postmortem about it. The else branch fires on every request, from every user, all day, forever. Does this read go to the leader or to a replica? Does this write return after one ack or after a majority? Does the cross-region hop happen before you answer or after? You will make that call several million times before lunch. A guide that teaches only CAP has taught you the branch that almost never fires and skipped the one you live in. If you take one sentence from this page: your everyday trade-off is L versus C, not A versus C.

6. Quorums: turning consistency into a dial

Here's the elegant trick AP databases use to tune where they sit. Say each piece of data is replicated to N nodes. You get to choose how many must respond:

  • W = how many replicas must confirm a write before it counts.
  • R = how many replicas you read from and compare.

The beautiful part: if R + W > N, your read set is guaranteed to overlap the latest write on at least one node — so a read can return the latest acknowledged value on demand (which is a weaker promise than linearizability, and weaker still under failure — the next section walks a real one through a partition to show exactly where the edges are). Want speed instead? Lower R and W and accept staleness. One formula, a whole spectrum, chosen per query. Cassandra and DynamoDB expose exactly this.

N = 3 replicas
W = 2, R = 2  →  R + W = 4 > 3  →  strong-ish, balanced
W = 1, R = 1  →  R + W = 2 < 3  →  fast, possibly stale

What R + W > N actually buys you

It buys you intersection, and only intersection. Any set of R nodes and any set of W nodes drawn from N must share at least one member, so the nodes you read from include at least one that acknowledged the most recent successfully acknowledged write. That's a genuine, useful property. It is also the entire property.

Notice what that sentence doesn't say. It says a current copy is present in the responses, not that you can identify it — you still need versioning and a resolution rule to pick the winner out of the set, and if that rule is wrong the intersection guarantee doesn't save you. It says nothing about writes that failed: a write that reached one node out of three returns an error to the client but is not rolled back, so it can surface in a later read, or not, depending on which nodes answer. And it gives you nothing across operations — with reads landing on different node sets, two successive reads can go new-then-old until read-repair or anti-entropy catches up, which is a monotonicity violation, not a linearizability one, and users notice it.

Precision matters here R + W > N is not linearizability. Getting there needs more machinery: read-repair and anti-entropy so divergence actually converges rather than lingering; a conflict-resolution rule that doesn't silently drop data; and, for anything involving read-modify-write — increment a counter, check-and-set, reserve the last seat — a real consensus protocol, because no amount of quorum arithmetic gives you agreement on an order. Even for a plain read/write register, the classic construction only becomes linearizable when the reader writes the value it found back out to a quorum before returning it. Quorums are a dial for staleness. They are not a substitute for consensus, and a system that markets "tunable consistency" is selling you the dial, not the consensus.

Sloppy quorums and hinted handoff

Now the part that quietly undoes the arithmetic. When the usual replicas for a key are unreachable, some Dynamo-style systems don't fail the write — they accept it on whichever N nodes they can reach, tagged with a hint saying "this really belongs to C," and hand it off once C returns. This is a sloppy quorum with hinted handoff, and it is excellent for durability and availability: your write is on disk somewhere, on the right number of machines, and it will get home.

But during the handoff window, the write is sitting on nodes that are not in the key's replica set. A reader doing a strict R-of-N read against the proper replicas can intersect all it likes and still miss it. The R + W > N intersection argument is simply not in force at exactly the moment you were counting on it — the failure that made you want the guarantee is the failure that suspends it. Worth knowing which of your systems does this by default, because most of them advertise the formula and bury the exception.

8. When writes collide: clocks, version vectors, CRDTs

Line t4 above ended with "something must now decide." That something deserves its own section, because the default answer is bad and almost nobody changes it.

Last-write-wins is a data-loss policy with good branding

The obvious rule is: attach a wall-clock timestamp to every write, and when two versions conflict, keep the newer one. It's simple, it's stateless, and it's wrong in a way that produces no evidence.

Consider two nodes whose clocks disagree by 300 ms — an entirely ordinary amount of NTP drift, and a rounding error compared to what a bad VM migration or a leap-second handler can do. A user updates their shipping address on node A at 12:00:00.000; A's clock is fast, so the write is stamped 12:00:00.300. A moment later, genuinely afterwards, they correct a typo via node B at 12:00:00.150; B's clock is accurate, so that write is stamped 12:00:00.150. Last-write-wins compares the stamps, keeps the address from A, and discards the correction. The package goes to the old address. There was no error, no retry, no warning, no log line — the system did precisely what it was configured to do, and the only artefact is a confused customer. With last-write-wins, your consistency guarantee is only as good as your clock synchronisation, and clock synchronisation is a best-effort background daemon.

Logical clocks: ordering without trusting time

The fix in principle is to stop asking "when did this happen?" and start asking "what did this write know about?" A version vector tags each value with a per-replica counter, so when two versions meet you can compare them structurally: if one vector dominates the other on every entry, that write genuinely happened after — keep it, no clocks involved. If neither dominates, the writes are concurrent, and you now know something a timestamp could never tell you: this is a real conflict, not a slow packet. (Lamport clocks give you a total order that's consistent with causality, but they can't distinguish concurrent from ordered; vectors can, which is why they're the ones you want at a merge point.)

The honest costs. Vectors grow with the number of writers — fine for a handful of replicas, awkward when every client is an actor, which is why real systems reach for dotted version vectors, pruning, and other machinery to stop the metadata outgrowing the data. And detection is not resolution: a version vector can tell you two writes are concurrent, but it has no opinion about what your business wants done about it. Riak's answer was to hand the application both siblings and let it decide, which is honest and is also why teams found it exhausting. Someone still has to write the merge function, and that function is where the actual correctness lives.

CRDTs: make the conflict impossible instead

The other move is to change the data type so there's nothing to resolve. A CRDT — conflict-free replicated data type — is one whose merge operation is commutative, associative and idempotent, meaning replicas that have seen the same set of updates in any order, with duplicates, end up identical. Order stops mattering, so divergence stops being a problem to fix and becomes a state to merge. It's the same instinct as making a queue consumer idempotent: design the operation so repetition and reordering are harmless, rather than building machinery to prevent them.

The catalogue is real and in production. Counters that only grow, or a pair of them for increment-and-decrement. Sets with explicit add/remove tagging so a concurrent add and remove resolve by rule rather than by luck. And collaborative text — the reason two people can type in the same document and neither one's cursor jumps.

The limit, stated plainly Not every problem has a commutative formulation. CRDTs converge; they do not enforce invariants that span replicas. "The set of items in the cart" merges beautifully. "This balance must never go below zero" does not — two replicas can each independently approve a withdrawal that's fine locally and catastrophic jointly, and no merge function can retroactively make that legal, because the invariant was violated before the merge existed. Global invariants need coordination. Your bank balance is not a CRDT, and neither is the last seat on the flight.

9. Locks aren't enough: fencing tokens

Somewhere in your system there's a job that must only run once, guarded by a distributed lock. Here's why that lock, on its own, guarantees nothing.

c1 acquires lock, lease 10s, token 33 c1 stops. GC pause / VM freeze. 14 seconds. +10s lease expires. The lock service is right to release it — c1 looks dead. c2 acquires lock, token 34 c2 write(data, token=34) → accepted c1 ...wakes up. Believes it still holds the lock, because from c1's point of view no time passed at all. c1 write(data, token=33) → rejected: 33 < 34 without the token, c1's write lands last and wins

The lease didn't fail; it did its job. The problem is that "I hold the lock" is a statement about the past, and an arbitrary amount of wall-clock time can elapse between checking it and acting on it. A stop-the-world GC pause of several seconds is routine. A VM being live-migrated or a laptop lid closing can be worse. No amount of re-checking closes the gap, because the pause can always land between the check and the write.

The fix is a fencing token: the lock service hands out a monotonically increasing number with every grant, the client passes it along with every write, and the storage layer remembers the highest token it has seen and rejects anything lower. Note where the enforcement lives — not in the client, which is the thing that can't be trusted, and not in the lock service, which isn't in the write path. The resource itself has to check. If your storage can't do that, you don't have mutual exclusion; you have a strong hint. This is the cleanest example in the whole guide of why distributed correctness is about what you can enforce, not what you can agree.

10. Transactions, 2PC, and sagas

On a single database, ACID transactions make several changes all-or-nothing: transfer money between two accounts and either both sides happen or neither does. Bliss. But once those accounts live on different shards or services, a single transaction can't span them cheaply — distributed transactions (two-phase commit) are slow and fragile.

"Slow" is the complaint people repeat; the blocking window is the actual problem. In two-phase commit, the coordinator asks every participant to prepare. A participant that votes yes has made a durable promise that it can commit, and to keep that promise it holds its locks and waits. Now kill the coordinator between collecting the votes and broadcasting the decision. Every participant is stuck: it can't commit unilaterally, because someone else may have voted no; it can't abort, because someone else may already have been told to commit. So it holds those locks and blocks — potentially until a human intervenes. A protocol whose worst case is "rows are locked until the on-call engineer wakes up" is not one you want on your checkout path. (The modern answer is to make the coordinator itself a replicated, consensus-backed group so it can't simply vanish — which works, and costs you another round of coordination.)

So distributed systems often trade the guarantee for a saga: break the operation into a sequence of local steps, each with a compensating undo. Charge the card → reserve the item → book shipping. If shipping fails, run the compensations backward: un-reserve the item, refund the card. You lose instant atomicity and gain eventual correctness — the system passes through briefly-inconsistent states but always lands somewhere valid. It's consistency rebuilt out of Lego instead of carved from marble.

Compensation is not rollback A rollback erases history: after an ABORT, nobody ever saw the intermediate state, because isolation hid it. A compensating transaction is a new, forward action that approximately undoes an old one — and in the gap between the two, the intermediate state was visible to everybody. Refunding a charge is not the same as never charging. The customer saw the charge, their bank saw it, the fraud model saw it, and if it pushed them into an overdraft the refund doesn't unpush them. Worse, some steps have no compensation at all: you cannot un-send an email, un-ship a parcel, or un-tell someone their loan was approved. The design consequence is concrete — order your saga so the reversible steps come first and the irreversible ones last, and where you can, reserve rather than commit (hold the seat, don't sell it) so the "undo" is releasing a hold instead of retracting a fact. And since compensations run in a failure path, they will themselves fail and be retried, which means they must be idempotent too.

11. Read-your-writes: the anomaly users actually notice

Almost everything above is invisible to your users. This one is not, and it generates more support tickets than every other consistency bug combined.

Someone posts a comment. The write goes to the primary. The page reloads, the read is load-balanced to a replica that's 200 ms behind, and their comment isn't there. From inside the system this is textbook, expected replication lag, working exactly as designed. From outside it is "your site ate my comment" — so they post it again, and now you have a duplicate, which is a data problem born entirely from a perception problem.

You've violated read-your-writes (rung 4 of the ladder), which is the cheapest guarantee on the whole spectrum and the one users treat as non-negotiable. Three ways to buy it back, in increasing order of correctness:

  • Route the writer to the primary for a window. After a user writes, send their reads to the primary for the next few seconds — session-sticky routing, the same mechanism as in the Load Balancing guide. Simple, and two catches: it adds read load to the node you least want loaded, and the window has to cover your p99 lag, not your average, or you've just made the bug rarer and harder to reproduce.
  • Carry a version token. The write returns its position in the replication stream — an LSN in Postgres, a GTID in MySQL. The client hands that token back with the next read, and the router either waits for a replica to catch up to it or picks one that already has. This is the correct fix: it's precise, it degrades to "slightly slower read" rather than "wrong answer," and it costs you a token on the wire.
  • Pin the session to one replica to get monotonic reads as well, so a refresh never shows older data than the previous one. Cheap, and it stacks with the above.

Rendering the new comment optimistically from the write response is worth doing for the feel of it, but be clear about what it is: it fixes the perception, not the data. Refresh on a second device and the ticket comes back.

12. Real-world examples

War story · GitHub's 43 seconds → 24 hours On October 21, 2018, a routine maintenance event severed connectivity between GitHub's East Coast network hub and its primary East Coast data center for just 43 seconds. But their database automation, seeing the partition, promoted a West Coast replica to primary — while the East Coast primary had also kept taking writes. Now two databases had diverged, each holding writes the other lacked. This is CAP made painfully literal: during the partition, the system had chosen availability, and reconciling the split-brain data safely took engineers over 24 hours. Forty-three seconds of network trouble, a day of cleanup.

Amazon's shopping cart — famously AP. Amazon decided that a cart must always accept an "add to cart," even during failures, because a rejected click is lost revenue. The cost: in rare cases a deleted item could reappear as replicas reconciled. Amazon happily took a resurrected item over a broken cart — an explicit CAP choice worth billions.

Google Spanner — and why it does not beat CAP. This is the most-cited "well actually" in distributed systems, and it's wrong. Spanner puts GPS receivers and atomic clocks in every data centre so its TrueTime API can return not a timestamp but an interval: the true time is somewhere in [earliest, latest], with the uncertainty bounded to a few milliseconds. The trick isn't that Google's clocks are correct — it's that Spanner knows how wrong they might be, and then deliberately waits out the uncertainty before making a commit visible. That's commit-wait: the transaction sits there, holding its locks, doing nothing, until its timestamp is definitely in the past everywhere. Spanner buys external consistency by paying latency on purpose, which is the PACELC else-branch chosen about as explicitly as it can be chosen. And it's still CP: partition a replica group badly enough and the minority side stops serving. Google's own framing is that Spanner is "effectively CA" only because its private global network makes partitions rare enough to disappear into the general noise of outages — that's an argument about the frequency of P, not an escape from it. Nobody found a loophole; they bought better clocks and a private network.

Your bank, actually — the ATM story is why real ATMs offline-limit withdrawals to a small amount: they cap the blast radius of the inconsistency they're knowingly allowing. Even banks choose availability sometimes — they just bound the risk.

The one-liner to remember You can't have perfect consistency, perfect availability, and a network that sometimes breaks. Since the network will break, choose per-data-type: refuse-and-stay-correct for money, stay-up-and-reconcile for everything that can tolerate a moment of "close enough."

13. Recap in 60 seconds

  • CAP's C is linearizability. ACID's C is your constraints. They share a letter and nothing else. Ask which one someone means before you design anything.
  • P isn't a choice. The real decision is C or A, and only during a partition. A single node is trivially CP, which tells you how little the label is worth.
  • A partition is a timeout you configured. Shorter timeout, more partitions resolved faster; longer timeout, fewer partitions that hurt longer. There is no zero.
  • PACELC's else-branch is the one that runs. Latency vs. consistency is decided on every request all day; availability vs. consistency is decided a few minutes a year.
  • R + W > N means the read set and the write set intersect. That's all it means. Not linearizable, no help for read-modify-write, and suspended entirely during a sloppy quorum.
  • Last-write-wins is a data-loss policy. If your clocks disagree by 300 ms, so does your idea of "last" — and the loss is silent. Version vectors detect concurrency honestly; CRDTs remove it by construction; neither decides what a conflict means to your business.
  • A lock is a statement about the past. Add a fencing token the storage layer checks, or accept that a paused process will eventually wake up and overwrite you.
  • Compensation is not rollback. The intermediate state was visible, some actions can't be undone, so put the irreversible steps last. And 2PC's real danger is the blocking window when the coordinator dies mid-protocol.
  • Read-your-writes is the one users notice. Route their reads to the primary for a window, or carry an LSN/GTID and wait for the replica to reach it.
  • Choose per data type, not per system. Strong for money and inventory, session guarantees for a user's own content, eventual for counters.

And the numbers underneath all of it. These are order-of-magnitude figures — your network is not these numbers, but it is within a factor of two or three of them, and that's enough to do the arithmetic that matters.

Rough numberWhat it isWhat it costs you

~1–2 msRound trip cross-AZ, same regionA synchronous quorum across three availability zones costs a millisecond or two per write. That's cheap insurance against losing a data centre — take it.

The point those numbers exist to make: synchronous cross-region consensus has a latency floor set by physics, and no engineering gets under it. If someone asks for global strong consistency with a p99 under 50 ms, they haven't asked for an optimisation — they've asked you to move Europe closer. The only real move is to shrink the set of data that needs global agreement until what's left can afford the round trip, and let everything else be regional, cached, or eventual.

14. Check yourself

If you can answer these without scrolling up, the guide worked.

Your team says "we chose AP." What have they actually committed to on a normal, partition-free Tuesday?
Strictly speaking, nothing — CAP only describes behaviour during a partition, and partitions are rare. That's the trap: "we're AP" is a statement about a few minutes a year. What they've almost certainly also signed up for, without saying so, is the else-branch: low-latency writes that return before all replicas agree, which means stale reads and concurrent-write conflicts every single day. The right follow-up question is never "are we AP?" but "what's our conflict resolution rule, and who wrote it?"
You run N=3, R=2, W=2 and you still lost an update. Name two ways that happens.
Easiest two: (1) last-write-wins plus clock skew — two writes conflicted, the resolution rule compared wall-clock timestamps from unsynchronised machines, and it kept the one that actually happened first. (2) A sloppy quorum — the write was accepted on substitute nodes during a blip, so the strict R-of-N read didn't intersect it during the handoff window. Two more, for credit: read-modify-write on a value read from a quorum has no atomicity, so two clients can both read 5 and both write 6; and a write that got only one ack and returned an error isn't rolled back, so it can win a later merge.
A user posts a comment and doesn't see it on refresh. Which consistency model did you violate, and what's the cheapest fix?
Read-your-writes — the read went to a replica that hadn't applied their write yet. Cheapest real fix is session-sticky routing: send that user's reads to the primary for a few seconds after they write. Size the window against p99 replication lag, not the average, or you've made the bug rare instead of gone. The more correct version is to return the write's LSN/GTID and have the read wait for a replica that has reached it. Note the collateral damage of not fixing it: users re-submit, so a perception bug becomes duplicate rows.
Your monitoring shows partitions jumped 4× after a deploy that changed nothing about the network. What probably happened?
Somebody changed a timeout, or changed something that made responses slower until they crossed one. You never detect partitions; you detect non-answers within a window you chose, so partition count is a property of your failure detector as much as your network. Look for a shortened client or health-check timeout, a new synchronous call on a hot path, or a GC/heap change that lengthened pauses past the threshold. The fix is usually to tune the detector deliberately rather than to go hunting for a cable.
A batch job holds a 10-second lease, freezes for 20 seconds, wakes up and writes. What must have been in place for that to be safe?
A fencing token, enforced at the storage layer. The lock service was right to expire the lease and right to grant it to someone else; nothing the client does can make "I hold the lock" true again, because the check happened 20 seconds ago. Safety requires that the resource itself track the highest token it has seen and reject the stale writer's lower one. If enforcement lives in the client or only in the lock service, you don't have mutual exclusion — you have an agreement between processes that one of them has stopped honouring.
Product wants strong consistency across three continents with a p99 write latency under 50 ms. What do you tell them?
That it's a physics request, not an engineering one. A majority write across three continents needs at least one round trip to the second-closest region, which is 60–90 ms before your code does anything, and consensus protocols often want more than one round. Then negotiate the actual requirement: which specific data needs global agreement? Usually it's a thin slice — balances, unique names, seat inventory — that can be pinned to a home region and accessed strongly from there, while the other 95% goes regional with session guarantees. You shrink the strongly-consistent set until it fits the budget; you don't make the round trip shorter.
That's the last of the six ideas. Every guide so far has handed you one tool at a time. The capstone spends all seven at once on a single system: Design the Checkout traces one order from tap to confirmation email, shows exactly where each idea gets used, and then breaks it four ways to see what holds.

2. Requirements — and what we're not building

Split these apart deliberately. Functional requirements are what it does; non-functional requirements are what makes the design hard. Interviewers care about the second list, and so should you.

Functional

View a cart. Place an order. Take payment. Confirm to the customer. Reserve inventory so we don't sell the same item twice. Show order status and history. Let the customer cancel while it's still cancellable.

Non-functional

p99 under 800 ms on checkout. Never charge without an order. Never lose an order we confirmed. Survive a payment provider being slow. Survive the loss of one availability zone. Absorb 5× traffic on a known date.

Explicitly out of scope

Search and recommendations. Pricing and promotions engines. Returns and refunds beyond the compensating action. Fraud scoring beyond "there is a service and we call it." Multi-currency and tax calculation. Anything to do with the warehouse past handing it a message.

Assumptions stated out loud

One region to start. Payment is an external provider, not something we build. Catalogue and pricing come from an existing service. Traffic peaks are known in advance, not surprises.

Scoping out loud is not throat-clearing — it's the difference between a design you can defend and a design that grows a new requirement every time someone asks a question. The out-of-scope list is the most useful list on the page.

3. The naive version, and exactly where it breaks

Start with the thing you'd actually build on day one, because it's correct and it's fast to ship: one application server, one database, everything synchronous.

POST /checkout

  2. check inventory
  3. charge the card          (external, ~250 ms)
  4. write the order
  5. decrement inventory
  6. generate invoice PDF     (~400 ms)
  7. send receipt email       (~600 ms, sometimes 6 s)
  8. notify the warehouse     (~200 ms)
  9. update analytics         (~100 ms)
 10. return 200 OK

Now apply the numbers. Steps 1–5 are the parts a customer is actually waiting for; steps 6–9 are roughly 1.3 seconds of work the customer does not care about and cannot see. Our budget was 800 ms. We are over it before anything goes wrong.

And here is what breaks first, which is not what most people guess. It isn't the database — 200 writes a second is comfortable. It's concurrency. Little's Law says the number of requests in flight is throughput multiplied by latency:

normal day 12 orders/s × 1.9 s = 23 in flight thread pool of 200 = fine black friday 200 orders/s × 1.9 s = 380 in flight thread pool of 200 = queueing, then timeouts black friday, slow email 200 orders/s × 6.5 s = 1300 in flight thread pool of 200 = total collapse in ~1 s

Read that last block again, because it contains the whole argument for everything that follows. The site does not go down because buying is hard. It goes down because the email server had a slow afternoon and we made every customer wait for it. Every request in the process is holding a thread while it waits, and threads are the resource that runs out. The Reliability guide covers this arithmetic in detail; here it is deciding our architecture on the first page.

4. The forced moves

Now we build it up. The rule for this section — and for your own designs — is that every move must be forced by a number or a failure. Not by fashion, not by what the last place you worked used, and definitely not by what sounds impressive. If you can't name the figure that made a component necessary, the component is decoration.

Move 1 — split the request in two

Steps 6–9 are not part of the transaction the customer is waiting on. Push them onto a queue and return as soon as the money is taken and the order is recorded. This is the single highest-leverage change in the entire design and it costs one component.

synchronous, must finish now validate → reserve → charge → save ≈ 260 ms asynchronous, must finish soon invoice · receipt · warehouse analytics · loyalty · recommendations ≈ 1.3 s, nobody watching

Concurrency drops from 380 in flight to about 52 at peak, and the slow-email scenario stops existing: the email is now a message in a queue, and a queue getting longer is a metric, not an outage. See the Queues guide for why the queue must be bounded — an unbounded buffer just relocates the failure.

Move 2 — make the app tier stateless, then multiply it

200 orders/s and 25,000 reads/s is more than one box, and one box is a single point of failure regardless. Put a load balancer in front and run many identical instances. The prerequisite is statelessness: no session in local memory, no cart on the local disk, nothing an instance knows that another instance couldn't reconstruct. Sessions go in a shared cache; carts go in the database with a cache in front.

This move is what buys you rolling deploys, autoscaling, and surviving an instance death. It's also the move that makes every later move possible — the Databases guide assumes a stateless app tier the moment it starts talking about replicas. Read the Load Balancing guide for the settings that make this safe: connection draining so deploys don't produce error spikes, readiness distinct from liveness so a warming instance doesn't get traffic, and a health check that fails before the box is unusable rather than after.

Move 3 — cache the read path, because that's where the traffic is

25,000 reads/s against a database that is comfortably handling 200 writes/s is the actual scaling problem, and it barely involves the checkout at all. It's people looking at products.

The catalogue is nearly static, read enormously, and tolerant of being a few seconds stale — which is the exact profile of something that should be cached. A cache in front of the product and pricing reads takes the overwhelming majority of that 25,000 rps and never troubles the database with it. The Caching guide covers the two traps waiting here: jittered TTLs so a batch of keys written together doesn't expire together, and single-flight so a popular key expiring doesn't send a thousand simultaneous misses at the database.

The thing you must not cache Inventory counts on the checkout path. Everywhere else, staleness costs you a slightly wrong number on a page. Here it costs you an oversell, a cancelled order and an angry customer. We'll handle inventory explicitly in section 8 — the rule for now is that the number you display and the number you decrement are two different values with two different consistency requirements, and conflating them is one of the most common bugs in commerce systems.

Move 4 — indexes first, then replicas

Before adding any database machinery, check the queries. The Databases guide's rule zero applies: an unindexed lookup on a 400-million-row orders table will destroy you long before your write rate does, and adding replicas to a system with a missing index just gives you more machines running the same terrible query.

Once the queries are honest, add read replicas for the things that genuinely only read: order history, admin reporting, the analytics extracts. Keep the checkout path on the primary. And note the trap now, because it will bite in section 10 — a customer who places an order and is immediately shown a history page served by a lagging replica will not see their own order. That's a read-your-writes violation, and it appears only under load, which means only in production.

5. The move we are not making

Here is where most designs go wrong, including in interviews, where candidates shard because they think sharding is the answer the interviewer wants. Let's price it honestly.

We write 200 orders/s at peak and roughly 12/s the rest of the year. We accumulate about 2 TB of order data per year including indexes, and 18 months of that is hot — call it 3 TB of working set, with the rest archived. A single modern database instance handles both of those figures without breathing hard. Sharding is not indicated.

And the bill for doing it anyway, from the Databases guide: every schema migration becomes N migrations. Every backup becomes N backups plus a coordinated restore procedure you have to actually test. Cross-shard queries become scatter-gather or become unavailable. Cross-shard transactions become a saga, which means compensating actions, which means the intermediate state was visible to somebody. Resharding stops being a task and becomes a quarter.

What you do instead, in this order, and only when a metric demands it: archive cold orders out of the hot table; partition the orders table by month so old data can be dropped and queries can prune; add replicas for anything that only reads; and move genuinely separate workloads — analytics, reporting — off the transactional database entirely.

The signal that would change our mind Not "we're big now." Specifically: sustained write throughput within ~2× of what the instance can do, or a hot dataset that no longer fits in memory and won't after the next hardware tier, or a restore time that has grown past what the business will tolerate. Any of those is a real reason. None of them is currently true, so the correct architecture diagram has one database on it, and being able to say why is worth more than being able to draw sixteen.

6. Making the order and its event inseparable

Back to the cold open. We charge the card, we save the order, and we publish an "order placed" event so the receipt gets sent and the warehouse gets told. Three side effects, at least two systems, and no transaction spanning them. Every ordering of those operations has a crash window that produces a state nobody wants.

save, then publish save order ✓ crash publish event ✗ → order exists, nobody told. no receipt, nothing ships. publish, then save publish event ✓ crash save order ✗ → warehouse ships an order that does not exist.

You cannot fix this by reordering the two writes, and you cannot fix it with a try/catch, because the process can die between any two instructions. The fix is to stop having two writes. The transactional outbox puts the event in a table in the same database transaction as the order:

BEGIN;
  INSERT INTO orders (...)  VALUES (...);
  INSERT INTO outbox (topic, payload)
       VALUES ('order.placed', :json);
COMMIT;
-- a separate relay reads outbox,
-- publishes, marks rows sent.

Now the order and the intent to announce it commit or fail together. The relay may still publish a message twice — it can crash after publishing and before marking the row sent — so this gives at-least-once, not exactly-once, which is exactly why every consumer must be idempotent. The Queues guide has the full treatment, including the race in the naive idempotency check that quietly charges people twice.

And the money

The payment provider is outside our transaction and always will be. What makes that safe is an idempotency key — a unique identifier we generate for this checkout attempt and pass to the provider. If our request times out and we retry, the provider recognises the key and returns the original result instead of charging again. This is why payment APIs have that field, and it is not optional at any real volume.

Order of operations matters here. Write the order in a pending_payment state first, then authorise with the key, then confirm. If we die after authorising, a reconciliation job finds orders stuck in pending_payment, asks the provider what happened to that idempotency key, and settles them — completing the ones that succeeded and voiding the ones that didn't. Money and orders can then never disagree for longer than the reconciliation interval, which is a bound you can state out loud and hold yourself to.

"Fail open to the database" is not free The cache is absorbing roughly 96% of 25,000 reads/s. If it dies cold, the database instantly receives about 25× its normal read load. Two settings that people consistently miss, and that this design depends on. Three layers each retrying three times turns one user action into twenty-seven requests, arriving precisely when the system can least afford them.

8. Staleness, decided field by field

This is the section that separates a design from a shopping list. "Is the system consistent?" is the wrong question — the Consistency guide's central point is that consistency is a per-field decision with a per-field price. So go field by field and say what you're buying.

The genuinely hard one: overselling

Two customers, one remaining item, requests arriving 8 ms apart. Both see stock, both proceed, one of them is going to be disappointed and it's your job to decide how.

Optimistic decrement is the simple version: make the decrement conditional in a single statement, so the database arbitrates rather than your application.

UPDATE inventory
   SET available = available - :qty
 WHERE sku = :sku
   AND available >= :qty;
-- 0 rows updated → someone beat you.
-- Sold out. Tell the customer now,
-- before you charge the card.

That is atomic and correct, and it has one flaw: it decrements before the payment succeeds. If the card is declined thirty seconds later, you've held stock hostage. Reserve-then-confirm fixes it — the same conditional update creates a reservation with a short expiry, the payment runs, success converts the reservation to a sale, and failure or expiry returns the stock. That's a small state machine and a sweeper job, and it is the design most real commerce systems land on.

The uncomfortable industry truth Many large retailers accept a small oversell rate on purpose. Perfectly serialised global inventory across every channel — web, app, stores, marketplaces — costs enormous latency on every read and a coordination protocol that becomes the bottleneck on your busiest day. Occasionally apologising, refunding and offering a voucher is cheaper. That is a commercial resolution to a distributed systems problem, and recognising when one is available is a genuine engineering skill. It is also, precisely, the AP branch being chosen deliberately: stay available, reconcile the conflict afterwards.

10. Now break it

A design you haven't tried to break is a diagram. Four failures, each one traced, each one saved by something a guide taught.

Failure 1 — the payment provider gets slow, but not dead

This is the worst kind of failure because nothing is down. Their p99 goes from 200 ms to 8 s. No error, no alert from them, just treacle.

the arithmetic 200 orders/s × 8 s = 1,600 concurrent slots needed thread pool = 400 → exhausted in ~2 s → every endpoint dies, including ones that never touch payments with a bulkhead of 300 300 in flight ÷ 8 s = 37 checkouts/s served the other 163/s fail fast browsing, cart, history: unaffected then the breaker opens error rate crosses threshold → stop calling for 30 s → half-open: a trickle, jittered → recovery without a stampede

Note what the bulkhead actually bought: not a working checkout — 163 customers a second still can't buy — but a working site, and a failure confined to the one feature that genuinely depends on the broken thing. That is the whole point of a bulkhead, and it's why a circuit breaker alone wouldn't have saved us: the breaker only opens after enough failures, and by then the pool is already gone.

Failure 2 — a replica falls behind at peak

Replication lag is near zero until it isn't, and it spikes exactly when you're busiest. At 14:00 on Black Friday the replica is 4 seconds behind. A customer places an order, gets their 201, taps "My orders" — and the page, served from the replica, is empty. They have just been told their order doesn't exist. Some of them will order again.

The fix is read-your-writes: after a customer writes, route their reads to the primary for a short window, or carry a version token (an LSN or GTID) with the session and have the replica wait until it has caught up to that point. The first is cruder and simpler; the second is precise and needs support from your database. Either is better than the third option, which is discovering this from a support ticket. And alert on replication lag in bytes as well as seconds — a lightly-loaded replica can report a small time lag while being far behind in work.

Failure 3 — the consumer fleet dies for twenty minutes

A bad deploy takes out every queue consumer. Nobody notices immediately, because checkout is unaffected — orders are being taken and committed and the outbox is publishing happily. What's failing is invisible: no receipts, nothing reaching the warehouse.

the backlog 200 msg/s × 1,200 s = 240,000 messages waiting the drain each consumer: 50 msg/s arrivals still: 200 msg/s N consumers drain at (N × 50) − 200 per second N = 4 → 0/s never drains N = 6 → 100/s 40 min N = 12 → 400/s 10 min

Two lessons. First, a queue with no headroom above its arrival rate never recovers from a spike — four consumers is exactly break-even and will sit at 240,000 messages forever, looking stable and being catastrophic. Second, the metric that would have caught this in ninety seconds is consumer lag, not queue depth. Depth tells you how much is waiting; lag tells you whether you're falling behind. Alert on lag and its rate of change.

Failure 4 — a config push marks every instance unhealthy

Someone tightens the readiness check so it also verifies the recommendations service. Recommendations has a blip. Every instance in the fleet reports unready simultaneously, and the load balancer, doing exactly what it was told, has nowhere to send traffic. The site is down because an optional feature hiccuped.

Two defences, both from the Load Balancing guide. A readiness check should only test dependencies the instance genuinely cannot serve without — recommendations is not one of them, which is why it fails open in section 7. And the load balancer needs a panic threshold: when the fraction of healthy backends drops below some level, ignore health status entirely and spray traffic across everything, on the reasoning that a degraded backend beats no backend. Health checks that can take down a whole fleet at once are not a safety feature.

The pattern across all four Not one of these is a component breaking. A slow provider, a lagging replica, a stopped consumer, an over-eager health check — every single one is a system doing exactly what it was configured to do, in a situation nobody pictured while configuring it. This is what real incidents look like, and it's why the settings in section 7 deserve more design attention than the boxes in the diagram.

11. What you'd build only if you had to

The last discipline is knowing what you left out and why. Here is everything a reader will be tempted to add to this design, and the specific signal that would justify each one. Absent the signal, adding it makes the system worse — more moving parts, more failure modes, more onboarding, and no benefit.

Tempting additionThe signal that would justify it
Sharding the databaseSustained writes within ~2× of the instance ceiling, or a hot dataset that won't fit the next hardware tier, or a restore time the business won't accept. Not "we're big now."
CQRS (separate read and write models)Read and write shapes that have genuinely diverged — the read side needs joins and aggregates the write side shouldn't be optimised for. Replicas solve the easy 90% of this first.
Event sourcingA hard audit requirement for every state change, or a real need to reconstruct historical state. It is a serious commitment: replay, versioning and snapshots become permanent concerns.
Multi-region active-activeA regulatory data-residency requirement, or users far enough away that RTT is a product problem, or an availability target a single region provably can't meet. Then accept that you've bought a conflict-resolution problem for every writable field.
Service meshEnough services that per-service retry, timeout and mTLS configuration has become unmanageable by hand. With six services, the mesh is more operationally complex than the thing it manages.
Microservices, generallyTeams blocking each other on deploys. It's an organisational fix with a technical cost — you trade in-process calls for network calls, and every one of those is a new failure mode.
Kafka instead of a simple queueYou need replay, multiple independent consumer groups over the same stream, or retention as a feature. If you need a work queue, use a work queue.

Notice that every justification is a measurement or a constraint, never an aspiration. That's the test. If the argument for a component is "we'll need it eventually," you are paying today's complexity for tomorrow's maybe — and the version of this system that gets built with restraint is also the version that's still comprehensible when the real problem arrives.

12. Recap in 60 seconds

  • Numbers first. Requests per second, read/write ratio, payload size, storage growth, latency budget. A design defended without them is a guess.
  • Separate must-finish-now from must-finish-soon. Take the money, record the order, return. Everything else is a message.
  • Statelessness is the enabling move — it's what makes load balancing, autoscaling and rolling deploys possible.
  • The read path is usually the scaling problem. 120:1 browse-to-buy means caching matters two orders of magnitude more than sharding.
  • Indexes before replicas, replicas before sharding, and sharding probably never. Name the metric that forces each rung.
  • Two writes with no transaction between them is a bug waiting for a crash. Outbox for your own events; idempotency keys for someone else's API.
  • Consistency is a per-field decision. The inventory you display and the inventory you decrement are different values with different rules.
  • A timeout is a concurrency budget. Bulkheads cap what any one dependency can consume; breakers stop you calling the dead; shedding is for too much load, not slow dependencies.
  • Propagate deadlines, budget retries, retry at one layer only.
  • A queue with no headroom above its arrival rate never recovers. Alert on consumer lag, not depth.
  • Real incidents are components behaving as configured in situations nobody pictured. The settings deserve more attention than the diagram.
  • Every addition needs a signal. No signal, no component.

13. Check yourself

These are harder than the per-guide questions on purpose — each one needs at least two guides to answer properly. Try them before opening the answers; getting one wrong is the moment the idea actually lands.

The payment provider's p99 goes from 200 ms to 8 s. Walk through what happens to your checkout endpoint, in order.
Requests start piling up in flight: Little's Law says 200/s × 8 s demands 1,600 concurrent slots against a pool of 400, so the pool exhausts in roughly two seconds. Without a bulkhead, that pool is shared, so every endpoint fails — including browsing, which never touches payments. With a bulkhead of 300, checkout throughput drops to about 37/s and the rest of the site is untouched. The circuit breaker opens once the error rate crosses its threshold and stops you calling a dead dependency at all, then half-opens with a jittered trickle so recovery doesn't stampede. The breaker alone would not have saved you — it trips after failures, and the pool dies first.
Where in this design can a customer be charged without an order existing, and what prevents it?
Between authorising the payment and committing the order transaction. The process can die in that window and the money is gone with nothing recorded. Three things together close it: the order is written in pending_payment before the charge, so there's always a record to reconcile against; the charge carries an idempotency key, so retrying can't double-charge; and a reconciliation job sweeps stuck pending_payment orders, asks the provider what happened to that key, and either completes or voids. You can't make it impossible — the provider is outside your transaction — but you can bound how long the disagreement lasts.
You add a second region. Name the three decisions that just got harder.
First, inventory: a globally serialised count now needs cross-region coordination on every checkout, and cross-region round trips are 60–150 ms set by the speed of light. Second, the database: one writable primary means one region pays a latency penalty on every write, while two writable primaries means conflict resolution for every field — and last-write-wins on an inventory count silently loses data. Third, failover: "the region is down" is a judgement call made by a timeout you configured, and getting it wrong in either direction is expensive. Most teams start with one write region and read replicas elsewhere, precisely to avoid the second problem.
Your cache dies completely at peak. Trace what happens, and say why "the app still works" is not a good answer.
The cache absorbs about 96% of 25,000 reads/s, so the database instantly sees roughly 25× its normal read load. It saturates, query latency climbs, connections back up, and because the pool is shared, checkout starts timing out too — a read-path failure has become a write-path outage. Then clients retry, adding load, and the system can stay collapsed even after the cache comes back, because the retry traffic and cold cache are now self-sustaining. That's metastable failure: you can't wait it out, you have to shed load and reintroduce it gradually. "It degrades instead of erroring" is true for about four seconds.
A customer says they were charged twice. The logs show one request. What are the two most likely explanations?
First, the visibility timeout: if the payment consumer's work takes longer than the queue's invisibility window, the broker assumes it died and redelivers to a second consumer while the first is still running — genuine concurrent duplicate processing, with no retry in the logs to show for it. Second, the check-then-act idempotency race: if the code checks "already processed?" and then does the work, two concurrent duplicates both read false before either writes, and both charge. The fix for the second is claiming the ID atomically before doing the work; the fix for the first is a timeout above your real p99 plus heartbeating. Note that "one request in the logs" is what makes both of these so nasty to diagnose.
Your interviewer says "now make it handle 10× the traffic." What do you change, and what do you deliberately not change?
10× is 2,000 orders/s and 250,000 reads/s. The read path scales by adding cache capacity and replicas — that's more of the same, not a redesign. The app tier is stateless, so it scales horizontally by definition. The write path at 2,000/s is now within range of a single instance's ceiling rather than an order of magnitude below it, so this is where sharding finally earns its place — and you'd shard by customer or order ID, accept scatter-gather on cross-customer reporting, and move reporting off the transactional store entirely. What you don't change: the outbox, the idempotency keys, the guardrails, and the per-field consistency decisions. Those were correct at 200/s and they're correct at 2,000/s — which is a decent sign they were the right calls.
The one-liner to remember A system design is not a diagram, it's a sequence of decisions — and each one is only defensible if you can name the number that forced it and the failure it prevents. Everything else on the whiteboard is decoration, and decoration is the part that pages you at three in the morning.
