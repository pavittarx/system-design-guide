A Twelve-Part Field Guide

System Design Basics

Twelve guides on how real systems get fast, hold their data, distribute work, stay up and stay correct — then how you see inside them, guard their front door, beat distance, get machines to agree, and push data live. Each opens with a disaster, each ends with questions that make you prove you understood it, and the last one puts all of it into a single working design.

What this is, and what it isn't This is a working engineer's field guide, not a reference and not exam prep. It covers the six ideas that decide whether an ordinary web system survives its own growth, five further guides on running that system once it's real — observability, APIs & gateways, the edge, coordination, and real-time — and a capstone that assembles them. Every concept is attached to a failure it prevents, every guide ends with a cheat sheet and self-test questions, and the recurring argument throughout is restraint — climb only as high as your load forces you to. What it deliberately leaves out: storage engine internals, networking below the packet, machine learning infrastructure, and anything specific to a single cloud vendor's product catalogue. Assumed background: you've written a web application and deployed it somewhere.

The through-line: follow one request

These topics aren't a random pile — they're the stops a single request makes on its way through a well-built system. Trace one click and the whole series falls into place. Note that the stops are in request order, which is not the order the guides are numbered in; the guides are ordered by what you'll need first in a real job, and caching is almost always the first thing anyone reaches for.

Humming underneath every stop is one recurring question — how fresh does this data really need to be? — the consistency trade-off that ties caching, replication and CAP into a single idea (Guide 6). Watching the whole thing from the outside is observability (Guide 7); underneath it, machines have to agree on who's in charge (Guide 10); and when the server has to push data back instead of waiting to be asked, the model inverts entirely (Guide 11). Guide 12 then walks a real checkout through every stop with the numbers attached — the only way to find out whether any of it stuck.

Hands-On Portfolio Projects (Build & Benchmark)

Reading about system design is passive; benchmarking it is active. Here are five hands-on projects designed to be built in a weekend, load-tested locally, and uploaded to your GitHub portfolio to show you understand real operational limits.

Project 1: Cache Stampede & Coalescer Lab

The concept: Request coalescing (single-flight) under heavy concurrency.

The build: Write an HTTP server with a slow endpoint (simulating a 500ms database read). Under load, cache-misses will trigger a "stampede" hammering the DB. Implement a coalescer (e.g. Go's singleflight or Node's promise sharing) to group concurrent identical reads into a single database query.

Stack: k6 · Docker · Redis · Go/Node/Python

Project 2: Database Connection Pooler Benchmark

The concept: Little's Law, process overhead, and connection multiplexing.

The build: Spin up Postgres in Docker. Write a script that attempts to run queries across 300 concurrent threads. Watch Postgres exhaust its connection limit and slow down due to process context-switching. Insert PgBouncer in front, route traffic through it with a pool size of 16, and measure the latency and memory difference.

Stack: Postgres · PgBouncer · Docker Compose · python/go

Project 3: Consistent Hashing Router from Scratch

The concept: Key-space partitioning and replication ring distribution.

The build: Write a library that implements a consistent hashing ring. Add virtual nodes to distribute keys evenly. Write tests to measure key migration: hash 10,000 keys across 3 nodes, add a 4th node, and verify that only ~25% of keys migrate (compared to ~75% with modulo routing hash % N).

Stack: Go / TypeScript / Python (zero libraries)

Project 4: The Transactional Outbox Worker

The concept: Event delivery guarantees without distributed transactions.

The build: Build a mock checkout api. In one DB transaction, insert an Order and a pending Event record in an outbox table. Run a background daemon that polls the outbox table, publishes events to RabbitMQ/Kafka, and marks them processed upon broker ACK. Simulate broker failure to verify zero data loss.

Stack: Postgres · RabbitMQ/Kafka · Python/Node/Go

Project 5: Load Shedding & Concurrency Limiter

The concept: Server stability under load, tail latency control, and HTTP 429/503.

The build: Build a server with a CPU-bound endpoint. Load test it past capacity with k6. p99 will grow infinitely as queries queue. Implement an active request limiter (concurrency gate). If in-flight requests exceed limit, reject instantly with 429 Too Many Requests. Show that accepted requests stay fast and the server survives.

Stack: Go / Rust / Node.js · k6 load generator

Numbers to argue with

Most design arguments are settled by an order of magnitude, not a benchmark. These are the figures worth carrying in your head — every one is approximate, hardware-dependent and a starting point for a conversation rather than a measurement of your system.

RoughlyWhat it isWhy it settles arguments
~100 nsRead from local process memoryThe thing a remote cache is 1,000× slower than. In-process caching is not the same tool.
~0.5–2 msRedis/Memcached round trip, same AZFast enough to be free, slow enough that ten of them in a loop is a bug.
~1–10 msIndexed single-row database queryIf yours isn't in this range, the problem is the query, not the database.
~0.5 msRound trip within an availability zoneWhy "put it in the same AZ" is the cheapest latency win there is.
~1–2 msRound trip between AZs in one regionA synchronous cross-AZ quorum costs you this on every write. Usually worth it.
~60–150 msRound trip between distant regionsSet by the speed of light in fibre. No engineering gets under it — which is why synchronous cross-region consistency is expensive by physics, not by implementation.
99.9%= 8.8 hours of downtime a yearSounds impressive, is roughly one bad afternoon a quarter.
99.99%= 53 minutes a yearLess than one incident's worth of debugging. This number is a staffing decision.
0.99910 ≈ 99.0%Ten hard dependencies, each at three ninesAvailability multiplies. You cannot be more available than the product of the things you can't work without.
~1k–10k/sSingle-row writes a well-tuned single database instance sustainsMost products never reach this. Sharding conversations that start below it are usually premature.
≈ throughput × latencyLittle's Law — the concurrency you needTurns "the site is slow" into a number. A timeout is a concurrency budget.

The pillars, in one breath

If you remember nothing else, remember the shape of the problem each guide solves. First the five that get you built and scaled:

Speed don't redo expensive work — cache it.
State one database has a ceiling — replicate and shard past it.
Distribution one server is fragile — spread load across a stateless herd.
Async don't make users wait for work they don't care about — queue it.
Resilience failure is constant — contain it so it can't cascade.

…and the question threaded through every one: consistency — how much staleness can this particular piece of data safely tolerate? Answer that per feature, and most design decisions answer themselves.

Those five build and scale the system; the back half of the series keeps it alive once it's real:

Visibility you can't fix what you can't see — instrument it.
Interface the API is a promise you can't take back — design the contract to outlive the code.
Distance the speed of light is a hard floor — keep a copy near the user.
Agreement two machines can't tell slow from dead — elect one and fence the rest.
Push a live connection makes the server stateful — plan for the reconnect.

The words everyone uses and nobody defines
Latency vs. throughput
Latency is how long one request takes; throughput is how many you finish per second. They trade against each other, and improving one often degrades the other — batching is the classic example.
p50, p99, p99.9
Percentiles of response time. p99 = 1% of requests are slower than this. Averages hide outages; percentiles don't. At scale, p99 is somebody's whole experience.
Horizontal vs. vertical scaling
Vertical is a bigger box — simple, instant, and it runs out. Horizontal is more boxes — unlimited in principle, and it makes everything else in this series necessary.
Stateless
A server that keeps nothing between requests that it couldn't reconstruct. It's what makes servers interchangeable, which is what makes load balancing, autoscaling and rolling deploys possible.
Idempotent
Doing it twice has the same effect as doing it once. The property that makes retries safe, and therefore the property that makes distributed systems tolerable.
Backpressure
A system under strain telling its callers to slow down, rather than silently queueing until it dies. The opposite of an unbounded buffer.
Hot key / hot shard
One key or one partition receiving wildly more traffic than its peers. Adding capacity doesn't help, because the routing sends it all to the same place regardless.
Eventual consistency
If writes stop, all replicas converge on the same value — eventually. It says nothing about how long that takes, which is the part that bites.

The meta-lesson across all twelve Every guide ends up in the same place: climb only as high as your load forces, and add complexity only when the metrics demand it. The best system is the simplest one that meets its targets. Restraint isn't the boring option — across Figma, Discord, Netflix, and the rest, restraint is the strategy.
How to actually retain this Reading all twelve guides straight through will feel productive and won't work. Do this instead: read one guide, close it, and answer its "Check yourself" questions from memory before opening the answers. Getting one wrong is the point — that's the moment the idea actually lands. Then come back a week later and answer them again. A dozen guides retained badly are worth less than half of them read this way.
