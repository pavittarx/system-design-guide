Understanding Caching

What a cache really is, where caches live, the read/write patterns worth knowing, and the parts that quietly break in production — explained for developers.

The opener to Scaling Databases, Load Balancing, Message Queues, Reliability, and Consistency & CAP.

◇ the ninety seconds after the key expired

19:42 on a Tuesday, the busiest hour of the week. One key — the homepage feed, cached for an hour, requested about 8,000 times a second — reaches the end of its TTL. Every one of those 8,000 requests looks in the cache, finds nothing, and does the obvious thing: asks the database. The query takes 40 ms when the database is idle. It is not idle; it is now running 8,000 of them at once, so it takes four seconds, then twelve. Clients time out at two seconds and retry, which adds a second wave on top of the first. Nobody deployed anything. Nobody's disk failed. A timer ran out, and by 19:44 the site is down.

1. What a cache actually is

A cache is a small, fast store that keeps copies of data close to where it's needed, so you don't have to redo expensive work — a database query, an API call, a heavy computation, a network round-trip. You spend a little memory and some added complexity to buy a lot of speed and a much lighter load on the systems behind it.

The reason it matters is a gap in speed. Reading from an in-memory cache is measured in microseconds (local) to well under a millisecond (a Redis hop); the same request that falls through to a database and back can take tens of milliseconds — often orders of magnitude slower. When most requests are answered by the cache, average latency collapses and the origin barely notices the traffic.

The whole tension in one line "There are only two hard things in Computer Science: cache invalidation and naming things." — attributed to Phil Karlton. Caching is easy to add and hard to keep correct. That's the real subject of this guide.

3. Read/write strategies

Each pattern answers two questions: who talks to the cache, and when does the cache get written. The read patterns decide how misses get filled; the write patterns decide how the cache stays in step with the source of truth.

Cache-aside (lazy loading) — the default

The application manages the cache. On a read: check cache → hit returns it → miss reads the DB, writes the value into the cache, then returns it. On a write: update the DB and invalidate the cached entry.

  • + Only requested data is cached (lean, cheap). If the cache disappears, reads still return — they fall through to the database instead of erroring.
  • − The first request for any key always misses (cold start). The app carries the caching logic. A small window exists where DB and cache can disagree.
"Resilient to cache failure" has an asterisk on it You will read that cache-aside means "if the cache dies, the app still works." What it actually means is that the app degrades rather than throwing errors — which is not the same thing as surviving. If your cache was absorbing 95% of reads, then the moment it goes away cold your database receives twenty times its normal read load, all at once, with no ramp. Databases do not politely queue; they fall over. Losing a cache cold is one of the best-documented ways to take a service down, and it is why cache warmup, request coalescing and load shedding exist at all. Cache-aside buys you a failure mode you can survive if you built for it — see the Reliability guide for the machinery.

Read-through

Like cache-aside, but the cache knows how to load from the DB on a miss (via a library/provider), so the app only ever talks to the cache. Cleaner app code; loading logic moves into the caching layer.

Write-through

Every write updates the cache and the DB synchronously, together.

  • + Cache and DB stay consistent; any key that's been written is served warm (unwritten or evicted keys still miss).
  • − Every write pays to write both; you cache data that may never be read (bloat). Often paired with cache-aside reads.

Write-back (write-behind)

Write to the cache immediately and return; flush to the DB asynchronously later, in batches.

  • + Very fast writes; absorbs bursts; fewer DB writes.
  • − Data loss risk if the cache node dies before the flush. More complex.

Write-around

Writes go straight to the DB, bypassing the cache; the cache fills later on a read miss.

  • + Avoids flooding the cache with write-heavy data that isn't read soon.
  • − Recently written data is a guaranteed miss on first read.

Worth saying out loud: caching is not the only way to take read load off a database. Read replicas move the same reads to a different machine without introducing a second copy of the truth with its own lifetime — see the Database Scaling guide. Caching wins when the work is expensive to compute, not merely expensive to fetch.

4. Cache-aside in code — and four bugs in it

Everything above is vocabulary. Here is what cache-aside looks like when you actually write it, and it is worth staring at, because this exact function is in production somewhere near you right now.

def get_user(user_id):
    key = f"user:{user_id}"
    cached = redis.get(key)
    if cached:
        return json.loads(cached)

    user = db.query_one("SELECT * FROM users WHERE id = %s", user_id)
    redis.setex(key, 3600, json.dumps(user))
    return user

def update_user(user_id, fields):
    db.update("users", user_id, fields)
    redis.delete(f"user:{user_id}")

Thirteen lines, textbook-correct in shape, and wrong in at least four ways.

1. Nothing coalesces the misses

Ten thousand concurrent requests for the same missing key run this function ten thousand times. Each one sees an empty cache, and each one issues its own SELECT. The cache does not queue them; it does not know they are related. You have built a mechanism that converts a single expiry event into ten thousand simultaneous database queries — the cold open of this guide, in thirteen lines. The fix is single-flight: the first caller to miss takes a short lock and does the load, and everyone else waits for its answer.

2. The TTL is a constant

3600, exactly, for every key. If you warm the cache after a deploy, or a batch job populates ten thousand keys in one loop, all of those keys were written within the same second and will therefore expire within the same second — an hour later, at a time nobody chose. Constant TTLs manufacture synchronised expiry. Randomise it.

3. The stale-forever race

This one is subtle and it is the reason people lose faith in their cache. Think of it as a story of a Reader thread that gets temporarily "distracted" (descheduled by the CPU) while a Writer updates the database in the background:

Here is what happens step-by-step during this race:

  1. The Reader misses the cache, loads the old row value (Ada) from the database, and is just about to write it back to Redis.
  2. Right then, the Reader gets suspended by the operating system (e.g. during a garbage collection pause or network lag).
  3. While the Reader is asleep, a Writer updates the database to Grace and deletes the Redis key. Since the key was already empty, this delete is a silent no-op.
  4. The Reader wakes up and finishes its write, saving the stale value Ada back into the empty Redis slot.

Now, the database has Grace but the cache confidently serves Ada. No subsequent writes will clear this key unless a user updates their profile again. The cache will remain stale for the entire 60 minutes.

This is why invalidation-on-write alone is not sufficient, no matter how carefully you find every call site. The window is small, but "small" times "a million writes a day" is a support ticket. Narrowing it is possible — Facebook's leases hand the missing reader a token that the writer's delete invalidates, so the late fill is simply rejected; a "delayed double delete" removes the key again a second after the write. Eliminating it needs versioned compare-and-set on the fill.

And it is why a bounded TTL is a safety net rather than a nicety. The TTL is the only thing in the buggy version above that ever repairs this. Every key you cache without an expiry is a key that can be silently wrong forever. If you find yourself writing SET with no TTL, you are betting that your invalidation logic is perfect. It is not.

Check yourself: You invalidate on every write, you've checked every call site, and users still report stale data — for almost exactly your TTL duration. What happened?
The stale-forever race. A reader missed, read the old value from the database, got descheduled; your writer updated the row and deleted a key that wasn't there; the reader woke up and wrote its stale value into the empty slot. Your invalidation ran before the poisoning write, so it invalidated nothing. The giveaway is the duration: it's the TTL, because the TTL is the only thing that ever clears it. Narrow the window with leases or a delayed second delete, and never remove the TTL.

4. Misses and empty results are the same thing

db.query_one returns None for a user that doesn't exist. json.dumps(None) is the string "null", which gets cached for a full hour and is indistinguishable from a real value. So a user created one second after somebody looked them up stays invisible for an hour. Flip the code the other way — only cache when user is not None — and you get the opposite failure, cache penetration: every request for a non-existent ID misses the cache and hits the database, forever, which is a free denial-of-service for anyone who can guess URLs.

The answer is to cache negatives deliberately, with their own short TTL and a sentinel you can tell apart from real data. (While you are in there: if cached: is also wrong — an empty cached value is falsy, so a legitimately-empty entry is treated as a miss on every read. Test is not None.)

The version that survives contact

MISS = "◇none"                      # sentinel: cached "does not exist"

def safe_decode(val):
    # Handles both string and bytes (for redis-py decode_responses setting)
    return val.decode('utf-8') if isinstance(val, bytes) else val

def jitter(ttl):
    return ttl + random.randint(0, ttl // 10)

def get_user(user_id):
    key = f"v3:user:{user_id}"      # v3 = serialisation version
    hit = redis.get(key)
    if hit is not None:
        return None if safe_decode(hit) == MISS else json.loads(hit)

    with single_flight(key):        # only one loader per key (conceptual lock)
        hit = redis.get(key)        # check if someone filled it while we waited
        if hit is not None:
            return None if safe_decode(hit) == MISS else json.loads(hit)

        user = db.query_one("SELECT * FROM users WHERE id = %s", user_id)
        if user is None:
            redis.set(key, MISS, ex=jitter(60), nx=True)
        else:
            redis.set(key, json.dumps(user), ex=jitter(3600), nx=True)
        return user

def update_user(user_id, fields):
    db.update("users", user_id, fields)
    redis.delete(f"v3:user:{user_id}")   # delete, don't write the new value in

What changed: misses collapse to one query, TTLs no longer synchronise, non-existent users get a short negative entry instead of either an hour of invisibility or an open channel to the database, and the key carries a schema version. nx=True means a slow reader can never clobber a value someone else has already refreshed — it does not close the stale-forever race, because after the writer's DEL the slot is empty and the stale SET succeeds. Only the bounded TTL saves you there, which is the whole point.

Note also the last line: the writer deletes rather than writing the new value. Two concurrent writers who both write their value into the cache can land in the opposite order they landed in the database. Delete-on-write has one outcome — the next reader goes and finds out — and one outcome is much easier to reason about than two.

5. HTTP caching (the web layer)

If you work on anything web-facing, this layer is standardized and immediately actionable. It's controlled by response headers.

Cache-Control — the main lever

Validation & 304s

Instead of re-sending a whole resource, the client revalidates cheaply. The server sends an ETag (a content fingerprint); the browser later sends If-None-Match. If nothing changed, the server replies 304 Not Modified with no body. (Last-Modified + If-Modified-Since is the timestamp-based equivalent.) Big bandwidth savings, still fresh.

Fingerprinted assets

app.a1b2c3.js — cache forever. Modern bundlers (Vite, Webpack, Next.js) name files by a hash of their content. Because any change in the code generates a new filename, a deploy never serves stale JavaScript/CSS. We can safely cache them for a year:

Cache-Control: public,
  max-age=31536000, immutable

Frequently-updated HTML

Serve recent copies fast, revalidate quietly, pair with an ETag:

Cache-Control: public,
  max-age=300,
  stale-while-revalidate=30

CDNs apply these same rules at the edge — which is exactly why the s-maxage (edge lifetime) vs max-age (browser lifetime) split is so useful.

Vary — the header that leaks other people's data

A shared cache keys entries on the URL. That is the whole model. If two different responses can come back from the same URL, the cache needs to be told which request headers made them different, and that is what Vary is for: Vary: Accept-Encoding means "store gzip and brotli separately," Vary: Accept-Language means "store per language."

Now consider GET /dashboard, which renders the logged-in user's name, and which your framework marks Cache-Control: public, max-age=60 because someone was tuning performance. The response varies by the session cookie. The header does not say so. The CDN stores Alice's dashboard under the URL alone and serves it to Bob for the next sixty seconds. This is not a hypothetical class of bug; it has shipped, repeatedly, at companies you have heard of, and it usually surfaces as a support ticket that reads "I'm logged in as someone else."

The blunt instrument, and why you want it Cache-Control: private tells shared caches not to store the response at all — only the end user's own browser may. For anything personalised, reach for private (or no-store if it's sensitive) rather than trying to get Vary exactly right. Vary: Cookie is technically correct and practically useless: if your site sets any cookie at all, every visitor has a unique key and your hit rate goes to roughly zero. The real fix for a page that is mostly public is to cache the public shell and fetch the personalised fragment separately.
Check yourself: Which of these must never be cached in a shared CDN, and why: (a) the logged-in dashboard HTML, (b) app.9f2a1c.js, (c) /api/me, (d) a public product image?
(a) and (c). A shared cache keys on the URL plus whatever Vary declares, and both of those return different bytes to different people at the same URL — so the first response gets stored and handed to the next visitor. Mark them Cache-Control: private, or no-store if they carry anything sensitive. Don't rely on Vary: Cookie to save you: it's correct in theory and gives you a ~0% hit rate in practice, so someone will eventually "optimise" it away.

6. Eviction & TTL: keeping the cache lean

A cache has finite memory, so it must decide what to drop.

Expiration (TTL) gives every entry a time-to-live; after it lapses, the entry is refetched. TTL is the simplest correctness tool — it bounds how stale data can get without any explicit invalidation. Short TTL = fresher but more misses; long TTL = faster but staler.

◈ In the wild: DNS (domain name resolution) is the world's largest example of TTL-based caching. When a website owner updates a DNS record, resolvers worldwide continue serving the old IP address from their caches until the record's TTL lapses. This is why DNS changes "take time to propagate" and represent eventual consistency in action.

Eviction policies decide what to drop when memory is full:

  • LRU (Least Recently Used) — drop what's gone unused longest. The default sweet spot for most workloads.
  • LFU (Least Frequently Used) — drop the least-often accessed; better when popularity is stable.
  • FIFO — drop the oldest inserted, regardless of use.
  • Random / TTL-based — simpler, occasionally the right call.
Eviction ≠ invalidation Eviction is the cache freeing space on its own terms. Invalidation is you deciding a value is now wrong. Conflating the two is a common source of confusion.

7. The hard parts

This is what separates "I added a cache" from "I run a cache in production."

Cache invalidation

The cache holds a copy. The moment the source of truth changes, that copy might be wrong. Three broad approaches:

  • TTL / expiry — let entries lapse. Simple, eventually consistent, but stale within the window.
  • Write-time invalidation — when you update the DB, delete/update the cache entry in the same flow. Fresher, but you must find every place a value is cached, and the DB-write + cache-delete pair isn't atomic (a failure between them leaves you inconsistent).
  • Event-driven invalidation — publish change events (pub/sub, a CDC stream, Redis Pub/Sub) that fan out and purge keys. Scales well, more moving parts, and you inherit every delivery guarantee question the transport has — see the Message Queues guide, because "at-least-once purge" and "at-most-once purge" are very different promises about your cache.
Ask this before caching anything How stale can this specific data safely be? The answer determines your caching strategy for each field.

◈ In the wild: On an e-commerce product page, the description and images barely change, so they are cached aggressively at the CDN for hours. But the price and inventory count must be near-real-time to avoid selling out-of-stock items, so they are cached for only seconds, written through on every change, or fetched live from the origin.

Most caches give eventual consistency — for a window, readers may see old data. If that trade-off is critical for your data type (like account balances), the Consistency & CAP guide unpacks exactly what you are and aren't promised.

Cache key versioning

Prefix every key with a schema version: v3:user:123. You will not appreciate why until the deploy where you add a field to the serialised shape, and every instance running the old code starts reading objects that have it while every instance running the new code reads objects that don't. Without a version prefix your options are (a) flush the cache, which is the cold-start outage described below, or (b) write defensive deserialisation forever. With one, you bump v3 to v4, the new code writes and reads new keys, the old keys are read by nobody and quietly age out under their own TTL or get evicted by LRU. It costs six characters per key.

Cache stampede — two different problems that people merge into one

These get taught together but are caused by different mechanics and have completely different fixes. Adding jitter to a hot-key issue will not fix it, and adding single-flight to a mass-expiry issue is overkill. Let's compare them:

1. Synchronised Mass Expiry (Multiple keys, same expiry). Many different keys were written at roughly the same moment — a deploy warmed them, a batch job populated them, the cache restarted and refilled in a burst — and because they all got the same fixed TTL, they all expire at roughly the same moment too. One second you're at a 95% hit rate; the next you're at nothing, and the database gets the whole read load.

  • The fix is TTL jitter: Randomise expiry per key — e.g. 3600 seconds plus 0–360 random — so the cliff becomes a slope. This is a simple, three-line fix that you should do by default.

2. A Single Hot Key Expiring (One key, high traffic). A single key is requested thousands of times a second (like the homepage feed or a celebrity user profile). When its TTL expires, every in-flight request misses simultaneously and queries the database. Note that jitter does nothing here: there is only one key, it has one expiry time, and randomising when the cliff happens doesn't reduce the height of the drop.

  • Request coalescing / single-flight: The first request to miss takes a lock and recomputes; the rest wait for its result. N misses become one query. This is the actual fix.
  • Probabilistic early expiration (XFetch): (See below).
  • Serve-stale-while-revalidate: Keep the old value past its nominal freshness and hand it back instantly while one background task refreshes it. Nobody waits, nobody misses.
◈ In the wild · Meta Meta runs one of the largest Memcached tiers on the planet in front of its databases, and it ships a coalescing throttle for exactly the hot-key stampede above. In the paper "Scaling Memcache at Facebook" (NSDI 2013) they describe leases: on a miss for a hot key, only the first request is handed a short-lived token to recompute the value, while the requests arriving behind it are told to wait briefly or are served a slightly stale copy. That is single-flight, enforced at the cache, at production scale.

Probabilistic early expiration (XFetch)

This is the mathematically elegant answer to the hot-key case, and it requires no locks or coordination. Instead of waiting for a key to expire and risking a stampede of misses, XFetch forces one lucky request to refresh the cache before it actually expires.

The "Water Cooler" Analogy Imagine a water jug in a busy office. If you wait until it is 100% empty, the next person has to wait 5 minutes to refill it, creating a line (a database queue bottleneck).

Instead, imagine each person who gets water rolls a die. If the jug is 20% empty, they only refill it if they roll a 6. If the jug is 90% empty, they refill it if they roll anything other than a 1. Because the office is busy, someone will eventually roll the right number and refill the jug in the background before it ever goes completely dry. Nobody ever waits for an empty jug.

The math does exactly this. On every read, alongside the value, the cache stores how long the last database fetch took (delta) and the expiry deadline. Then, each client reader rolls a mathematical "die" on read, deciding to trigger an early background refresh if:

now - delta * beta * ln(random())  >=  expiry_time

Since random() returns a decimal between 0 and 1, its natural log ln(random()) is a negative number. This pushes the left-hand side ahead of now. As the key gets closer to its expiration, the probability of rolling a "yes" climbs smoothly. A single request volunteers to refresh the data in the background, updates the cache, and every other user continues hitting a warm cache. beta (default 1) lets you tune how early you want the background refreshes to start.

Metastable failure — the self-sustaining death spiral

This is the failure mode that surprises engineers because the original trigger (the bug, the bad deploy) is gone, but the system remains down. It is a **vicious loop** that feeds on its own recovery attempts:

Phase What happens in the system
1. The Trigger A cache node crashes or is flushed at peak traffic. Hit rate drops to 0%.
2. DB Saturation Thousands of concurrent misses hit the database. DB queries slow from 10ms to 8 seconds.
3. Timeout & Retry Clients time out waiting for the database, assume failure, and **retry**. Traffic doubles or triples.
4. The Trap The database is now too busy processing retries to answer *any* query. Because no queries finish, **the cache can never be refilled**.

The system is trapped. Reverting the bad code or restarting the cache does nothing because the offered load is self-sustaining. The only exit is to **forcefully break the loop**: shed traffic at the gateway, disable the expensive endpoint, or drop client retry budgets to zero. Once database load drops, it can finally answer queries, refill the cache, and recover. Only then can you gradually ramp the traffic back up.

Check yourself: You flush the cache during a 3am deploy every week and it's fine. You do it at peak and the site is down for 40 minutes, even though you reverted the change within seconds. Why didn't reverting help?
At 3am the database has enough headroom to serve 100% of reads while the cache refills. At peak it doesn't, so it saturates, requests exceed the client timeout, clients retry, and offered load doubles or triples at the worst possible moment. That's a metastable failure: the load keeping you down is now being generated by the outage itself, so removing the original trigger changes nothing. You have to shed traffic until the database can answer enough queries to repopulate the cache, then ramp back. Also: version your keys instead of flushing.

Hot keys don't get fixed by more cache nodes

Worth being explicit, because it's the first thing everyone tries. A cache cluster distributes keys by hashing them — consistent hashing, usually — which means user:celebrity maps to exactly one node. Adding nodes changes which node. It does not change how many. You can triple your cluster and that one node is still absorbing 100% of the traffic for that key while the other nodes idle. The fixes are different in kind:

  • Key splitting — write the same value under user:celebrity#0 … #7, and have readers pick a suffix at random. Eight keys hash to (probably) eight nodes and the load divides. You pay for it in invalidation: a write now has to clear all eight.
  • A client-local tier — a small in-process cache in front of the shared one, holding the top few hundred keys for a second or two. A one-second local TTL on a key read 8,000 times a second turns 8,000 remote reads into one. The cost is a second of extra staleness and the fact that every instance can now disagree.
◈ In the wild · Twitter/X Timelines Rather than assemble home timelines on every read, Twitter historically precomputed them: when a user tweets, the tweet is fanned out and written into the cached timelines of their followers in Redis ahead of time (fan-out-on-write).

However, when a celebrity with 100M followers tweets, fanning out the write to 100M active timeline caches immediately causes a severe write bottleneck. Twitter solved this hot key challenge by hybridizing strategies: celebrity tweets bypass the write fan-out and are instead merged dynamically into a user's timeline only at read time (merge-on-read).

Check yourself: You added jitter to every TTL and your hot-key stampede is exactly as bad as before. What did you misunderstand?
Jitter desynchronises different keys that were written at the same moment. A hot key is one key with one expiry time — randomising when that moment arrives doesn't reduce the number of requests that miss when it does. You need single-flight so only one request rebuilds the value, or probabilistic early expiration so one request refreshes it slightly early and nobody ever sees the miss, or stale-while-revalidate so the old value is served during the rebuild.

8. Operational reality: Redis and Memcached

The patterns above are portable. These are the specific ways the two boxes you'll actually run will embarrass you.

Redis: maxmemory-policy defaults to noeviction

This one catches almost everybody. Redis is a database that people use as a cache, and its defaults are a database's defaults. Set maxmemory, leave maxmemory-policy alone, and when the cache fills up Redis does not evict anything — it starts returning OOM command not allowed when used memory > 'maxmemory' on every write. Your cache stops accepting new entries, which means every miss stays a miss, which means the database takes the full load. A full cache has become a total cache outage, quietly, without a single alarm firing.

  • For a pure cache you want allkeys-lru or allkeys-lfu. Then a full cache does what you expect: makes room.
  • volatile-lru and friends only consider keys that have a TTL set. Forget the TTL on one code path and those keys become permanently un-evictable — and if enough of them accumulate, Redis runs out of eviction candidates and falls back to erroring anyway.
  • Don't leave maxmemory at its default of 0 (unlimited) either. That just moves the failure from Redis to the kernel's OOM killer, which is a worse place for it.
  • Redis's LRU is approximate — it samples a handful of keys (maxmemory-samples, default 5) and evicts the best candidate among them, rather than tracking a true global ordering. Close enough for caching, but don't reason as if it's exact.
Check yourself: Your Redis is at its memory limit. Instead of evicting anything, it started returning errors on SET — and your database load quietly tripled. What's the setting?
maxmemory-policy, which defaults to noeviction because Redis is a database first and a cache second. A full cache that refuses writes can never fill a miss, so every miss stays a miss and the whole read load lands on the origin. Set allkeys-lru or allkeys-lfu for a pure cache. Avoid volatile-* unless you're certain every key has a TTL — those policies only consider keys that have one, and can run out of candidates and start erroring anyway.

Memcached: slab calcification

Memcached carves memory into pages and assigns each page to a slab class — a bucket for items of a particular size range. Once a page belongs to the 1 KB class, it stays there. So if your workload shifts — you start storing bigger serialised objects, or a new feature caches small counters — the new size class runs out of pages and starts evicting aggressively while another class sits half-empty holding memory it no longer needs. Your hit rate drops and your memory graph shows plenty free. That's calcification. Modern versions can rebalance (slab_reassign / slab_automove), but it is not something to discover during an incident: watch per-slab eviction counts, not just the total.

The numbers may not mean what you think

Redis reports mem_fragmentation_ratio in INFO memory — resident memory divided by the memory Redis thinks it's using. Meaningfully above 1 (say 1.5) means the allocator is holding memory it isn't handing back, so your 8 GB instance is really using 12 and your capacity planning is fiction. Below 1 is worse: it means part of your in-memory cache has been swapped to disk, and a cache that reads from disk is just a slow database with extra steps. Check it before you conclude anything from a memory graph. Likewise, keyspace_hits and keyspace_misses are server-wide counters since boot — if three services share the instance, that ratio is nobody's hit rate. Instrument hit rate in your own client, per cache.

9. When not to cache

Caching isn't free — it adds a whole new class of bugs (stale reads, invalidation races). Skip or minimize it when:

  • Data changes constantly and must be exact — financial ledgers, inventory at checkout.
  • Data is user-specific and rarely re-read — a low hit rate is pure overhead.
  • Correctness beats latency and you can't tolerate any staleness.
  • The added complexity outweighs a modest speedup.

A cache you can't reason about is a liability, not an optimization. Measure the hit rate — a cache with a low hit rate is often worse than none.

10. Metrics that matter

Hit / miss rate

The headline number. A low hit rate means the cache isn't earning its keep.

Latency (p50 / p99)

The actual user-facing win — watch the tail, not just the average.

Eviction rate

High evictions suggest the cache is too small for the working set.

Origin load reduction

How much traffic the cache absorbs before it reaches the DB/API.

Check yourself: Your hit rate is 94% and p99 latency got worse after you added the cache. What's the likely cause?
p99 is made of the 6% that miss, and a miss now costs a cache round trip plus the database query it always cost — you added latency to exactly the requests that were already slowest. Averages improved, the tail didn't. Look also for serialisation cost on large objects, connection-pool contention against the cache, and one slow node in the cache cluster dragging a slice of traffic. Instrument hit latency and miss latency as separate metrics; a single blended number will hide this forever.

11. Where to start

If you're adding caching to something real, resist the urge to reach for the fanciest pattern. A reliable progression:

  1. Start with cache-aside + a TTL. It's simple, resilient, and covers most read-heavy workloads.
  2. Measure the hit rate. If it's low, you're caching the wrong things — fix that before adding machinery.
  3. Add TTL jitter from the start — it is three lines and it prevents keys written together from expiring together. Note that it does nothing for a single hot key; that one needs single-flight.
  4. Reach for write-through, event-driven invalidation, or coalescing only when the numbers actually ask for them.

Add complexity in response to evidence, not anticipation. The best caching setup is the simplest one that hits your latency and freshness targets.

12. Recap in 60 seconds
  • A cache trades memory and a new class of bugs for latency and origin load. The bugs are the price, not a defect.
  • Cache-aside is the default: read cache, miss, read DB, fill, return; on write, update DB and delete the key. Deleting beats writing the new value, because two concurrent writers can land in either order.
  • "The app still works without the cache" means it degrades rather than errors. A cache absorbing 95% of reads leaves the database facing 20× its normal load the instant it goes cold.
  • Always set a TTL. It is the only mechanism that repairs an invalidation you got wrong, and you will get one wrong.
  • Jitter fixes synchronised mass expiry (many keys written together). Single-flight fixes a hot key expiring (one key, many concurrent misses). They are different problems; jitter does nothing for the second.
  • The stale-forever race: a slow reader writes its pre-update value into a slot the writer just cleared. Invalidation-on-write alone can't prevent it; the TTL is what eventually cleans it up.
  • Cache negative results deliberately, with a short TTL and a distinguishable sentinel. Not caching them at all is an open channel to your database.
  • A hot key is not fixed by more cache nodes — consistent hashing sends it all to one node anyway. Split the key, or add a client-local tier with a one-second TTL.
  • Personalised responses need Cache-Control: private. A shared cache keys on URL; getting Vary subtly wrong serves one user's page to another.
  • Version your keys (v3:user:123) so a serialisation change never forces you to choose between a flush and reading garbage.
  • Redis's maxmemory-policy defaults to noeviction: a full cache returns write errors instead of making room. Set allkeys-lru.
  • Once retries are amplifying, the outage is self-sustaining. Recovery is shedding load, not waiting.

The one-liner to remember A cache is a second copy of the truth with its own lifetime, and every hard problem in caching is a consequence of that sentence. Give every entry a TTL, delete on write rather than overwriting, collapse concurrent misses into one query, and remember that the cache is now load-bearing — losing it is an outage you have to design for, not a graceful fallback you get for free.
