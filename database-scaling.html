Scaling Databases

The database is where most systems hit their ceiling first. This is the ladder of moves — from tuning one box, to replicas, to sharding — and the trade-offs at every rung, with how real companies climbed it.

A companion to Caching, Load Balancing, Message Queues, Reliability, and Consistency & CAP.

◇ 09:14 · the query that was fine last quarter

Nobody changed the code. A single SELECT against the orders table has shipped untouched for eighteen months — at 100,000 rows it returned in 3 ms and nobody ever looked at it again. The table is now 40 million rows, the index that would have saved it was never created, and this morning that query takes six seconds, scanning the whole table and holding a database connection for every one of them. At 30 requests a second, six seconds each, you need 180 connections in flight against a pool of 100. The pool empties. And now the login page is timing out, and the health check is timing out, and the settings endpoint that has never in its life touched the orders table is timing out — because they are all queued behind a connection that isn't coming back. The CPU graph looks almost calm; the box is just waiting on disk. It is not a capacity problem. It is one missing index, and it took the whole product down.

1. Why the database breaks first

You can add app servers behind a load balancer almost endlessly — they're stateless and interchangeable. The database is different: it holds state, and there's usually one authoritative copy that every write must go through. That makes it the natural bottleneck.

Two pressures build up, and they need different fixes:

  • Read pressure — too many queries reading data. Usually the easier problem; you can serve reads from copies.
  • Write pressure — too many inserts/updates, or simply too much data to fit and index on one machine. The harder problem, because all writes contend for the one source of truth.
The golden rule of scaling Every rung up this ladder adds complexity and new failure modes. So climb it only as far as your load actually forces you to — and no further. Most applications never need sharding. Diagnose whether you're read-bound or write-bound first; it decides which rung you need. The next section is how you actually do that.

2. Diagnose first: read-bound or write-bound?

"The database is slow" is not a diagnosis, and the two pressures send you to completely different rungs. Worse, the wrong answer is expensive in a specific way: if you're write-bound and you add read replicas, you have not just failed to help — you've added machines that each replay every single write, plus a replication stream to monitor and a new failure mode. You made it worse and you paid for the privilege.

Here is a triage you can genuinely run on a Monday morning. Five signals, in order of how quickly they answer the question.

1. The read/write mix, from the database's own counters

Every engine counts this for you. In Postgres, pg_stat_database gives you tup_returned / tup_fetched against tup_inserted + tup_updated + tup_deleted; pg_stat_user_tables breaks it down per table. In MySQL, SHOW GLOBAL STATUS gives you Com_select versus Com_insert/Com_update/Com_delete, and Innodb_rows_read versus Innodb_rows_inserted. These are cumulative since restart, so take two samples an hour apart and subtract — the absolute numbers are meaningless, the delta is the answer. They're row counters, not statement counters, so treat them as order-of-magnitude signal, not gospel.

2. Which p99 actually moved

This is the one that settles arguments. Split your latency percentiles by statement type and look at what degraded when the trouble started, not what is slowest in absolute terms. Writes are often slower than reads on a healthy system; that's normal and tells you nothing. If SELECT p99 went from 40 ms to 600 ms while INSERT p99 barely moved, you are read-bound. If your writes are the ones climbing while reads hold steady, you are write-bound. pg_stat_statements (ordered by total_exec_time, not mean_exec_time — the query that costs you most is usually a fast one run absurdly often) or the MySQL slow query log will point at the specific statements.

3. Replication lag climbing vs. lock wait time climbing

These two are near-perfect discriminators. Replication lag rising means the primary is generating write-ahead log faster than replicas can apply it — that is a write-volume problem by definition, and it is a leading indicator you'll hit the write ceiling. Lock wait time rising means writes are contending with each other or with long-running readers: check pg_stat_activity for wait_event_type = 'Lock', or SHOW ENGINE INNODB STATUS for row-lock waits. Contention is a write-shaped problem too, but it's usually fixed by shortening transactions rather than by buying hardware.

4. Buffer cache hit ratio

From pg_stat_database: blks_hit / (blks_hit + blks_read), or InnoDB's buffer pool hit rate. For an OLTP workload you want this above about 99%. When it starts falling, your working set has outgrown RAM and reads that used to be memory hits are now disk reads — a read-side problem that vertical scaling (more RAM) fixes instantly and cheaply. One honest caveat: Postgres counts a "miss" whenever it goes to the operating system, and the OS page cache may still serve it from memory, so the true disk-read count is lower than this ratio suggests. Use the trend, not the value.

5. Rows examined per row returned

The single most diagnostic number in this entire guide. For each expensive query, divide the rows the database touched by the rows it gave back — Rows_examined vs. Rows_sent in the MySQL slow log, or Rows Removed by Filter in EXPLAIN (ANALYZE, BUFFERS). Near 1 is healthy. Above 100 means the database is doing a hundred times more work than the answer requires, and the fix is an index or a rewritten query — not a bigger machine, not replicas, and absolutely not sharding.

$ triage — pg_stat_database delta, 09:00 → 10:00 rows returned by reads .............. 4,120,000,000 rows inserted + updated + deleted ... 3,900,000 ≈ 1000:1 $ which p99 moved (pg_stat_statements) SELECT p99 .......... 42 ms → 610 ms ◀ this one INSERT p99 .......... 6 ms → 7 ms unchanged $ supporting signals buffer cache hit .... 99.6% → 91.2% working set left RAM rows examined/returned 1.2 → 3,400 a plan went sequential replication lag ..... 40 ms (flat) writes are fine lock wait time ...... flat nothing is blocking verdict: READ-BOUND → index the query, then cache, then replicas

What each answer sends you to

  • Read-bound → indexes, then cache, then replicas. In that order, and the order is not negotiable. Indexing is free and can be 100×. Caching removes the query entirely and needs no new database. Replicas are last because they're the first move that adds a distributed system, replication lag, and a whole class of read-your-writes bugs to your life.
  • Write-bound → batching, then vertical, then partitioning, then sharding. Batching first, because the cheapest write is the one that shares a transaction and an fsync with 999 others — a queue in front of the database turns a spiky per-request write into a steady batched one. Then vertical: faster NVMe and more RAM move the write ceiling further than people expect. Then partitioning, which fixes size and maintenance but not throughput. Then sharding, which is the only thing on this list that actually multiplies write capacity. Read replicas do nothing for you here — every replica applies every write, so they add write work rather than absorbing it.
The third answer nobody expects Sometimes you are neither. If the database's own CPU, I/O, and lock waits are all unremarkable but your application's latency is terrible, the bottleneck is in front of the database — connection-pool queueing, an N+1 loop issuing 400 tiny queries per request, or a missing timeout letting one slow endpoint hold every connection. That's the cold open at the top of this page, and no rung of this ladder fixes it. See the gotchas.

3. Rule zero: make one box faster before you add boxes

Before any distributed anything, exhaust the cheap wins on a single database. They routinely buy 10–100× and cost a fraction of the complexity.

Indexing

The single biggest lever. An index lets the DB jump to the rows it needs instead of scanning the whole table. Most "the database is slow" problems are really "this query has no usable index."

Query & schema tuning

Fix N+1 queries, avoid SELECT *, read the query plan (EXPLAIN), remove accidental full scans. Free performance hiding in plain sight.

Vertical scaling (scale up)

Move to a bigger machine — more CPU, RAM, faster NVMe. Zero code change. The ceiling is real (and pricey at the top), but it buys you time.

Connection pooling

Each DB connection costs memory; thousands of app instances can exhaust the server. A pooler (PgBouncer, RDS Proxy) multiplexes many clients onto few connections.

Do this first, always A well-indexed query on a single beefy box beats a poorly-designed sharded cluster every time. Sharding a slow query just gives you many slow queries.

4. Worked example: the index that isn't used

"We have an index on that" is one of the most confidently wrong sentences in software. Having an index and using an index are separate facts, and only one of them makes queries fast. Here are the two ways it goes wrong, both of which look completely fine in code review.

Case 1: the composite index and the leftmost prefix

You have an events table, 40 million rows, and an index that was created for a dashboard query:

CREATE INDEX idx_events_org_created ON events (org_id, created_at);

-- Fast. Filters on the leading column.
SELECT * FROM events
WHERE  org_id = 42
  AND  created_at > now() - interval '7 days';

-- Slow. Same index, same table, no predicate on org_id.
SELECT * FROM events
WHERE  created_at > now() - interval '7 days';

A composite B-tree index is sorted by its columns in order: first by org_id, and only within each org_id by created_at. Think of a phone book sorted by last name, then first name. Ask it for everyone called Okafor and it's instant. Ask it for everyone called James, with no last name, and the sort order is worthless — the Jameses are scattered across every page, so you may as well read the whole book. That's the leftmost-prefix rule: an index on (a, b, c) can serve predicates on a, on a AND b, and on a AND b AND c, but not on b alone or c alone. Some engines can partially work around this with a skip scan when the leading column has very few distinct values — MySQL 8.0, Oracle, and PostgreSQL 18 all have one — but it's a consolation prize, not a design you should rely on. The fix is a second index on (created_at), or reordering the columns if the single-column query is the important one.

Here's what the arbiter says. Before:

Seq Scan on events (cost=0.00..982431.00 rows=1204 width=88) (actual time=0.031..4128.774 rows=1187 loops=1) Filter: (created_at > (now() - '7 days'::interval)) Rows Removed by Filter: 39998813 Execution Time: 4131.006 ms

Forty million rows touched to return 1,187. After CREATE INDEX idx_events_created ON events (created_at);:

Index Scan using idx_events_created on events (cost=0.44..421.90 rows=1204 width=88) (actual time=0.028..1.902 rows=1187 loops=1) Index Cond: (created_at > (now() - '7 days'::interval)) Execution Time: 2.140 ms

Case 2: the function that hides the column

This one is subtler, because the index is on exactly the column you're filtering on:

CREATE INDEX idx_users_email ON users (email);

-- Sequential scan. Every time.
SELECT * FROM users WHERE lower(email) = 'ada@example.com';

The index stores the values of email, verbatim. It has never seen lower(email) — as far as the planner is concerned that's a different expression, computed per row, and the only way to compute it for every row is to read every row. Same bug, different costumes: WHERE created_at::date = '2026-01-01', WHERE substr(sku, 1, 3) = 'ABC', and the classic WHERE account_number = 12345 where account_number is a varchar and the implicit cast quietly wraps the column. The fix is to index the expression you actually query, or to stop applying the function:

CREATE INDEX idx_users_email_lower ON users (lower(email));
-- or normalise on write, or use a case-insensitive column type (citext)
EXPLAIN is the arbiter, and dev data will lie to you Never reason about index usage from first principles — run EXPLAIN (ANALYZE, BUFFERS) and read what the planner actually chose. Two things to watch for. First, EXPLAIN alone gives estimates; ANALYZE executes the query and gives you real row counts and timings (it also really runs the statement, so wrap writes in a transaction you roll back). Second, on a 5,000-row development table the planner will correctly choose a sequential scan no matter how perfect your index is, because reading the whole thing is genuinely cheaper. Index decisions have to be validated against production-shaped data volumes, or you're testing the wrong database.

5. Read replicas & replication

The first distributed move, and the answer to read pressure. You keep one primary (a.k.a. leader) that takes all writes, and add replicas (followers) that receive a stream of those changes and serve read-only queries. Point your reporting, search, and read-heavy traffic at the replicas; the primary breathes easier.

Synchronous vs. asynchronous replication

How the primary waits for replicas defines the core trade-off:

  • Asynchronous (the common default) — the primary commits and replies immediately, then ships changes to replicas after the fact. Fast, but replicas trail slightly.
  • Synchronous — the primary waits for a replica to confirm before acknowledging the write. Little to no data loss on failover (depending on quorum config), but every write is slower.
The gotcha: replication lag With async replication, a replica is a few milliseconds (sometimes seconds, under load) behind the primary. So a user who writes a comment and immediately reloads from a replica may not see it — a "read-your-own-writes" bug. Fixes: route reads that need freshness to the primary, "stick" a user to the primary briefly after they write, or wait for the replica to catch up. This is the same eventual consistency trade-off as cache staleness, one layer down — and the same dial the Consistency & CAP guide turns. There's more to this than the usual one-paragraph treatment; see the gotchas for why this bug only ever appears in production.

Replicas scale reads, add read capacity cheaply, and give you a failover target — but they do nothing for write throughput or total data size. When those are the problem, you have to split the data itself.

6. Partitioning: splitting a table

Partitioning breaks one big table into smaller pieces. Two flavors, often confused:

  • Vertical partitioning — split by columns / tables: move different groups of tables (or rarely-used wide columns) onto separate databases. E.g. put "billing" tables on one DB and "content" tables on another. Figma started here.
  • Horizontal partitioning — split by rows: keep the same columns but divide rows across partitions by a key (e.g. by month, or by a hash). Within a single database engine this is just called "partitioning"; the app still queries one logical table and the engine prunes to the relevant partition.

Horizontal partitioning within one server helps with table size, index bloat, and lifecycle management (drop last year's partition instantly). But it's still one machine's CPU and IOPS. When you need to spread rows across separate machines, horizontal partitioning becomes sharding.

7. Sharding: splitting across machines

Sharding is horizontal partitioning taken across independent database servers. Each shard holds a slice of the rows and runs on its own hardware, so writes, storage, and IOPS all scale out. It's the most powerful move — and by far the most complex. This is the top of the ladder for a reason.

The shard key is everything

You pick a shard key (user ID, org ID, channel ID…) and a function that maps each row's key to a shard. Every design decision flows from this choice, because it determines how evenly load spreads and which queries stay cheap.

StrategyHow it mapsStrengthWeakness
RangeContiguous key ranges (A–M, N–Z; or by date)Fast range scans; easy to reason aboutHot spots — recent dates or popular ranges overload one shard

DirectoryA lookup table maps key → shardFlexible; can rebalance individual keysThe lookup service is a new dependency & potential bottleneck

Why sharding is hard — the four taxes you pay

  • Hot shards / hot keys — if one tenant, channel, or celebrity dominates, their shard melts while others idle. Hashing helps distribute keys, but a single hot key still lands on one shard. (This is the DB-level twin of the "hot key" cache problem.)
  • Cross-shard queries & joins — a query spanning shards must fan out and merge results; joins across shards are painful or impossible. Every accidental cross-shard join becomes an app-level problem.
  • Distributed transactions — an atomic change touching two shards needs two-phase commit or careful redesign. Most teams avoid cross-shard transactions entirely by choosing the key so related data lives together. What that atomicity really costs you across a network is the subject of the Consistency & CAP guide.
  • Rebalancing & resharding — adding shards means moving live data without downtime. Consistent hashing and logical-vs-physical shard separation exist largely to make this survivable.
The pro move: logical vs. physical shards Create many logical shards up front (say 1,000) and pack them onto a few physical machines. To grow, you move logical shards to new machines — no re-hashing of keys. Instagram and Figma both lean on this split; it's what makes resharding a data-move instead of a rewrite.

One assumption underneath all of this deserves saying out loud: sharding presumes your application tier is stateless, so that any app server can talk to any shard and be replaced at will. If your app servers are still holding per-user state in local memory, fix that first — see the Load Balancing guide. A sharded database behind sticky, stateful app servers is two hard problems wearing one trench coat.

8. Worked example: picking a shard key, as arithmetic

Shard-key choice is usually taught as a list of strategies. It's better understood as arithmetic plus a short list of queries you refuse to make slow. Let's do it properly on a Slack-shaped product: workspaces contain channels, channels contain messages, and everything a user does is scoped to one workspace at a time.

Step 1: the numbers

$ the shape of the data workspaces .......................... 250,000 messages / day ...................... 30,000,000 avg row + index overhead ............ 400 bytes data added per day .................. 12 GB retention ........................... 2 years (730 days) $ therefore total rows .......... 30M × 730 ..... 21,900,000,000 total size .......... 21.9B × 400B .. ~8.8 TB comfortable data per shard .......... ~1.5 TB minimum shards ...... 8.8 / 1.5 ..... 5.9 → 6 provisioned (headroom, power of two) 16 logical shards ...................... 1,024 (64 per machine) $ write rate average ............. 30M / 86,400 .. ~350 writes/s peak (4× average) ................... ~1,400 writes/s per shard at 16 shards .............. ~90 writes/s

Read that last line again, because it's the most useful thing in this section. Ninety writes per second is nothing. A laptop does ninety writes per second. You are not sharding because of write throughput — you are sharding because 8.8 TB of hot data with its indexes does not fit comfortably on one machine, and because a table of 22 billion rows makes every maintenance operation, backup, and schema change a negotiation. Knowing which constraint is forcing your hand changes what a good shard key looks like.

Step 3: what workspace_id costs you, stated honestly

This is the part that gets skipped, so here it is with numbers attached.

  • One workspace can outgrow a shard. Workspace sizes follow a power law: the median workspace has a dozen people, and your largest customer has 200,000 seats generating 2 million messages a day. That's 800 MB/day, roughly 290 GB/year — survivable on storage, but it is 6.7% of all your writes on a single shard, when an even split across 16 shards would be 6.25%. Your biggest customer, by themselves, is already more than one average shard's entire load. And you cannot split them without a second-level key. So you need a plan before you need it: a directory-style mapping so whales can be pinned to dedicated shards, and a sub-sharding scheme (by channel_id, within the workspace) for the day one customer stops fitting. Hash-and-forget is not available to you.
  • Cross-workspace search becomes a fan-out. Any query that isn't scoped to one workspace — global admin search, "which workspaces use this integration", usage analytics, compliance export across an enterprise grid of 40 linked workspaces — now touches every shard and waits for the slowest one. The usual answer isn't to make that fast on the shards; it's to stop asking the shards. Push those into a dedicated search index or an analytics warehouse fed by change-data-capture, and let the sharded store answer only the workspace-scoped questions it's shaped for.
  • Rebalancing is now a real activity. Because the distribution is uneven and changes as customers grow, you will move logical shards between machines on purpose, periodically, forever. That's the trade for keeping the hot path single-shard, and it's the right trade — but it's a job someone owns, not a config value.
The rule underneath the arithmetic Pick the shard key that matches the boundary your product already draws around data. If almost every request is scoped to one workspace, one tenant, or one account, then that is your shard key — because it turns "distributed database" back into "a lot of small ordinary databases" for the 99% of queries that stay inside the boundary. Even distribution is a nice-to-have. Keeping the hot query on one shard is the requirement. Slack's own move onto Vitess used workspace as the dominant sharding key for exactly this reason.

9. Avoiding the query entirely

The cheapest query is the one you never run. Several techniques reduce database load without splitting it:

  • Caching — put Redis/Memcached in front of the DB so hot reads never reach it. Often the highest-leverage move before you shard, and the rung immediately before replicas — see the Caching guide.
  • Denormalization — store data pre-joined/pre-computed so reads are a single lookup, trading write complexity and some redundancy for read speed. Standard in NoSQL data modeling.
  • Materialized views — precompute an expensive aggregate/report and refresh it periodically, instead of recomputing per request.
  • CQRS (read models) — separate the write model from purpose-built read models (often kept fresh via events), so reads and writes scale independently. The event stream that keeps them fresh is a message queue.
  • Write buffering — put a queue between the request and the database so bursts are absorbed and writes arrive batched and steady instead of spiky. It converts a peak-throughput problem into a latency-budget problem, which is a much easier problem. Again: the Message Queues guide.

10. CAP & consistency: the trade-off underneath

The moment your data lives on more than one node, the CAP theorem applies: when a network partition splits your nodes, you must choose between Consistency (every read sees the latest write) and Availability (every request still gets an answer). You can't have both during a partition.

In practice this shows up as a spectrum you tune per workload:

  • Strong consistency — always read the latest value. Simplest to reason about; costs latency and availability. Right for money, inventory, auth.
  • Eventual consistency — reads may be briefly stale but the system stays fast and available. Right for feeds, counts, timelines — the same call you made with cache TTLs and replication lag.

Replication lag, quorum reads/writes, and "tunable consistency" in databases like Cassandra are all just knobs on this one dial. The Consistency & CAP guide takes this apart properly, including why "CP" and "AP" are less binary than the theorem makes them sound.

11. Distributed SQL & NoSQL: scaling as a built-in

Instead of bolting sharding onto a single-node database, you can adopt an engine designed to scale horizontally from the start:

Distributed / NewSQL

Spanner, CockroachDB, TiDB, YugabyteDB — SQL and transactions, but data auto-shards and replicates across nodes. You get horizontal scale without hand-rolling a shard router.

Sharding middleware

Vitess (born at YouTube for MySQL) and Citus (for Postgres) add sharding on top of engines you already know, transparently routing queries.

Wide-column NoSQL

Cassandra, ScyllaDB, DynamoDB, Bigtable — built for massive write throughput and horizontal scale, at the cost of flexible queries and (often) strong consistency.

The trade-off

These solve distribution for you, but impose their data model and consistency rules. You trade freedom and familiarity for scale that "just works."

12. The gotchas that bite later

None of these appear in the architecture diagram. All of them show up in the incident channel.

Connection pool sizing is Little's Law, not a vibe

Pool sizes get chosen by doubling until the errors stop. There is an actual formula, and it's the one queueing theory has been quietly holding out the whole time: concurrency = throughput × latency. If you serve 2,000 queries per second and the average query takes 4 ms, then 2,000 × 0.004 = 8 queries are in flight at any instant. Eight. A pool of 20 is comfortable headroom; a pool of 200 is 192 connections that will never be simultaneously useful.

And an oversized pool isn't merely wasteful, it's actively harmful. A database can only do so much genuine parallel work — bounded by cores, by disk queue depth, by lock contention on the hot rows. Beyond that point, extra concurrent queries don't get executed in parallel, they get interleaved: the same total work, sliced into more pieces, with context switches and cache-line thrash between the slices. In Postgres each connection is a separate OS process with its own memory; 200 of them on a 16-core box means the scheduler spends real time deciding who runs next. Throughput stays flat while every individual query gets slower, so your p99 climbs even though nothing about the workload changed. The widely used rule of thumb (from HikariCP) is (cores × 2) + effective_spindle_count — a folk formula, not physics, but it lands in the right order of magnitude, which is tens, not hundreds.

The part people miss: a small pool is a feature. When the pool is full, requests queue in your application, where you can see the queue, put a timeout on it, and shed load. When the pool is huge, the queue moves inside the database, where you can do none of those things.

Idle-in-transaction is a slow leak

A connection sitting in state idle in transaction has begun a transaction, read something, and then gone quiet — usually because the code made an HTTP call, or hit a breakpoint, or threw an exception on a path that forgot to roll back. It looks harmless in the connection list. It is not. That transaction holds a snapshot, and while it does, VACUUM cannot reclaim any row version that became dead after it started — not just in that table, anywhere in the database. So the dead tuples accumulate, the table and its indexes bloat, and every sequential scan against them now reads pages of garbage. Queries get slower with no code change and no traffic change, which makes it a genuinely awful thing to debug.

Long-running read-only transactions do the same thing, and so does a replica running a long analytical query with hot_standby_feedback on — that pins the primary's vacuum horizon from another machine. Defences: set idle_in_transaction_session_timeout and statement_timeout, never perform network I/O inside a transaction, and alert on pg_stat_activity rows where state = 'idle in transaction' and xact_start is older than a minute.

Online schema migration: ALTER TABLE is an outage waiting for a big enough table

On a small table, ALTER TABLE is instant and you learn nothing. On a hot 40-million-row table it can take an exclusive lock for minutes while it rewrites the file — and in Postgres the failure mode is worse than the wait. The lock request queues, and because it's an ACCESS EXCLUSIVE lock, every query that arrives after it queues behind it. So a migration that spends 30 seconds waiting politely for one slow SELECT to finish has blocked every read and write on that table for those 30 seconds. Your migration didn't need to run slowly to cause an outage; it only needed to wait.

What to do. Set a short lock_timeout on migrations and retry, so a blocked migration fails fast instead of building a queue behind it. Prefer the operations your engine has made cheap: modern Postgres adds a column with a constant default as a metadata-only change, MySQL 8 has ALGORITHM=INSTANT for some changes, and both support building indexes without blocking writes (CREATE INDEX CONCURRENTLY in Postgres, online DDL in InnoDB). Add constraints as NOT VALID and VALIDATE them separately. And for the genuinely heavy changes on MySQL, use the tools built for precisely this — gh-ost and pt-online-schema-change, both of which build a shadow copy of the table, keep it in sync while it fills, and swap it in with a brief atomic rename.

OFFSET pagination degrades linearly, and it is everywhere

This is the single most common cause of a slow endpoint in a maturing product, and it ships in every tutorial:

-- Page 5,000 at 20 per page.
SELECT * FROM messages
ORDER BY created_at DESC
LIMIT 20 OFFSET 100000;

OFFSET is not a seek. The database has to produce the first 100,000 rows in sorted order and throw every one of them away before it can return the 20 you asked for. Page 1 is instant, page 100 is fine, page 5,000 does 5,000× the work of page 1 for an identical-looking response. Nobody notices during development because nobody clicks to page 5,000 — and then a crawler does, repeatedly, in parallel.

Keyset (or "seek") pagination fixes it by remembering where you stopped instead of counting from the beginning:

-- Simple case: a monotonic id.
SELECT * FROM messages
WHERE  id > :last_seen_id
ORDER BY id
LIMIT  20;

-- Sorting by a non-unique column needs a tiebreaker for a total order.
SELECT * FROM messages
WHERE  (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT  20;

That's an index seek straight to the right position: constant cost regardless of depth, and it doesn't skip or duplicate rows when the underlying data changes mid-scroll, which OFFSET quietly does. The price is that you lose "jump to page 5,000" — you get next/previous, not random access. For infinite scroll, feeds, exports, and APIs, that's not a loss at all. For a UI that genuinely needs numbered pages, keep OFFSET but cap the depth.

Secondary indexes under sharding: pick your poison

Once data is sharded, "add an index on email" stops being a one-line decision, because there are two completely different things that sentence could mean.

  • Local index — each shard indexes only its own rows. Cheap, and consistent for free because the index update happens in the same transaction as the write. But it can only be searched shard by shard, so any lookup that isn't on the shard key becomes scatter-gather: 16 shards, 16 queries, latency equal to the slowest of the 16, and 16× the total cluster work for one user's login-by-email. It works fine until that query gets popular, at which point a single lookup pattern is consuming the whole cluster.
  • Global index — a separate structure keyed by the indexed column, mapping value → shard and primary key. One lookup, no fan-out. But it lives on different machines than the data it points at, which means every insert is now a distributed write. You get two options and no third: update the index asynchronously and accept that it's briefly wrong (so a just-created user isn't findable by email for a moment, and you now own that bug class), or run two-phase commit on every write and pay the latency plus a coordinator that can fail mid-commit. DynamoDB makes this trade in the open — global secondary indexes are eventually consistent by design, and local secondary indexes are strongly consistent but must share the partition key.

A global index is not a feature you enable. It is a distributed system you now operate.

Replication lag is not a constant

The mental model that causes the bugs is "replicas are about 50 ms behind." They aren't. Lag is near zero, and near zero, and near zero — and then it is eleven seconds. It spikes when a backfill or bulk delete floods the write-ahead log; when a long query on the replica blocks log replay; when a vacuum generates a burst of changes; during failover; and generally whenever write volume exceeds what the replica's apply process can keep up with, which is often more single-threaded than the primary's write path.

Combine those triggers and you get the defining property: lag is worst exactly when load is highest. Which means read-after-write bugs are invisible in development, invisible in staging, invisible in production at 4 AM — and appear for a fraction of users at peak, unreproducibly, in the exact window when you have the least attention to spare.

Two real fixes. The simple one is a sticky primary window: after a user writes, route that user's reads to the primary for a few seconds. Cheap to implement, costs a little primary capacity, and covers the overwhelming majority of cases. The precise one is a version token: capture the write's position in the log at commit time — an LSN from pg_current_wal_lsn(), or a GTID in MySQL — carry it in the session or a cookie, and have the read path either wait for the replica to reach that position (WAIT_FOR_EXECUTED_GTID_SET, or comparing against pg_last_wal_replay_lsn()) or fall back to the primary if it hasn't. One more operational note: monitor lag in bytes of log distance as well as seconds. "Seconds behind" reports a cheerful zero on an idle system and is a lagging indicator on a busy one.

The bills that arrive later

The decision to shard gets modelled as an engineering cost paid once. It is mostly a set of recurring costs paid by people who weren't in the room. None of these are hypothetical; all of them are boring.

  • Data transfer. Shards spread across availability zones for durability means cross-AZ traffic, which is billed per gigabyte, in a line item that grows with every fan-out query you add. Cross-region replication is the same charge, continuously, forever. A scatter-gather query is no longer just slow — it has a price per execution.
  • Backup and restore multiply by shard count. Sixteen shards is sixteen backup jobs, sixteen restore procedures, and a point-in-time recovery that has to be coordinated across all of them or you restore a cluster that's internally inconsistent. Your recovery time objective is now "the slowest shard's restore," and rehearsing it is a sixteen-fold exercise that nobody schedules.
  • Every schema migration becomes N migrations. And they can be half-applied: shard 7 has the new column, shard 8 doesn't, and your application must tolerate both states for as long as the rollout takes. That constraint never goes away — it changes how you write every migration from now on.
  • Resharding is a project, not a task. Going from 16 shards to 32 needs a plan, a backfill, a dual-write period, a cutover, and a rollback story. Weeks, with a named owner. Logical shards make it a data move rather than a rewrite — they do not make it free.
  • Cross-shard transactions are either unavailable or a trap. Where two-phase commit exists it's slow and it introduces a coordinator whose failure mid-commit leaves locks held on multiple machines. So in practice you design around it: sagas, idempotency keys, compensating actions, reconciliation jobs. That is permanent application complexity you now maintain, and it's the real reason the shard key matters so much — see Consistency & CAP for what you're actually buying, and the Reliability toolkit for the retry and timeout machinery you'll need around it.
  • On-call surface. One database with a replica is two things that can page you. Sixteen shards with replicas is thirty-two, each with its own failover, its own disk, and its own capacity to be the one that's different.

13. Real-world examples

How real teams actually climbed this ladder — including where they stopped.

Figma — vertical partitioning, then in-house sharding

Figma ran a single Postgres instance on AWS's largest box in 2020. They first scaled by vertical partitioning — splitting tables like "Files" and "Organizations" onto separate databases — reaching about a dozen databases with replicas and caching by late 2022. But some tables hit terabytes and billions of rows, bumping into RDS IOPS limits and Postgres vacuum problems that partitioning couldn't fix. So they built horizontal sharding in-house: multiple shard keys (UserID, FileID, OrgID) rather than one, hashed for even distribution, with "colos" grouping related tables so joins stay within a shard — and a routing service, DBProxy. They deliberately chose this over CockroachDB or Vitess to stay on their known Postgres. First table sharded in September 2023 with ~10 seconds of partial impact. (Figma Engineering)

Discord — MongoDB → Cassandra → ScyllaDB

Discord outgrew MongoDB and moved to Cassandra in 2017, partitioning messages by channel_id plus a time bucket. By early 2022 it was trillions of messages across 177 nodes — and struggling: popular channels became hot partitions, and Java garbage-collection pauses caused latency spikes and heavy on-call toil. They migrated to ScyllaDB (a C++ reimplementation of Cassandra) and added a Rust data-services layer that coalesces concurrent requests for the same hot channel — the exact request-coalescing trick from the Caching guide, at the database tier. Result: 177 nodes down to 72, and p99 message reads from 40–125 ms to ~15 ms. (Discord Engineering)

Instagram — thousands of logical shards on few machines

Instagram sharded Postgres early by creating thousands of logical shards mapped onto a smaller number of physical servers, and encoded the shard ID directly inside their 64-bit primary keys. Growing capacity meant moving logical shards to new hardware — no re-hashing. It's the textbook logical-vs-physical split from section 7.

The pattern across all three Every team climbed the ladder in order — one box, then partitioning/replicas, then sharding — and only sharded when size or write load genuinely forced it. None reached for the most complex tool first. That restraint is the strategy.

14. The scaling ladder — where to start

Climb in order. Stop the moment your load is handled; most systems never reach the top.

1

Index & tune queries

Fix the slow queries first. Often the only step you need.

↓ still slow?
2

Scale up + pool connections

Bigger box, connection pooler. Cheap, zero code change.

↓ read-bound?
3

Add caching

Keep hot reads off the DB entirely. Highest leverage per unit of effort.

↓ still read-bound?
4

Add read replicas

Scale reads out; mind replication lag for fresh-read paths.

↓ write- or size-bound?
5

Partition, then shard

Split the data — vertically first, then horizontally across machines. Or adopt a distributed database that does it for you.

The best database architecture is the simplest one that meets your load and freshness needs. Add a rung only when the metrics — query latency, replica lag, CPU/IOPS saturation, write throughput — actually demand it.

15. Recap in 60 seconds

  • Rung 0 — Measure. Read/write mix from the engine's own counters, which p99 moved, rows examined per row returned. Climb only on evidence; the answer decides everything after this.
  • Rung 1 — Index and fix queries. Most "slow database" is one missing or unusable index. Climb when EXPLAIN shows an index scan and it's still not fast enough.
  • Rung 2 — Scale up, and right-size the pool. More RAM fixes a falling cache hit ratio outright; the pool should be tens, not hundreds. Climb when you're near the largest sensible instance or its IOPS ceiling.
  • Rung 3 — Cache. The cheapest query is the one you never send. Climb when the hit rate is already high and the remaining reads still saturate the box.
  • Rung 4 — Read replicas. Scales reads, gives you a failover target, hands you replication lag and read-your-writes bugs in exchange. Climb when the bottleneck moves to the write path — replicas cannot help there, they add to it.
  • Rung 5 — Partition, then shard. On the write side, batch first (a queue in front turns spiky writes into steady ones), then partition for size and maintenance, then shard for genuine write and storage multiplication. Climb only when one machine cannot hold the data or absorb the writes — and shard on the boundary your product already draws around data.
  • The costs are permanent, not one-off. N shards means N backups, N migrations, resharding as a project, cross-shard transactions you design around forever, and a data-transfer line item that grows with every fan-out query.

16. Check yourself

If you can answer these without scrolling up, you have the guide.

Reads are slow. You add three read replicas. Nothing improves. What did you get wrong?
Almost certainly the diagnosis. A replica runs the same schema and the same query plan as the primary, so if the query is doing a sequential scan over 40 million rows, you have just bought three more machines to do that badly in parallel. Replicas add read capacity; they do nothing about work per query. Check rows examined per row returned before you check anything else. The other common answer is duller: the reads never moved. Traffic still goes to the primary because nothing routes it, or the queries sit inside transactions, which most routers pin to the primary by default.
You shard by user_id. One customer's shared service account generates most of their API traffic and melts the shard it lands on. What should you have done?
Hashing distributes keys evenly, not load per key — a single hot key always lands on exactly one shard no matter how good your hash is, so no hashing scheme was ever going to save you here. Hot keys need their own mechanism: a directory-style mapping so that key can be pinned to a dedicated shard, a second-level key to split it, or request coalescing and caching in front so the shard sees one query instead of a thousand. And there's a second mistake underneath: in a tenant-scoped product, user_id scatters each customer's data across every shard, so all your tenant-scoped queries were already fanning out. The tenant boundary was the shard key.
Your p99 doubled after you raised the connection pool from 20 to 200. Throughput didn't change. Why?
Because 20 was already more than enough, and 200 doesn't create parallelism the database can use. Concurrency = throughput × latency, so 2,000 queries/second at 4 ms each is only 8 queries genuinely in flight. Past the point where the database can execute work in parallel — bounded by cores, disk queue depth, and lock contention — extra connections just interleave the same work into more slices, adding context switches and (in Postgres, where each connection is a process) real scheduler overhead. Total throughput stays flat while every individual query takes longer, which is exactly the shape of a p99 that doubles for no visible reason. The bigger loss is that the queue moved from your application, where you can time it out and shed it, into the database, where you can't.
A read-your-writes bug affects about 2% of users, only at peak, and has never once reproduced in staging. Where do you look?
Replication lag, and the reason it hides is that lag isn't a constant — it's near zero until it spikes, and it spikes under exactly the conditions you can't recreate: heavy write volume, a backfill flooding the log, a long analytical query on the replica blocking replay. Staging has no load, so staging has no lag, so staging has no bug. Fix it structurally rather than by chasing it: give each user a sticky window that routes their reads to the primary for a few seconds after they write, or carry a version token (a Postgres LSN, a MySQL GTID) captured at commit and make the read path wait for the replica to reach it or fall back to the primary.
A migration adding one nullable column ran in 200 ms in staging and made the table unavailable for 30 seconds in production. The migration itself wasn't slow. What happened?
The migration spent 30 seconds waiting, not working. It requested an exclusive lock, a long-running query was already holding a conflicting one, and while the migration sat in the lock queue every subsequent query on that table queued behind it — because a pending exclusive lock blocks the readers arriving after it, not just the migration. So one slow report plus one polite ALTER TABLE equals a table-wide stall. The defence is a short lock_timeout on migrations with retry, so a blocked migration fails immediately instead of building a queue, plus using the non-blocking variants (concurrent index builds, NOT VALID constraints validated separately) or a shadow-table tool like gh-ost for the heavy changes.
One customer's list endpoint has been getting steadily slower for six months. No deploys, no schema changes, and it's fast for everyone else. What's your first guess?
They have the most rows, and something in that endpoint costs more as their row count grows — most often OFFSET pagination, where page depth makes the database produce and discard everything before the page you want, so the customer with ten times the data pays ten times the cost on the same click. Keyset pagination makes it flat. If it isn't pagination, the same shape shows up as an unbounded query whose result set grows with the tenant, or an index that stopped being selective for them specifically. The general lesson: in a multi-tenant system, "slow for one customer" is usually not a customer-specific bug, it's your largest tenant arriving at a limit ahead of everyone else — and telling you where the whole product will be in a year.
The one-liner to remember Every rung of this ladder trades a simple problem for a harder one, so make each rung earn its place with a measurement. In practice, most "we need to shard" turns out to be one missing index, one unbounded query, and a connection pool sized by superstition.
