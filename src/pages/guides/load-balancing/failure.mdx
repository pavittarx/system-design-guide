<h3 id="draining">Connection draining, or: why every deploy has an error spike</h3>

You remove an instance — a rolling deploy, a scale-in, a health check that flipped. The naive implementation cuts it out of rotation and stops the process. Every request that was *already in flight* on that box dies mid-sentence. The client gets a reset or a 502, and because a rolling deploy does this to each instance in turn, the spike is proportional to your fleet size and it happens on every single release. Teams live with this for years and call it "deploy noise."

The correct sequence has three steps, in order. The instance starts **failing its readiness check** (or is explicitly marked draining), so the load balancer stops sending it *new* requests. It keeps serving the connections it already has. Only when those finish — or a **drain timeout** expires — does the process exit.

The knob has a different name everywhere: *deregistration delay* on an AWS target group (default 300s), *drain timeout* in HAProxy and Envoy, `terminationGracePeriodSeconds` plus a `preStop` hook in Kubernetes. Set it longer than your slowest normal request and shorter than your patience for a deploy. And note the ordering trap: the pod must fail readiness *before* it gets SIGTERM, or the load balancer is still sending it traffic while it's shutting down — which is the same error spike with more steps.

<h3 id="liveness-readiness">Liveness and readiness are different questions</h3>

Liveness asks: *should I be restarted?* Readiness asks: *should I get traffic right now?* These are not the same question and wiring them to the same handler produces two distinct outages.

Conflate them one way and an instance that is merely **warming up** — filling a connection pool, loading a model, JIT-compiling — gets killed by the liveness probe before it ever serves a request. Deploy, crash-loop, repeat. Conflate them the other way and a **saturated** instance keeps receiving requests because the process is technically alive, which is exactly the failure the cascade below is built on.

A readiness handler that returns a static `200` from a constant string tells you the process is running and the port is open. That's it. It cannot tell you whether a request would succeed, because it doesn't do anything a request does. A useful readiness check touches what the request path touches: can I take a connection from the pool, is config loaded, is the cache client connected, is my in-flight count below the line where I stop being useful.

<Note type="warn" label="…but not too deep">

If every instance's readiness check queries the same database, and that database has a bad ten seconds, every instance fails readiness at the same moment and the load balancer has nothing left to send traffic to. A shared dependency turns a dependency blip into a total outage. Check the dependency, cache the result for a few seconds so you're not hammering it, and don't fail readiness for anything you can serve degraded.

</Note>

<h3 id="fail-open">Fail-open and the panic threshold</h3>

If health checks are the only thing standing between you and an outage, then a bug in the health check *is* an outage. A config push that changes the health path. A certificate that expires on the health port. A probe timeout tuned for an idle box, now being evaluated on a busy one. Any of these can mark one hundred percent of your fleet unhealthy inside a single check interval, and a strictly correct load balancer will then dutifully send traffic to nobody.

Real proxies refuse to be that correct. Envoy has a **panic threshold**, default 50%: once fewer than half the hosts in a cluster are healthy, it stops honouring health status and load balances across *all* hosts, sick ones included. The reasoning is blunt and right — if most of your fleet appears dead, the likelier explanation is that your health checking is broken, and a degraded backend beats no backend.

Whatever proxy you run, find out what it does when zero hosts are healthy, and find out before the day it matters.

<h3 id="slow-start">Slow start: don't hand a cold instance the firehose</h3>

A freshly added instance has empty caches, empty connection pools, and a JIT that hasn't compiled anything hot. It is the slowest machine in your fleet and it is also, to a least-connections balancer, the emptiest one. So the balancer points the firehose at it. It falls over, fails its health check, restarts, comes back cold, and does it again — a loop you can watch on a graph for hours.

The fix is **slow start**: ramp the new instance's share from near-zero to full over a window — thirty seconds to a couple of minutes is the usual range. Nginx Plus, Envoy, and AWS ALB target groups all have a setting for it. The complementary fix is on the instance itself: warm your caches and pools *before* you report ready. Readiness is a promise. Don't make it early.

<h3 id="keepalive-l4">Keepalive and HTTP/2 quietly defeat L4 round robin</h3>

An L4 balancer distributes *connections*, not requests. It makes one decision, at connection setup, and every byte on that connection goes to the same backend for as long as it lives.

With HTTP/1.1 keepalive that's already thousands of requests riding a single decision. With **HTTP/2 or gRPC** it's far worse: one connection multiplexes many concurrent streams, so a client that connected at 03:00 keeps hammering the one backend it was assigned, indefinitely. Add capacity and the new instance gets nothing at all — nobody is opening new connections, so there is nothing to balance.

The tell is a dashboard that lies to you in a very specific way: connections per backend are beautifully even, and CPU is 90% on one box and 8% on the others.

Three fixes, roughly in order of preference. Balance at **L7**, so the decision is made per request (or per HTTP/2 stream) rather than per connection. Set a **maximum connection age or max requests per connection**, so clients are periodically forced to reconnect and get re-balanced. Or move the decision to the client — a service mesh sidecar or a client-side balancer that knows about streams.

<h3 id="client-ip">The client's IP disappears at L7</h3>

Once an L7 proxy terminates the client connection, your backend's socket shows the *proxy's* address. Every access log, every rate limit, every geo-block is now pointed at your own load balancer. The standard fix is `X-Forwarded-For`: the proxy appends the client's address to the header as the request passes through.

Now the trap. `X-Forwarded-For` is a header, and headers are whatever the sender says they are. If you read it naively on a request that arrived from the internet, anyone can send `X-Forwarded-For: 203.0.113.9` and your rate limiter, your geo-block, and your audit log all believe them — which is to say your rate limiting is now optional.

Your edge proxy must overwrite or normalise the header, and everything behind it must count from the trusted end and trust only the number of hops you actually operate. Nginx expresses this as `set_real_ip_from` plus `real_ip_recursive`; Envoy as `xff_num_trusted_hops`. Get the hop count wrong and you are trusting an attacker-supplied value again, just with more configuration.

At L4 the equivalent is the **PROXY protocol**: the balancer prepends a small fixed header to the TCP stream carrying the original source and destination addresses, before any application bytes. Because it sits underneath the application protocol it works for anything — SMTP, Postgres, raw TCP — but the backend must be configured to expect it, and must accept it *only* from the proxy, for exactly the same spoofing reason.

<h3 id="retry-amplification">Retry amplification</h3>

Retries are individually reasonable and collectively catastrophic. The mobile SDK retries. The CDN retries. The API gateway retries. The service client retries. The database driver retries. Three layers that each make three attempts is 3³ = **27 requests for one user action** — and they arrive during precisely the window when the system is already failing, which is when a 27× multiplier is least survivable.

They're also *correlated*. Everyone's timeout fires at roughly the same moment, so the retries land as a synchronised wave rather than a smear. That's a retry storm, and it is how a five-second dependency blip becomes a twenty-minute outage.

Three fixes, and you want all of them. **Retry at exactly one layer** and make every other layer fail fast — pick the layer with the most context, usually the one closest to the caller who can actually do something about it.

Put a **retry budget** on that layer: cap retries as a fraction of successful traffic, so a total outage multiplies load by nothing at all rather than by three (Envoy's default budget is 20% of active requests; Finagle popularised the idea). And add **jitter** to your backoff so the wave spreads out instead of arriving as a spike. The full treatment — circuit breakers, budgets, shedding — is in [the Reliability guide](/guides/reliability-toolkit/).

<h3 id="p2c">Least connections doesn't scale — use the power of two choices</h3>

True least-connections needs to know every backend's current load at the instant of the decision. That's easy with one load balancer and impossible with a tier of them: each has only its own view, and if they all independently spot the same emptiest server, they all stampede it simultaneously. It's the same mechanism that makes least-connections dogpile a just-restarted instance, only now with a multiplier.

**Power of two random choices** is the fix, and it is almost insultingly simple: pick two backends uniformly at random, compare only those two, send the request to whichever has fewer outstanding requests. No global state, no coordination, no single "best" server for everyone to converge on.

The theoretical result (Azar, Broder, Karlin and Upfal, 1994) is that this is not a small improvement over pure random — it's an exponential one. Throwing *n* requests at *n* servers uniformly at random leaves the worst-loaded server with roughly log *n* / log log *n* of them; sampling two and taking the lighter drops that to roughly log log *n*. A second sample buys you most of the distance to perfect balance. A third buys almost nothing.

This is what large systems actually run: Nginx (`random two least_conn`), HAProxy (`balance random`), Envoy (its `LEAST_REQUEST` policy samples two hosts by default), and most client-side balancers in a service mesh. If you're picking an algorithm and you don't have a specific reason for something else, pick this one.

<h3 id="death-spiral">The capacity death spiral</h3>

Ten instances, each at 70% CPU. One dies. The other nine now carry its share and sit at 78%. Latency rises; requests queue; queued requests hold memory, connections, and thread slots, so the next instance saturates and drops out too. Now eight are at 87%. Then seven, at 100% — and there is no seven-instance configuration that serves this traffic.

Every removal makes the next removal more likely, and sooner. The load balancer's failover, which is genuinely the right behaviour when one box dies in a healthy fleet, becomes the transmission mechanism.

Autoscaling cannot save you here and it's worth being precise about why. A scale-up needs a metric window (tens of seconds), then an instance boot, then application start, then cache warm, then enough consecutive passing health checks to be added. Minutes, at best. The collapse runs in seconds. By the time the new capacity is ready there's nothing left to relieve.

The only thing that operates on the right timescale is **refusing work**. Load shedding: when the queue is longer than you can serve inside your latency budget, return `503` to the excess immediately rather than accepting everything and serving none of it. Per-instance concurrency limits: a hard cap on in-flight requests, so an instance degrades predictably instead of falling over. Both trade visible errors for a surviving fleet, which is a trade people resist right up until the first time they watch the alternative. Details in [the Reliability guide](/guides/reliability-toolkit/).

<Collapse id="cascade" title="2. Anatomy of a cascade: 03:14 to 03:19">

Back to the launch that worked too well. Here is what actually happened between the moment the graph went vertical and the moment it came back — every step of it a mechanism from the sections above. Six instances, round robin, health check every 10 seconds with an unhealthy threshold of 3. Each instance tops out around 2,800 requests per second.

```trace
**03:14:02**  6 instances · round robin · all green
          offered 12,400 rps · p99 240ms · cpu 74%

**03:14:38**  web-03 heap 91%, GC pausing every 400ms
          web-03 p99: 240ms -> 2.1s
          GET /health -> 200 OK in 3ms
          (the handler returns a constant. it always will.)

**03:15:05**  ~~LB still sends web-03 exactly 1/6 of traffic~~
          round robin counts requests, not seconds
          web-03 in-flight: 41 -> 900

**03:15:31**  clients hit the 3s timeout. clients retry.
          ~~offered 12,400 -> 15,100 rps~~
          demand did not change. the retries did.
          the five healthy boxes: 2,517 rps each, 90% cpu

**03:16:12**  web-03's health check finally times out
          strike 1 of 3 · 10s interval

**03:16:32**  ~~strike 3 · web-03 removed from the pool~~
          900 in-flight requests killed, not drained
          the edge hands every one of them a 502

**03:16:33**  web-03's share redistributes to 5 survivors
          15,100 / 5 = 3,020 rps each
          ~~each can serve 2,800. that is 108% of capacity.~~
          ~~the removal that was supposed to help~~
          ~~is now the thing making it worse~~

**03:17:04**  web-05 queue passes its latency budget
          p99 4.8s · clients time out · clients retry
          ~~offered 15,100 -> 18,600 rps~~

**03:17:58**  ~~web-05 removed · 4 instances left~~
          capacity 11,200 rps. arriving: 18,600 rps.
          there is no 4-instance answer to this

**03:18:10**  autoscaler fires · +6 requested
          boot, app start, cache warm, 3 passing checks
          ~~eta ~4 minutes. the collapse took 86 seconds.~~

**03:18:24**  ++concurrency limit engaged++
          ++750 in-flight per instance, hard cap++
          past the cap: 503 in 2ms, no queue slot

**03:18:25**  ~~40% of requests get an immediate 503~~
          ++60% get a real answer in 270ms++
          queues drain · heaps stop climbing

**03:18:52**  ++clients stop timing out, so they stop retrying++
          ++offered 18,600 -> 12,600 rps++
          most of the "traffic spike" was our own echo
          still shedding ~11%. no longer collapsing.

**03:19:05**  ++web-03 and web-05 back · warm before ready++
          readiness now fails at heap > 85% or in-flight > 600
          slow start: 0 -> full share over 30s

**03:19:41**  ++6 healthy · 12,400 rps · p99 250ms · shedding off++
          the +6 instances land at 03:22 and are scaled
          back down at 03:41. they were never the fix.
```

<h3 id="cascade-mechanisms">What you just watched</h3>

Nine minutes, and almost none of it was a capacity problem. Naming the parts:

- **03:14:38 — a health check that measured the wrong thing.** web-03 was answering `/health` in 3ms while answering real requests in 2.1 seconds, because the health handler returns a constant and a constant is always fast. See [health checks](/guides/load-balancing/health/#health) and [liveness vs readiness](#liveness-readiness).

- **03:15:05 — round robin is blind to work.** It counts requests handed out, not time spent. A backend taking 2.1 seconds per request receives exactly as many as one taking 20ms. Least-connections or [power of two choices](#p2c) would have starved web-03 automatically, because its in-flight count was screaming. See [the algorithms](/guides/load-balancing/layers/#algos).

- **03:15:31 and 03:17:04 — retry amplification.** Offered load went from 12,400 to 18,600 rps without one extra user showing up. Half the "spike" was the system talking to itself. See [retry amplification](#retry-amplification).

- **03:16:32 — no connection draining.** 900 in-flight requests were terminated at the instant of removal instead of being allowed to finish. Every one became a visible 502. See [connection draining](#draining).

- **03:16:33 to 03:17:58 — the death spiral.** Removing the sick instance moved its traffic onto five survivors who were already at 90%. Failover is correct behaviour in a healthy fleet and a detonator in a saturated one. See [the capacity death spiral](#death-spiral).

- **03:18:10 — autoscaling on the wrong timescale.** Four minutes of provisioning against an 86-second collapse. It arrived after the incident was over and cost money for a day. See [autoscaling](/guides/load-balancing/health/#auto).

- **03:18:24 — what actually stopped it.** A concurrency cap and load shedding, both of which act in milliseconds because they are just refusals. The instant clients stopped timing out, they stopped retrying, and the offered load fell by a third on its own. See [shedding](#death-spiral) and [the Reliability guide](/guides/reliability-toolkit/).

- **03:19:05 — the two changes that make it not happen again.** A readiness check that fails while the instance is *degrading* rather than after it's unusable, so the balancer stops feeding a box that can't keep up; and [slow start](#slow-start), so a cold instance isn't handed a full share the second it comes back.

<Note type="key" label="The uncomfortable part">

Every single default in that timeline was a reasonable default. Round robin, a fast health endpoint, remove-on-unhealthy, retry-on-failure, scale-up-on-CPU. Nothing was misconfigured in the sense of being obviously wrong. Cascades are what reasonable defaults do when they compose.

</Note>
