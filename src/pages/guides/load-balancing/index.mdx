<ColdOpen tag="◇ 3:00 AM · the launch that worked too well">

Your product hits the front page. Traffic 40×'s in ten minutes. Somewhere, a single server — the one you've been meaning to "clean up later" — glows red-hot, accepts one connection too many, and quietly dies. Every user gets a spinning wheel. The tragedy isn't that you had too many visitors. It's that you had exactly one server to greet them, and nobody was standing at the door directing traffic. That doorman is a load balancer, and this guide is about hiring one.

</ColdOpen>

<Collapse id="why" title="1. Why one server isn't enough">

A single server has a ceiling: finite CPU, memory, and network. You can buy a bigger one (*vertical scaling*), but that ladder runs out — and a single anything is a single point of failure. The moment it reboots, your whole product is offline.

The alternative is **horizontal scaling**: run many identical servers and split the work between them. It scales almost linearly and survives individual deaths. But it raises one immediate question — when a request arrives, *which* server should handle it? Answering that, well and instantly, millions of times a second, is the entire job of a load balancer.

</Collapse>

<Collapse id="what" title="2. The load balancer, explained">

<Note type="wild" label="◈ In the wild · Anycast + DNS at the Edge">

Before a request even reaches a traditional load balancer, providers like Cloudflare announce the *same* IP address from data centers worldwide (anycast), so the network itself routes you to the nearest physical location. Load balancing starts at the level of the internet's routing tables.

</Note>

A load balancer sits in front of your fleet of servers. Clients connect to *it*; it picks a healthy server and forwards the request. To the outside world there's one address; behind it, a crowd. Think of a restaurant host: diners don't wander in and fight over tables — the host seats them, keeps things even, and quietly skips the table with a broken chair.

Because that one address is now itself a single point of failure, real deployments run the load balancer *redundantly* too (multiple LBs, DNS-level distribution, or a cloud service that handles this for you). Turtles, but only a couple deep.
