<ColdOpen tag="◇ 3:00 AM · the launch that worked too well">

Your product hits the front page and traffic jumps 40× in ten minutes. All of it lands on one server, the one you've been meaning to "clean up later". It runs out of CPU, accepts one connection too many, and dies. Every visitor gets a spinning wheel.

Too many visitors wasn't the problem. The problem was that you had exactly one server to greet them, and nobody at the door sending people somewhere else. That doorman is a load balancer, and this guide is about hiring one.

</ColdOpen>

<Collapse id="why" title="1. Why one server stops being enough">

Every server has a ceiling: so much CPU, so much memory, so much network. When you hit it, the first instinct is to buy a bigger machine. This is called **vertical scaling**, and it works until there's no bigger machine to buy.

It also leaves a worse problem in place. With one server, every reboot, crash or bad deploy takes your whole product offline. A part whose failure takes everything down with it is called a **single point of failure**.

The other way out is to run many identical copies of your app and split the traffic between them. This is called **horizontal scaling**. Capacity grows roughly in step with the number of servers, and one server dying just means the others carry a bit more.

It raises one question straight away: when a request arrives, *which* copy should handle it? Answering that correctly and instantly, for every request, is the whole job of a load balancer.

</Collapse>

<Collapse id="what" title="2. One address, many servers: what a load balancer does">

Your users type one address. Behind it you now have ten servers. Something has to stand between the two, accept each request and pass it to one of the ten, and it has to skip any server that has just died.

That something is the **load balancer**. Clients connect to *it*; it picks a healthy server and forwards the request. The servers behind it are called **backends**, and the group of them is the **pool**. To the outside world there is one address; behind it, a crowd.

Think of a restaurant host. Diners don't wander in and fight over tables. The host seats them, keeps the sections evenly busy, and quietly skips the table with the broken chair.

You've moved the single point of failure, not removed it: if the load balancer dies, so does the one address. So real deployments run the load balancer redundantly too: several of them, spread with DNS, or a cloud service that handles this for you. Turtles, but only a couple deep.

<Note type="wild" label="◈ In the wild · Anycast at the edge">

Balancing can start before a request reaches any load balancer. Providers like Cloudflare announce the *same* IP address from data centres worldwide, so the internet's own routing sends you to the nearest one. This is called **anycast**: load balancing done by the internet's routing tables.

</Note>
