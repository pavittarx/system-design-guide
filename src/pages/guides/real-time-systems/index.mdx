<ColdOpen tag="◇ Discord, 2017">

Every user connected to Discord has a small process on a server that holds their session. When it connects, it asks which machine owns each of the user's communities; the average user is in five. Each question took about 12 microseconds, all answered by one process. Nothing, until bursts of users reconnected: that process fell behind and the whole system overloaded. A restart of one machine holding 500,000 sessions meant about 30 seconds of questions.

Discord cut those 30 seconds to 750 ms, and the pile-up moved one hop down. Nearly 5,000,000 sessions hammered ten registry processes, timed out, retried after a backoff and piled up again, until servers ran out of memory and the outage cascaded. Normal traffic never looks like that. In a system that holds connections, **the reconnect is the load test**: every client at once, at the worst possible moment. ([Discord](https://discord.com/blog/how-discord-scaled-elixir-to-5-000-000-concurrent-users))

</ColdOpen>

<Collapse id="inversion" title="1. What changes when the server speaks first">

You want a live unread count in the corner of your app. Today the browser asks, the server answers, and the server forgets the browser exists. Now the server has to tell the browser "you have a new message" at a moment the browser didn't choose. To do that, it needs a line that stays open.

Everything in this series so far assumed the first shape: ask, answer, forget. That forgetting is what made the earlier guides work. It's why you can put ten identical servers behind a load balancer and send each request to whichever is least busy. It's why a server can be killed mid-deploy and nobody notices. It's why capacity is just requests per second.

Holding a connection open gives that up. A server that remembers who is connected to it is called **stateful**, and the moment yours becomes stateful, three things break at once.

<CardGrid>
  <Card pill="Servers become stateful" tone="bad">
    Connection X lives on server 7. Not "any server": server 7 specifically. Deploys, scaling and failures now move connections, not just requests.
  </Card>
  <Card pill="Capacity has two dimensions" tone="bad">
    Requests per second no longer sizes you on its own. You are also sized by *concurrent connections*, which use memory whether or not they are doing anything.
  </Card>
  <Card pill="Messages need addressing" tone="bad">
    An event happens on server 3 for a user connected to server 7. Something must know where that user is and get the message there.
  </Card>
</CardGrid>

None of that is a reason to avoid real-time. It's a reason to be honest that you're building a different kind of system, with a different capacity model and different failures, and to notice when a feature request drags you across that line. "Can we show a live unread count?" is a small product ask and a large architectural one.

</Collapse>

<Collapse id="options" title="2. Four ways to get news to the browser">

Say the browser wants to know the moment an order ships. There are four common ways to do it. They form a ladder: each rung delivers faster and adds more of the new problems above.

<Stack>
  <Layer idx="1">**Short polling.** The browser asks "anything new?" every *n* seconds. Dead simple, works everywhere, and caches and load-balances like any other request. On average news waits *n*/2 seconds, and most requests come back empty.</Layer>
  <Layer idx="2">**Long polling.** The browser asks, and the server *holds the request open* until it has something to say, or until a timeout (typically 30 s), after which the browser asks again. News arrives almost instantly over plain HTTP. But you're holding a connection per client anyway, so you pay most of the cost of WebSockets plus extra overhead on every message.</Layer>
  <Layer idx="3">**Server-Sent Events (SSE).** One HTTP response that never ends: the server keeps writing events into it. Server to client only, and text only. The browser's built-in `EventSource` reconnects by itself and tells the server the last event it saw, which is a bigger deal than it sounds.</Layer>
  <Layer idx="4">**WebSockets.** An ordinary HTTP request asks to *upgrade*, and the connection turns into a two-way channel that can carry text or binary in both directions. Maximum power, and you now own reconnection, heartbeats, message framing and slow clients yourself.</Layer>
</Stack>

### What polling really costs: 10,000 users

Put numbers on it. 10,000 users sit on a page that changes about once a minute per user.

<Note type="key" label="Short polling vs push, 10,000 users">

Polling every 5 s: **2,000 requests a second**, each carrying full HTTP headers and cookies (~800 bytes) plus a response. That's roughly **1.6 MB/s of pure overhead**. Each user asks 12 times a minute and has news once, so **11 requests in 12 come back empty**. Average wait for news: 2.5 s.

SSE or WebSocket: 10,000 idle connections, a heartbeat every 30 s, and one small message, with a few bytes of framing, at the instant something happens. Wait: **milliseconds**. Bandwidth when idle: nearly zero.

</Note>

That's why the ladder exists. But look at what each side pays with. Polling wastes bandwidth and adds delay, which are cheap and easy to measure. Push costs *state*: memory held per user, and connections you must route, drain and recover. That cost shows up as operational pain rather than as a line on a graph.

<Collapse id="choose" title="3. Picking one by asking who talks">

You're adding a notification bell. The team says "it's real-time, so WebSockets". Stop and ask a narrower question: **does the browser need to send a stream too, or just receive one?**

For a notification bell, a live dashboard, a build log, a price ticker or a streaming LLM response, the browser only receives. Its occasional actions, like "mark as read", can be ordinary HTTP POSTs. That's exactly what SSE is for, and it's the most under-used option on the ladder.

Why SSE fits so well: it's plain HTTP, so it passes through proxies and your existing infrastructure unchanged. And it gives you reconnect-and-resume for free. Every event can carry an `id:`, and when the connection drops, the browser reconnects and sends the last one it saw in a `Last-Event-ID` header, so the server can send what was missed.

<Note type="warn" label="The SSE gotcha worth knowing up front">

Over HTTP/1.1, browsers allow only **six connections per origin**, and each SSE stream holds one open forever. Open the app in six tabs and they use all six; a seventh tab hangs, and so does every ordinary request to that origin.

Over HTTP/2, many streams share one connection and the limit effectively disappears. If you use SSE, use HTTP/2 end to end, and check that your load balancer isn't quietly falling back to HTTP/1.1.

</Note>

Choose WebSockets when the browser genuinely streams too: chat with typing indicators, collaborative editing with live cursors, multiplayer games, live drawing. Choose polling when updates are rare and a few seconds of staleness costs nothing. A five-second poll on a page one person has open is not a design failure; it's a good use of a boring tool.

Here's the whole ladder side by side:

<Table numeric>

| | Short poll | Long poll | SSE | WebSocket |
| --- | ---------- | --------- | --- | --------- |
| Direction | Client pull | Client pull | Server → client | Both ways |
| Protocol | HTTP | HTTP | HTTP | Upgraded from HTTP |
| Auto-reconnect | N/A | Manual | **Built in** | You write it |
| Binary payloads | Yes | Yes | No (text/base64) | Yes |
| Proxy/CDN friendliness | Excellent | Fair | Good | Needs config |
| What the server holds | Nothing | A waiting request | An open response | A full connection |
| Best for | Rare, tolerant updates | Legacy fallback | Feeds, notifications, progress | Chat, games, collaboration |

</Table>

<Note type="key" label="What to remember">

- Push means the server must remember who is connected, and where. That one change breaks stateless scaling, deploys and capacity planning.
- Pick by direction: if only the server streams, use SSE; if both sides stream, use WebSockets; if updates are rare, polling is fine.
- Plan for the reconnect. It's the busiest moment your system will have, and it comes from every client at once.

</Note>

<Lab
  title="Build a Real-Time SSE Stream with Heartbeats & Gap Recovery"
  tip="Include this SSE project in your portfolio to show hands-on mastery of lightweight push protocols and gap-tolerant stream design."
>

Build this portfolio project to implement a production-ready, low-overhead Server-Sent Events stream:

- **The Server:** Write an API server in Node.js or Python. Create a `GET /events` route.

- **Configure SSE Headers:** Set the required headers to keep the browser socket open and disable proxies buffering output:

  ```javascript
  res.writeHead(200, {
    'Content-Type': 'text/event-stream',
    'Cache-Control': 'no-cache',
    'Connection': 'keep-alive',
    'X-Accel-Buffering': 'no' // Prevent Nginx buffering
  });
  ```

- **Heartbeats & Resync:** Read the incoming header `Last-Event-ID` (if present). Keep a short rolling memory buffer of recent events. If the client sends an ID, replay missed items. Otherwise, send heartbeats every 15s to keep the socket alive:

  ```javascript
  // Send a comment frame to keep the socket warm
  const heartbeatInterval = setInterval(() => {
    res.write(': keepalive\n\n');
  }, 15000);

  // Sending an event frame
  function sendEvent(id, name, data) {
    res.write(`id: ${id}\n`);
    res.write(`event: ${name}\n`);
    res.write(`data: ${JSON.stringify(data)}\n\n`);
  }
  ```

- **Test Disconnects:** Connect a client in a browser. Kill your network connection briefly and verify that the client auto-reconnects, passes the last seen ID, and recovers missing events cleanly without duplicates.

</Lab>
