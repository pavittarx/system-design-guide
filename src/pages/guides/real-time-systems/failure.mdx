<Collapse id="reconnect" title="1. Why reconnecting clients take down healthy servers">

A load balancer restarts at 10:00. Every client connected through it drops. By 10:00:01 they're all reconnecting, and by 10:05 servers that had nothing wrong with them are falling over too. This is the failure from the [cold open](/guides/real-time-systems/), and it gets its own section because it's the one that turns a small incident into a long one.

### The loop that keeps it going

The trigger can be anything that drops many clients at once: a gateway crash, a deploy, a network blip, a load balancer restart. What happens next is always the same:

<Stack>
  <Layer idx="1">**Many clients drop at once.** Every one notices within the same second or two.</Layer>
  <Layer idx="2">**They all reconnect immediately.** And reconnecting is the most expensive thing a client does: TLS handshake, login check, resubscribing, and catching up on missed state.</Layer>
  <Layer idx="3">**The survivors drown.** The remaining servers were already carrying the failed ones' share. Now they get a synchronised burst of the most expensive operation in the system.</Layer>
  <Layer idx="4">**The survivors fall over.** Their clients drop too, and go back to step 2.</Layer>
</Stack>

Notice that the original trigger can be long gone and the loop keeps running, because the recovery traffic *is* the load. This is the **metastable failure** from [The Reliability Toolkit](/guides/reliability-toolkit/) in its purest form: a system that stays broken after the cause is fixed.

### Defence 1: spread the retries out at random

The usual first fix is **exponential backoff**: wait 1 s, then 2 s, then 4 s, doubling each time. It doesn't help on its own. Watch two of the 50,000 clients:

Every client computes the same waits, so they stay in lockstep forever. The fix is to wait a *random* amount up to the backoff limit, which is called **jitter**:

<Race a="Client A" b="Client B" result="Result: the same 50,000 retries, spread across the window instead of stacked on one instant" tone="good" steps={[
  { a: "Dropped at 0 s. Picks a random wait between 0 and 1 s: 0.3 s" },
  { b: "Dropped at 0 s. Picks a random wait between 0 and 1 s: 0.8 s" },
  { a: "Retries at 0.3 s. Connects", tone: "good" },
  { b: "Retries at 0.8 s. The server has room. Connects", tone: "good" }
]} />

In code, it's one line. Not `2^n` seconds, but a random number between 0 and `2^n`, with a cap:

```js
// attempt = 0, 1, 2, … ; reset to 0 once a connection has stayed up a while
const delayMs = Math.random() * Math.min(60_000, 1000 * 2 ** attempt);
```

Cap the wait at 30–60 s. And reset `attempt` only after a connection has been *stable* for a while; otherwise a connection that drops every few seconds resets its backoff each time and never slows down.

### Defences 2 to 4: make reconnecting cheap and controlled

<Note type="key" label="The defences, in order of importance">

**1 · Jittered exponential backoff, client-side.** Random waits that double up to a cap, as above.

**2 · Make reconnection cheap.** Resume from a sequence number instead of resending full state. A resume is a few kilobytes; a full resync can be megabytes. That's the difference between a spike and an outage.

**3 · Limit new connections at the gateway.** Cap new connections per second and reject the excess quickly with a "retry later" hint. This is called **admission control**. A fast "no" that a client backs off from is far better than a slow "yes" that takes the server down with it.

**4 · Tell clients when to come back.** On a planned shutdown, send a close frame with a suggested delay and, if you have one, a gateway to reconnect to. Now you're scheduling the reconnects instead of receiving them.

</Note>

The uncomfortable part: all four live in code you must have shipped *before* the incident, much of it on clients you can't update quickly. A mobile app with a bad retry loop stays a liability for months after you fix the server, because people don't update their apps. Get backoff and jitter right in the client on day one; it's the highest-leverage twelve lines in the whole system.

<Collapse id="backpressure" title="2. What to do with a client that can't keep up">

You're pushing messages to a client on a train with two bars of signal. It can't receive them as fast as you send. Where do the messages go?

By default, into a buffer in your server's memory, and buffers grow. One slow client in a busy channel can build up tens of megabytes of undelivered messages. A few hundred of them can use up the memory of a gateway serving fifty thousand healthy clients, and when it crashes, the healthy clients go down with it. The sick connections took out the healthy ones: a failure of isolation, which is exactly what **bulkheads** (walls that keep one failure from spreading) exist to prevent.

Pushing back on a sender that's faster than its receiver is called **backpressure**.

<Note type="warn" label="Unbounded queues are not a design, they are a deferral">
Every send queue needs a maximum size, and a decision about what happens when it's full. There are only four options, and not choosing means choosing "grow until the process dies".
</Note>

<CardGrid>
  <Card pill="Drop oldest" tone="mid">
    Keep the newest messages. Right for streams where only the current value matters, like prices, positions and dashboards: old values are worthless.
  </Card>
  <Card pill="Drop newest" tone="mid">
    Keep what's already queued. Rarely what you want, but correct when the queued items are already committed work.
  </Card>
  <Card pill="Collapse / conflate" tone="good">
    Replace outdated messages with the latest one for the same key. A ticker sends one current price, not four hundred stale ones. The best option when it applies.
  </Card>
  <Card pill="Disconnect" tone="good">
    Close the connection and let the client reconnect and catch up from its sequence number. Brutal, bounded, and correct: it turns an unbounded memory problem into one bounded reconnect.
  </Card>
</CardGrid>

"Disconnect and let them catch up" is the option teams resist and then adopt, because it's the only one whose worst case is bounded. It's also why the sequence numbers from [Part 2](/guides/real-time-systems/delivery/#ordering) matter so much: cheap catch-up is what makes disconnecting slow clients a policy rather than data loss.

The other half is to **send less**:

- **Combine rapid updates.** Gather changes for a few milliseconds and send them as one message.
- **Send changes, not whole objects.** "Price is now 41.20", not the full product.
- **Send only what's on screen.** Let the client say what it's looking at. A client viewing one channel doesn't need live updates for the other four hundred it belongs to.

</Collapse>

<Collapse id="gotchas" title="3. Seven gotchas that actually bite">

<Note label="1 · Idle timeouts you didn't set">
Load balancers, corporate proxies and mobile networks close connections that have been quiet for 30–120 seconds, usually without telling either side. Send a small heartbeat message every 20–30 s from your application, and use it to detect a dead connection in both directions. A TCP connection can look open for many minutes after the other side is gone.
</Note>

<Note label="2 · WebSockets bypass your HTTP middleware">
Login checks, rate limiting, logging, tracing and request-size limits usually run as HTTP middleware, once per request. After the upgrade there are no more requests, only messages, so none of it runs. Every message needs its own permission check and rate limit: a client that logged in an hour ago may have lost access since.
</Note>

<Note label="3 · Cross-Site WebSocket Hijacking">
A malicious page can open a WebSocket to your server, and the browser sends your user's cookies with the handshake. The browser's same-origin rules don't block this for WebSockets, so the attacker's page talks to your server as the logged-in user. Check the `Origin` header on the server during the handshake, and prefer a token in the first message over cookie login.
</Note>

<Note label="4 · Mobile backgrounding">
iOS and Android suspend apps in the background, and their connections with them, usually within seconds. Live delivery to a backgrounded app doesn't work and can't be made to. That path is push notifications through APNs or FCM, a separate system with different guarantees. Design the switch between foreground and background on purpose; it isn't an edge case.
</Note>

<Note label="5 · Load balancing long-lived connections">
A load balancer only decides where *new* connections go; open ones never move. So after a deploy or scale-up, the imbalance stays for hours, and least connections makes it worse by sending every new connection to the emptiest server, swamping a just-restarted one. Spread new connections randomly or by capacity, and rebalance deliberately rather than hoping the algorithm does it.
</Note>

<Note label="6 · Encoding the message once per recipient">
Turning the same message into JSON once per recipient makes a 200-byte broadcast cost megabytes of allocation in a large channel. Encode once and send the same bytes to everyone. This single change has rescued more real-time systems than any other small optimisation.
</Note>

<Note label="7 · Load tests that miss the storm">
Load tests from a single machine hit the ~64k port limit and rarely reproduce what actually breaks you: everyone reconnecting at once. Test the storm on purpose: connect 50,000 clients, kill a gateway, and watch what the survivors do.
</Note>

<Note type="key" label="What to remember">

- The reconnect is the load test. Many clients dropping at once come back together, with the most expensive request you have.
- Defend it before the incident: random backoff on the client, cheap resume from a sequence number, and a cap on new connections at the gateway.
- Every send queue needs a limit and a policy. For a client that can't keep up, disconnecting and letting it catch up is the one option with a bounded worst case.

</Note>

<Collapse id="check" title="Check your understanding">

<Quiz q="Reconnection is a standard client requirement. Why is it also your system's most dangerous load test, and what defuses it on the server?" options={["Reconnecting clients re-download the app bundle; serve it from a CDN with longer cache headers", "Old sockets linger while new ones open, doubling connections; raise file-descriptor limits and add memory", "Every client reconnects at once with the most expensive operation in the system; use server-directed reconnect, admission control and cheap resumes"]} answer={2}>

When many clients drop together, they all try to reconnect at the same moment. A reconnect costs far more than an ordinary message: a TLS handshake, a login check, and catching up on state. That burst can overload the surviving servers, whose clients then drop and reconnect too, and the loop keeps itself going.

Three server-side defences:

- **Tell clients when to come back.** On shutdown, send a close frame with a randomised delay and, if you can, a gateway to use.
- **Cap new connections.** Limit how many handshakes a gateway accepts per second and reject the rest quickly, so those clients back off.
- **Make resuming cheap.** Let clients resume from a sequence number and fetch only what they missed, instead of a full resync.

</Quiz>

<Quiz q="WebSockets upgrade from HTTP. Why is this upgrade a security and rate-limiting trap?" options={["The upgrade drops TLS, so frames after the handshake travel unencrypted", "After the upgrade, HTTP middleware no longer runs, so authorisation, rate limits and size limits must apply per message", "Load balancers drop upgraded connections, so clients silently reconnect without authenticating"]} answer={1}>

Your HTTP middleware (logging, permission checks, body-size limits, firewall rules) runs once per request. After the upgrade, the connection stays open for hours and carries messages, not requests, so none of that runs on them.

Concretely: a user removed from a channel an hour ago still has an open socket that keeps sending and receiving unless something checks. A client can send ten thousand messages a second with no rate limiter in the way. An enormous or malformed message can reach a parser that was never tested because "the gateway limits body size".

So check permission on each message against current state (cached briefly, not taken from what was true at connect time), rate-limit each connection, limit message size, and re-check the login token periodically, closing the connection when it expires. And check the `Origin` header during the handshake, since the browser's same-origin rules don't protect WebSockets.

</Quiz>
