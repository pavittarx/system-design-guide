<Collapse id="cost" title="1. What a connection actually costs">

The "C10K problem" was solved twenty years ago and the folklore has not caught up. Modern servers using epoll or kqueue hold enormous numbers of idle connections; WhatsApp famously reached **2 million connections on a single FreeBSD box** in 2012. The cost is not the connection, it is what you attach to it.

<Note type="key" label="The memory arithmetic">

Per connection you pay: kernel socket buffers (typically **4–64 KB** combined, and tunable), TLS session state (**~10–20 KB**), and your own per-connection object — user ID, subscriptions, send queue, parser state.

At **50 KB** per connection, 100,000 connections is **5 GB** — comfortable. At **500 KB**, because someone attached a generous send buffer and a cached user profile, the same 100,000 connections is **50 GB**, and you are buying ten times the machines for the same product.

</Note>

So the tuning levers are: keep the per-connection object small (store an ID, not an object graph), bound the send queue explicitly (see [backpressure](/guides/real-time-systems/failure/#backpressure)), reduce socket buffer sizes for connections you know carry small messages, and prefer TLS session resumption so handshake state is not duplicated.

Then there is CPU, which behaves differently. Idle connections cost almost nothing. Each message costs a syscall, a framing operation, and possibly TLS encryption. The killer is *fan-out*: one message to a 50,000-member channel is 50,000 sends. If you also serialise the message once per recipient rather than once per broadcast, you have turned a 200-byte message into 10 MB of allocation and JSON encoding, per broadcast. Serialise once, send many.

<Note type="warn" label="Ephemeral ports">

A single client IP can open at most ~64,000 connections to a single server IP:port, because that is the size of the ephemeral port space. This is invisible in production (clients have different IPs) and appears instantly in load testing from one machine, where it is usually misdiagnosed as a server limit.

It also bites *between* your own tiers: a gateway holding many connections to one backend can exhaust ports. Fix with multiple backend ports or IPs, and by reusing pooled connections rather than opening new ones.

</Note>

</Collapse>

<Collapse id="routing" title="2. Routing to a stateful server">

Your user is connected to gateway 7. An event for that user is generated by a worker that has never heard of gateway 7. Getting the message from one to the other is the central architectural problem of real-time systems, and there are three standard answers.

<Stack>
  <Layer idx="A">**Registry.** Every gateway writes "user 8817 is on gateway-7" into a shared store (Redis, or a coordination store from [Getting Machines to Agree](/guides/coordination-consensus/)). Senders look it up and deliver directly. Precise and efficient; the registry becomes a hot dependency, and it goes stale the instant a gateway dies.</Layer>
  <Layer idx="B">**Broadcast bus.** Every gateway subscribes to a pub/sub topic; senders publish and every gateway discards what isn't theirs. No registry, no staleness, trivially correct. Cost is that every gateway sees every message — fine at ten gateways, ruinous at a thousand.</Layer>
  <Layer idx="C">**Sharded topics.** The middle ground and the usual answer at scale. Partition by channel or conversation; a gateway subscribes only to the partitions its connected users care about. Senders publish to a partition without knowing who is listening. Scales because each gateway's traffic is proportional to its users' interests, not to global volume.</Layer>
</Stack>

Layered on top of routing is the question of which gateway a client lands on in the first place. The load balancer must support the upgrade (an L7 balancer that doesn't understand the WebSocket handshake will break it), and it must not balance mid-stream. Long-lived connections also defeat ordinary load balancing in a subtle way described in [Load Balancing](/guides/load-balancing/): least-connections works beautifully for short requests and terribly for long ones, because a server that has been up longest accumulates the most connections and never sheds them.

<Note type="warn" label="The deploy problem">

Restart a gateway holding 50,000 connections and all 50,000 clients reconnect simultaneously — the Slack failure mode. Roll a fleet of twenty gateways and you do that twenty times in a row.

Mitigations: drain slowly, closing connections at a controlled rate (say 500/s) rather than all at once; send a close frame with a reason so clients know to reconnect with jitter rather than immediately; and deliberately rebalance a small fraction of connections continuously in normal operation, so that "reconnect" is a well-exercised path rather than a rare emergency.

</Note>

</Collapse>

<Collapse id="fanout" title="3. Fan-out: on write or on read?">

When one user's action must reach many users' screens, you choose when to pay for the multiplication. This is the single biggest design decision in a feed or chat system, and it is genuinely a choice — both answers are correct for different workloads.

<CardGrid>
  <Card pill="Fan-out on write (push)" tone="good">
    On publish, immediately write the item into every follower's inbox. Reads are a single sequential fetch of a precomputed list — extremely fast, trivially cacheable. Writes are O(followers) and can be enormous.
  </Card>
  <Card pill="Fan-out on read (pull)" tone="mid">
    Store the item once. On read, gather items from everyone this user follows and merge them. Writes are O(1). Reads are expensive, hard to cache, and get worse as the user follows more people.
  </Card>
</CardGrid>

<Note type="key" label="Why the hybrid exists">

Most users have hundreds of followers. Fan-out on write costs a few hundred small writes — nothing.

A celebrity has **100 million** followers. One post at fan-out-on-write is **100 million inbox writes**, which is not a post, it is an incident. Worse, most of those inboxes belong to people who will not open the app today, so the work is wasted.

**The hybrid:** fan out on write for ordinary accounts, and mark accounts above a threshold as "pull". A user's feed is then *their precomputed inbox* merged at read time with *the recent posts of the handful of celebrities they follow*. Both operations stay small. This is, in outline, what Twitter, Instagram and their peers actually do.

</Note>

For chat the same choice appears with different names. A two-person conversation fans out on write, always. A 200,000-member community channel does not — you store the message once in the channel's log and let connected clients read from it, which is roughly Discord's approach: a channel is a stream, and only the members currently connected and currently looking at it receive a push.

The refinement that makes the difference at scale is to fan out only to *active* recipients. A message needs to reach the screens that are open right now; everyone else can be served from the channel log the next time they connect, and can receive a push notification through an entirely separate, much cheaper path. Fan-out cost then scales with concurrent viewers rather than with membership, and those two numbers can differ by three orders of magnitude.

</Collapse>

<Collapse id="check" title="Check your understanding">

<Quiz q="A server can easily hold 100,000 idle connections, but crashes when they actually start receiving traffic. What changed?" options={["The epoll event loop cannot track that many active file descriptors at once", "TLS handshakes for 100,000 clients exhaust the CPU once they all become active", "Socket buffers and send queues grow with undelivered data, so memory per connection jumps once traffic flows"]} answer={2}>

An idle TCP connection costs very little: basic kernel sockets and connection registry metadata (~10–30 KB). The scaling ceiling changes completely when traffic starts flowing. Kernel-level read/write socket buffers dynamically grow (often to 64 KB or higher) to support outstanding data, and application-level send queues can buffer undelivered payloads for slow clients.

If 100,000 connections each accumulate 200 KB of buffered data (e.g. because of slow network receivers), the server requires 20 GB of memory just for queues. Unbounded buffers degrade isolation, causing healthy connections to be dropped when the host goes out of memory. Defensive engineering requires setting hard queue limits and forcing disconnections on slow consumers so they resync from a sequence log later.

</Quiz>

</Collapse>
