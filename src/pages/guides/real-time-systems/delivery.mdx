<Collapse id="presence" title="1. Presence, typing and the cheap-signal trap">

Presence — the green dot — looks like the smallest feature on the page and is reliably one of the most expensive things in a real-time system, for a reason that generalises: **the cost of a signal is its rate times its audience, and presence is high on both.**

Consider a 1,000-member channel where 200 people are online. Each of those 200 has a status that can change. If every change is broadcast to every member, one person opening their laptop generates 1,000 messages. Now imagine a busy morning where people connect and disconnect constantly — a mobile client on a train changes state every few minutes — and presence traffic dwarfs the actual conversation by an order of magnitude.

<Note type="key" label="Four techniques that make presence affordable">

**1 · Only tell people who are looking.** Presence updates go to users currently viewing that channel, not all members. Usually a 10–100× reduction on its own.

**2 · Batch on an interval.** Collect changes and flush every 1–5 seconds as one message. Presence has no correctness requirement, so a two-second delay is invisible, and a burst of fifty changes becomes one frame.

**3 · Debounce flapping.** Do not mark someone offline the instant a connection drops — wait 30–60 seconds. Mobile clients disconnect constantly, and a green dot that flickers is worse than one that is slightly stale.

**4 · Pull on demand.** For a large member list, do not push presence at all. Send the current state when the user opens the list, and refresh it while it is open.

</Note>

Typing indicators are the same problem in miniature and are best handled with a simple protocol: the client sends "typing" at most once every few seconds while the user types, the server broadcasts it with no persistence whatsoever, and the indicator expires on the receiving client after a few seconds without renewal. No "stopped typing" message is needed, which conveniently means a lost message cannot leave someone permanently typing.

The general lesson is worth extracting because it applies to read receipts, cursor positions, live reactions and anything else in this family: **ephemeral signals must never touch durable storage, must be batched, and must be scoped to the audience actually looking.** Persisting a typing indicator to a database is a mistake with a remarkably high ceiling on how much damage it can do.

</Collapse>

<Collapse id="ordering" title="2. Ordering, gaps and catch-up">

A connection that drops for eleven seconds creates a hole in the user's view of the world, and the client cannot see the hole — it only knows what it received. Making that recoverable requires the same primitive in every design: a **monotonic sequence number per stream**.

Every message carries a sequence. The client tracks the highest it has seen. On reconnect it says "I have up to 4,812", and the server replays everything after that from a log. SSE has this built in — the server sets `id:` on each event and the browser sends `Last-Event-ID` automatically on reconnect. With WebSockets you build it yourself, and it is the first thing you should build.

```trace
client seq 4812   ++connected++
  ├─ 4813 delivered            ++ok++
  ├─ ~~connection drops — 4814, 4815, 4816 missed~~
  ├─ reconnect, client sends **last_seq=4813**
  ├─ server replays 4814, 4815, 4816 from the channel log
  └─ 4817 delivered live       ++ok — no gap, no duplicate++
```

Two decisions follow. First, **how far back can you replay?** The log is finite. If the client has been away longer than the retention window, you cannot replay — you must tell it so, and the client must resynchronise from scratch by fetching current state. Handle this explicitly with a "too far behind, resync" response, because the alternative is a client that silently believes it is up to date and is not.

Second, **ordering guarantee within a stream.** Sequence numbers give you per-stream order, which is what users perceive: messages in one conversation appear in the order they were sent. Global ordering across all streams is far more expensive and nobody notices its absence. Scope your ordering guarantee to the conversation, the channel, or the document — the same partition-and-order reasoning as [Message Queues & Async](/guides/message-queues/).

<Note type="wild" label="◈ In the wild · Figma">

Figma leans on exactly this idea for multiplayer editing: each open document lives on a single server that owns the authoritative order of changes. Rather than full CRDTs, it uses last-writer-wins per object property, with that server as referee, so two people dragging the same rectangle converge without a merge conflict. A client that drops resyncs from the server's ordered log — the same "replay from where I left off" move. Their team wrote it up in [how Figma's multiplayer technology works](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/).

</Note>

And since replay means a message can be delivered twice, clients must deduplicate by message ID. Idempotent handling on the receiving side is what makes at-least-once delivery acceptable, exactly as it is on the server side.

</Collapse>

<Collapse id="check" title="Check your understanding">

<Quiz q="Presence traffic is 10× your message traffic. Where did it go wrong, and how do you fix it without removing the feature?" options={["Presence is persisted to the database; moving it to Redis fixes the volume", "Every status change is broadcast to every member; scope it to viewers, batch it, debounce going offline, and pull it for large lists", "Heartbeats are too frequent; raising the heartbeat interval cuts the presence messages"]} answer={1}>

The usual cause is broadcasting every status change to every member of every channel the user belongs to. One person opening a laptop, in ten channels averaging a thousand members, is ten thousand messages — for a green dot. Mobile clients making it worse by flapping on and off the network several times a minute is the second half of the problem.

Four fixes, roughly in order of payoff. Scope to viewers: send presence only to users currently looking at that channel, not all members — typically 10–100× on its own. Batch: collect changes and flush every one to five seconds as a single message; presence has no correctness requirement so the delay is invisible. Debounce: wait 30–60 seconds before marking someone offline, which removes most flapping entirely. And for large member lists, stop pushing altogether — fetch presence when the user opens the list and refresh it while it is open.

Underneath all four is one rule: ephemeral signals must never touch durable storage, must be batched, and must be scoped to the audience actually looking.

</Quiz>

<Quiz q={"Your users report messages \"arriving out of order\" after a brief network blip. What's actually happening?"} options={["It is a gap: messages sent during the disconnect never arrived, and the client cannot see the hole", "TCP reordered packets while retransmitting after the blip", "Two gateways delivered the same stream and the client sorted by their unsynchronised clocks"]} answer={0}>

Almost certainly not reordering — TCP guarantees order within a connection. What they are seeing is a *gap*: messages sent while they were disconnected never arrived, so a later message appears immediately after an earlier one with the middle missing. The client has no way to know something is absent unless you tell it.

The fix is a monotonic sequence number per stream. The client tracks the highest it has seen and sends it on reconnect; the server replays everything after it from the channel log. If the client is further behind than your retention window, respond with an explicit "too far behind — resync" so it fetches current state rather than silently believing it is complete.

Two details to get right: replay means duplicates are possible, so clients must deduplicate by message ID; and scope the ordering guarantee to a single stream (conversation, channel, document). Global ordering across all streams is far more expensive and nobody perceives its absence.

</Quiz>
