Before any distributed anything, exhaust the cheap wins on a single database. They routinely buy 10–100× and cost a fraction of the complexity.

<CardGrid>

### Back to 09:14

The cold open's fix was `CREATE INDEX CONCURRENTLY idx_orders_customer_created ON orders (customer_id, created_at);`. Six seconds became 3 ms. At 30 requests a second, that's `30 × 0.003 ≈ 0.1` connections in flight instead of 180 — the pool never empties and the login page never notices. The second fix was a `statement_timeout`, so the next bad query fails alone instead of taking every endpoint with it.

### The index that isn't used

"We have an index on that" is one of the most confidently wrong sentences in software. Having an index and *using* an index are separate facts. Two ways it goes wrong, both of which look fine in code review.

**Case 1: the composite index and the leftmost prefix.** You have an `events` table, 40 million rows, and an index built for a dashboard query:

```sql
CREATE INDEX idx_events_org_created ON events (org_id, created_at);

-- Fast. Filters on the leading column.
SELECT * FROM events
WHERE  org_id = 42
  AND  created_at > now() - interval '7 days';

-- Slow. Same index, same table, no predicate on org_id.
SELECT * FROM events
WHERE  created_at > now() - interval '7 days';
```

A composite B-tree is sorted by its columns *in order*: first by `org_id`, and only within each `org_id` by `created_at`. Think of a phone book sorted by last name, then first name. Ask it for everyone called Okafor and it's instant. Ask for everyone called James, with no last name, and the sort order is worthless — the Jameses are on every page.

That's the **leftmost-prefix rule**: an index on `(a, b, c)` serves predicates on `a`, `a AND b`, and `a AND b AND c`, but not on `b` alone. Some engines have a skip scan for a leading column with few distinct values — a consolation prize, not a design. The fix is a second index on `(created_at)`.

```trace
Seq Scan on events  (actual time=0.031..~~4128.774~~ rows=1187)
  Filter: (created_at > (now() - '7 days'::interval))
  ~~Rows Removed by Filter: 39998813~~
Execution Time: ~~4131.006 ms~~

**after CREATE INDEX idx_events_created ON events (created_at):**
Index Scan using idx_events_created on events
  (actual time=0.028..++1.902++ rows=1187)
Execution Time: ++2.140 ms++
```

Forty million rows touched to return 1,187 — a ratio of about 34,000. That is the number from the triage, and this is what it looks like.

**Case 2: the function that hides the column.** The index is on exactly the column you filter on, and it still isn't used:

```sql
CREATE INDEX idx_users_email ON users (email);

-- Sequential scan. Every time.
SELECT * FROM users WHERE lower(email) = 'ada@example.com';
```

The index stores `email` verbatim. It has never seen `lower(email)`; to compute that for every row, the database has to read every row. Same bug, different costumes: `WHERE created_at::date = '2026-01-01'`, `WHERE substr(sku, 1, 3) = 'ABC'`, and `WHERE account_number = 12345` against a `varchar` column, where an implicit cast wraps the column. Index the expression you query — `CREATE INDEX ON users (lower(email))` — or normalise on write.

<Note type="key" label="EXPLAIN is the arbiter, and dev data will lie to you">

Never reason about index usage from first principles — run `EXPLAIN (ANALYZE, BUFFERS)` and read what the planner chose. `ANALYZE` really executes the statement, so wrap writes in a transaction you roll back. And on a 5,000-row development table the planner will correctly pick a sequential scan however perfect your index is, because reading the whole thing is cheaper. Validate index decisions against production-shaped data.

</Note>

Indexes fix the work each query does. The rest of Part 1 is about how many queries you send, and how many you let in at once.

<Collapse id="queries" title="2. Queries and connections">

Indexes made each query cheap. The next three problems are about how queries arrive: too many of them, ones that get slower the deeper they page, and too many at once.

### N+1: four hundred tiny queries

The ORM makes it easy: load 50 orders, then loop over them and load each order's customer. That's 51 round trips where one would do, and every round trip pays network latency before the database does any work. It hides in development because the list has three items. Find it by counting queries per request — ORM debug logs and most APM tools show it — and fix it with a join or a single `WHERE id IN (…)` batch load.

### `OFFSET` pagination degrades linearly, and it's everywhere

```sql
-- Page 5,000 at 20 per page.
SELECT * FROM messages ORDER BY created_at DESC LIMIT 20 OFFSET 100000;
```

`OFFSET` isn't a seek: the database produces 100,000 sorted rows and throws them away before returning your 20. Page 5,000 does 5,000× the work of page 1 — and nobody notices until a crawler starts clicking. **Keyset pagination** remembers where you stopped instead:

```sql
SELECT * FROM messages
WHERE  (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT  20;
```

Constant cost at any depth, and no skipped or duplicated rows when data changes mid-scroll. You lose "jump to page 5,000", which feeds, exports and APIs never needed.

### Right-size the pool: Little's Law, not a vibe

Pool sizes get chosen by doubling until the errors stop. There's an actual formula: **concurrency = throughput × latency**. At 2,000 queries a second and 4 ms each, `2,000 × 0.004 = 8` queries are in flight at any instant. A pool of 20 is comfortable headroom; a pool of 200 is 192 connections that will never be useful at the same time.

An oversized pool is actively harmful. A database can only do so much genuinely parallel work — bounded by cores, disk queue depth and lock contention. Beyond that, extra queries get *interleaved*, not parallelised: the same work in more slices, with context switches between them. In Postgres every connection is a separate OS process. Throughput stays flat while each query gets slower. The HikariCP rule of thumb, `(cores × 2) + effective_spindle_count`, is folk wisdom, but it lands in the right order of magnitude: tens, not hundreds.

The part people miss: when a small pool is full, requests queue in *your application*, where you can see the queue, time it out, and shed load. When the pool is huge, the queue moves inside the database, where you can do none of those things.

### Then, and only then, scale up

Once queries are lean, a bigger machine is the cheapest capacity there is. More RAM lifts a falling cache hit ratio immediately, faster NVMe raises the write ceiling, and neither needs a line of code. The ceiling is real and the largest instances are expensive, but it buys time without adding a single distributed-systems problem.

A fast database can still be a *wrong* one. [Part 2](/guides/database-scaling/correct/) is about what happens when two of those fast queries touch the same row at the same moment.

<Collapse id="check" title="Check your understanding">

<Quiz q="Your p99 doubled after you raised the connection pool from 20 to 200. Throughput didn't change. Why?" options={["The database ran out of memory for the extra connections", "Twenty connections already covered the work the database can do in parallel; the extra ones only add switching overhead", "The application now sends more queries per request"]} answer={1}>

Because 20 was already enough, and 200 doesn't create parallelism the database can use. Past the point where it can do real parallel work, extra connections interleave the same work into more slices — context switches and, in Postgres, scheduler overhead across hundreds of processes. Throughput stays flat while every query takes longer, which is exactly a p99 that doubles for no visible reason. The bigger loss is that the queue moved from your application, where you could time it out, into the database, where you can't.

</Quiz>
