<ColdOpen tag="◇ 09:14 · the query that was fine last quarter">

Nobody changed the code. One `SELECT` on the orders table has shipped untouched for eighteen months. At 100,000 rows it answered in 3 ms, so nobody ever looked at it again. The table now holds 40 million rows, the index that would have kept it fast was never created, and this morning the query takes six seconds: it reads the whole table, and holds a database connection for every one of those seconds.

The app shares a pool of 100 connections. At 30 requests a second, each holding one for six seconds, it needs 180. The pool runs dry. Now the login page times out, the health check times out, and the settings page, which has never touched the orders table, times out too, because they are all waiting for a connection that isn't coming back. The CPU graph looks almost calm: the server isn't working hard, it's waiting on disk. It is not a capacity problem. It is one missing index, and it took the whole product down.

</ColdOpen>

<Collapse id="why" title="1. Why the database breaks first">

### Why more app servers didn't help

Your app is slow at peak, so you add two more app servers behind the [load balancer](/guides/load-balancing/). Nothing gets faster.

App servers are easy to add because they're interchangeable: they keep nothing between requests, so any server can handle any request. The database is different. It holds the data itself, the **state**, and there's usually one authoritative copy that every write must go through. More app servers just means more requests queuing at the same database. That's why it's the natural bottleneck, and why the cold open above is the most common outage in a growing product.

### Three different kinds of "too much"

When a database struggles, it's one of three things, and each needs a different fix:

- **Too many reads.** Lots of queries fetching data. Usually the *easier* problem, because the same answer can be served from a cache or a copy of the database.
- **Too many writes.** Lots of inserts and updates, or simply more data than one machine can store and index. The *harder* problem, because every write has to reach the one authoritative copy.
- **Too many requests fighting over the same rows.** Not much work in total, but many requests want the same rows at once and have to wait their turn. This is called **contention**. It looks like slowness, and it's often a correctness bug as well: two requests that both "won" the last seat.

### The ladder: climb only as far as you need

This guide is a ladder in four parts. Each part answers one question, and each costs more than the one before, so stop at the first one that solves your problem:

1. **[Make one box fast](/guides/database-scaling/fast/)**: is every query doing the least work it can?
2. **[Keep it correct under load](/guides/database-scaling/correct/)**: do simultaneous requests and deploys leave the data right?
3. **[Take load off it](/guides/database-scaling/offload/)**: can reads be answered without touching the main database?
4. **[Split it](/guides/database-scaling/split/)**: for when one machine can't hold the data or keep up with the writes.

The [recap](/guides/database-scaling/recap/) puts the whole ladder on one page, with the numbers worth remembering.

Part 2 isn't really a rung, because it applies at every rung. It comes early because it's where production databases actually lose data or go dark.

<Note type="key" label="The golden rule of scaling">

Every rung up this ladder adds complexity and new ways to fail. So climb **only as far as your load actually forces you to**, and no further. Most applications never need sharding. Diagnose first; the diagnosis decides which rung you need.

</Note>

<Collapse id="diagnose" title="2. Find out what kind of slow it is">

"The database is slow," says the alert. One teammate wants read replicas, another a bigger server, a third has been waiting years to shard. Only one of them is right, and the wrong ones can make things worse.

Suppose the real problem is too many writes, and you add read replicas: read-only copies of the database that Part 3 covers. Every replica has to replay *every single write* the main database does. You've added machines that repeat the exact work that was already too much, plus a copy stream to monitor and a new way to fail. Slower, and you paid for the privilege.

So measure before you choose. The database already keeps counters that tell the three pressures apart.

### Collecting the signals

Every signal comes from counters the database already keeps. Here is where to find each one, then how to read it.

<Table>

| Signal | PostgreSQL | MySQL (InnoDB) |
| :--- | :--- | :--- |
| **Read/write mix** | `pg_stat_database`: `tup_returned`, `tup_fetched` vs. `tup_inserted`, `tup_updated`, `tup_deleted` | `SHOW GLOBAL STATUS`: `Com_select` vs. `Com_insert`, `Com_update`, `Com_delete` |
| **Which p99 moved** | `pg_stat_statements`, ordered by `total_exec_time` | Slow query log |
| **Replication lag** | `pg_stat_replication`: `replay_lag` | `SHOW REPLICA STATUS`: `Seconds_Behind_Source` |
| **Lock waits** | `pg_stat_activity` where `wait_event_type = 'Lock'` | `SHOW ENGINE INNODB STATUS` |
| **Buffer cache hits** | `pg_stat_database`: `blks_hit`, `blks_read` | `Innodb_buffer_pool_read_requests`, `Innodb_buffer_pool_reads` |
| **Rows examined per row returned** | `EXPLAIN (ANALYZE, BUFFERS)`: `Rows Removed by Filter` | Slow log: `Rows_examined`, `Rows_sent` |

</Table>

**The read/write mix.** How many rows are read for every row written. These counters count up from the last restart, so take two samples an hour apart and use the change between them, written Δ:

$$
\text{read : write} \;=\; \frac{\Delta\,\text{rows read}}{\Delta\,\text{rows inserted} + \Delta\,\text{rows updated} + \Delta\,\text{rows deleted}}
$$

A read-heavy web app sits in the hundreds or thousands to one; the trace below shows 1,000 : 1.

**Which p99 moved.** p99 is the time that 99% of queries finish within: the slow tail your unluckiest users feel. This signal settles arguments. Split it by statement type and look at what got worse *when the trouble started*, not at what's slowest overall, because on a healthy system writes are often slower than reads. Order `pg_stat_statements` by `total_exec_time`, not `mean_exec_time`: the query that costs you most is usually a fast one run absurdly often.

**Replication lag vs. lock waits.** Replication lag is how far a read-only copy has fallen behind the main database. A lock wait is a request standing still because another request is holding the row it needs. These two tell the problems apart almost perfectly:

- *Lag rising*: the main database is producing changes faster than its copies can apply them. That's a write-volume problem by definition.
- *Lock waits rising*: requests are fighting over the same rows. Usually fixed by making transactions shorter, not by buying hardware.

**Buffer cache hit ratio.** The database keeps recently used pieces of each table in memory, its buffer cache. The hit ratio is the share of reads answered from that memory instead of from disk:

$$
\begin{aligned}
\text{Postgres:}\quad \text{hit ratio} &= \frac{\texttt{blks\_hit}}{\texttt{blks\_hit} + \texttt{blks\_read}} \\[10pt]
\text{InnoDB:}\quad \text{hit ratio} &= 1 - \frac{\texttt{Innodb\_buffer\_pool\_reads}}{\texttt{Innodb\_buffer\_pool\_read\_requests}}
\end{aligned}
$$

Above about 99% is healthy for a typical web-app workload (OLTP: many small reads and writes). When it falls, the data your queries touch most no longer fits in memory, reads that were memory hits have become disk reads, and more RAM fixes it at once. Postgres counts a read served from the operating system's own file cache as a miss, so watch the trend rather than the exact value.

**Rows examined per row returned.** The single most diagnostic number in this guide:

$$
\text{work ratio} \;=\; \frac{\text{rows examined}}{\text{rows returned}}
\qquad
\begin{cases}
\approx 1 & \text{healthy} \\
> 100 & \text{an index is missing or unused}
\end{cases}
$$

Above 100, the database is doing a hundred times more work than the answer needs. The fix is an index or a rewritten query, not a bigger machine.

### Putting the signals together

Once you've read the signals, the diagnosis is a lookup:

<Table>

| If you see… | It means | Go to |
| :--- | :--- | :--- |
| `SELECT` p99 climbing, `INSERT` p99 flat | Too many reads, or reads doing too much work | Indexes → cache → read replicas |
| Rows examined per row returned above 100 | A query is reading the whole table instead of jumping to the rows it needs | Add an index or rewrite the query. Do not buy hardware |
| Buffer cache hit ratio falling below 99% | The data you use most no longer fits in memory | Scale up (more RAM) |
| Replication lag climbing under write bursts | Too many writes | Batching → scale up → partition → shard |
| Lock wait time climbing | Requests fighting over the same rows | Shorten transactions, fix the access pattern ([Part 2](/guides/database-scaling/correct/#transactions)) |
| Database calm, application slow | The bottleneck is in front of the database | Pool sizing, N+1 queries, missing timeouts |

</Table>

Here is the cold open, seen through those counters:

```trace
**$ triage — pg_stat_database delta, 09:00 → 10:00**
  rows returned by reads .............. 4,120,000,000
  rows inserted + updated + deleted ...     3,900,000   ≈ 1000:1

**$ which p99 moved (pg_stat_statements)**
  SELECT p99 ..........  42 ms  →  610 ms   ~~◀ this one~~
  INSERT p99 ..........   6 ms  →    7 ms   ++unchanged++

**$ supporting signals**
  buffer cache hit ....  99.6%  →  91.2%    working set left RAM
  examined/returned ...    1.2 →    3,400  ~~plan went sequential~~
  replication lag .....  40 ms  (flat)      ++writes are fine++
  lock wait time ......  flat              ++nothing is blocking++

**verdict: READ-BOUND** → index the query, then cache, then replicas
```

Reads got slow, writes didn't, and each read examines thousands of rows to return one. That's a missing index, not a capacity problem. [Part 1](/guides/database-scaling/fast/) fixes it in one line.

</Collapse>
