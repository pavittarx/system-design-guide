<Collapse id="recap" title="Recap in 60 seconds">

<Recap>

- **Measure first.** Read/write mix, which p99 moved, rows examined per row returned. The answer decides which rung you need.
- **Index and fix queries.** Most "slow database" is one missing or unusable index. `EXPLAIN (ANALYZE, BUFFERS)` on production-shaped data is the arbiter.
- **Scale up and right-size the pool.** More RAM fixes a falling cache hit ratio; pools are tens, not hundreds.
- **Correctness is not free at the default isolation level.** Read-then-write in code is a race. Push the check into the write, back it with a constraint, lock or go `SERIALIZABLE` only when you must — and retry.
- **Every migration must work with the code before and after it.** Short `lock_timeout`, concurrent index builds, expand and contract.
- **Cache, then replicas.** Replicas scale reads and bring lag that's worst at peak.
- **Partition, then shard — on the boundary your product already draws.** The costs are permanent: N backups, N migrations, resharding as a project.

</Recap>

Numbers worth carrying in your head. These are **order-of-magnitude reference points, not benchmarks** — each moves 10× with hardware, row width and workload. Use them to know when a number is *surprising*.

<Table numeric>

| Order of magnitude | What it is | What moves it |
| ------------------ | ---------- | ------------- |
| ~10<sup>8</sup> rows<br />(few hundred GB) | Comfortable ceiling for one well-indexed table on one box | Lookups stay cheap far past this; vacuum, index builds and whether the working set fits RAM degrade first. |
| 1,000–10,000<br />writes/s | Single-row write transactions, one tuned OLTP instance on NVMe | Transaction size, `fsync` behaviour, row width, and index count — every index is another write per row. |
| ~10<sup>5</sup><br />rows/s | Bulk ingest on the same box (`COPY` / multi-row `INSERT`) | The gap between this row and the one above is the whole argument for batching before sharding. |
| Tens | Useful connection pool size | Little's Law: throughput × latency. Past a few hundred server-side connections, put a pooler in front. |
| &lt; 10 ms same-region | Healthy async replication lag | Spikes to seconds under bulk writes, long replica queries and failover — at peak. |
| &lt; 10 good<br />&gt; 100 broken | Rows examined per row returned | Above 100 the fix is an index or a rewrite, never a bigger machine. |
| &gt; 99% | Buffer cache hit ratio, OLTP | Falling means the working set outgrew RAM. |
| 0.5–2 TB | What one shard should top out at | Often the real limit is "small enough to restore inside your recovery time objective". |

</Table>

<Note type="key" label="The one-liner to remember">

Every rung of this ladder trades a simple problem for a harder one, so make each rung earn its place with a measurement. Most "we need to shard" turns out to be one missing index, one unbounded query, and a connection pool sized by superstition.

</Note>
