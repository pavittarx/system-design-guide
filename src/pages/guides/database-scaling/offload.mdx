<Collapse id="avoid" title="1. Don't run the query at all">

Your queries are indexed and lean, and the database is still busy. Look at what it's busy with: often the same expensive question, asked thousands of times, getting the same answer every time. The cheapest query is the one you never run. Each of these cuts database load without splitting the database:

- **Keep recent answers in memory.** Put Redis or Memcached in front, so popular reads never reach the database. This is **caching**, and it's the biggest win before replicas; see the [Caching guide](/guides/understanding-caching/).
- **Store data already joined.** Copy the customer's name onto each order row, so showing an order is one lookup instead of a join. This is **denormalisation**: reads get faster, and writes get more complicated, because the same fact now lives in two places.
- **Compute the expensive summary ahead of time.** Store the result of a heavy aggregate and refresh it every few minutes, instead of recalculating it per request. This is a **materialised view**.
- **Build separate tables shaped for reading.** Writes go to the normal tables; change events keep purpose-built read tables up to date, so reads and writes scale independently. This is **CQRS**, and the event stream that feeds it is a [message queue](/guides/message-queues/).
- **Smooth out write bursts.** Put a queue between the request and the database, so a burst of writes arrives batched and steady. This is **write buffering**. Why it helps: the database no longer has to survive the peak, it only has to keep up with the average, and the queue turns the excess into a short delay.

If the cache already answers most reads and what's left still saturates the server, it's time for copies.

</Collapse>

<Collapse id="replicas" title="2. Copies that answer reads">

Reads still saturate the database. The next move is more databases that can answer them.

Keep one server that accepts all writes: the **primary** (or leader). Add copies that receive a stream of every change it makes and answer read-only queries: **replicas** (or followers). Point reporting, search and read-heavy traffic at the replicas, and the primary breathes easier.

### Should the primary wait for the copy?

When a write arrives, the primary can confirm it to your app straight away, or wait until a replica has it too. That choice is the whole trade-off:

- **Asynchronous** (the usual default): the primary saves the change, replies at once, then ships the change to replicas. Writes are fast, but replicas trail behind, and if the primary dies, the last few writes it hadn't shipped yet can be lost.
- **Synchronous**: the primary waits for a replica to confirm before replying. A failover loses little or nothing, but every write is slower.

<Note type="wild" label="◈ In the wild · Uber, 2016">

Uber moved its core storage from Postgres to MySQL, largely because of replication. Their write-up explains that a Postgres update writes a new row version and updates *every* index on the table. Postgres replicates those physical changes, so this "write amplification" travels down the replication stream too, multiplying cross-data-centre bandwidth. The clearest real account of storage internals deciding what replication costs. [(Uber Engineering)](https://www.uber.com/blog/postgres-to-mysql-migration/)

</Note>

### Why the comment vanished: replication lag

Priya posts a comment and the page reloads. The write went to the primary; the reload's read went to a replica.

With asynchronous replication, a replica is always somewhat *behind* the primary. The gap is called **replication lag**, and this bug is a **read-your-own-writes** failure: you changed something and then couldn't see your own change.

The belief that causes these bugs is "replicas are about 50 ms behind". They aren't. Lag is near zero, and near zero, and then it's eleven seconds. It spikes when a backfill or bulk delete floods the change stream, when a long query on the replica blocks it from applying changes, during failover, and whenever writes outrun the replica's apply process, which is often more single-threaded than the primary. **Lag is worst exactly when load is highest**, so these bugs never show up in staging and appear for a few users at peak.

### Three fixes, cheapest first

1. **Send a user's reads to the primary for a few seconds after they write.** This is a **sticky primary window**. Why it works: the only person who notices the lag right away is the one who just wrote, and they're the one reading from the primary. Covers most cases.
2. **Remember how far the write got, and wait for the replica to catch up.** At commit, capture the write's position in the change log (a Postgres LSN from `pg_current_wal_lsn()`, a MySQL GTID) and carry it in the session. This is a **version token**. The read path waits until the replica has applied that position, or falls back to the primary.
3. **Always read critical pages from the primary.** Account settings and checkout confirmation are worth the extra load.

Monitor lag as a *distance in the change log* (bytes behind), not only as seconds. Time-based lag is measured from recent transactions, so it can mislead: in Postgres, `replay_lag` shows the delay of the most recent changes, and on a quiet, caught-up system it goes blank (NULL) rather than reading zero.

This is the same trade-off as [cache staleness](/guides/understanding-caching/), one layer down: you accept slightly old answers in exchange for speed, which is called **eventual consistency**. The [Consistency & CAP guide](/guides/consistency-cap/) turns that dial properly.

<Note type="key" label="What to remember">

- The cheapest load is the query you never run: cache, precompute, or store data the way it's read.
- Replicas add read capacity and a failover target. They do **nothing** for write volume or total data size.
- Replication lag isn't a constant; it spikes at peak. Send a user's reads to the primary right after they write.

</Note>

When writes or total data size are the problem, you have to split the data itself: [Part 4](/guides/database-scaling/split/).

</Collapse>

<Collapse id="check" title="Check your understanding">

<Quiz q="Reads are slow. You add three read replicas. Nothing improves. What's the most likely mistake?" options={["Replication lag is too high for the replicas to help", "The diagnosis: the slow query reads the whole table, and a replica runs the same query the same way", "Three replicas are too few for the read volume"]} answer={1}>

Almost certainly the diagnosis. A replica has the same tables, indexes and query plans as the primary, so a query that reads all 40 million rows now does it on four machines instead of one. Replicas add read *capacity*; they don't reduce the work each query does. Check rows examined per row returned first.

The other common answer is routing: nothing actually sends traffic to the replicas, or the reads sit inside transactions, which most routers send to the primary.

</Quiz>

<Quiz q="About 2% of users sometimes can't see a change they just made, only at peak, and it never reproduces in staging. Where do you look?" options={["A race condition in the frontend", "Cache TTLs that are too long", "Replication lag, which spikes under peak write load and stays near zero in staging"]} answer={2}>

Replication lag. It hides because it isn't constant: near zero until it spikes under heavy writes, backfills or long replica queries, none of which staging has. The user's read went to a replica that hadn't applied their write yet.

Fix it structurally: send each user's reads to the primary for a few seconds after they write, or carry a version token that the read path waits for.

</Quiz>
