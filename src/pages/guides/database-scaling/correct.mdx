<Collapse id="transactions" title="1. Two requests, one seat">

Part 1 made every query fast. This part is about a different failure: queries that are fast, each one correct on its own, and together still wrong. It only shows up when two requests touch the same data at the same moment, which is why it never appears on your laptop and always appears in production.

### The race

A coaching platform sells sessions. Slot 7 holds 10 people and 9 are booked. Alice and Bob both press "Book" within the same few milliseconds. The booking code is the obvious one: read how many are booked, check there's room, then save the booking.

<Race a="Alice's request" b="Bob's request" result="Result: 11 people booked into a slot for 10" steps={[
  { a: "Reads slot 7: 9 of 10 booked" },
  { b: "Reads slot 7: 9 of 10 booked" },
  { a: "9 is less than 10, so there's room. Saves booking, sets count to 10", tone: "good" },
  { b: "9 is less than 10, so there's room. Saves booking, sets count to 10", tone: "bad" }
]} />

Each request did exactly the right thing with what it saw. The problem is *when* it saw it. Bob read the count before Alice saved hers, so Bob made his decision from a number that was about to be wrong. This is called a **race condition**: the result depends on the timing of two things that run at once.

<Note type="war" label="◈ The incident · Flexcoin, 2 March 2014">

A Bitcoin exchange checked each sender's balance, then moved the coins. An attacker sent thousands of transfers at the same moment. Every one read the same untouched balance, every one passed the check, and money was created out of thin air. The exchange closed.

</Note>

### "But it was inside a transaction"

The natural fix is to wrap the read and the write in a transaction, with `BEGIN` before and `COMMIT` after. Most booking code already does. It doesn't help, and the reason is the single most useful thing on this page.

A transaction promises **all or nothing**: either every statement in it happens, or none of them do. If the server crashes halfway through saving a booking, you won't end up with the booking saved but the count not updated. That promise is real and you can rely on it.

A transaction does **not** promise that nobody else can read or change the same data while you're working. Alice's transaction and Bob's transaction both ran from start to finish, both committed cleanly, and the slot still ended up overbooked.

How much transactions are shielded from each other is a separate setting called the **isolation level**. Every database ships with it turned down for speed, because full shielding makes requests wait for each other.

### Why both requests saw 9: reading from a photo

To let many requests work at once without queuing behind each other, Postgres and MySQL never make a reader wait for a writer. Instead, when a request reads, it sees a **snapshot**: think of it as a photo of the data, taken at a moment when nobody was halfway through a change. When someone writes, the database keeps the old version around for anyone still looking at their photo, and adds the new version beside it.

That's why reads are fast, and it's exactly what bit Alice and Bob. Both took their photo while the count was 9. Nothing was wrong with either photo; it just didn't show what the other request was about to do.

<Note type="wild" label="◈ In the wild · ACIDRain, 2017">

Researchers checked 12 popular self-hosted e-commerce platforms, software behind about 2 million shops, and found 22 races of this exact shape: gift cards spent twice, stock sold that didn't exist. Every piece of code looked correct when read one request at a time. ([ACIDRain](http://www.bailis.org/papers/acidrain-sigmod2017.pdf))

</Note>

### Fix 1: make the check part of the write

Instead of reading the count and deciding in your code, give the decision to the database in a single statement:

```sql
UPDATE slots
SET    booked = booked + 1
WHERE  id = 7 AND booked < capacity;
-- then check how many rows changed: 1 means booked, 0 means full
```

Why this works: when a request changes a row, the database **locks** that row until the request commits. Anyone else who wants to change the same row waits in line. When it's their turn, the database checks the `WHERE` condition again against the latest data, not against an old photo.

<Race a="Alice's request" b="Bob's request" result="Result: 10 booked, and Bob gets a clear &quot;slot is full&quot;" tone="good" steps={[
  { a: "UPDATE … WHERE booked < capacity. Row is locked; count goes to 10" },
  { b: "Same UPDATE. Row is locked by Alice, so it waits", note: true },
  { a: "Commits. Lock released", tone: "good" },
  { b: "Re-checks: 10 < 10 is false. Changes 0 rows, so the app shows \"full\"", tone: "good" }
]} />

This is the right fix most of the time: counters, stock levels, balances, seat maps. It's one statement, it needs no extra code, and it can't race.

### Fix 2: hold the row while you decide

Sometimes the decision needs logic you can't fit in a `WHERE` clause, like checking a membership tier or applying a discount rule. Then lock the row *before* you read it:

```sql
BEGIN;
SELECT booked, capacity FROM slots WHERE id = 7 FOR UPDATE;  -- lock it now
-- …your application logic decides…
UPDATE slots SET booked = 10 WHERE id = 7;
COMMIT;
```

`FOR UPDATE` means "I'm going to change this, so nobody else may change it, or lock it, until I'm done." Bob's request stops at its own `SELECT … FOR UPDATE` and waits. When Alice commits, Bob reads the fresh count of 10 and correctly says no.

The cost is that everyone after Alice queues. Keep the time between `BEGIN` and `COMMIT` tiny, and never call another service (a payment API, an email sender) while holding the lock. One slow network call and every booking for that slot waits behind it.

### Fix 3: check nothing changed when you save

For things people edit slowly, like a form left open for ten minutes, holding a lock that long isn't an option. Instead, give each row a `version` number and save only if it hasn't moved since you read it:

```sql
UPDATE slots SET booked = 10, version = 42
WHERE  id = 7 AND version = 41;
-- 0 rows changed means someone else saved first: reload and try again
```

It's the same idea as a document editor telling you "this file changed since you opened it". Nobody waits, and conflicts are caught at save time. This is called **optimistic locking**. Fix 2 is the **pessimistic** version.

### The safety net: let the database refuse bad data

Whichever fix you use, also tell the database what must never be true, so a bug in some other code path can't break it:

```sql
ALTER TABLE slots ADD CONSTRAINT not_overbooked CHECK (booked <= capacity);
```

Now an overbooking attempt fails with an error instead of quietly succeeding. A constraint is the cheapest insurance on this page.

### A harder race: two people, two different rows

The fixes so far all work because Alice and Bob fought over the **same row**, so the database could make one wait. Some races don't share a row.

A hospital requires at least one doctor on call. Dr Shah and Dr Lee are both on call, both feel unwell, and both press "Go off call" at the same moment:

<Race a="Dr Shah" b="Dr Lee" result="Result: nobody is on call" steps={[
  { a: "Counts doctors on call: 2. Fine to leave" },
  { b: "Counts doctors on call: 2. Fine to leave" },
  { a: "Updates own row: off call", tone: "bad" },
  { b: "Updates own row: off call", tone: "bad" }
]} />

Each request changed a *different* row (its own), so no row lock ever made one of them wait. The rule they broke, "at least one doctor", lives across rows. This is called **write skew**, and booking systems hit it too: "a coach can't have two sessions at the same time" is a rule about a row that doesn't exist yet, so there's nothing to lock. The example comes from Martin Kleppmann's *Designing Data-Intensive Applications*.

There are two ways out:

- **Lock everything the decision read.** Instead of just counting, select the on-call doctors' rows with `FOR UPDATE` and count them in your code. Now both rows are locked, so the second request has to wait for the first, and then sees only one doctor left. (Postgres won't put `FOR UPDATE` on a `COUNT(*)` itself.)
- **Use the strictest isolation level, `SERIALIZABLE`.** The database watches what each transaction read and wrote. If two of them could only have produced their result by running at the same time, as opposed to one after the other, it cancels one with an error. Your code catches that error and runs the whole transaction again, and the retry sees the new state.

Postgres can also enforce "no overlapping time ranges" directly, with an **exclusion constraint**, so a double-booked coach is refused like the `CHECK` above.

### The isolation levels, now that you've seen the problems

Each level shields transactions from a few more kinds of interference. Here are all five kinds, with the two you've already met:

<Table>

| What can go wrong | In plain words | Read Committed | Repeatable Read | Serializable |
| :--- | :--- | :--- | :--- | :--- |
| **Dirty read** | You see someone's change before they've committed it, and then they cancel it | <Pill tone="good">Prevented</Pill> | <Pill tone="good">Prevented</Pill> | <Pill tone="good">Prevented</Pill> |
| **Non-repeatable read** | You read the same row twice in one transaction and get two different answers | <Pill tone="bad">Allowed</Pill> | <Pill tone="good">Prevented</Pill> | <Pill tone="good">Prevented</Pill> |
| **Phantom** | You run the same search twice and new rows have appeared | <Pill tone="bad">Allowed</Pill> | <Pill tone="mid">Varies</Pill> | <Pill tone="good">Prevented</Pill> |
| **Lost update** | Alice and Bob: two read-then-write cycles overlap and one overwrites the other | <Pill tone="bad">Allowed</Pill> | <Pill tone="mid">Postgres only</Pill> | <Pill tone="good">Prevented</Pill> |
| **Write skew** | The doctors: each changes a different row and together they break a rule | <Pill tone="bad">Allowed</Pill> | <Pill tone="bad">Allowed</Pill> | <Pill tone="good">Prevented</Pill> |

</Table>

Postgres, Oracle and SQL Server default to **Read Committed**; MySQL defaults to **Repeatable Read**. So out of the box, the Alice-and-Bob race goes through on all of them. Postgres's Repeatable Read does catch it: it cancels Bob's update with an error, which your code has to retry.

The same level name doesn't mean exactly the same thing in every database. "Varies" in the table is the clearest case: the SQL standard allows phantoms at Repeatable Read, but Postgres and MySQL both stop them for ordinary reads. Martin Kleppmann's [Hermitage](https://github.com/ept/hermitage) project tests each database against each problem, so check yours there rather than trusting the name.

### One more trap: the transaction left open

Remember the photos? The database has to keep every old version of a row that some open transaction might still look at. A transaction that starts and then sits idle forces it to keep everything changed since it began, across the whole database.

That happens more than you'd think: code that opens a transaction and then calls a slow API, a debugger paused mid-request, an error path that forgets to roll back. Old versions pile up, tables grow, and every query slows down, with no code change and no traffic change to explain it.

Two settings stop it: `idle_in_transaction_session_timeout` ends transactions that sit idle too long, and `statement_timeout` ends queries that run too long. Then alert on any connection idle in a transaction for more than a minute.

<Note type="key" label="What to remember">

- A transaction means all or nothing. It does not stop other requests reading the same data at the same time.
- Read-then-decide-then-write in your code is a race unless something stops it.
- First choice: put the check inside the write. Then add a constraint as a safety net. Use locks or `SERIALIZABLE` only when the rule can't be written as one statement.

Once the data lives on several machines, all of this gets harder. That's the subject of [Consistency & CAP](/guides/consistency-cap/).

</Note>

<Collapse id="migrations" title="2. Schema changes without an outage">

Locks cause a second kind of outage, and this one happens during deploys rather than at peak traffic: changing the shape of a table.

### Why a tiny change can freeze a table

To change a table's structure, such as adding a column, the database needs the table completely to itself for a moment. Postgres calls this an `ACCESS EXCLUSIVE` lock: while it's held, nobody else can even read the table.

On its own that's fine, because adding a column usually takes milliseconds. The trap is the **queue**. If a long query is already reading the table, the migration has to wait for it to finish. And while the migration is waiting at the door, every new query that arrives lines up *behind the migration*, because the database serves locks in order. [GoCardless wrote up exactly this failure](https://gocardless.com/blog/zero-downtime-postgres-migrations-the-hard-parts/):

```trace
**$ 14:02:00**  a report starts: SELECT … FROM orders   (40 s)
**$ 14:02:05**  ALTER TABLE orders …        ~~queued for its lock~~
  14:02:05+  every new query on orders   ~~queued behind it~~
**$ 14:02:40**  report ends; ALTER runs in 0.2 s; queue drains

**verdict:** ~~35 s outage on orders~~ from a 0.2 s migration
```

The migration itself took 0.2 seconds. The orders table was unusable for 35, because the migration was waiting at the door and blocking everyone behind it.

### Four habits that prevent it

- **Give up fast, then retry.** Set `lock_timeout` to a few seconds before each migration. If it can't get the table quickly, it fails instead of blocking everyone, and you run it again a moment later.
- **Build indexes in the background.** `CREATE INDEX CONCURRENTLY` in Postgres, or online DDL in MySQL, builds the index without stopping writes. It's slower, but nobody waits.
- **Add rules in two steps.** Adding a constraint normally checks every existing row while holding the table. Add it as `NOT VALID` first, which is instant and applies to new rows, then run `VALIDATE CONSTRAINT` separately, which checks old rows without blocking writes.
- **Prefer the changes that are instant.** Modern Postgres adds a column with a fixed default without rewriting the table, and MySQL 8 can do some changes `INSTANT`ly. For heavy changes in MySQL, tools like `gh-ost` build a copy of the table in the background and swap it in at the end.

### Changes that span several deploys

There's a second problem, and it's about your code rather than the database. Most deploys are **rolling**: new servers start while old ones are still finishing their requests, so for a minute or two, old code and new code run side by side against the same database.

Suppose a migration renames `users.name` to `full_name`, and runs just before the new code starts. For that minute, every old server is still asking for `name`, which no longer exists, and every one of those requests fails.

The fix is to never make a breaking change in one step. Split it into small changes that each work with both the old and the new code. This is called **expand and contract**:

<Stack>
  <Layer idx="1" title="Expand" speed="deploy 1">Add `full_name` as a new, empty column. Old code doesn't know it exists, so nothing breaks.</Layer>
  <Layer idx="2" title="Write to both" speed="deploy 2">New code saves to both `name` and `full_name`, but still reads `name`.</Layer>
  <Layer idx="3" title="Backfill" speed="background job">Copy old rows across in small batches, a few thousand at a time with pauses, so you never hold a big lock.</Layer>
  <Layer idx="4" title="Switch reads" speed="deploy 3">Code now reads `full_name`. A check confirms both columns agree.</Layer>
  <Layer idx="5" title="Stop writing the old column" speed="deploy 4">Nothing uses `name` any more.</Layer>
  <Layer idx="6" title="Contract" speed="later release">Drop `name`.</Layer>
</Stack>

It feels slow, but every step can be undone until the last one, and none of them ever breaks a running server. Stripe used this pattern to move millions of live subscription records between tables without downtime; [their write-up](https://stripe.com/blog/online-migrations) is the best one available.

With queries fast, writes correct and deploys safe, one database server is in good shape. When it still can't keep up, [Part 3](/guides/database-scaling/offload/) starts by not asking it at all.

</Collapse>

<Collapse id="check" title="Check your understanding">

<Quiz q="You wrapped the read and the save in one transaction and still sold 11 places in a slot of 10. Why didn't the transaction protect you?" options={["The transaction rolled back without telling you", "A transaction means all or nothing; it doesn't stop another request reading the same count before you save", "The save ran outside the transaction"]} answer={1}>

A transaction makes your changes all-or-nothing; it doesn't stop other transactions from reading the same row before you write it. At Read Committed, the Postgres default, both requests read `booked = 9`, both decided there was room, and both saved.

Fix it by making the check part of the write (`UPDATE … WHERE booked < capacity`, then check how many rows changed), adding a `CHECK` constraint as a safety net, or locking the row with `SELECT … FOR UPDATE` before deciding.

</Quiz>

<Quiz q="Two doctors both go off call at the same moment, and the hospital is left with nobody on call. Why didn't row locks stop it?" options={["Each request changed a different row, so neither had to wait for the other", "Row locks don't work at the Read Committed level", "The count query was too slow"]} answer={0}>

Row locks only make requests wait when they want to change the same row. Each doctor changed only their own row, so both went straight through. The rule they broke, "at least one doctor on call", spans several rows. That's write skew.

Fix it by locking every row the decision depended on (select the on-call rows with `FOR UPDATE` before counting), or by running the transaction as `SERIALIZABLE` and retrying when the database cancels one.

</Quiz>

<Quiz q="You moved the payment path to SERIALIZABLE. At peak, logs fill with 'could not serialize access' errors. What should you do?" options={["Retry the whole transaction from the start, and keep things like emails and card charges out of the retried part", "Go back to Read Committed, because the errors mean Serializable is misbehaving", "Add more connections so the transactions stop colliding"]} answer={0}>

The errors are the database doing its job. It found two transactions that could only have produced their result by running at the same time, and cancelled one rather than let it corrupt data.

With `SERIALIZABLE`, your code is expected to retry the whole transaction from `BEGIN`, re-reading everything, with a short backoff. Anything with an effect outside the database, like an email or a card charge, must not run inside the part you retry, or must be safe to repeat; see [Message Queues](/guides/message-queues/). And if retries pile up at peak, the contention is real, and a single conditional `UPDATE` may be the better tool.

</Quiz>

<Quiz q="Your pipeline runs migrations, then swaps in the new servers. After a deploy that renamed a column, you get about 40 seconds of errors. What happened?" options={["The migration held a table lock for 40 seconds", "The new servers started before the migration finished", "Old servers kept serving during the swap and asked for a column that no longer existed"]} answer={2}>

For those 40 seconds, the old servers were still handling requests, and they asked for the old column name, which the migration had already removed. The pipeline is fine; the migration wasn't compatible with the code still running.

Split it with expand and contract: add the new column, write to both, backfill, switch reads, and drop the old column in a later deploy. The rule: a migration must work with both the code before it and the code after it.

</Quiz>
