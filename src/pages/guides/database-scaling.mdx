<ColdOpen tag="◇ 09:14 · the query that was fine last quarter">

Nobody changed the code. A single `SELECT` against the orders table has shipped untouched for eighteen months — at 100,000 rows it returned in 3 ms and nobody ever looked at it again. The table is now 40 million rows, the index that would have saved it was never created, and this morning that query takes six seconds, scanning the whole table and holding a database connection for every one of them. 

At 30 requests a second, six seconds each, you need 180 connections in flight against a pool of 100. The pool empties. And now the login page is timing out, and the health check is timing out, and the settings endpoint that has never in its life touched the orders table is timing out — because they are all queued behind a connection that isn't coming back. The CPU graph looks almost calm; the box is just waiting on disk. It is not a capacity problem. It is one missing index, and it took the whole product down.

</ColdOpen>

<Collapse id="why" title="1. Why the database breaks first">

You can add app servers behind a [load balancer](/guides/load-balancing/) almost endlessly — they're stateless and interchangeable. The database is different: it holds *state*, and there's usually one authoritative copy that every write must go through. That makes it the natural bottleneck.

Two pressures build up, and they need completely different fixes:

- **Read pressure** — too many queries reading data. Usually the *easier* problem; you can serve reads from copies or caches.
- **Write pressure** — too many inserts/updates, or simply too much data to fit and index on one machine. The *harder* problem, because all writes contend for the single source of truth.

<Note type="key" label="The golden rule of scaling">

Every rung up this ladder adds complexity and new failure modes. So climb it **only as far as your load actually forces you to** — and no further. Most applications never need sharding. Diagnose whether you're read-bound or write-bound first; it decides which rung you need. The next section is how you actually do that.

</Note>

</Collapse>

<Collapse id="diagnose" title="2. Diagnose first: read-bound or write-bound?">

"The database is slow" is not a diagnosis, and the two pressures send you to completely different rungs. Worse, the wrong answer is expensive in a specific way: if you're write-bound and you add read replicas, you have not just failed to help — you've added machines that each replay *every single write*, plus a replication stream to monitor and a new failure mode. You made it worse and you paid for the privilege.

### Quick Triage Decision Matrix

<Table>

| If You Observe... | Diagnostic Meaning | Right Scaling Move |
| :--- | :--- | :--- |
| `SELECT` p99 latency climbing; `INSERT` flat | **Read-bound** workload | Indexes $\rightarrow$ Cache $\rightarrow$ Read Replicas |
| Replication lag climbing under write bursts | **Write-volume bound** | Batching $\rightarrow$ Scale Up $\rightarrow$ Sharding |
| Lock wait times climbing (`wait_event_type = 'Lock'`) | **Write contention / Lock bottleneck** | Shorten transactions, remove external I/O |
| Buffer cache hit ratio dropping below 99% | Working set outgrew RAM | Vertical scaling (Add RAM to single box) |
| Rows examined / rows returned ratio $> 100$ | Unindexed sequential scans | Add index / rewrite query (Do NOT scale hardware) |

</Table>

Here is how you collect these five signals from production:

### 1. The read/write mix, from the database's own counters
Every engine counts this for you:
- **PostgreSQL**: `pg_stat_database` gives `tup_returned` / `tup_fetched` against `tup_inserted + tup_updated + tup_deleted`.
- **MySQL**: `SHOW GLOBAL STATUS` gives `Com_select` vs. `Com_insert + Com_update + Com_delete`.

*Tip*: Take two samples an hour apart and subtract — the absolute numbers are cumulative since restart, so the delta is your real signal.

### 2. Which p99 latency actually moved
Split your latency percentiles by statement type and look at what degraded *when the trouble started*, not what is slowest in absolute terms. If `SELECT` p99 went from 40 ms to 600 ms while `INSERT` p99 barely moved, you are read-bound. Use `pg_stat_statements` (ordered by `total_exec_time`) or the MySQL slow query log to identify the target queries.

### 3. Replication lag climbing vs. lock wait time climbing
- **Replication lag rising**: The primary is generating write-ahead log faster than replicas can apply it — a write-volume problem by definition.
- **Lock wait time rising**: Writes are contending with each other or long-running readers. Check `pg_stat_activity` (`wait_event_type = 'Lock'`) or `SHOW ENGINE INNODB STATUS`.

### 4. Buffer cache hit ratio
From `pg_stat_database`: `blks_hit / (blks_hit + blks_read)`. For OLTP workloads, target **>99%**. When this ratio drops, your active working set has outgrown RAM and reads are falling back to disk — a read-side problem that vertical scaling (more RAM) fixes instantly.

### 5. Rows examined per row returned
The single most diagnostic ratio in system design:

**Efficiency Ratio = Rows Examined / Rows Returned**

- **Near 1**: Healthy query indexing.
- **> 100**: The database is doing 100× more work than needed. The fix is an index or query rewrite — not a bigger machine or replicas.

```trace
$ triage — pg_stat_database delta (09:00 → 10:00)
  rows returned by reads .............. 4,120,000,000
  rows inserted + updated + deleted ...     3,900,000   (≈ 1000:1 ratio)

$ latency breakdown (pg_stat_statements)
  SELECT p99 ..........  42 ms  →  610 ms   [◀ READ BOTTLENECK]
  INSERT p99 ..........   6 ms  →    7 ms   [✓ Unchanged]

$ supporting telemetry
  buffer cache hit ....  99.6%  →  91.2%    (Working set left RAM)
  rows examined/returned    1.2 →    3,400  (Plan went sequential scan)
  replication lag .....  40 ms  (flat)      (Write pipeline healthy)

VERDICT: READ-BOUND → Index the query, then cache, then replicas.
```

### Action Plan by Diagnosis

- **Read-bound**: **Indexes → Cache → Replicas**. Indexing is free and yields up to 100× gains. Caching removes the query entirely. Replicas are last because they introduce distributed consistency trade-offs.
- **Write-bound**: **Batching → Scale Up → Partitioning → Sharding**. Batching shares transactions and `fsync` calls. Vertical scaling raises the ceiling with fast NVMe/RAM. Partitioning organizes maintenance. Sharding multiplies write capacity. *(Note: Read replicas do NOT help write-bound systems!)*

<Note type="warn" label="The third answer: application-side bottlenecks">

If database CPU, I/O, and lock waits are all normal but application latency is high, the bottleneck is in front of the database — connection pool queueing, N+1 query loops, or missing query timeouts.

</Note>

</Collapse>

<Collapse id="rule-zero" title="3. Rule zero: make one box faster before you add boxes">

Before adopting distributed infrastructure, exhaust single-database optimization. They routinely deliver 10–100× gains at a fraction of the operational cost.

<CardGrid>
  <Card title="1. Indexing">
    The single highest-leverage optimization. Indexes turn full table scans into fast B-tree lookups.
  </Card>
  <Card title="2. Query & Schema Tuning">
    Eliminate N+1 query patterns, select specific columns instead of `SELECT *`, analyze `EXPLAIN` execution plans.
  </Card>
  <Card title="3. Vertical Scaling (Scale Up)">
    Upgrade to larger hardware instances (more RAM, higher IOPS NVMe). Zero application code changes required.
  </Card>
  <Card title="4. Connection Pooling">
    Multiplex thousands of short-lived client connections into a tight pool of persistent DB handles via PgBouncer or RDS Proxy.
  </Card>
</CardGrid>

<Note label="Single-node efficiency beats premature distribution">

A well-indexed database on a single well-tuned instance routinely outperforms a poorly designed sharded cluster.

<Question q="Check yourself: Your p99 latency doubled after increasing connection pool size from 20 to 200. Throughput remained flat. Why?">

Because 20 connections were already saturating parallel execution capacity. Concurrency follows Little's Law (**Concurrency = Throughput × Latency**). Extra connections do not add parallelism; they introduce context switching, CPU cache thrashing, and OS process overhead.

</Question>

</Note>

</Collapse>

<Collapse id="worked-index" title="4. Worked example: the unused index">

Having an index defined on a table does not guarantee the database engine uses it. Here are two classic failure modes encountered in production.

### Case 1: Composite Index & Leftmost Prefix Rule

Consider an `events` table with 40 million rows and the following composite index:

```sql
CREATE INDEX idx_events_org_created ON events (org_id, created_at);

-- FAST: Uses leading column (org_id)
SELECT * FROM events 
WHERE org_id = 42 
  AND created_at > NOW() - INTERVAL '7 days';

-- SLOW: Scans entire table! Skips leading column (org_id)
SELECT * FROM events 
WHERE created_at > NOW() - INTERVAL '7 days';
```

<Note type="key" label="Mental Model: The Phonebook Analogy">

Think of a composite index on `(org_id, created_at)` like a printed phonebook sorted by **(Last Name, First Name)**. 
- Searching for someone with Last Name `"Smith"` and First Name `"John"` is instantaneous.
- Searching for everyone with First Name `"John"` without specifying a Last Name forces you to read every single page in the book from start to finish.
That is the **Leftmost Prefix Rule**: an index on `(A, B, C)` can only serve queries filtering by `A`, `A AND B`, or `A AND B AND C`.

</Note>

#### Performance Impact (EXPLAIN ANALYZE)

**Before (Missing `created_at` leading index):**
```trace
Seq Scan on events  (cost=0.00..982431.00 rows=1204 width=88)
                    (actual time=0.031..4128.774 rows=1187 loops=1)
  Filter: (created_at > (now() - '7 days'::interval))
  Rows Removed by Filter: 39,998,813
Execution Time: 4131.006 ms  [❌ FULL TABLE SCAN]
```

**After (`CREATE INDEX idx_events_created ON events (created_at);`):**
```trace
Index Scan using idx_events_created on events
  (cost=0.44..421.90 rows=1204 width=88)
  (actual time=0.028..1.902 rows=1187 loops=1)
  Index Cond: (created_at > (now() - '7 days'::interval))
Execution Time: 2.140 ms     [✓ 1900× FASTER]
```

### Case 2: Function Wrapping the Column

```sql
CREATE INDEX idx_users_email ON users (email);

-- SLOW: Function wrapper disables standard index lookup!
SELECT * FROM users WHERE lower(email) = 'ada@example.com';
```

Because the index stores raw `email` values, applying `lower()` forces a full table scan. 
**Solution**: Create an expression index or normalize data on write:
```sql
CREATE INDEX idx_users_email_lower ON users (lower(email));
```

<Note type="warn" label="Production vs Dev Data">

Always validate index performance with `EXPLAIN (ANALYZE, BUFFERS)` on production-scale data volumes. Small dev datasets (e.g. 5,000 rows) will mask performance issues because query planners deliberately favor sequential scans for small tables.

</Note>

</Collapse>

<Collapse id="replicas" title="5. Read replicas & replication">

<DiagramDatabaseScaling1 />

Read replication isolates write traffic to a single **Primary** (leader) node while offloading query volume to horizontal **Replicas** (followers).

<Stack>
  <Layer idx="W" title="Primary (Leader)" speed="Source of Truth">
    Handles 100% of mutation writes (INSERT, UPDATE, DELETE). Streams changes to replicas.
  </Layer>
  <Arrow>↓ Asynchronous or Synchronous WAL Stream ↓</Arrow>
  <Layer idx="R" title="Replicas (Followers)" speed="Read Scaling & Failover">
    Serve read requests. Provide high availability for automated failover.
  </Layer>
</Stack>

### Replication Modes Comparison

| Replication Mode | Latency Impact | Data Loss Risk on Failover | Use Case |
| :--- | :--- | :--- | :--- |
| **Asynchronous** | Zero write latency overhead | Small window of un-replicated writes | Default for high-throughput web apps |
| **Synchronous** | Higher write latency (waits for ACK) | Near zero data loss | Financial transactions, critical audit logs |

<Note type="warn" label="Gotcha: Replication Lag & Read-Your-Own-Writes">

In asynchronous mode, replicas lag behind the primary by milliseconds to seconds. A user posting a comment and immediately refreshing may read a stale replica.

**Three Fix Strategies**:
1. **Primary Grace Window**: Route user reads to Primary for 5 seconds after any write.
2. **Commit Token Validation**: Pass WAL commit position (Postgres LSN / MySQL GTID) in session cookies and wait for replica replay.
3. **Strict Path Pinning**: Force critical paths (e.g., user account settings, checkout confirmation) to execute on Primary.

</Note>

<Question q="Check yourself: You added three read replicas, but read latency did not improve. What went wrong?">

1. **Unindexed queries**: Replicas run the same schema and query plans; unindexed scans remain slow on all nodes.
2. **Transaction routing**: Reads executed inside explicit transactions (`BEGIN ... END`) are pinned to the Primary by default by most connection routers.

</Question>

</Collapse>

<Collapse id="partition" title="6. Partitioning: splitting a table">

<DiagramDatabaseScaling2 />

<CardGrid>
  <Card title="Partitioning (1 Machine)">
    Divides a single large table into smaller physical file segments **on the same database server**. Helps with table bloat and fast index scans.
  </Card>
  <Card title="Sharding (N Machines)">
    Distributes table partitions across **multiple independent server instances** over a network. Multiplies write throughput and total storage capacity.
  </Card>
</CardGrid>

Partitioning divides a single logical table into smaller structural subsets on a single database instance:

- **Vertical Partitioning**: Split by *columns or domain tables*. Move billing tables to DB-A and user media tables to DB-B.
- **Horizontal Partitioning**: Split by *rows*. Group rows by range (e.g. `created_at` by month) or hash key. The database query engine automatically prunes unneeded partitions.

Horizontal partitioning reduces index bloat and makes archival maintenance instant (`DROP TABLE partition_2024_q1`). However, it remains constrained by single-machine CPU/IOPS limits.

</Collapse>

<Collapse id="sharding" title="7. Sharding: splitting across machines">

<Note type="wild" label="◈ In the wild · Figma">

Figma initially scaled via **vertical partitioning** (separating Files and Organizations databases). As tables grew to billions of rows, they introduced **horizontal sharding** using an internal proxy router (DBProxy) with logical shard keys (`UserID`, `FileID`, `OrgID`) to keep relational joins co-located on single shards.

</Note>

Sharding distributes horizontal partitions across **independent database instances**. Storage, write IOPS, and memory scale horizontally across the cluster.

### Sharding Strategy Matrix

<Table>

| Strategy | Mapping Logic | Key Advantage | Main Disadvantage |
| :--- | :--- | :--- | :--- |
| **Range-Based** | Contiguous ranges (A-M, N-Z or dates) | Fast range scans | Hot spots on active ranges (e.g. current date) |
| **Hash-Based** | hash(key) mod N | Uniform distribution | Range queries fan out to all shards |
| **Directory-Based** | Central lookup table | Flexible key placement | Lookup service becomes a central dependency |

</Table>

### The Four Taxes of Sharding

1. **Hot Keys**: A single viral key lands on one shard, overloading that instance regardless of hashing uniform distribution.
2. **Cross-Shard Joins**: Queries spanning multiple shards require application-level scatter-gather merges.
3. **Distributed Transactions**: Multi-shard atomicity requires 2-Phase Commit (2PC) or saga patterns.
4. **Resharding Overhead**: Rebalancing shards requires live data migration across networks.

<Note label="Pro Architecture Pattern: Logical vs Physical Shards">

Allocate 1,024 **logical shards** at launch and map them to a small cluster of physical machines (e.g., 4 instances holding 256 logical shards each). Scaling out simply moves logical shards between nodes without changing key hashing logic.

</Note>

</Collapse>

<Collapse id="worked-shard" title="8. Worked example: picking a shard key as arithmetic">

Selecting a shard key requires analyzing dataset sizing, write rates, and critical read query paths. Let's work through a multi-tenant messaging system (Slack-like architecture).

### Step 1: Data & Load Arithmetic

```trace
$ Dataset Estimates
  workspaces .......................... 250,000
  messages / day ...................... 30,000,000
  avg row size + index overhead ....... 400 bytes
  data growth / day ................... 12 GB/day
  retention period .................... 2 years (730 days)

$ Storage & Capacity Projections
  total rows (30M × 730) .............. 21,900,000,000 rows
  total raw data size (21.9B × 400B) .. ~8.8 TB
  target max storage per shard ........ 1.5 TB
  minimum physical shards required .... 8.8 / 1.5 = 5.9 → 6 shards
  provisioned capacity (power of 2) ... 16 physical shards
  logical shard allocation ............ 1,024 logical shards

$ Write Throughput
  average write rate (30M / 86,400) ... ~350 writes/s
  peak write rate (4× multiplier) ..... ~1,400 writes/s
  per-shard peak write rate (1,400 / 16) ~90 writes/s
```

*Key Insight*: 90 writes/sec per shard is negligible for database engines. Sharding is required here due to **8.8 TB storage volume and maintenance costs**, not write IOPS.

### Step 2: Evaluating Shard Key Candidates

<Table>

| Candidate Shard Key | Single-Shard Query Path | Fan-Out / Breakdown Penalty | Evaluation Verdict |
| :--- | :--- | :--- | :--- |
| `message_id` | Single message lookup | Fetching recent channel history requires querying all 16 shards | <Pill tone="bad">REJECT</Pill> Poor query locality |
| `created_at` (Time Range) | Historical log archival | 100% of active write traffic hits the single newest shard | <Pill tone="bad">REJECT</Pill> Severe write hotspot |
| `user_id` | User activity feeds | Channel rendering requires fanning out across all user shards | <Pill tone="bad">REJECT</Pill> Wrong boundary |
| `channel_id` | Single channel message history | Workspace-wide queries (member lists, unreads) fan out | <Pill tone="mid">MARGINAL</Pill> Too fine-grained |
| `workspace_id` | Channels, messages, members, and workspace search stay co-located on 1 shard | Large enterprise tenants require sub-sharding or dedicated instances | <Pill tone="good">RECOMMENDED</Pill> Aligns with domain model |

</Table>

<Note type="key" label="The 3-Step Shard Key Framework">

1. **Find the dominant query boundary**: Identify the entity parameter present in 95%+ of your application's hot read requests (`workspace_id`, `tenant_id`, `account_id`).
2. **Verify tenant variance**: Check if single large tenants (whales) outgrow a physical shard capacity. If yes, prepare a directory mapping or sub-sharding key.
3. **Isolate global search**: Offload non-tenant queries (global search, cross-tenant metrics) to a CDC pipeline into Elasticsearch/Snowflake rather than querying database shards.

</Note>

</Collapse>

<Collapse id="avoid" title="9. Avoiding the query entirely">

Offload database operations by implementing architectural buffers in front of storage engines:

- **Application Caching**: Store hot read keys in Redis/Memcached to eliminate database round trips ([Caching Guide](/guides/understanding-caching/)).
- **Read-Optimized Denormalization**: Maintain pre-aggregated views or flattened JSON document structures to simplify queries.
- **CQRS (Command Query Responsibility Segregation)**: Separate transactional write models from specialized read models populated via event streams.
- **Write Queue Buffering**: Place message queues (e.g. Kafka/RabbitMQ) in front of write paths to convert unpredictable request spikes into smooth batch writes ([Message Queues Guide](/guides/message-queues/)).

</Collapse>

<Collapse id="cap" title="10. CAP & consistency: the trade-off underneath">

When database state is distributed across network partitions, the **CAP Theorem** forces a choice between **Strong Consistency** and **High Availability**:

- **Strong Consistency (CP)**: Reads return the latest write across all nodes. Requests fail or block if nodes cannot communicate. Required for financial ledgers and inventory counts.
- **Eventual Consistency (AP)**: Replicas handle reads immediately, but may return stale data briefly. System remains available during network partitions ([Consistency & CAP Guide](/guides/consistency-cap/)).

</Collapse>

<Collapse id="gotchas" title="12. The gotchas that bite later">

### 1. Connection Pool Sizing is Physics, Not Superstition
- 🚨 **The Symptom**: Increasing connection pool size from 20 to 200 doubles query latency while throughput stays flat.
- ⚡ **Why It Breaks**: Extra connections exceed physical CPU core concurrency limits. Postgres spawns separate backend processes per connection, causing CPU context switching and memory thrashing.
- 🛠️ **The Fix**: Size connection pools strictly using HikariCP formula: **Pool Size = (CPU Cores × 2) + Effective Spindle Count**.

### 2. Idle-In-Transaction Leaks Block VACUUM
- 🚨 **The Symptom**: PostgreSQL table and index size inflates dramatically; sequential scans get slower across all tables.
- ⚡ **Why It Breaks**: Connections left in `idle in transaction` hold open MVCC snapshots. PostgreSQL `VACUUM` cannot reclaim dead row versions updated *after* that snapshot started.
- 🛠️ **The Fix**: Set `idle_in_transaction_session_timeout = 60000` (60s) and never make external HTTP API calls inside a database transaction block.

### 3. Non-Blocking Schema Migrations
- 🚨 **The Symptom**: Running `ALTER TABLE` on a 40-million row table locks out all application traffic and causes site outage.
- ⚡ **Why It Breaks**: `ALTER TABLE` requests an `ACCESS EXCLUSIVE` lock. In PostgreSQL, queued lock requests block all subsequent read/write queries behind them.
- 🛠️ **The Fix**: Configure short `lock_timeout` values on migrations and use online DDL shadow-copy tools (`gh-ost`, `pt-online-schema-change`, or `CREATE INDEX CONCURRENTLY`).

### 4. `OFFSET` Pagination Cost is $O(N)$
- 🚨 **The Symptom**: Deep pagination endpoints (e.g. Page 5,000) take multi-second response times and trigger database CPU spikes.
- ⚡ **Why It Breaks**: `OFFSET 100000` forces the database to read, sort, and discard the first 100,000 rows before returning the 20 requested rows.
- 🛠️ **The Fix**: Replace `OFFSET` with Keyset (Seek) Pagination ($O(1)$ lookup):
```sql
SELECT * FROM messages WHERE (created_at, id) < (:last_created, :last_id)
ORDER BY created_at DESC, id DESC LIMIT 20;
```

### 5. Local vs Global Secondary Indexes under Sharding
- 🚨 **The Symptom**: Login-by-email query consumes 100% of cluster CPU after sharding by `user_id`.
- ⚡ **Why It Breaks**: Local indexes require querying all 16 shards in parallel (scatter-gather penalty) for non-shard-key lookups.
- 🛠️ **The Fix**: Create an asynchronous Global Secondary Index (e.g., DynamoDB GSI) mapping `email → user_id` to route requests to a single shard.

### 6. Replication Lag Spikes under Peak Load
- 🚨 **The Symptom**: Intermittent "read-your-own-writes" bugs affect 2% of users during peak traffic bursts.
- ⚡ **Why It Breaks**: Async replication lag is non-linear; single-threaded follower log replay falls behind during heavy primary write spikes.
- 🛠️ **The Fix**: Carry LSN/GTID commit tokens in user sessions or enforce a 5-second sticky primary read window after user mutations.

### 7. The Permanent Operational Tax of Sharding
- 🚨 **The Symptom**: Maintenance costs explode after scaling to 16 database shards.
- ⚡ **Why It Breaks**: Sharding multiplies administrative overhead across backups, point-in-time recovery, schema migrations, and cross-AZ data transfer fees.
- 🛠️ **The Fix**: Use logical shard abstractions (1,024 logical shards mapped to few physical nodes) to delay adding physical hardware instances.

<Note type="key" label="The core pattern across all gotchas">

Operational scaling bugs rarely appear in local testing or low-volume staging. They are non-linear failures — pool exhaustion, index bloat, lock queueing, and replication lag spikes — that only manifest under real concurrency and production data volumes. Always measure metrics at the extremes.

</Note>

</Collapse>

<Collapse id="recap" title="14. Recap in 60 seconds">

<Recap>

- **Diagnose First**: Measure read/write ratios, row examination efficiency, and latency percentiles before adding infrastructure.
- **Exhaust Single-Node Wins**: Proper indexing, query tuning, and connection pooling eliminate 90% of scaling bottlenecks.
- **Cache Before Replicas**: Caching removes queries entirely without introducing database replication complexity.
- **Shard by Domain Boundaries**: Choose a shard key (e.g. `workspace_id`) that co-locates relational queries on single instances.
- **Account for Operational Overhead**: Sharding multiplies backup procedures, migration complexity, and cross-node latency taxes.

</Recap>

### Reference Metrics Table

<Table numeric>

| Metric / Threshold | Operational Significance | Target Benchmark |
| :--- | :--- | :--- |
| **Examined / Returned Ratio** | Query index efficiency indicator | Target &lt; 10; &gt; 100 indicates missing index |
| **Buffer Cache Hit Ratio** | Memory working set sufficiency | Target &gt; 99% for OLTP workloads |
| **Connection Pool Size** | Maximum useful DB concurrency | (Cores × 2) + Spindles (tens, not hundreds) |
| **Single-Node Write Limit** | Single OLTP instance throughput ceiling | 1,000 - 10,000 writes/sec (tuned NVMe) |
| **Target Physical Shard Size** | Restorability and backup threshold | 0.5 - 1.5 TB per physical shard |

</Table>

Every rung of the scaling ladder trades architectural simplicity for operational complexity. Always demand empirical data before climbing to the next step.
