<ColdOpen tag="◇ the field that was always there">

The change is one line. An optional response field, `legacy_id`, unused and deprecated for two years, gets deleted. It ships on a Tuesday afternoon. Within four minutes, a mobile app version released eighteen months ago starts crashing as it reads the response, because a developer who has long since left wrote a decoder that treats every declared field as required.

That version is on 340,000 phones, and you can't patch them. The rollback takes six minutes, and now the field is permanent: in every response, forever, doing nothing. This is the API tax. The code is trivially deletable; the *promise* is not.

</ColdOpen>

<Collapse id="promise" title="1. Why the API is the one thing you can't change">

Every other guide in this series is about things you can change without anyone noticing. Swap the database, replace the cache, re-shard, move to a different queue: users never know. The API is the one layer where that stops being true. The moment someone else writes code against it, its shape is no longer yours.

### The mistake: designing it like an internal function

Teams tend to design APIs the way they design internal function signatures: whatever is convenient to build today. Then the API outlives three rewrites of the system behind it, and every rewrite is harder because the contract was never meant to outlive its first implementation.

<Note type="key" label="The test that catches most of it">

Before shipping an endpoint, ask: *if we replaced the entire backend next year, would this contract still make sense?*

An endpoint called `/v1/get-user-from-cache` fails at once. So does a response that mirrors your table columns, pagination that exposes your database offsets, or error codes that are your ORM's exception names. Each one welds a caller's code to a detail you were planning to change.

</Note>

### Two audiences who want different things

An API has at least two audiences. The developer building the client wants exactly the data they need, in one round trip. The team that owns the API wants a small number of stable, cacheable, well-understood endpoints. Every API style below settles that tension differently, and none of them makes it go away.

</Collapse>

<Collapse id="styles" title="2. REST, RPC and GraphQL: one screen, three ways">

A mobile app's order screen needs four things: the order, its line items, the customer, and the shipping status. Here's how each of the three main API styles serves that screen, and the bill each one sends later.

### REST: four requests, and the whole web understands them

**REST** models your system as **resources** (things with addresses, like `/orders/88213`) and a fixed set of verbs such as `GET` and `POST`. Its real advantage isn't elegance. It's that every piece of HTTP infrastructure already understands it: shared caches know a `GET` can be stored, proxies know which requests are safe to retry, browsers understand status codes, and every CDN can serve a cacheable response without knowing anything about your domain. That's a lot of infrastructure you don't have to build ([CDNs & the Edge](/guides/cdn-edge/)).

The cost is round trips. The order screen needs four requests. On a mobile connection with 120 ms round-trip time, done one after another, that's nearly half a second of nothing but waiting.

### RPC: call a function on the server

**RPC** (remote procedure call) models your system as functions: `SubmitOrder(request) → response`. gRPC and Thrift are RPC frameworks, and so is the plain JSON-over-POST that most "REST" APIs actually are. It matches how the code is organised, and it generates typed client code from a schema. gRPC also gets HTTP/2 multiplexing (many calls over one connection), binary encoding and streaming.

The cost is that the outside world can't see in. To a cache, a proxy or a browser, every call is an opaque `POST`. You've traded the free HTTP ecosystem for efficiency and type safety. That's often a good trade between your own services, and a poor one for a public API.

### GraphQL: the client asks for exactly what it wants

**GraphQL** gives the client a query language. The order screen sends one query naming exactly the fields it needs, and gets them in one round trip. That genuinely solves mobile **over-fetching** (downloading data you'll throw away), and it ends the "we need a new endpoint for the new screen" cycle that makes APIs sprawl.

<Note type="warn" label="GraphQL moves the cost, it does not remove it">

Now every client can compose any query, and some are expensive in ways nobody anticipated. A nested query walking users → orders → items → recommendations can fan out into thousands of database calls from a single HTTP request, because each level runs one query per item from the level above. That's the **N+1** problem.

Three defences are effectively mandatory: **query depth limiting**, **query cost analysis** (give each field a cost and reject anything over a budget), and **batching** at the data-loading layer, so each level becomes one query instead of N.

Caching is also much harder, because every distinct query string is a distinct response. **Persisted queries**, where clients send the hash of a query registered in advance, restore most of what you lost.

</Note>

### The three side by side

<Table>

| | REST | RPC / gRPC | GraphQL |
| --- | ---- | ---------- | ------- |
| In plain words | Addresses plus HTTP verbs | Call a function on the server | Send a query, get exactly those fields |
| Round trips per screen | Many | Many | One |
| HTTP cacheable | Yes, natively | No | Only with persisted queries |
| Typed client generation | Via OpenAPI | Built in | Built in |
| Cost of a hostile client | Bounded per endpoint | Bounded per method | Unbounded without cost limits |
| Best fit | Public APIs, cacheable reads | Internal service-to-service | Rich clients, many screens |

</Table>

Most large systems end up with all three: gRPC inside, REST at the public edge, and GraphQL for their own apps. That isn't indecision. It's each style used where its trade-off is favourable.

<Note type="key" label="What to remember">

- Once someone builds against your API, its shape is a promise; design it to survive a backend rewrite.
- REST buys the whole HTTP ecosystem, RPC buys efficiency and types, GraphQL buys one round trip per screen.
- GraphQL needs depth limits, cost limits and batching, or one request can cost thousands of queries.

</Note>

</Collapse>
