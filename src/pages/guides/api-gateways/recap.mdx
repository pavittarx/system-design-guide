<Recap>

- **The API outlives the code behind it.** Design the contract so a full backend rewrite wouldn't change it.

- **REST gets the whole HTTP ecosystem for free; RPC gets speed and typed clients; GraphQL gets one round trip per screen.** Each sends a different bill. GraphQL's is that one query can cost thousands of database calls, so depth limits, cost limits and batching are mandatory.

- **Adding is usually safe; removing, renaming, new enum values, stricter validation and changed defaults are not.** The last two break clients without any error to notice.

- **Page with a cursor, not an offset,** and always add a unique tiebreaker to the sort, or rows get duplicated and skipped.

- **4xx means the client must change something before retrying (429 and 408 aside); 5xx means a retry might work.** Never send 200 with an error body: caches, metrics and client error handling all read it as success.

- **The gateway does only the jobs every service shares.** It checks who the caller is; the service that owns the data decides what they may do. Business logic in the gateway grows into a bottleneck every team depends on.

- **Use a token bucket or a sliding-window counter** for almost everything; a fixed window lets a client through at double the limit across a boundary.

- **One limit across many gateways is a coordination problem.** Splitting the limit is cheap and wrong; a shared counter is accurate but adds a round trip and a dependency. Decide what happens when the limiter fails before it does.

- **Reject with 429 and Retry-After, and make sure clients add jitter,** or every rejected client comes back in the same second.

</Recap>

</Collapse>
