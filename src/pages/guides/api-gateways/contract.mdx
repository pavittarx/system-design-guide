<Collapse id="versioning" title="1. Which changes you can ship without a v2">

Your order status can be `pending`, `paid` or `shipped`. You add `refunded`. Nothing was removed, so it feels safe. A partner's code has a `switch` over the three statuses it knows, and every refunded order now falls into its error branch.

The useful question isn't "how do we version?" It's "which changes are safe?" Most are, and teams that know which ones almost never need a v2.

### Adding is usually safe

An old client never sends a field it doesn't know about, so a new *optional* request field is safe: the server fills in a default. A new endpoint is safe because nobody calls it yet. A new response field is usually safe, because most clients ignore fields they don't read, but not if a client validates strictly and rejects anything unfamiliar.

### Removing, renaming and tightening break callers

If a client reads a field and it's gone, the client breaks; that's the [cold open](/guides/api-gateways/). Making an optional field required breaks every caller that doesn't send it. A new enum value breaks clients that handle every known value and treat anything else as an error, as in the `refunded` example.

### The two that break silently

Two kinds of change don't look like API changes in a code review. Someone adds a length check to a validator, and requests that worked yesterday now get a 400. Someone flips a default from `false` to `true`, and behaviour changes with no error at all. A partner's integration starts misbehaving with no version bump and no announcement.

<Table>

| Change | Safe? | Why |
| ------ | ----- | --- |
| Add an optional request field | Safe | Old clients omit it; the server defaults it |
| Add a response field | Usually safe | Unless a client rejects fields it doesn't recognise |
| Add a new endpoint | Safe | Nobody calls it yet |
| Add a new enum value | Breaking | Clients that handle each known value fall into their error branch |
| Make an optional field required | Breaking | Every existing caller starts failing validation |
| Remove or rename a field | Breaking | Callers still read it — see the [cold open](/guides/api-gateways/) |
| Tighten validation | Breaking, invisibly | Requests that worked yesterday now get a 400 |
| Change a default | Breaking, silently | Behaviour changes with no error to notice |

</Table>

### When you genuinely must break

The options, from cheapest to most expensive: a **new field alongside the old one** (both filled in during a transition), a **new endpoint**, a **version in the URL** (`/v2/`), or a **version chosen by a request header**.

URL versioning is the most common because it's visible and easy to debug. Its real cost isn't the routing. It's that you now run two implementations, and the old one still needs security patches long after everyone has stopped caring about it.

<Note label="Deprecation that actually works">

Announce, then instrument, then chase, then remove. Instrumenting is the step people skip and the only one that matters: log every call to the old path with the caller's identity. Then, when you propose removing it, you can say "eleven integrations still call this, here they are" instead of guessing.

HTTP has standard headers for the announcement, `Deprecation` and `Sunset`, and essentially no client reads them, so send email as well.

</Note>

### Make clients forgiving

Write clients to ignore fields they don't know, treat unknown enum values as a defined "other" case, and never assume field order. A client written this way is called a **tolerant reader**. It's the same discipline as schema evolution in [Message Queues & Async](/guides/message-queues/), for the same reason: the producer and the consumer are never upgraded at the same instant.

</Collapse>

<Collapse id="pagination" title="2. Paging through a list that keeps changing">

Every list endpoint eventually returns more rows than anyone wants, so you return them a page at a time. How you do that decides whether it's a small problem or a permanent one.

### Page numbers: skip N rows, take 20

The first version everyone builds is `?page=5&limit=20`, which becomes `OFFSET 80 LIMIT 20` in SQL. This is called **offset pagination**. It has two defects.

The first is speed. `OFFSET 100000` makes the database walk past and throw away a hundred thousand rows before returning anything, so page 5,000 is thousands of times more expensive than page 1.

The second is correctness, and it's worse. Watch what happens when someone adds an order while a user is paging through the newest-first list:

<Race a="User paging (20 per page)" b="Another customer" result="Result: the user sees one order twice. A delete instead would make them skip one" steps={[

  { b: "Places an order. It becomes the newest, pushing every other order down one place" },
  { a: "Loads page 2 (OFFSET 20). Its first row is the order that ended page 1", tone: "bad" }
]} />

The position "20th row" moved under the user's feet. A delete does the opposite: everything shifts up one, and one row is never shown at all.

### Cursors: "carry on after this row"

Instead of counting rows, remember *where you stopped*. The server returns a token encoding the sort values of the last row, such as `?after=eyJpZCI6ODgyMTN9`, and the next query asks for rows that come after it:

```sql
SELECT … FROM orders
WHERE  (created_at, id) < (:ts, :id)
ORDER  BY created_at DESC, id DESC
LIMIT  20;
```

This is called **cursor** (or **keyset**) **pagination**. The query jumps straight to the right spot in the index, so page 5,000 costs the same as page 1. And because the position is defined by a *value* rather than a count, inserts and deletes elsewhere can't shift it.

The trade-off: no "jump to page 47". Almost no real client needs it, and the ones that do can get it from a search index.

<Note type="warn" label="The tiebreaker is not optional">

Sort by a column that isn't unique, like `ORDER BY created_at` when thousands of rows share a timestamp, and the order among those ties is undefined. The database can return them differently each time, so pages duplicate and skip rows at random.

Always add a unique tiebreaker such as `id` to the sort, and include it in the cursor. This is the single most common pagination bug in production, and it shows up as an intermittent, unreproducible "sometimes a record is missing". [Scaling Databases](/guides/database-scaling/) covers the query-plan side.

</Note>

### Keep the cursor a black box

Encode the cursor so it's **opaque**: clients can pass it back but can't read or build one by hand. That keeps you free to change what's inside. The moment a customer discovers your cursor is `base64("id:88213")`, someone will generate cursors, and your encoding becomes part of a contract you never meant to make.

Two more rules: always enforce a **maximum page size** on the server, whatever the client asks for. And don't allow filtering on any field the client likes, because every filterable field is a query you've promised to serve fast, which means an index you've promised to maintain.

<Collapse id="errors" title="3. Errors that tell the client what to do next">

A request fails. The client's code has to decide what to do, usually without understanding your domain at all. An error response has exactly one job: make that decision obvious. There are only four answers: fix your request, authenticate, retry later, or give up.

### The status code says whose fault it was

The first and coarsest signal is the status code, and the 4xx/5xx split matters more than any single code.

- **4xx: the client did something wrong.** Sending the identical request again will fail the same way. The notable exceptions are 429 Too Many Requests and 408 Request Timeout, which do invite a later retry.
- **5xx: the server failed.** The same request might succeed later.

That split lets a generic client library decide whether to retry. Return a 500 for a validation failure and clients will retry a request that can never succeed. At scale that's a self-inflicted traffic multiplier: the retry storm in [The Reliability Toolkit](/guides/reliability-toolkit/).

<Note type="warn" label="The 200-with-an-error-body anti-pattern">

`HTTP 200 {"success": false, "error": "insufficient funds"}` is popular and wrong. Everything between you and the client (load balancers, CDNs, monitoring, the client's own HTTP library) reads the status code and nothing else. A 200 gets cached, counted as a success in your SLI, and silently swallowed by generic error handling. Your error-rate dashboard shows a flat 0% during a total functional outage.

</Note>

### The body says what to fix

The body carries the detail. RFC 9457, which replaced RFC 7807, defines a standard shape with `type`, `title`, `status`, `detail` and `instance` fields. Whether or not you adopt it literally, copy its properties:

- A **stable machine-readable code** clients can branch on: `insufficient_funds`, not a sentence that will get reworded.
- A human-readable message for logs.
- For validation failures, *which field* was wrong.

Put your request ID in every error body. It turns a support ticket from an archaeology dig into a lookup.

### "Did it go through?": the timeout case

Within the 5xx range, the codes mean different things. A 503 with a `Retry-After` header is an instruction: come back in this many seconds. A 500 is an unknown. A 504 Gateway Timeout means a proxy gave up waiting, and the request may well have been processed anyway:

<Race a="Client" b="Payment service" result="Result: the customer is charged twice" steps={[
  { a: "POST /charges for $40" },
  { b: "Charges the card. The reply is slow", tone: "good" },
  { a: "Gateway gives up: 504. Did it work? Unknown, so it retries" },
  { b: "Sees a new POST /charges. Charges the card again", tone: "bad" }
]} />

The fix is to let the server recognise a retry. The client generates a unique key for each operation and sends it with every attempt. The server records the outcome against that key, and a retry with the same key gets the original result back instead of doing the work twice. This is called an **idempotency key** (an operation is **idempotent** if doing it twice has the same effect as doing it once). Use one on any endpoint that moves money or creates records.

<Note type="wild" label="◈ In the wild · Stripe">

Stripe lets a client attach an `Idempotency-Key` header to any POST and records the outcome against the key. A client retrying after a timeout gets the original result instead of a second charge. Keys are kept for at least 24 hours. See [Stripe's idempotent-requests documentation](https://docs.stripe.com/api/idempotent_requests).

</Note>

<Note type="key" label="What to remember">

- Adding is usually safe; removing, renaming, new enum values, tighter validation and changed defaults break clients, the last two silently.
- Paginate with a cursor and a unique tiebreaker; offsets are slow deep down and shift when rows change.
- The status code says whose fault it is and whether to retry; never send 200 with an error, and use idempotency keys where a retry could repeat work.

</Note>

</Collapse>

<Collapse id="check" title="Check your understanding">

<Quiz q="You add a new field to a response. Optional, backwards compatible. Two weeks later a partner's integration breaks. What happened?" options={["Their client validates strictly and rejects fields it does not recognise", "The server started treating the new field as required for their requests", "A cache between you and the partner kept serving the old schema"]} answer={0}>

Almost certainly a client that validates strictly. Many generated clients and contract-testing tools reject any payload containing a field they don't recognise, so "optional on our side" doesn't matter: the field's mere presence fails their validator. New enum values are the related trap: technically additive, but they break every client that only handles the values it knew about.

Both are why tolerant readers matter: ignore unknown fields, map unknown enum values to a defined "unrecognised" case, never assume order. You can't make your clients tolerant, but you can document the expectation loudly, ship reference clients that behave that way, and announce added fields rather than assume nobody will notice.

</Quiz>

<Quiz q="Users report that paging through a list occasionally skips a record. The query is ORDER BY created_at DESC LIMIT 20 OFFSET n. What's wrong?" options={["The page size is too small, so rows fall between pages", "Offsets shift when rows are inserted or deleted, and created_at isn't unique, so ties come back in no fixed order", "The index on created_at is missing, so rows come back in storage order"]} answer={1}>

Two separate bugs, and both need fixing. First, an offset is a position, and positions move. Insert a row near the top between page requests and everything shifts down one: the last record on page 1 shows up again as the first on page 2. Delete a row and everything shifts up: one record is never shown.

Second, `created_at` is almost certainly not unique. Rows with the same timestamp have no defined order, so the database can return them differently on two runs of the same query, which duplicates and skips rows even with no writes at all.

The fix for both is cursor pagination with a unique tiebreaker: sort by `(created_at, id)` and have each request carry the last row's values instead of a count. It's also faster, because the database jumps into the index instead of counting past n rows it will throw away.

</Quiz>

<Quiz q="A client's POST /orders gets a 504 after 30 seconds. Should it retry?" options={["No, 5xx errors are never safe to retry", "Yes, with the same idempotency key, so the server can return the original result if the order was already created", "Yes, immediately, without any key, because the order clearly failed"]} answer={1}>

A 504 means a gateway stopped waiting, not that the order failed. The service behind it may have finished the work after the gateway gave up. Retry blindly and you may create a second order; refuse to retry and you may abandon a real failure.

An idempotency key removes the guesswork. The client sends the same key on every attempt, and the server returns the stored result if it has already seen that key, so retrying is always safe.

</Quiz>
