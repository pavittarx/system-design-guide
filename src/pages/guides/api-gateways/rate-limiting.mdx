<Collapse id="gateway" title="1. What a gateway does — and what it shouldn't">

You have forty services. Each one decrypts HTTPS, checks the caller's token, limits abusive clients and writes an access log. That's forty implementations of the same four jobs, and thirty-nine of them will have a subtly different bug.

### One front door for the jobs every service shares

An **API gateway** is a single front door in front of all your services. It decrypts HTTPS (**TLS termination**), works out who the caller is (**authentication**), enforces rate limits, sends each request to the right service (**routing**), and writes one consistent access log. Here's one request passing through it:

```trace
**POST /v1/orders**  client → gateway → service   **total 84 ms**
  **1.** TLS terminate                              ++reused session++
  **2.** parse + normalise                 0.2 ms
  **3.** authenticate (cached JWKS)        0.4 ms   ++sub=acct_9f21++
  **4.** rate limit (token bucket)         0.9 ms   ++83/100 left++
  **5.** route /v1/orders → orders-svc     0.1 ms
  **6.** forward, upstream work           81.0 ms
  **7.** add X-RateLimit-* + request-id    0.1 ms
  **8.** emit access log + metrics         0.2 ms
```

Steps 2–5 and 7–8 add up to under two milliseconds. That's the gateway's whole budget, and it's worth guarding jealously. The gateway sits in front of *everything*, so a gateway that adds 20 ms adds it to every request in the company.

### Why business logic creeps in, and where it leads

What a gateway should refuse is business logic. The pull is real: it already sees every request, so it's tempting to add "just one" transformation, then a fan-out to two services, then a rule based on account type.

Keep doing that for two years and you've rebuilt the **enterprise service bus**: one central component that all traffic and logic flows through, that every team must coordinate changes to, that nobody fully understands, and whose failure takes down the whole product. Orchestration belongs in a service that owns it.

The test for whether something belongs in the gateway: would it be identical for a service you haven't written yet? Authentication, yes. "Premium accounts get free shipping", no.

<Note label="Backend-for-frontend">

Sometimes a client genuinely needs aggregation: the mobile app wants one call that returns four things. The pattern that survives is a **BFF**, a thin service owned by the client team, sitting behind the gateway, that does exactly that aggregation for exactly that client. It keeps client-specific logic out of the shared gateway and out of the domain services, and it can be deleted when the client is.

</Note>

</Collapse>

<Collapse id="algorithms" title="2. Five ways to count requests">

Rate limiting asks one question: "has this caller had too much?" There are five standard ways to answer it. They differ in memory, in how they treat bursts, and in how badly they fail at the edges.

### Fixed window: one counter per minute, and a hole at midnight

Count each caller's requests per calendar minute and reset the count at the top of the minute. One counter per caller, trivially cheap. This is a **fixed window**, and it has a well-known hole:

```trace
  limit: 100 requests per minute, fixed window
  11:59:59.9  client sends 100   11:59 window  100/100  ++ok++
  12:00:00.0  new window: counter resets to 0
  12:00:00.1  client sends 100   12:00 window  100/100  ++ok++

**verdict:** ~~200 requests in 0.2 s~~, double the limit
```

Both windows stayed within the limit, and the server absorbed **200 requests in 0.2 seconds**: double the rate you thought you'd guaranteed, delivered as a spike. And it happens exactly at the boundary every client's cron job is aligned to.

### Sliding log: exact, and memory-hungry

Store a timestamp for every request. On each new one, throw away timestamps older than a minute and count what's left. This **sliding log** is exactly correct, with no boundary hole.

The cost is memory: one timestamp per request per caller. At 100 requests per caller and 8 bytes per timestamp, ten million active callers is roughly **8 GB**, just for a limiter.

### Sliding window counter: two numbers and a weighted guess

Keep only two counts per caller: this minute's and last minute's. Then estimate how many requests fall in the last 60 seconds by assuming last minute's requests were spread evenly. This is the **sliding window counter**, the pragmatic compromise.

Worked example: you're 15 seconds into the current minute, so the last 60 seconds still include 45 seconds, or 75%, of the previous minute. The previous minute had 80 requests; this one has 30 so far.

$$
80 \times 0.75 + 30 = 90
$$

With a limit of 100, the next request is allowed. That's two integers per caller, roughly **160 MB** for the same ten million callers, and the boundary burst is gone. The "evenly spread" assumption is wrong, and it almost never matters.

### Token bucket: save up for a burst

Picture a bucket that holds up to C tokens and refills at R tokens per second. Each request takes one token; an empty bucket means rejection. This is a **token bucket**.

You only store two numbers: the token count and when you last refilled. There's no background job topping buckets up. When a request arrives, you work out how many tokens have dripped in since last time, add them, then spend one. Here are five requests against a small bucket, capacity 3, refilling 1 token per second:

```trace
  capacity 3, refill 1 token/s, bucket starts full
  t=0.0 s  request 1   3 → 2 tokens        ++allowed++
  t=0.0 s  request 2   2 → 1               ++allowed++
  t=0.0 s  request 3   1 → 0               ++allowed++
  t=0.0 s  request 4   0 left              ~~rejected: 429~~
  t=1.0 s  request 5   +1 dripped in → 0   ++allowed++
```

Its defining property is that it *allows controlled bursts*. With C = 100 and R = 10 per second, a client idle for a minute can fire 100 requests at once, then settle to 10 per second. That's usually what you want: real clients are bursty, and a limiter that punishes bursts punishes normal behaviour.

### Leaky bucket: a queue that drains at a fixed pace

Requests join a queue that drains at a fixed rate, like water leaking from a hole in a bucket. Output is perfectly smooth, which is the point when the thing you're protecting can't tolerate spikes at all. The cost is added latency, and a queue that can itself become a problem.

This is a **leaky bucket**: load-levelling, the same shape as a queue in front of a slow consumer. [Message Queues & Async](/guides/message-queues/) covers when smoothing beats rejecting.

### The five side by side

<Table>

| Algorithm | In plain words | State per caller | Bursts | Boundary bug | Use when |
| --------- | -------------- | ---------------- | ------ | ------------ | -------- |
| Fixed window | Count per calendar minute | 1 integer | Uncontrolled at edges | Yes, 2× | Rough quotas, low stakes |
| Sliding log | Remember every request time | N timestamps | Exact | No | Few callers, strict correctness |
| Sliding counter | Two minutes' counts, weighted | 2 integers | Smooth | No | The sane default at scale |
| Token bucket | Tokens drip in; each request spends one | 2 numbers | Deliberate, bounded | No | Public APIs with bursty clients |
| Leaky bucket | Queue drained at a fixed rate | Queue | None by design | No | Protecting something spike-intolerant |

</Table>

<Lab
  title="Build an API Rate Limiter in Redis"
  tip="Include this atomic Redis Lua rate limiter in your portfolio as a benchmark of low-overhead distributed traffic policing."
>

Build this mini-project to implement custom token-bucket limits via shared cache:

- **The Server:** Write an API server in Node.js or Python. Create a single endpoint `GET /api/data`.

- **Redis Lua Script:** Write a Lua script for Redis that checks and decrements client tokens. The script should receive keys: `ratelimit:client_ip`, and arguments: `bucket_capacity`, `refill_rate`, and `now_timestamp`. By performing the calculations inside Redis in Lua, you ensure atomicity without lock churn:

  ```lua
  local key = KEYS[1]
  local capacity = tonumber(ARGV[1])
  local refill_rate = tonumber(ARGV[2])
  local now = tonumber(ARGV[3])
  local state = redis.call('HMGET', key, 'tokens', 'last_refill')
  local tokens = tonumber(state[1]) or capacity
  local last_refill = tonumber(state[2]) or now
  local elapsed = math.max(0, now - last_refill)
  tokens = math.min(capacity, tokens + elapsed * refill_rate)
  if tokens >= 1 then
    tokens = tokens - 1
    redis.call('HMSET', key, 'tokens', tokens, 'last_refill', now)
    return {1, tokens}
  else
    return {0, tokens}
  end
  ```

- **Send Rate Limit Headers:** Run the Lua script in your middleware on every request. If returned status is `1`, allow the request and set headers: `X-RateLimit-Limit`, `X-RateLimit-Remaining`. If status is `0`, reject with `429 Too Many Requests` and a `Retry-After` header.

- **Test Bursts:** Run a load test using `k6` and verify that bursts up to capacity are allowed, after which traffic flatlines perfectly to the refill rate.

</Lab>

<Collapse id="distributed" title="3. One limit, twenty gateways">

Everything above assumes one counter. In production you have twenty gateway instances behind a load balancer, and a customer's requests land on all of them. The counter is now shared state, which makes this a distributed-systems problem dressed as an infrastructure one.

### Option one: split the limit twenty ways

The limit is 1,000 per minute, so each of the twenty instances allows 50. No coordination, no added latency.

It's also wrong in both directions. A client whose connections land unevenly gets throttled well under 1,000. And during a deploy the number of instances changes, so every effective limit silently moves with it. Fine for crude abuse prevention; unacceptable for a documented quota a customer pays for.

### Option two: one shared counter, updated atomically

Keep the counter in Redis and have every instance check it on every request. The obvious code reads the count, checks it, then writes it back. Two instances handling the same customer at the same moment break it:

  { a: "999 is under 1,000: allows it, writes 1,000", tone: "good" },
  { b: "999 is under 1,000: allows it, writes 1,000", tone: "bad" }
]} />

The fix is to make check-and-increment one step that nothing can interleave with. Redis runs a script from start to finish before handling any other command, so you do the read, the check and the write inside one script. That's exactly what the Lua script in the lab does.

That makes the shared counter accurate and simple. The cost is a network round trip on every request. At 50,000 requests per second with a 1 ms round trip, you have about 50 requests sitting in flight waiting on the limiter at any moment. (That's **Little's Law**: requests in flight = arrival rate × time each one waits.) And you've put a hard dependency in front of your entire API.

<Note type="warn" label="The limiter is now a single point of failure — decide in advance">

Redis goes down. Do you **fail open** (let everything through unlimited) or **fail closed** (reject everything, turning a limiter outage into a total outage)? It depends on what the limit is for.

A limit enforcing a paid quota can usually fail open: briefly letting someone exceed their plan costs far less than rejecting paying customers. A limit protecting a fragile downstream, or stopping abuse, shouldn't simply fail open, because that drops the protection exactly when you've already lost a component. Fall back to a conservative local limit instead.

Whichever you choose, choose it deliberately and alert on it. A limiter that has been silently failing open for three weeks looks exactly like one that's working, right up until the day it matters.

</Note>

### Option three: local buckets that sync in the background

Each instance keeps its own token bucket and, every so often, reports what it has spent to a shared store. It gets back the fleet's total and adjusts its own allowance. No request ever waits on a network call.

It's approximate, and briefly too generous after a burst. This is broadly the shape large providers converge on, because perfect accuracy costs a synchronous coordination step on every request and is rarely worth it. If the limit genuinely must be exact, you're asking for consensus, and [Coordination & Consensus](/guides/coordination-consensus/) explains what that costs.

<Note type="key" label="What to remember">

- A gateway handles the jobs every service shares, in under a couple of milliseconds; business logic in it grows into a bottleneck everyone depends on.
- Fixed windows let through double the limit at a boundary; token buckets and sliding-window counters don't.
- A shared counter must check and increment in one atomic step, costs a round trip, and needs a decided fail-open or fail-closed behaviour.

</Note>

</Collapse>

<Collapse id="check" title="Check your understanding">

<Quiz q="Your limit is 100 requests per minute, fixed window. A client legitimately gets 200 through in under a second. How?" options={["The limiter counts per instance, and the client reached two instances", "The counter increment isn't atomic, so concurrent requests overwrote each other", "They straddled a window boundary: 100 just before the reset and 100 just after"]} answer={2}>

They straddled a window boundary: 100 requests at 11:59:59 and 100 more at 12:00:00, each inside its own window, so both counters were satisfied. Over any stretch that spans a reset, a fixed window lets through up to twice its limit. That matters because bursts cluster at boundaries: cron jobs everywhere start on the round minute.

A sliding-window counter fixes it by weighting last minute's count by how much of it still overlaps the last 60 seconds, at the cost of one extra integer per caller. A token bucket avoids it entirely because its allowance refills continuously instead of resetting. If your fixed-window limiter seems to hold but the service behind it keeps getting spikes, look here first.

</Quiz>

<Quiz q="Your rate limiter's Redis goes down. Fail open or fail closed?" options={["Always fail open, so a limiter outage never becomes an API outage", "It depends on what the limit is for, so decide per limit and alert when you enter the fallback", "Always fail closed, because an unprotected API is worse than an unavailable one"]} answer={1}>

It depends on what the limit is *for*, so decide per limit, not globally. A limit protecting a fragile downstream from overload should fail closed or drop to a conservative local limit. Failing open removes the protection exactly when you've already lost a component and can least absorb a surge.

A limit enforcing a paid quota should usually fail open. Rejecting paying customers because the limiter is down is a much worse outcome than briefly letting someone exceed their plan.

The middle path most large systems take: fall back to a local bucket on each instance, sized at the fleet limit divided by the number of instances. It's approximate and unfair at the margins, but bounded. Alert loudly on entering that state, because the dangerous case is a limiter that has been silently failing open for weeks.

</Quiz>

<Quiz q="Twenty gateway instances, a documented limit of 1,000 requests/minute per customer. How do you enforce it without adding a Redis round trip to every request?" options={["Local token buckets that sync their consumption to a shared store off the hot path, accepting a bounded error", "Give each instance a fixed 50 per minute and never coordinate", "Use sticky sessions so each customer always lands on the same instance"]} answer={0}>

Accept approximation and move the coordination off the request path. Each instance keeps a local token bucket and reports its spending to a shared store every few hundred milliseconds, getting back the fleet's total. An instance seeing heavy traffic from one customer learns within a fraction of a second that the fleet-wide budget is nearly gone, and tightens up, without ever making a request wait on a network call.

The error is limited to what the fleet can spend in one sync interval, which you can shrink as far as you need. If an instance loses contact with the shared store, it falls back to its local share.

First, though, ask whether the limit needs to be exact at all. If it exists to protect infrastructure, approximate is fine and much cheaper. Precision only earns its cost when the number is a contractual commitment someone will audit.

</Quiz>
