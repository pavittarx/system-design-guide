<Collapse id="cacheable" title="1. What's cacheable (the static/dynamic lie)">

The received wisdom is that CDNs serve static assets — images, CSS, JavaScript — and dynamic content goes to the origin. This was true around 2005 and has been costing people performance ever since.

The useful question is not "is this static?" but **"how stale can this be, and for whom?"** Answer it per response and the categories look completely different:

<Table>

| Content | Tolerable staleness | Where it can live |
| ------- | ------------------- | ----------------- |
| Fingerprinted JS/CSS (`app.9f2c1a.js`) | Infinite — the name changes | Edge, one year, immutable |
| Product images | Days | Edge |
| Product listing page | Seconds to minutes | Edge, short TTL |
| Price / stock level | Seconds | Edge, very short TTL + purge on change |
| Personalised homepage | Zero for the personal parts | Cached shell + edge-assembled personal bits |
| Cart contents | Zero | Origin, never cached |
| Anything behind a POST | N/A | Origin |

</Table>

The row that changes systems is the listing page. A product listing served to everyone identically, cached at the edge for even **ten seconds**, absorbs an enormous fraction of traffic on a busy site — because a page requested 5,000 times a minute is generated 6 times a minute instead of 5,000. That is a 99.9% reduction in origin work for a ten-second staleness budget nobody will ever perceive.

<Note type="key" label="Short TTLs are dramatically more powerful than they look">

Origin requests per minute = 60 ÷ TTL(seconds), per PoP, per object — *regardless of how much traffic arrives.* A 10-second TTL means at most 6 origin fetches a minute for that object at one PoP whether it's requested a hundred times or a hundred thousand. The relationship between traffic and origin load isn't reduced; it's *severed*.

Going from a 10-second to a 60-second TTL only takes you from 6 to 1 — the first ten seconds bought you almost all of the benefit, which is why "we can't cache, our data changes constantly" is nearly always an argument for a short TTL rather than for no TTL.

</Note>

</Collapse>

<Collapse id="cachekey" title="2. The cache key, and how to shatter it">

A CDN decides whether two requests are "the same" by computing a cache key — by default, roughly the host, the path, and the query string. Every distinct key is a distinct cached object. Which means every dimension you add to the key divides your hit rate.

**Query strings are the usual culprit.** Marketing appends tracking parameters, and now `/shoes`, `/shoes?utm_source=email`, `/shoes?utm_source=twitter&utm_campaign=spring` and ten thousand other permutations are ten thousand separate objects, each fetched from origin at least once, each occupying cache space, each with a hit rate near zero. The page is identical every time. The fix is to normalise the key: strip the parameters that don't affect the response, sort the ones that do (`?a=1&b=2` and `?b=2&a=1` are different strings and therefore different keys), and drop everything unrecognised.

<Note type="warn" label="Vary is a hit-rate multiplier, and the multiplier is often four figures">

`Vary: Accept-Encoding` is fine — a handful of values, and you genuinely need separate gzip and brotli copies.

`Vary: User-Agent` is catastrophic. There are effectively unlimited user-agent strings; every browser build, every OS patch level, every crawler gets its own copy of every object. Hit rates collapse from 95% to single digits and the origin discovers what its real traffic looks like.

`Vary: Cookie` is worse still, because every user has a distinct session cookie, so the cache is now per-user and does nothing except consume disk.

</Note>

The cookie interaction is where correctness, not just performance, is at stake. If a response carrying `Set-Cookie` gets cached and served to another user, you have handed one person another person's session. CDNs default to refusing to cache responses with `Set-Cookie` for exactly this reason, and the danger arrives when someone overrides that default to "fix" a hit-rate problem. The safe pattern is to keep personalised and cacheable content on different URLs, so no configuration mistake can ever confuse them.

Used deliberately, key customisation is powerful: including a `country` value derived from geolocation gives you three or five variants and correct regional pricing. Including the raw client IP gives you one variant per user. The difference between a useful dimension and a catastrophic one is entirely its cardinality — the same lesson as metric labels in [Seeing Inside the Machine](/guides/observability/), for the same reason.

</Collapse>

<Collapse id="shield" title="3. Origin shielding and tiered caching">

Here is a problem that only appears once the CDN is working. You have a hundred PoPs. A popular object expires. The next request into each PoP is a miss, so each PoP goes to origin. Your origin, which was happily serving nothing, receives a hundred simultaneous requests for the identical bytes. Multiply by every object expiring in that minute and the CDN — the thing you bought to protect your origin — has become a distributed denial-of-service tool pointed at yourself.

<Note type="key" label="The shield arithmetic">

100 PoPs, one object, TTL expires. Without a shield: **100 origin fetches** for the same bytes.

With a shield: each PoP misses to the shield, the shield fetches **once**, the other 99 are served from the shield.

Origin sees **1** request instead of 100 — a 99% reduction on nothing but topology.

</Note>

An **origin shield** is a single designated PoP (or a small set of them) that sits between all other PoPs and your origin. Edge PoPs never talk to your origin directly; they talk to the shield, and only the shield talks to you. The shield is usually placed geographically near your origin, so the shield-to-origin hop is short and the connection can stay warm.

This is the same single-flight idea from [Understanding Caching](/guides/understanding-caching/), just applied one layer up: collapse many concurrent misses for the same key into one upstream fetch. Good CDNs also do request coalescing *within* a PoP, so a thousand simultaneous users hitting one cold PoP produce one shield request, not a thousand. The two mechanisms compose: a thousand users per PoP across a hundred PoPs — a hundred thousand requests — becomes one origin fetch.

The cost of a shield is a hop. A user in Sydney whose PoP misses now waits for Sydney → shield (say, Virginia) → origin instead of Sydney → origin. If the shield and origin are co-located, the added latency is small and only paid on misses. If you put the shield in the wrong place — say, in Europe when your origin is in Oregon — every miss takes a scenic detour across two oceans.

Tiered caching generalises this: edge tier, regional tier, shield tier, origin. Each tier has more storage and fewer, larger caches, so long-tail objects that would fall out of a small edge cache still get a hit one tier up. It is a memory hierarchy, and it obeys the same rules as the one in your CPU.

<Collapse id="check" title="Check your understanding">

<Quiz q="You lower a TTL from 3600s to 10s across your whole catalogue. What actually happens to origin load?" options={["Roughly unchanged, because the hit rate stays above 99%", "It rises 360× per PoP per object, multiplied across every PoP and object, which can be an outage", "It falls, because fresher objects need fewer revalidations"]} answer={1}>

Per PoP, per object, origin requests go from 60 ÷ 3600 ≈ 0.017 per minute to 60 ÷ 10 = 6 per minute — a 360× increase, and it is multiplied by your number of PoPs and your number of objects. On 100 PoPs and 10,000 objects that is 6 million origin requests per minute, which is not a TTL change, it is an outage.

The fixes, in order: put an origin shield in front so the 100 PoPs collapse to 1, add `stale-while-revalidate` so the refetches are background work rather than user-facing latency, and add jitter so they do not all land in the same second. With all three, a short TTL is genuinely affordable — that is the combination that makes near-real-time content viable on a CDN.

</Quiz>

<Quiz q="Your hit rate is near 0%, cache usage is huge, and database load is pinning. You see Vary: User-Agent in the headers. What's the arithmetic?" options={["Every distinct User-Agent string gets its own copy, so hundreds of thousands of variants each miss", "User-Agent changes on every request, so the CDN refuses to cache the response at all", "The CDN caches one copy but revalidates it with origin for every new browser"]} answer={0}>

User-Agent strings are effectively unique per browser build, OS version, and device — hundreds of thousands of distinct values in real traffic. `Vary: User-Agent` tells the cache to store a separate copy per distinct string, so you get an enormous number of near-identical objects, a hit rate near zero, storage costs that look like a bug, and an origin that is being hit as if the CDN were not there.

If you genuinely need to serve different markup to mobile and desktop, have the edge normalise User-Agent into a small header like `X-Device: mobile|desktop|tablet` and vary on that — three variants instead of three hundred thousand. Better still, serve one responsive document to everyone and let CSS handle it.

</Quiz>

<Quiz q="Your hit rate is 94% and your origin bill went up anyway. What are the two most likely causes?" options={["The shield tier counts its hits twice, so the real hit rate is lower", "Origin egress is billed per request, so the 6% of misses cost more each month", "The misses are the large objects, so the byte hit rate is far lower; or a cache key change split objects into many variants"]} answer={2}>

First: hit rate is measured in *requests*, but egress is measured in *bytes*. If the 6% of misses are your large objects — video segments, big images, uncompressed downloads — a 94% request hit rate can be a 50% byte hit rate. Always look at both.

Second: a cache key change fragmented your cache. Someone added a query parameter, a `Vary` header, or a geo dimension, and now each object exists in many variants, each of which must be fetched from origin once per PoP. The hit rate can stay high in aggregate while origin fetches multiply, because the denominator grew.

</Quiz>
