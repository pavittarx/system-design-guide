<ColdOpen tag="◇ the outage nobody could see">

Support tickets start arriving at 09:14: checkout is broken. You open the dashboard. Request rate normal, error rate 0.02%, CPU flat, database healthy, every panel green. You can't reproduce it, and for forty minutes you argue with the evidence, because the evidence says nothing is wrong.

At 09:56 someone tries a purchase on a phone over cellular data. It hangs for eleven seconds, then succeeds. A *success*: counted as one, and averaged into a mean that never moved. The system wasn't lying to you. Your instruments could only see the failures someone had already thought of.

</ColdOpen>

<Collapse id="green" title="1. How a dashboard stays green while users fail">

Staring at a wall of healthy graphs while customers say the product is unusable is a special kind of misery. It isn't bad luck. It follows directly from how most teams build their instruments, so it's worth seeing exactly how it happens.

### The list was written in advance

Most teams pick the things they expect to break and watch them: CPU, memory, disk, error rate. Each of those has caught a real outage. This is called **monitoring**.

The weakness is the list itself. People wrote it by imagining failures, and the failure that takes you down is, almost by definition, the one nobody imagined. In the cold open, checkout didn't fail. It got slow for some users, and "slow for some users" wasn't on the list.

### Averages hide small groups

Every panel on that dashboard was an **aggregate**: one number summarising many requests, like an average or a total. Aggregates are cheap because they throw detail away, and the detail they throw away is not random. They hide small groups.

Suppose 2% of users wait eleven seconds and then succeed. No request failed, so the error rate stays at 0.02%. If the problem only hits one customer, and that customer is your largest, it vanishes from every graph completely.

### The property you actually want

So the useful question isn't "do we have monitoring?" Everyone does. It's this: *when something breaks in a way we didn't predict, can we find it in the data we already collect?* Most teams learn the answer is no in the middle of an incident.

<Note type="key" label="The distinction worth keeping">

**Monitoring** answers questions you thought of in advance. It's a set of dashboards.

**Observability** is being able to answer questions you *didn't* think of in advance, without shipping new code. It's a property of your data: enough detail about each request (which user, which region, which version), kept long enough, that you can slice a problem in a direction you've never tried and still get an answer.

</Note>

</Collapse>

<Collapse id="signals" title="2. Three signals, three jobs">

You have three kinds of **telemetry** (data your system reports about itself). They aren't three formats for the same information. Each is cheap for one job and ruinous for another, and most wasted observability spend comes from using the wrong one.

### Metrics: numbers that are cheap at any traffic

A **metric** is a running number, like "requests served so far" or "connections in use", tagged with a few **labels** such as endpoint or region. Ten requests and ten million requests both just bump the same counter, so traffic doesn't change the cost.

What does change the cost is labels. Every distinct combination of label values is stored separately, so adding the wrong label multiplies your bill. [Part 2](/guides/observability/logs-traces/#cardinality) works through why.

### Logs: one record per event

A **log** is a record of one thing that happened: "order 88213 failed after 3 retries". Labels cost nothing extra, because each record can carry whatever fields it likes. But ten million requests produce ten million records, so cost grows in a straight line with traffic.

### Traces: one request's whole journey

A **trace** follows a single request through every service it touched, with timings for each step. Its cost grows with traffic times the number of services, so nearly everyone keeps only a sample of requests. Choosing which ones to keep turns out to matter a great deal.

### The three side by side

<Table>

| Signal | In plain words | Cost grows with | Answers |
| ------ | -------------- | --------------- | ------- |
| **Metrics** | Running numbers with a few tags | Distinct label combinations, *not* traffic | "Is something wrong, and roughly where?" |
| **Logs** | One record per event | Traffic, in a straight line | "What exactly happened to this one request?" |
| **Traces** | One request's path across services | Traffic × services, so usually sampled | "Where did the time go, and who called whom?" |

</Table>

<Note label="A rule of thumb that holds up">

Metrics tell you *that* something is wrong. Traces tell you *where*. Logs tell you *why*. If you find yourself trying to answer "why" from a metric, you're about to add a label you'll regret.

</Note>

A fourth signal, **profiles**, has become practical in the last few years. Continuous CPU and memory profiling in production answers "which line of code is burning the CPU", the way traces answer "which service is burning the time". It's worth knowing about, but it isn't yet standard kit the way the other three are.

<Note type="key" label="What to remember">

- Monitoring watches a list written in advance; the outage that hurts is the one not on the list.
- Averages and totals hide small groups of users, especially when the symptom is slowness rather than errors.
- Metrics are cheap per request but expensive per label; logs are the opposite; traces sit between and are sampled.

</Note>
