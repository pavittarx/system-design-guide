<Collapse id="inseparable" title="1. Making the order and its event inseparable">

Back to the cold open. We charge the card, we save the order, and we publish an "order placed" event so the receipt gets sent and the warehouse gets told. Three side effects, at least two systems, and no transaction spanning them. Every ordering of those operations has a crash window that produces a state nobody wants.

```trace
**save, then publish**
  save order        ✓
  ~~crash~~
  publish event     ✗
  → order exists, nobody told.
    no receipt, nothing ships.

**publish, then save**
  publish event     ✓
  ~~crash~~
  save order        ✗
  → warehouse ships an order
    that does not exist.
```

You cannot fix this by reordering the two writes, and you cannot fix it with a try/catch, because the process can die between any two instructions. The fix is to stop having two writes. The **transactional outbox** puts the event in a table in the *same database transaction* as the order:

```sql
BEGIN;
  INSERT INTO orders (...)  VALUES (...);
  INSERT INTO outbox (topic, payload)
VALUES ('order.placed', :json);
COMMIT;
-- a separate relay reads outbox,
-- publishes, marks rows sent.
```

Now the order and the intent to announce it commit or fail together. The relay may still publish a message twice — it can crash after publishing and before marking the row sent — so this gives at-least-once, not exactly-once, which is exactly why every consumer must be idempotent. The [Queues guide](/guides/message-queues/) has the full treatment, including the race in the naive idempotency check that quietly charges people twice.

### And the money

The payment provider is outside our transaction and always will be. What makes that safe is an **idempotency key** — a unique identifier we generate for this checkout attempt and pass to the provider. If our request times out and we retry, the provider recognises the key and returns the original result instead of charging again. This is why payment APIs have that field, and it is not optional at any real volume.

Order of operations matters here. Write the order in a `pending_payment` state first, then authorise with the key, then confirm. If we die after authorising, a reconciliation job finds orders stuck in `pending_payment`, asks the provider what happened to that idempotency key, and settles them — completing the ones that succeeded and voiding the ones that didn't. Money and orders can then never disagree for longer than the reconciliation interval, which is a bound you can state out loud and hold yourself to.

<Lab
  title="Implement the Transactional Outbox Pattern"
  tip="Feature this Transactional Outbox pattern on your portfolio as a capstone benchmark of bulletproof transactional consistency."
>

Build this capstone mini-project to implement the transactional outbox pattern with SQLite and Python/Node.js:

- **The Database Schema:** Set up an SQLite table:

  ```sql
  CREATE TABLE orders (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    customer_id INT,
    total_cents INT,
    status TEXT
  );
  CREATE TABLE outbox_events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    topic TEXT,
    payload TEXT,
    status TEXT DEFAULT 'PENDING'
  );
  ```

- **Atomic Transaction:** Write a script that writes to both tables inside a single atomic transaction:

  ```python
  def create_order(db_conn, customer_id, total_cents):
      cursor = db_conn.cursor()
      cursor.execute("BEGIN;")
      try:
          cursor.execute("""
              INSERT INTO orders (customer_id, total_cents, status)
              VALUES (?, ?, 'CONFIRMED')
          """, (customer_id, total_cents))
          order_id = cursor.lastrowid
          event_payload = {"order_id": order_id, "total": total_cents}
          cursor.execute("""
              INSERT INTO outbox_events (topic, payload)
              VALUES ('order.placed', ?)
          """, (json.dumps(event_payload),))
          cursor.execute("COMMIT;")
      except Exception as e:
          cursor.execute("ROLLBACK;")
          raise e
  ```

- **The Outbox Relay:** Write a separate background process (the relay) that polls the `outbox_events` table periodically, publishes messages, and marks them as `PROCESSED` in a transaction:

  ```python
  def poll_and_relay(db_conn):
      cursor = db_conn.cursor()
      cursor.execute("SELECT id, topic, payload FROM outbox_events WHERE status = 'PENDING' LIMIT 10")
      pending = cursor.fetchall()
      for event_id, topic, payload in pending:
          # Simulate publishing to RabbitMQ/Kafka
          print(f"Relaying event {event_id} to {topic}: {payload}")
          # Mark processed atomically
          cursor.execute("UPDATE outbox_events SET status = 'PROCESSED' WHERE id = ?", (event_id,))
      db_conn.commit()
  ```

- **Validate Crashes:** Run the creator script and kill it midway. Verify that order and outbox records are either both committed or both rolled back. Run the relay, simulate a network dropout, and verify that no events are lost and duplicates are safely handled downstream.

<Collapse id="guardrails" title="2. Guardrails around every dependency">

Every arrow leaving our service is a way for someone else's bad day to become ours. The [Reliability guide](/guides/reliability-toolkit/) supplies the toolkit; here is where each tool actually goes, and what it costs us if we get it wrong.

<Table>

| Dependency | Timeout | Retry | Guardrail | When it fails |
| ---------- | ------- | ----- | --------- | ------------- |
| **Payment provider** | 3 s connect+read | Once, with the same idempotency key | Bulkhead: max 300 concurrent. Breaker on error rate. | Fail the checkout with a clear message. Do not fake success — you cannot ship what you weren't paid for. |
| **Primary database** | 2 s statement | No | Bounded pool, sized by Little's Law | Hard down. Nothing to degrade to. This is what replicas and failover are for. |
| **Cache** | 50 ms | No | Fail open to the database | Degrades, doesn't error — but see the warning below. |
| **Queue broker** | 1 s publish | No — the outbox is the retry | Outbox relay backs off | Nothing user-visible. Messages accumulate in the outbox table and drain later. |
| **Fraud service** | 400 ms | No | Fail open, score offline | Take the order, score it asynchronously, cancel later if needed. A business decision, made in advance. |
| **Recommendations** | 150 ms | No | Fail open to a static list | Nobody notices. This is what graceful degradation looks like when it's done right. |

</Table>

<Note type="warn" label="&quot;Fail open to the database&quot; is not free">

The cache is absorbing roughly 96% of 25,000 reads/s. If it dies cold, the database instantly receives about 25× its normal read load. "The app still works" is technically true for about four seconds. This is why the cache tier needs its own redundancy, why the fallback path needs request coalescing, and why load shedding exists — a design that treats the cache as optional has not thought about what happens when it goes away.

</Note>

Two settings that people consistently miss, and that this design depends on. First, **deadline propagation**: if the customer's request has 800 ms of budget and 500 ms are already spent, the payment call must know it has 300 ms left, not its own independent 3-second timeout. Otherwise we burn capacity computing answers nobody is waiting for.

Second, **retry budgets**: retry at exactly one layer, and cap total retries at a small fraction of live traffic. Three layers each retrying three times turns one user action into twenty-seven requests, arriving precisely when the system can least afford them.

</Collapse>

<Collapse id="staleness" title="3. Staleness, decided field by field">

This is the section that separates a design from a shopping list. "Is the system consistent?" is the wrong question — the [Consistency guide](/guides/consistency-cap/)'s central point is that consistency is a per-field decision with a per-field price. So go field by field and say what you're buying.

<Table>

| Data | Staleness allowed | What you buy |
| ---- | ----------------- | ------------ |
| **Payment record** | None | Nothing. This is the money. Strong consistency on the primary, no exceptions, no cache. |
| **Order exists / order status** | None for the owner; seconds for everyone else | The customer reads their own order from the primary for a short window after writing. Everyone else can read a replica. |
| **Inventory — the number we decrement** | None | Correctness at checkout. A conditional update on the primary, described below. |
| **Inventory — the number we display** | ~30 s | 25,000 reads/s served from cache instead of the database. "Only 3 left" being briefly wrong is a UX cost; being right costs you the read architecture. |
| **Order history** | ~1 s | Replica reads, with a read-your-writes window for the customer who just ordered. |
| **Recommendations, "recently viewed"** | Minutes to hours | Everything. Precompute it, cache it hard, and let it be wrong. Nobody has ever filed a bug about a stale recommendation. |
| **Analytics and reporting** | Minutes | Keeps a heavy, unpredictable workload entirely off the transactional database. |

</Table>

### The genuinely hard one: overselling

Two customers, one remaining item, requests arriving 8 ms apart. Both see stock, both proceed, one of them is going to be disappointed and it's your job to decide how.

**Optimistic decrement** is the simple version: make the decrement conditional in a single statement, so the database arbitrates rather than your application.

```sql
UPDATE inventory
   SET available = available - :qty
 WHERE sku = :sku
   AND available >= :qty;
-- 0 rows updated → someone beat you.
-- Sold out. Tell the customer now,
-- before you charge the card.
```

That is atomic and correct, and it has one flaw: it decrements before the payment succeeds. If the card is declined thirty seconds later, you've held stock hostage. **Reserve-then-confirm** fixes it — the same conditional update creates a reservation with a short expiry, the payment runs, success converts the reservation to a sale, and failure or expiry returns the stock. That's a small state machine and a sweeper job, and it is the design most real commerce systems land on.

<Note label="The uncomfortable industry truth">

Many large retailers accept a small oversell rate on purpose. Perfectly serialised global inventory across every channel — web, app, stores, marketplaces — costs enormous latency on every read and a coordination protocol that becomes the bottleneck on your busiest day. Occasionally apologising, refunding and offering a voucher is cheaper. That is a *commercial* resolution to a *distributed systems* problem, and recognising when one is available is a genuine engineering skill. It is also, precisely, the [AP branch](/guides/consistency-cap/) being chosen deliberately: stay available, reconcile the conflict afterwards.

</Note>

<Collapse id="check" title="Check your understanding">

<Quiz q="Where in this design can a customer be charged without an order existing, and what prevents it?" options={["Nowhere: the charge and the order commit in one database transaction", "Between authorising and committing; a pending_payment row first, an idempotency key on the charge, and a reconciliation sweep bound it", "In the outbox relay; making the consumers idempotent closes the gap"]} answer={1}>

Between authorising the payment and committing the order transaction. The process can die in that window and the money is gone with nothing recorded.

Three things together close it: the order is written in `pending_payment` *before* the charge, so there's always a record to reconcile against; the charge carries an idempotency key, so retrying can't double-charge; and a reconciliation job sweeps stuck `pending_payment` orders, asks the provider what happened to that key, and either completes or voids. You can't make it impossible — the provider is outside your transaction — but you can bound how long the disagreement lasts.

</Quiz>

<Quiz q="Your cache dies completely at peak. Why is &quot;the app still works&quot; not a good answer?" options={["The database takes about 25× its normal read load, saturates, starves checkout through the shared pool, and retries can keep it down", "Sessions are lost, so every customer is logged out, but checkout keeps working", "Reads get a few milliseconds slower until the cache restarts and refills"]} answer={0}>

The cache absorbs about 96% of 25,000 reads/s, so the database instantly sees roughly 25× its normal read load. It saturates, query latency climbs, connections back up, and because the pool is shared, checkout starts timing out too — a read-path failure has become a write-path outage.

Then clients retry, adding load, and the system can stay collapsed even after the cache comes back, because the retry traffic and cold cache are now self-sustaining. That's metastable failure: you can't wait it out, you have to shed load and reintroduce it gradually. "It degrades instead of erroring" is true for about four seconds.

</Quiz>

<Quiz q="You add a second region. Which three decisions just got harder?" options={["Caching, load balancing and the queue, because each needs a second copy", "Session storage, TLS certificates and DNS", "Inventory coordination, which region or regions may write, and when to fail over"]} answer={2}>

First, inventory: a globally serialised count now needs cross-region coordination on every checkout, and cross-region round trips are 60–150 ms set by the speed of light. Second, the database: one writable primary means one region pays a latency penalty on every write, while two writable primaries means conflict resolution for every field — and last-write-wins on an inventory count silently loses data.

Third, failover: "the region is down" is a judgement call made by a timeout you configured, and getting it wrong in either direction is expensive. Most teams start with one write region and read replicas elsewhere, precisely to avoid the second problem.

</Quiz>
