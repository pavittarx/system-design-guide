<Collapse id="inseparable" title="1. Making sure the order, its event and the money agree">

Back to the cold open. A checkout does three things that live in different places: it charges the card (at the payment provider), saves the order (in our database), and publishes an "order placed" event (to the queue), so the receipt goes out and the warehouse hears about it. No single transaction covers all three, so the process can die between any two of them.

### Every order of operations has a crash window

Try saving first, then publishing. Or publishing first, then saving:

```trace
**save, then publish**
  save order        ✓
  ~~crash~~
  publish event     ✗
  → order exists, nobody told.
    no receipt, nothing ships.

**publish, then save**
  publish event     ✓
  ~~crash~~
  save order        ✗
  → warehouse ships an order
    that does not exist.
```

Reordering doesn't help, and neither does a try/catch, because the process can die between any two instructions: a crash, a deploy, a machine losing power. The only fix is to stop having two separate writes.

### The fix: write the event into the same transaction

Put the event in a table in the *same database transaction* as the order. This is called the **transactional outbox**:

```sql
BEGIN;
  INSERT INTO orders (...)  VALUES (...);
  INSERT INTO outbox (topic, payload)
  VALUES ('order.placed', :json);
COMMIT;
-- a separate relay reads outbox,
-- publishes, marks rows sent.
```

Why this works: a database transaction is all or nothing. Either both rows are saved or neither is, so "order saved but nobody told" can't happen. A separate background process, the **relay**, reads unsent rows from the outbox, publishes them to the queue, and marks them sent.

The relay can still publish a message twice: it can crash after publishing but before marking the row sent, and publish it again on restart. So this gives **at-least-once** delivery, not exactly-once, which is why every consumer must be **idempotent**: handling the same message twice must have the same effect as handling it once. The [Queues guide](/guides/message-queues/) has the full treatment, including the race in the naive "have I seen this?" check that quietly charges people twice.

### And the money: the idempotency key

The payment provider is outside our database and always will be, so the outbox can't cover it. The danger there is a retry. Our charge request times out; did the card get charged or not? If we just retry, we might charge twice.

The fix is an **idempotency key**: a unique ID we generate for this checkout attempt and send with the charge. If we retry with the same key, the provider recognises it and returns the original result instead of charging again:

  { a: "Sends the charge with idempotency key chk-4417291" },
  { b: "Charges the card. The reply is lost on the way back", tone: "bad" },
  { a: "Times out. Retries with the same key, chk-4417291" },
  { b: "Recognises the key. Returns the original result; no second charge", tone: "good" }
]} />

Without the key, that retry is a second charge. This is why payment APIs have the field, and at any real volume it isn't optional.

### Order of operations around the charge

The order matters, because the process can still die right after the card is charged:

<Stack>
  <Layer idx="1" title="Write the order as pending_payment">Before touching the money, so there is always a record to check against.</Layer>
  <Layer idx="2" title="Authorise the payment, with the key">The provider holds the money on the card.</Layer>
  <Layer idx="3" title="Confirm the order">In one transaction: mark it confirmed and write the outbox event.</Layer>
  <Layer idx="4" title="Sweep for stragglers" speed="every few minutes">A reconciliation job finds orders stuck in `pending_payment`, asks the provider what happened to that idempotency key, and completes the ones that were paid and voids the rest.</Layer>
</Stack>

Why this works: if we die after step 2, the order from step 1 is still there, and step 4 finds it. Money and orders can then never disagree for longer than the sweep interval, which is a bound you can state out loud and hold yourself to.

<Lab
  title="Implement the Transactional Outbox Pattern"
  tip="Feature this Transactional Outbox pattern on your portfolio as a capstone benchmark of bulletproof transactional consistency."
>

Build this capstone mini-project to implement the transactional outbox pattern with SQLite and Python/Node.js:

- **The Database Schema:** Set up an SQLite table:

  ```sql
  CREATE TABLE orders (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    customer_id INT,
    total_cents INT,
    status TEXT
  );
  CREATE TABLE outbox_events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    topic TEXT,
    payload TEXT,
    status TEXT DEFAULT 'PENDING'
  );
  ```

- **Atomic Transaction:** Write a script that writes to both tables inside a single atomic transaction:

  ```python
  def create_order(db_conn, customer_id, total_cents):
      cursor = db_conn.cursor()
      cursor.execute("BEGIN;")
      try:
          cursor.execute("""
              INSERT INTO orders (customer_id, total_cents, status)
              VALUES (?, ?, 'CONFIRMED')
          """, (customer_id, total_cents))
          order_id = cursor.lastrowid
          event_payload = {"order_id": order_id, "total": total_cents}
          cursor.execute("""
              INSERT INTO outbox_events (topic, payload)
              VALUES ('order.placed', ?)
          """, (json.dumps(event_payload),))
          cursor.execute("COMMIT;")
      except Exception as e:
          cursor.execute("ROLLBACK;")
          raise e
  ```

- **The Outbox Relay:** Write a separate background process (the relay) that polls the `outbox_events` table periodically, publishes messages, and marks them as `PROCESSED` in a transaction:

  ```python
  def poll_and_relay(db_conn):
      cursor = db_conn.cursor()
      cursor.execute("SELECT id, topic, payload FROM outbox_events WHERE status = 'PENDING' LIMIT 10")
      pending = cursor.fetchall()
      for event_id, topic, payload in pending:
          # Simulate publishing to RabbitMQ/Kafka
          print(f"Relaying event {event_id} to {topic}: {payload}")
          # Mark processed atomically
          cursor.execute("UPDATE outbox_events SET status = 'PROCESSED' WHERE id = ?", (event_id,))
      db_conn.commit()
  ```

- **Validate Crashes:** Run the creator script and kill it midway. Verify that order and outbox records are either both committed or both rolled back. Run the relay, simulate a network dropout, and verify that no events are lost and duplicates are safely handled downstream.

</Lab>

<Collapse id="guardrails" title="2. Keeping someone else's bad day out of yours">

Every call our checkout makes to another system is a way for that system's bad day to become ours. If the fraud service takes 30 seconds to answer, every checkout waiting on it holds a thread for 30 seconds, and Part 1 showed where that ends. The [Reliability guide](/guides/reliability-toolkit/) supplies the tools. Here's what each one does, in plain words:

- **Timeout:** stop waiting after a fixed time.
- **Retry:** try again after a failure, but only when it's safe to.
- **Bulkhead:** a cap on how many calls to one dependency can be in progress at once, so it can't use up every thread.
- **Circuit breaker:** after enough failures, stop calling the dependency for a while and fail immediately instead.
- **Fail open:** carry on without the dependency, using a fallback.

And here is where each one goes in this design, and what we do when that dependency fails:

<Table>

| Dependency | Timeout | Retry | Guardrail | When it fails |
| ---------- | ------- | ----- | --------- | ------------- |
| **Payment provider** | 3 s connect+read | Once, with the same idempotency key | Bulkhead: max 300 concurrent. Breaker on error rate. | Fail the checkout with a clear message. Do not fake success — you cannot ship what you weren't paid for. |
| **Primary database** | 2 s statement | No | Bounded pool, sized by Little's Law | Hard down. Nothing to degrade to. This is what replicas and failover are for. |
| **Cache** | 50 ms | No | Fail open to the database | Degrades, doesn't error — but see the warning below. |
| **Queue broker** | 1 s publish | No — the outbox is the retry | Outbox relay backs off | Nothing user-visible. Messages accumulate in the outbox table and drain later. |
| **Fraud service** | 400 ms | No | Fail open, score offline | Take the order, score it asynchronously, cancel later if needed. A business decision, made in advance. |
| **Recommendations** | 150 ms | No | Fail open to a static list | Nobody notices. This is what graceful degradation looks like when it's done right. |

</Table>

<Note type="warn" label="&quot;Fail open to the database&quot; is not free">

The cache absorbs about 96% of 25,000 reads/s, so the database normally sees only the remaining 4%. If the cache dies, the database instantly gets the whole 25,000: about 25× its normal read load. "The app still works" is true for about four seconds. That's why the cache needs its own redundancy, why the fallback path needs request coalescing (one database query per key, however many requests want it), and why load shedding exists.

</Note>

### Pass the deadline along

Two settings people consistently miss, and this design depends on both. The first is **deadline propagation**. The customer's request has an 800 ms budget. If 500 ms are already spent when we call the payment provider, that call must know it has 300 ms left, not use its own separate 3-second timeout. Otherwise we spend capacity computing answers nobody is still waiting for.

### Retry at one layer only

The second is a **retry budget**. Suppose three layers each try a call up to three times. One customer click becomes 3 × 3 × 3 = 27 requests to the bottom layer, arriving exactly when it's already struggling. So retry at exactly one layer, and cap total retries at a small fraction of live traffic.

</Collapse>

<Collapse id="staleness" title="3. How out of date each piece of data may be">

The product page says "Only 3 left". Does that number have to be exactly right this millisecond? If yes, every page view must ask the primary database, and the cache from Part 1 is gone. If it can be 30 seconds old, the cache serves it. The answer is different for every field.

"Is the system consistent?" is the wrong question. The [Consistency guide](/guides/consistency-cap/)'s central point is that consistency is decided field by field, and each field has its own price. So go through them and say what you're buying:

<Table>

| Data | Staleness allowed | What you buy |
| ---- | ----------------- | ------------ |
| **Payment record** | None | Nothing. This is the money. Strong consistency on the primary, no exceptions, no cache. |
| **Order exists / order status** | None for the owner; seconds for everyone else | The customer reads their own order from the primary for a short window after writing. Everyone else can read a replica. |
| **Inventory — the number we decrement** | None | Correctness at checkout. A conditional update on the primary, described below. |
| **Inventory — the number we display** | ~30 s | 25,000 reads/s served from cache instead of the database. "Only 3 left" being briefly wrong is a UX cost; being right costs you the read architecture. |
| **Order history** | ~1 s | Replica reads, with a read-your-writes window for the customer who just ordered. |
| **Recommendations, "recently viewed"** | Minutes to hours | Everything. Precompute it, cache it hard, and let it be wrong. Nobody has ever filed a bug about a stale recommendation. |
| **Analytics and reporting** | Minutes | Keeps a heavy, unpredictable workload entirely off the transactional database. |

</Table>

### The hard one: two customers, one item

One item left. Two customers press "Buy" 8 ms apart, and the code does the obvious thing: read the stock, check it's above zero, then save the new count.

<Race a="Customer A" b="Customer B" result="Result: two customers charged for one item" steps={[
  { a: "Reads stock: 1 left" },
  { b: "Reads stock: 1 left" },
  { a: "1 is enough. Sets stock to 0, takes the payment", tone: "good" },
  { b: "1 is enough. Sets stock to 0, takes the payment", tone: "bad" }
]} />

Each request was right about what it saw; B just saw it before A saved. One customer is going to be disappointed, and it's your job to decide how, *before* you charge them.

### Fix 1: let the database decide in one statement

Make the decrement conditional, in a single statement, so the database decides instead of your code:

```sql
UPDATE inventory
   SET available = available - :qty
 WHERE sku = :sku
   AND available >= :qty;
-- 0 rows updated → someone beat you.
-- Sold out. Tell the customer now,
-- before you charge the card.
```

Why this works: while one request is changing a row, the database makes any other request that wants to change it wait. When B's turn comes, the database checks `available >= :qty` again against the current value, which is now 0, so B's update changes nothing:

<Race a="Customer A" b="Customer B" result="Result: one sale, and B hears &quot;sold out&quot; before being charged" tone="good" steps={[
  { a: "UPDATE … WHERE available >= 1. Row locked; stock goes to 0" },
  { b: "Same UPDATE. Waits for A's lock", note: true },
  { a: "Commits. Lock released", tone: "good" },
  { b: "Re-checks: 0 >= 1 is false. 0 rows updated, so: sold out", tone: "good" }
]} />

This is called an **optimistic decrement**. It's atomic and correct, with one flaw: it takes the stock before the payment succeeds. If the card is declined thirty seconds later, that item was held hostage for nothing.

### Fix 2: reserve, then confirm

**Reserve-then-confirm** fixes that. The same conditional update creates a reservation with a short expiry. Then the payment runs. Success turns the reservation into a sale; failure or expiry gives the stock back. It's a small state machine plus a sweeper job for expired reservations, and it's the design most real commerce systems land on.

<Note label="The uncomfortable industry truth">

Many large retailers accept a small oversell rate on purpose. Perfectly exact inventory across every channel at once (web, app, stores, marketplaces) costs latency on every read and a coordination system that becomes the bottleneck on your busiest day. Occasionally apologising, refunding and offering a voucher is cheaper. That's a *business* answer to a *distributed systems* problem, and spotting when one is available is a real engineering skill. It is also, precisely, the [AP branch](/guides/consistency-cap/) chosen on purpose: stay available, fix the conflict afterwards.

</Note>

<Note type="key" label="What to remember">

- Two writes to two systems with nothing tying them together will eventually disagree. Put the event in the order's transaction (the outbox), and send an idempotency key with every charge.
- Every call to another system gets a timeout, a retry policy, a cap on concurrent calls, and a decided answer for "what if it's down".
- Decide staleness field by field. The stock you display can be 30 seconds old; the stock you decrement is checked inside a single conditional update.

</Note>

<Collapse id="check" title="Check your understanding">

<Quiz q="Where in this design can a customer be charged without an order existing, and what prevents it?" options={["Nowhere: the charge and the order commit in one database transaction", "Between authorising and committing; a pending_payment row first, an idempotency key on the charge, and a reconciliation sweep bound it", "In the outbox relay; making the consumers idempotent closes the gap"]} answer={1}>

Between authorising the payment and committing the order. The process can die in that window, and the money is taken with nothing confirmed.

Three things together close it. The order is written as `pending_payment` *before* the charge, so there's always a record to check against. The charge carries an idempotency key, so a retry can't charge twice. And a reconciliation job sweeps orders stuck in `pending_payment`, asks the provider what happened to that key, and completes or voids each one. You can't make the window impossible, since the provider is outside your database, but you can limit how long a disagreement lasts.

</Quiz>

<Quiz q="Your cache dies completely at peak. Why is &quot;the app still works&quot; not a good answer?" options={["The database takes about 25× its normal read load, saturates, starves checkout through the shared pool, and retries can keep it down", "Sessions are lost, so every customer is logged out, but checkout keeps working", "Reads get a few milliseconds slower until the cache restarts and refills"]} answer={0}>

The cache absorbs about 96% of 25,000 reads/s, so without it the database suddenly sees about 25× its normal read load. It saturates, queries slow down, and connections back up. Because checkout shares the same connection pool, checkout starts timing out too: a problem on the read side has become an outage on the write side.

Then clients retry, adding more load, and the system can stay down even after the cache comes back, because the retries and the empty cache keep it overloaded. That's metastable failure: waiting doesn't fix it; you have to shed load and bring traffic back gradually. "It degrades instead of erroring" is true for about four seconds.

</Quiz>

<Quiz q="You add a second region. Which three decisions just got harder?" options={["Caching, load balancing and the queue, because each needs a second copy", "Session storage, TLS certificates and DNS", "Inventory coordination, which region or regions may write, and when to fail over"]} answer={2}>

First, inventory: an exact global count now needs the regions to agree on every checkout, and a round trip between regions takes 60–150 ms, a limit set by the speed of light. Second, the database: with one writable primary, one region pays that delay on every write; with two writable primaries, every field needs a rule for conflicting writes, and "last write wins" on an inventory count silently loses sales.

Third, failover: "the other region is down" is a judgement made by a timeout you configured, and getting it wrong in either direction is expensive. Most teams start with one region that takes writes and read replicas elsewhere, precisely to avoid the second problem.

</Quiz>
