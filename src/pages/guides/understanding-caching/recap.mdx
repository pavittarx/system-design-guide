<Recap>

- A cache trades memory and a new class of bugs for speed and a lighter database. The bugs are the price, not a defect.
- **Cache-aside** is the default: check the cache; on a miss, read the database, store the value, return it. On a write, update the database and *delete* the key. Deleting beats storing the new value, because two writers can reach the cache in the opposite order from the database.
- "The app still works without the cache" means it slows down instead of erroring. If the cache was answering 95% of reads, losing it hands the database 20× its normal load at once.
- Always set a TTL. It's the only thing that repairs an invalidation you got wrong, and you will get one wrong.
- **Jitter fixes many keys expiring together.** **Single-flight fixes one popular key expiring**, by letting one request rebuild it while the rest wait. Different problems: jitter does nothing for the second.
- The **stale-forever race**: a slow reader stores the old value right after a writer deleted the key. Deleting on write can't prevent it; the TTL is what eventually cleans it up.
- Cache "not found" on purpose, with a short TTL and a marker you can tell apart from real data. Never caching it leaves an open door to your database.
- More cache nodes don't fix a hot key: hashing sends that key to one node however many there are. Split the key, or cache it inside each app server for a second.
- Personalised responses need `Cache-Control: private`. A shared cache files responses by URL, and a missing or wrong `Vary` serves one user's page to another.
- Put a version in your keys (`v3:user:123`), so changing the stored format never forces you to choose between emptying the cache and reading garbage.
- Redis's `maxmemory-policy` defaults to `noeviction`: a full cache refuses writes instead of making room. Set `allkeys-lru`.
- Once retries are feeding the outage, it **sustains itself**. You recover by turning load away, not by waiting.

</Recap>

### Numbers worth having in your head

These are **order-of-magnitude figures, not benchmarks**. They exist so you can sanity-check a design in your head before you measure. Your hardware, payload sizes and network will move any of them by a factor of a few.

<Table numeric>

| Rough figure | What | Why it matters |
| ------------ | ---- | -------------- |
| ~100 ns | In-process hash lookup (Caffeine, a plain map) | Effectively free. No network, no serialisation. |
| ~0.2–1 ms | Redis/Memcached round trip, same AZ | ~2,000–10,000× slower than local, still ~10× faster than a DB query. |
| ~1–10 ms | Indexed database query, warm buffer pool | The thing you're avoiding. Add a lot if it goes to disk or joins. |
| ~10–30 ms | CDN edge hit from a nearby POP | Dominated by the user's last-mile latency, not the cache. |
| ~60–150 ms | Cross-region round trip (US coast-to-coast → transatlantic) | Speed of light. No cache tuning fixes this; move the data closer. |
| 90–99% | CDN hit rate, fingerprinted static assets | If it's below this, something is defeating the cache key. |
| 80–95% | Healthy object-cache hit rate, read-heavy workload | The normal target for cache-aside in front of a database. |
| < 70% | Time to ask whether this cache earns its keep | Every miss now pays cache latency *plus* DB latency. |

</Table>

<Note type="key" label="The one-liner to remember">

A cache is a second copy of the truth with its own lifetime, and every hard problem in caching is a consequence of that sentence. Give every entry a TTL, delete on write rather than overwriting, collapse concurrent misses into one query, and remember that the cache is now load-bearing — losing it is an outage you have to design for, not a graceful fallback you get for free.

</Note>

### Where to start

If you're adding caching to something real, resist the urge to reach for the fanciest pattern. A reliable progression:

- **Start with cache-aside + a TTL.** It's simple, resilient, and covers most read-heavy workloads.
- **Measure the hit rate.** If it's low, you're caching the wrong things — fix that before adding machinery.
- **Add TTL jitter from the start** — it is three lines and it prevents keys written together from expiring together. Note that it does nothing for a single hot key; that one needs single-flight.
- **Reach for write-through, event-driven invalidation, or coalescing** only when the numbers actually ask for them.

Add complexity in response to evidence, not anticipation. The best caching setup is the simplest one that hits your latency and freshness targets.
