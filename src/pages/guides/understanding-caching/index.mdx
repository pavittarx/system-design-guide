<ColdOpen tag="◇ the ninety seconds after the key expired">

19:42 on a Tuesday, the busiest hour of the week. One cached entry, the homepage feed, is requested about 8,000 times a second and was stored for an hour. Now its hour (its TTL, time to live) runs out. Every one of those 8,000 requests looks in the cache, finds nothing, and does the obvious thing: asks the database.

The query takes 40 ms when the database is idle. It is not idle: it's now running 8,000 of them at once, so each takes four seconds, then twelve. Clients give up at two seconds and retry, which adds a second wave on top of the first. Nobody deployed anything. No disk failed. A timer ran out, and by 19:44 the site is down.

</ColdOpen>

<Collapse id="what" title="1. What a cache is, and why it's fast">

Your product page runs a query that takes tens of milliseconds, and it returns the same answer to everyone who asks within the next hour. Running it again for every visitor is pure waste.

So keep a copy of the answer somewhere fast and close, and hand that out instead. That's a **cache**: a small, fast store holding copies of data near where it's needed, so you don't redo expensive work like a database query, an API call, a heavy computation or a network round trip. You spend a little memory, and take on some complexity, to buy a lot of speed and a much lighter load on the systems behind it.

Why it pays off: the gap in speed is huge. Reading from an in-memory cache takes microseconds if it's inside your process, and well under a millisecond across the network to Redis. The same request that falls through to a database and back can take **tens of milliseconds**, often orders of magnitude slower. When most requests are answered from the cache, average latency collapses and the database barely notices the traffic.

<Note type="key" label="The whole tension in one line">

*"There are only two hard things in Computer Science: cache invalidation and naming things."* — attributed to Phil Karlton. "Invalidation" means telling the cache its copy is now wrong. Caching is easy to add and hard to keep *correct*, and that's the real subject of this guide.

</Note>

</Collapse>

<Collapse id="layers" title="2. Where caches live">

A request for your homepage passes through several places on its way to the database, and any of them could have answered it from a copy. Caching isn't one thing; it's a series of layers between the user and the **source of truth** (the database or service that owns the real data). The earlier a request is answered, the cheaper it is. Walk one from the browser inward:

<Stack>

<Layer idx="1" title="Browser / client cache" speed="fastest">
The user's own device keeps files and responses it has already downloaded. Nothing beats not making a request at all. Controlled by HTTP headers your server sends.
</Layer>

<Arrow>↓ on miss</Arrow>

<Layer idx="2" title="CDN / edge cache" speed="very fast">

A **CDN** (content delivery network: Cloudflare, Fastly, CloudFront) is a global network of servers that keep copies of your content near users. It cuts latency *and* the load on your own servers.

**◈ In the wild:** Netflix Open Connect places caches directly inside internet providers' networks, and pushes popular shows to them during off-peak hours, so they're already there before viewers press play.

</Layer>

<Arrow>↓ on miss</Arrow>

<Layer idx="3" title="Reverse proxy / gateway" speed="fast">
Varnish or Nginx sitting in front of your app, storing whole responses so repeat requests never reach your code.
</Layer>

<Arrow>↓ on miss</Arrow>

<Layer idx="4" title="Application cache" speed="fast">
Inside your service: an in-memory map in each process (Caffeine, Guava), or a shared store all servers use (Redis, Memcached). This is where "caching strategies" live.
</Layer>

<Arrow>↓ on miss</Arrow>

<Layer idx="5" title="Database cache" speed="the origin">
The database's own memory cache of table data (its buffer pool) and precomputed results (materialised views). The source of truth, with its own caching inside.
</Layer>

</Stack>

These layers **stack up**: one page load might be served partly from the browser, partly from the CDN, and partly computed fresh. Each layer needs its own plan for staying correct.

<Note label="One copy per server, or one shared copy?">

You run three app servers, each with its own in-memory cache. A user changes their name; server 1 clears its copy, servers 2 and 3 keep showing the old one. That's the catch with an **in-process** cache: it's the fastest (no network hop), but every server has its own copy, they can disagree, and you pay for the memory three times. A **distributed** cache (Redis, Memcached) adds a network hop but gives every server one shared view. Once you have more than one server, distributed is usually the answer.

</Note>
