<Collapse id="strategies" title="1. Read/write strategies">

Each pattern answers two questions: *who talks to the cache*, and *when does the cache get written*. The read patterns decide how misses get filled; the write patterns decide how the cache stays in step with the source of truth.

### Quick Strategy Decision Matrix

<Table>

| Strategy | Consistency | Write Overhead | Ideal Workload / Use Case |
| :--- | :--- | :--- | :--- |
| **Cache-aside** | <Pill tone="mid">eventual</Pill> | Low | Read-heavy, general purpose. The safe default pattern. |
| **Read-through** | <Pill tone="mid">eventual</Pill> | Low | Read-heavy workloads where caching logic is encapsulated in data providers. |
| **Write-through** | <Pill tone="good">strong-ish</Pill> | High | Critical data requiring fresh reads, where write latency trade-off is acceptable. |
| **Write-back** | <Pill tone="bad">weak</Pill> | Very Low | Write-heavy, high-burst workloads where occasional node-crash data loss is tolerable. |
| **Write-around** | <Pill tone="mid">eventual</Pill> | Low | Data written frequently but rarely re-read immediately. |

</Table>

### Cache-aside (lazy loading) — the default

The application manages the cache. On a read: check cache → hit returns it → miss reads the DB, writes the value into the cache, then returns it. On a write: update the DB and invalidate the cached entry.

<DiagramUnderstandingCaching2 />

- <Pill tone="good">+</Pill> Only requested data is cached (lean, cheap). If the cache disappears, reads still *return* — they fall through to the database instead of erroring.
- <Pill tone="bad">−</Pill> The first request for any key always misses (cold start). The app carries the caching logic. A small window exists where DB and cache can disagree.

<Note type="warn" label='"Resilient to cache failure" has an asterisk on it'>

You will read that cache-aside means "if the cache dies, the app still works." What it actually means is that the app *degrades* rather than throwing errors — which is not the same thing as surviving. If your cache was absorbing 95% of reads, then the moment it goes away cold your database receives **twenty times** its normal read load, all at once, with no ramp. Databases do not politely queue; they fall over.

Losing a cache cold is one of the best-documented ways to take a service down, and it is why cache warmup, request coalescing and load shedding exist at all. Cache-aside buys you a failure mode you can survive *if you built for it* — see [the Reliability guide](/guides/reliability-toolkit/) for the machinery.

</Note>

### Read-through

Like cache-aside, but the *cache* knows how to load from the DB on a miss (via a library/provider), so the app only ever talks to the cache. Cleaner app code; loading logic moves into the caching layer.

### Write-through

Every write updates the cache and the DB synchronously, together.

- <Pill tone="good">+</Pill> Cache and DB stay consistent; any key that's been written is served warm (unwritten or evicted keys still miss).
- <Pill tone="bad">−</Pill> Every write pays to write both; you cache data that may never be read (bloat). Often paired with cache-aside reads.

### Write-back (write-behind)

Write to the cache immediately and return; flush to the DB asynchronously later, in batches.

- <Pill tone="good">+</Pill> Very fast writes; absorbs bursts; fewer DB writes.
- <Pill tone="bad">−</Pill> Data loss risk if the cache node dies before the flush. More complex.

### Write-around

Writes go straight to the DB, bypassing the cache; the cache fills later on a read miss.

- <Pill tone="good">+</Pill> Avoids flooding the cache with write-heavy data that isn't read soon.
- <Pill tone="bad">−</Pill> Recently written data is a guaranteed miss on first read.

Real systems mix these. AWS, for instance, recommends combining **write-through** (to keep the cache fresh) with **cache-aside** reads (as the miss fallback), plus TTLs to keep it lean.

Worth saying out loud: caching is not the only way to take read load off a database. Read replicas move the same reads to a different machine without introducing a second copy of the truth with its own lifetime — see [the Database Scaling guide](/guides/database-scaling/). Caching wins when the work is expensive to *compute*, not merely expensive to *fetch*.

</Collapse>

<Collapse id="worked" title="2. Cache-aside in code">

Everything above is vocabulary. Here is what cache-aside looks like when you actually write it, and it is worth staring at, because this exact function is in production somewhere near you right now.

```python
def get_user(user_id):
    key = f"user:{user_id}"
    cached = redis.get(key)
    if cached:
        return json.loads(cached)

    user = db.query_one("SELECT * FROM users WHERE id = %s", user_id)
    redis.setex(key, 3600, json.dumps(user))
    return user

def update_user(user_id, fields):
    db.update("users", user_id, fields)
    redis.delete(f"user:{user_id}")
```

</Collapse>

<Collapse id="bugs" title="3. Three invalidation bugs (and their fixes)">

Textbook cache-aside code is straightforward in shape but wrong in several critical ways. Let's trace how real-world scheduling, negative responses, and application rollouts break it.

### Cache invalidation

The cache holds a *copy*. The moment the source of truth changes, that copy might be wrong. Three broad approaches:

- **TTL / expiry** — let entries lapse. Simple, eventually consistent, but stale within the window.
- **Write-time invalidation** — when you update the DB, delete/update the cache entry in the same flow. Fresher, but you must find *every* place a value is cached, and the DB-write + cache-delete pair isn't atomic (a failure between them leaves you inconsistent).
- **Event-driven invalidation** — publish change events (pub/sub, a CDC stream, Redis Pub/Sub) that fan out and purge keys. Scales well, more moving parts, and you inherit every delivery guarantee question the transport has — see [the Message Queues guide](/guides/message-queues/), because "at-least-once purge" and "at-most-once purge" are very different promises about your cache.

<Note type="warn" label="The Core Question">

*How stale can this specific data safely be?* The answer determines your caching strategy for each field.

</Note>

<Note type="wild" label="🌍 In the wild: E-Commerce Product Pages">

On an e-commerce product page, the *description and images* barely change, so they are cached aggressively at the CDN for hours. But the *price and inventory count* must be near-real-time to avoid selling out-of-stock items, so they are cached for only seconds, written through on every change, or fetched live from the origin.

</Note>

<Note type="key" label="Eventual Consistency">

Most caches give **eventual consistency** — for a window, readers may see old data. If that trade-off is critical for your data type (like account balances), [the Consistency & CAP guide](/guides/consistency-cap/) unpacks exactly what you are and aren't promised.

</Note>

Thirteen lines, textbook-correct in shape, and wrong in at least four ways.

<CardGrid>

<Card title="Bug 1: Nothing coalesces the misses">

Ten thousand concurrent requests for the same missing key run the function ten thousand times. Each one sees an empty cache and issues its own `SELECT` query. The cache does not queue them or know they are related — converting a single expiry event into a database outage (thundering herd).

**The Fix: Single-flight / Request Coalescing** — The first caller to miss takes a short mutex lock and populates the cache while all other callers wait for its answer.

</Card>

<Card title="Bug 2: Constant TTL (Synchronised Expiry)">

Setting a fixed `3600s` TTL for all keys causes entries populated during a deploy or batch job to expire at the exact same second — manufacturing periodic load spikes.

**The Fix: Jitter** — Randomise the TTL (e.g. `3600 ± 300s`) to smooth out expiration times over a window.

</Card>

</CardGrid>

### Bug 3: The Stale-Forever Race

This one is subtle and it is the reason people lose faith in their cache. Think of it as a story of a **Reader** thread that gets temporarily "distracted" (descheduled by the CPU) while a **Writer** updates the database in the background:

<CacheRaceDiagram />

Here is what happens step-by-step during this race:

- The **Reader** misses the cache, loads the old row value (`Ada`) from the database, and is just about to write it back to Redis.
- Right then, the Reader gets suspended by the operating system (e.g. during a garbage collection pause or network lag).
- While the Reader is asleep, a **Writer** updates the database to `Grace` and deletes the Redis key. Since the key was already empty, this delete is a silent no-op.
- The Reader wakes up and finishes its write, saving the stale value `Ada` back into the empty Redis slot.

Now, the database has `Grace` but the cache confidently serves `Ada`. No subsequent writes will clear this key unless a user updates their profile again. The cache will remain stale for the entire 60 minutes.

This is why **invalidation-on-write alone is not sufficient**, no matter how carefully you find every call site. The window is small, but "small" times "a million writes a day" is a support ticket. Narrowing it is possible — Facebook's *leases* hand the missing reader a token that the writer's delete invalidates, so the late fill is simply rejected; a "delayed double delete" removes the key again a second after the write. Eliminating it needs versioned compare-and-set on the fill.

And it is why a **bounded TTL is a safety net rather than a nicety**. The TTL is the only thing in the buggy version above that ever repairs this. Every key you cache without an expiry is a key that can be silently wrong forever. If you find yourself writing `SET` with no TTL, you are betting that your invalidation logic is perfect. It is not.

### 4. Misses and empty results are the same thing

`db.query_one` returns `None` for a user that doesn't exist. `json.dumps(None)` is the string `"null"`, which gets cached for a full hour and is indistinguishable from a real value. So a user created one second after somebody looked them up stays invisible for an hour.

Flip the code the other way — only cache when `user is not None` — and you get the opposite failure, **cache penetration**: every request for a non-existent ID misses the cache and hits the database, forever, which is a free denial-of-service for anyone who can guess URLs.

The answer is to cache negatives *deliberately*, with their own short TTL and a sentinel you can tell apart from real data. (While you are in there: `if cached:` is also wrong — an empty cached value is falsy, so a legitimately-empty entry is treated as a miss on every read. Test `is not None`.)

### 5. Schema/key versioning during deploys

Prefix every key with a schema version: `v3:user:123`. You will not appreciate why until the deploy where you add a field to the serialised shape, and every instance running the old code starts reading objects that have it while every instance running the new code reads objects that don't.

Without a version prefix your options are (a) flush the cache, which is the cold-start outage described in [Part 2](/guides/understanding-caching/failure/#hotkeys), or (b) write defensive deserialisation forever. With one, you bump `v3` to `v4`, the new code writes and reads new keys, the old keys are read by nobody and quietly age out under their own TTL or get evicted by LRU. It costs six characters per key.

### The version that survives contact

```python
MISS = "◇none"                      # sentinel: cached "does not exist"

def safe_decode(val):
    # Handles both string and bytes (for redis-py decode_responses setting)
    return val.decode('utf-8') if isinstance(val, bytes) else val

def jitter(ttl):
    return ttl + random.randint(0, ttl // 10)

def get_user(user_id):
    key = f"v3:user:{user_id}"      # v3 = serialisation version
    hit = redis.get(key)
    if hit is not None:
        return None if safe_decode(hit) == MISS else json.loads(hit)

    with single_flight(key):        # only one loader per key (conceptual lock)
        hit = redis.get(key)        # check if someone filled it while we waited
        if hit is not None:
            return None if safe_decode(hit) == MISS else json.loads(hit)

        user = db.query_one("SELECT * FROM users WHERE id = %s", user_id)
        if user is None:
            redis.set(key, MISS, ex=jitter(60), nx=True)
        else:
            redis.set(key, json.dumps(user), ex=jitter(3600), nx=True)
        return user

def update_user(user_id, fields):
    db.update("users", user_id, fields)
    redis.delete(f"v3:user:{user_id}")   # delete, don't write the new value in
```

What changed: misses collapse to one query, TTLs no longer synchronise, non-existent users get a short negative entry instead of either an hour of invisibility or an open channel to the database, and the key carries a schema version. `nx=True` means a slow reader can never clobber a value someone else has already refreshed — it does *not* close the stale-forever race, because after the writer's `DEL` the slot is empty and the stale `SET` succeeds. Only the bounded TTL saves you there, which is the whole point.

Note also the last line: the writer *deletes* rather than writing the new value. Two concurrent writers who both write their value into the cache can land in the opposite order they landed in the database. Delete-on-write has one outcome — the next reader goes and finds out — and one outcome is much easier to reason about than two.

<Collapse id="check" title="Check your understanding">

<Quiz q="You invalidate on every write, you've checked every call site, and users still report stale data — for almost exactly your TTL duration. What happened?" options={["Redis evicted the key under memory pressure and refilled it from a lagging replica", "The CDN cached the API response for the same duration as the cache TTL", "A slow reader wrote its stale value back after the writer's delete, so only the TTL could clear it"]} answer={2}>

The stale-forever race. A reader missed, read the old value from the database, got descheduled; your writer updated the row and deleted a key that wasn't there; the reader woke up and wrote its stale value into the empty slot. Your invalidation ran before the poisoning write, so it invalidated nothing. The giveaway is the duration: it's the TTL, because the TTL is the only thing that ever clears it. Narrow the window with leases or a delayed second delete, and never remove the TTL.

</Quiz>
