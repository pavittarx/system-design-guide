<ColdOpen tag="◇ the checkout that punished success">

Black Friday. A user clicks "Buy". Behind that one click, your code charges the card, generates an invoice PDF, emails a receipt, updates the warehouse, pings the analytics service and posts to Slack, one after the other, while the user waits. The email server is having a slow day, so the user stares at a spinner for 11 seconds.

Multiply that by 50,000 shoppers at once and the whole site seizes. Buying isn't hard; you just insisted on doing *everything* before saying "thanks for your order". A queue is how you hand off the boring parts and reply straight away.

</ColdOpen>

<Collapse id="sync" title="1. Synchronous vs. asynchronous: do the work now, or later?">

Look at that checkout again. The user needs to know one thing: did my order go through? They don't need to *watch* the receipt email being sent, and they certainly don't need to wait for the analytics service.

There are two ways to ask another part of the system to do something. **Synchronous** is a phone call: both sides are on the line at once and you wait for the answer. **Asynchronous** is a text message: you send it and get on with your day; the other side handles it when it can.

Much of the work behind a click has no business being synchronous. So do the essential part while the user waits (record the order, take the money), write everything else down as a to-do for later, and return "success" immediately. The slow, non-urgent work happens in the background, and a slow email server only delays the email.

<Note type="wild" label="◈ In the wild · E-commerce checkout">

When you click "Buy" on Amazon or Shopify, the instant "Order confirmed!" is a fast asynchronous hand-off. The email, the warehouse booking and the card settlement details are queued, so the page can load straight away.

</Note>

</Collapse>

<Collapse id="queue" title="2. The queue as a shock absorber">

Those to-dos have to be kept somewhere safe until a worker gets to them, even if a server restarts in between. That place is a **message queue**: a durable line that work waits in. Each to-do is a **message**. Code that adds messages is a **producer**; code that takes them off and does the work is a **consumer**. The server that holds the queue is the **broker**.

<Stack>
  <Layer idx="1" title="Producer">
    Adds a "send receipt" message and moves on instantly.
  </Layer>
  <Arrow>↓ enqueue ↓</Arrow>
  <Layer idx="2" title="Queue (broker)" speed="the buffer">
    Holds messages durably until someone processes them. Absorbs bursts.
  </Layer>
  <Arrow>↓ dequeue ↓</Arrow>
  <Layer idx="3" title="Consumer(s)">
    Take messages at their own pace. Add more to go faster.
  </Layer>
</Stack>

Why this helps: producer and consumer no longer have to work at the same time or the same speed. When a traffic spike hits, the queue just gets longer; it doesn't fall over. Consumers work through the backlog at a steady rate the systems behind them can survive. Bursty in, smooth out.

### Buffer the spike, but bound the buffer

Absorbing a spike by letting the queue grow is called **load leveling**: the database takes writes at its own pace instead of being knocked over. It's the cheapest thing you can put in front of a database that's struggling with writes. Writes are the hard half to scale, as [the Database Scaling guide](/guides/database-scaling/) explains, and a queue lets you cap the write rate without dropping any writes.

A queue that can grow forever has its own failure: it eats memory, and the messages at the back get older and staler. So the next step is a *bounded* queue that, when full, pushes back on producers or turns work away. That push-back is called **backpressure**. Buffer for smoothness; bound the queue so the buffer can't sink you.

<Note type="wild" label="◈ In the wild · LinkedIn & Kafka">

LinkedIn built Kafka around 2010. Dozens of services needed data from dozens of others, and point-to-point wiring meant *N×M* brittle pipelines. Kafka replaced the web with one **durable, append-only log** every system writes to and reads from at its own pace. Open-sourced in 2011, it now carries much of the industry's event traffic.

</Note>

</Collapse>

<Collapse id="parts" title="3. One consumer or every consumer: two shapes of delivery">

Two kinds of message look alike and need opposite handling. "Send this receipt" should be done by exactly one worker; if three workers each send it, the customer gets three emails. "An order was placed" should reach billing, shipping *and* analytics; if only one of them hears it, the other two never act.

<CardGrid>
  <Card title="Work queue (point-to-point)">
    Each message goes to *exactly one* consumer. Ten workers share the load; a receipt gets emailed once. This is task distribution.
  </Card>
  <Card title="Pub/sub (publish–subscribe)">
    Each message goes to *every* interested subscriber. "Order placed" fans out to billing, shipping and analytics, and each gets its own copy. This is event notification.
  </Card>
</CardGrid>

Pub/sub is the backbone of **event-driven architecture**: services announce that something happened and don't care who's listening. Need a new feature that reacts to orders? Subscribe to the existing event stream; the producer never has to change. That's how big systems add capabilities without every service knowing about every other.
