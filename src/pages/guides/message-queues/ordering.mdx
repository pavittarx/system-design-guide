<Collapse id="order" title="1. Ordering & the dead-letter queue">

**Ordering.** Many queues don't guarantee messages come out in the order they went in — especially once you have multiple consumers racing. If order matters ("account created" must precede "account updated"), you either use a queue that preserves order within a partition (Kafka does, keyed by e.g. user ID) or design so order doesn't matter. Assuming global ordering you don't have is a top-tier source of Heisenbugs.

**Dead-letter queue (DLQ).** What about a message that *can't* be processed — malformed data, a bug, a permanent failure? Without a plan, your consumer retries it forever, blocking everything behind it (a "poison message"). The fix is a DLQ: after N failed attempts, shunt the message to a separate queue for humans to inspect later. It's the inbox of things that went wrong, and checking it occasionally will teach you a lot about your own system.

</Collapse>

<Collapse id="outbox" title="2. The dual-write problem and the transactional outbox">

Here's a line of code that appears in almost every service that uses a queue, and it's a bug:

```bash
db.insert(order)               # write 1
queue.publish(order_placed)    # write 2
                               # ...and nothing binds them
```

Two writes, two systems, no transaction spanning them. Crash between them and you get one of two bad outcomes, and which one you get depends on the order you chose.

Write the database first and die: you have taken the order and told nobody, so no receipt, no warehouse pick, no fraud check — a paid order that silently doesn't exist downstream. Publish first and die: you have announced an order you never recorded, and the shipping service is now confidently picking stock for a row that isn't there.

Wrapping it in a try/catch doesn't help, because the failure you're worried about is the process dying between the two lines, and dead processes don't run catch blocks.

The **transactional outbox** removes the second system from the critical path. You write the event into an `outbox` table in the *same transaction* as the business data — one commit, one database, atomic by construction. A separate relay process then reads unsent rows from that table and publishes them to the broker, marking them sent.

```sql
BEGIN;
  INSERT INTO orders (...)  VALUES (...);
  INSERT INTO outbox (topic, payload)
         VALUES ('order_placed', :json);
COMMIT;
-- a relay polls outbox and publishes,
-- then marks the row sent
```

Now the only question is *when* the event gets published, never *whether* — if the order committed, the event is in the table, and the relay will get to it. The other route to the same guarantee is **change data capture**: instead of a table you write yourself, a tool tails the database's own replication log (Postgres WAL, MySQL binlog) and turns committed rows into messages. Debezium is the usual name here. Less application code, more infrastructure to run; same property.

<Note type="warn" label="Outbox gives at-least-once, not exactly-once">

The relay can publish a message and crash before marking the row sent — so it publishes it again on restart. That's not a flaw to be engineered away; it's the same wall from [Part 1](/guides/message-queues/delivery/#delivery), moved one step. The outbox guarantees the event is never *lost*. Making a duplicate harmless is still the consumer's job, which is why the idempotent claim in [Part 1](/guides/message-queues/delivery/#idem) doesn't become optional just because you adopted an outbox.

</Note>

<Lab
  title="Build a Transactional Outbox Worker"
  tip="Put this project on your portfolio as a benchmark of high-reliability distributed outbox design."
>

Build this mini-project to implement atomicity between business databases and message brokers:

- **The Database Schema:** Spin up a Postgres database in Docker. Create an `orders` table and an `outbox_events` table. The `outbox_events` table should have fields: `id (UUID)`, `event_type (VARCHAR)`, `payload (JSONB)`, and `status (VARCHAR, default 'PENDING')`.

- **The Atomic Endpoint:** Write an API server with a POST endpoint `/checkout`. Inside a single database transaction, insert an order row AND insert an event row with type `'order_placed'`.

- **The Publisher Daemon (Relay):** Write a background program that polls the `outbox_events` table for `status = 'PENDING'` rows every 500ms. For each row, publish the event payload to a local message broker (like SQS or RabbitMQ), then mark the database event row status as `'PUBLISHED'`.

- **Simulate Failures:** Under a load test, force your broker connection to drop (e.g. stop the RabbitMQ Docker container), verify that transactions still commit successfully, and watch events queue up safely inside the database outbox. Restart RabbitMQ and verify that all queued events are delivered to consumers with zero loss.

</Lab>

<Collapse id="check" title="Check your understanding">

<Quiz q='Kafka guarantees ordering, so why did your "account created" and "account updated" events arrive backwards?' options={["Kafka only orders messages when a topic has a single consumer group", "Ordering is per partition, and the two events landed in different partitions because they didn't share a key", "The consumer committed offsets out of order during a rebalance"]} answer={1}>

Because the guarantee is per-partition, and those two events almost certainly landed in different partitions — either they were produced with no key (round-robin) or with different keys. Ordering only holds for messages that share a partition, so anything that must be ordered relative to each other has to share a partition key: here, the account ID. The corollary is that your key choice *is* your ordering design, and it also decides your blast radius when one message gets stuck.

</Quiz>

<Quiz q="Your service records the order correctly, but roughly once a week the confirmation email never sends. No exception, no DLQ entry. What's the architectural fix?" options={["A transactional outbox: write the event in the same transaction as the order and let a relay publish it", "Wrap the publish in a try/catch and retry it with backoff", "Send failed publishes to a dead-letter queue so they can be replayed"]} answer={0}>

This is the dual-write problem: the database commit and the queue publish are two separate writes, and once a week the process dies or the broker call fails in the gap between them. There's no exception because there's nobody left to catch it, and no DLQ entry because the message was never published. The fix is the transactional outbox — write the event to an outbox table inside the same transaction as the order, and let a relay publish it. Retrying the publish in a catch block only shrinks the window; it doesn't close it.

</Quiz>
