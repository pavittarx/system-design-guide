<Collapse id="delivery" title="1. Delivery guarantees: the three honesties">

Networks fail, consumers crash mid-task. So every queue has to answer: if things go wrong, how hard do we try to deliver? There are three honest answers, and physics won't let you have a perfect fourth.

<Table>

| Guarantee | Meaning | Risk | Use when |
| --------- | ------- | ---- | -------- |
| **At-most-once** | Fire and forget. Deliver 0 or 1 times. | Messages can be *lost*. | Metrics, logs — a dropped one won't hurt. |
| **At-least-once** | Retry until confirmed. Deliver 1 or more times. | Messages can be *duplicated*. | Almost everything — the common default. |
| **Exactly-once** | Deliver precisely once. The holy grail. | Expensive, complex, and often a comforting fiction. | Rarely truly needed; usually faked with at-least-once + idempotency. |

</Table>

<Note type="warn" label="The dirty secret">

*End-to-end* "exactly-once delivery" — across systems with real side effects — is famously close to impossible. The obstacle is the same one [the CAP & Consistency guide](/guides/consistency-cap/) circles: two independent systems can't agree on "this happened" in one indivisible step over an unreliable network, so somebody always has to choose between retrying (maybe twice) and giving up (maybe never).

What people actually build is **at-least-once delivery + idempotent processing**: deliver possibly twice, but make processing a duplicate a harmless no-op. The result *looks* exactly-once from the outside, which is all anyone wanted. (Kafka's exactly-once *processing* within its own ecosystem — idempotent producer + transactions — is the real exception, but it doesn't extend to arbitrary external side effects.)

</Note>

<Note type="wild" label="◈ In the wild · WhatsApp">

This is how WhatsApp delivers to a phone that's switched off: the server holds the message in an in-memory queue and retries until the device reconnects and *acks* receipt, then deletes it. The two grey ticks (✓✓) are that ack. In early 2014 it moved roughly **50 billion messages a day** for 450 million users on around 550 servers, run by **32 engineers**, on Erlang and a sharded in-memory [Mnesia store that tracked every in-flight message](https://newsletter.systemdesign.one/p/whatsapp-engineering). At-least-once-until-acked, at planetary scale.

</Note>

</Collapse>

<Collapse id="idem" title="2. Idempotency: the survival skill">

Idempotent means: **doing it twice has the same effect as doing it once.** Pressing an elevator button five times doesn't summon five elevators. This single property is what makes at-least-once delivery safe, and it's worth internalizing because it shows up everywhere in distributed systems.

The classic horror is a payment consumer that gets the same "charge $50" message twice (because the first ack got lost) and charges the customer $100. The fix: give each message a unique ID and record which IDs you've already processed. See a repeat? Skip it. Now the retry that would've double-charged is a shrug.

That's the idea. The obvious way to write it is wrong.

### The version everybody writes first — and it's broken

```bash
on message(id, action):
    if already_processed(id):   # seen this one?
        return ok               # harmless no-op
    do(action)
    mark_processed(id)
```

Read it as a single thread and it's flawless. Read it as two consumers — which is the entire point of a queue — and there's a gap between the check and the mark that is wide enough to drive a double charge through. Duplicates don't politely arrive one after the other; they arrive at the same moment, on two machines.

```trace
**t1**  C1 gets msg #7847 (charge $50)
**t1**  C2 gets msg #7847 — a duplicate
**t2**  C1  already_processed(7847)? → no
**t3**  C2  already_processed(7847)? → no
**t4**  C1  do(charge $50)  → card charged
**t5**  C2  do(charge $50)  → ~~charged again~~
**t6**  C1  mark_processed(7847)
**t7**  C2  mark_processed(7847)  (no-op)

~~result: $100 taken for a $50 order~~
```

Both consumers looked before either wrote. The guard did nothing. Note that no line of that trace is unusual — it's just two ordinary executions overlapping by a few milliseconds, which is the normal condition of any system with more than one worker.

### The fix: claim the ID before doing the work

Don't ask whether you've processed the message. *Claim* it — in one statement that the database is obliged to arbitrate, because a uniqueness constraint on `message_id` means only one of the two inserts can possibly succeed. If yours didn't insert a row, someone else owns this message and you go home.

```sql
on message(id, action):
    # one atomic claim; the DB picks a winner
    rows = execute("""
        INSERT INTO processed (message_id)
        VALUES (:id)
        ON CONFLICT (message_id) DO NOTHING
    """, id)

    if rows == 0:        # lost the race
        return ok        # the winner is handling it

    do(action)           # only the winner gets here
```

The check and the write are now the same operation, so there is no gap to lose. This is the general shape of the trick, not a Postgres detail: any store with a uniqueness constraint or a conditional write will do — a unique index, DynamoDB's `attribute_not_exists`, Redis `SET NX`. What you need is one operation that both tests and takes.

### What this still doesn't solve

The winner can crash between claiming and finishing. Now the ID is marked and the work never happened, and every redelivery bounces off a claim row belonging to a process that no longer exists — a permanently lost message that looks, from the outside, exactly like a successfully processed one.

That's why the claim row shouldn't be a bare marker. Give it a **status** (`claimed` / `done`) and a **lease** — a claim timestamp plus an expiry — so a claim that has gone stale can be taken over rather than blocking the message forever. Then "already claimed" and "claimed by a corpse" stop being the same state.

The genuinely robust version doesn't need a lease at all, because it puts the work and the claim in the *same transaction*: insert the claim row and write the business change together, commit once. Either both land or neither does, and a crash rolls the claim back along with everything else. Do this whenever the side effect lives in the same database as the claim — and notice how often it does.

<Note type="warn" label="When the work isn't in your database">

Charging a card is the case that breaks the pattern: you cannot enrol someone else's payment API in your transaction. The answer is to push idempotency across the boundary — send an **idempotency key** (your message ID, or something derived from it) with the charge request, and the provider dedupes on their side, returning the original result instead of charging again.

This is exactly what Stripe's and every other payment provider's idempotency keys are for. When you can't make the operation idempotent, make the *API call* idempotent and let the system that owns the money enforce it.

</Note>

<Note label="The table you'll forget about">

A `processed` table grows by one row per message forever, and nobody notices until it's the biggest table in the database and the unique index no longer fits in memory. Give it a retention policy from day one — delete rows older than your maximum redelivery window (hours or days, not years), with a partitioned table or a scheduled purge. You only need to remember an ID for as long as the queue could plausibly resend it.

</Note>

</Collapse>

<Collapse id="visibility" title="3. Visibility timeouts: the bug that duplicates your work">

This is the most common queue bug in production, and it hides because nothing in your code is wrong.

When a consumer takes a message, the broker doesn't delete it — it makes it **invisible** for N seconds (SQS calls this the visibility timeout; other brokers call it an ack deadline or ack timeout). If your ack arrives within N, the message is removed. If it doesn't, the broker assumes you died and hands the same message to another consumer. It has no way to tell "crashed" from "still working."

So if a job takes longer than N, the queue delivers it again *while the first consumer is still running it*. That is not a stray duplicate from a lost ack; it is genuine, guaranteed concurrent processing of the same message, and it's the scenario the race in [section 2](#idem) was drawn for.

Worse: if the job is slow for *everyone*, every redelivery also times out, and the message loops forever — redelivered, re-processed, never completed, burning capacity that the rest of the queue needed. A backlog that grows while your consumers are visibly busy is usually this.

- **Set the timeout above your real p99 processing time**, with headroom — not above the average, which is the mistake. The tail is what times out.

- **Heartbeat long jobs.** Most brokers let a consumer extend the timeout while it works (SQS `ChangeMessageVisibility`, RabbitMQ's consumer timeout tuning, Kafka's `max.poll.interval.ms` and background heartbeats). A job of genuinely unpredictable length should extend its own lease, not be given a huge fixed one — a huge fixed timeout means a real crash goes unnoticed for just as long.

- **Cap redelivery.** A maximum receive count turns the infinite loop into a DLQ entry, which is a problem you can see.

</Collapse>

<Collapse id="check" title="Check your understanding">

<Quiz q="You add a processed-IDs table and the double charges stop. A month later, a handful of payments silently never happen at all. What did the fix introduce?" options={["A claim that never expires: a consumer marked the ID, crashed before charging, and every redelivery now skips it", "The processed table's unique index outgrew memory and began rejecting inserts", "The payment provider started deduplicating on its own idempotency keys"]} answer={0}>

A claim with no way to expire. The consumer inserted the ID, then crashed before completing the charge, so the row now says "handled" for work that never ran — and every redelivery bounces off it and acks. You traded a loud failure for a silent one. The claim row needs a status and a lease so a stale claim can be taken over, or the claim and the work need to commit in one transaction; where the side effect is external, the provider's idempotency key is what lets you safely retry instead of guessing.

</Quiz>

<Quiz q="The same job runs three times. The logs show no errors and no retries. What's the first setting you check?" options={["The dead-letter queue's maximum receive count", "The consumer's retry policy", "The visibility timeout (or ack deadline) against your real p99 processing time"]} answer={2}>

The visibility timeout (or ack deadline) against your actual p99 processing time. No errors is the tell: nothing failed, the broker simply decided you'd died because you hadn't acked in time and gave the message to someone else — twice. Three executions of a job that takes just over the timeout is the classic signature. Fix the timeout, then heartbeat the job so its length stops being a guess, and check the receive count on the message to confirm — it's the number nobody thinks to look at.

</Quiz>
