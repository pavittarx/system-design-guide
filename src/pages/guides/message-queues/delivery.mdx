<Collapse id="delivery" title="1. Delivery guarantees: lost, or delivered twice?">

A consumer takes a "charge $50" message, charges the card, and crashes before it can tell the broker "done". The broker never heard back. Should it hand the message to someone else?

If it does, the customer may be charged twice. If it doesn't, and the crash happened *before* the charge, the order is never paid. The broker can't tell those two crashes apart, so every queue has to pick which mistake it would rather make.

### The confirmation: an ack

The "done" a consumer sends back is called an **acknowledgement**, or **ack**. Until the broker gets an ack, it doesn't know whether the work happened. The choice is what it does when the ack doesn't come.

- **Deliver once and never retry.** Nothing is ever duplicated, but a crash loses the message. This is called **at-most-once**.
- **Retry until acked.** Nothing is lost, but a lost ack means the work runs again. This is called **at-least-once**.
- **Exactly once** would be neither lost nor duplicated. The next note explains why that's mostly a story.

<Table>

| Guarantee | In plain words | Risk | Use when |
| --------- | -------------- | ---- | -------- |
| **At-most-once** | Fire and forget: delivered 0 or 1 times | Messages can be *lost* | Metrics, logs: a dropped one won't hurt |
| **At-least-once** | Retry until acked: delivered 1 or more times | Messages can be *duplicated* | Almost everything; the common default |
| **Exactly-once** | Delivered precisely once | Expensive, complex, and often a comforting fiction | Rarely truly needed; usually faked with at-least-once plus idempotency |

</Table>

<Note type="warn" label="The dirty secret">

*End-to-end* exactly-once delivery, across systems with real side effects, is famously close to impossible. The obstacle is the one [the CAP & Consistency guide](/guides/consistency-cap/) circles: two separate systems can't agree that "this happened" in one indivisible step over an unreliable network, so somebody must choose between retrying (maybe twice) and giving up (maybe never).

What people actually build is **at-least-once delivery plus idempotent processing**: a message may arrive twice, but processing the duplicate does nothing. From outside it *looks* exactly-once, which is all anyone wanted. Kafka's exactly-once *processing* inside its own ecosystem (idempotent producer plus transactions) is the real exception, but it doesn't extend to arbitrary external side effects.

</Note>

<Note type="wild" label="◈ In the wild · WhatsApp">

WhatsApp holds a message for a switched-off phone in an in-memory queue, retries until the device reconnects and *acks* it, then deletes it; the two grey ticks are that ack. In early 2014 that was about **50 billion messages a day** for 450 million users on around 550 servers, run by **32 engineers** ([write-up](https://newsletter.systemdesign.one/p/whatsapp-engineering)).

</Note>

</Collapse>

<Collapse id="idem" title="2. Idempotency: making duplicates harmless">

You chose at-least-once, so duplicates will happen. A payment consumer gets the same "charge $50" message twice, because the first ack got lost, and charges the customer $100. You need processing a duplicate to do nothing at all.

An operation where doing it twice has the same effect as doing it once is called **idempotent**. Pressing a lift button five times doesn't summon five lifts. This one property is what makes at-least-once delivery safe, and it shows up everywhere in distributed systems.

The plan: give each message a unique ID and remember which IDs you've processed. See a repeat? Skip it. That's the idea. The obvious way to write it is wrong.

### The version everybody writes first, and why it breaks

```python
def on_message(id, action):
    if already_processed(id):   # seen this one?
        return                  # skip the duplicate
    do(action)
    mark_processed(id)
```

Read it as one worker and it's flawless. But a queue exists so that several consumers run at once, and duplicates don't politely arrive one after the other. They can arrive at the same moment, on two machines:

  { b: "Gets message #7847 too: a duplicate" },
  { a: "Already processed #7847? No" },
  { b: "Already processed #7847? No" },
  { a: "Charges $50", tone: "good" },
  { b: "Charges $50 again", tone: "bad" },
  { a: "Marks #7847 processed" },
  { b: "Marks #7847 processed (no effect)", note: true }

Both consumers looked before either wrote, so the guard did nothing. No step in that sequence is unusual. It's two ordinary runs overlapping by a few milliseconds, which is the normal condition of any system with more than one worker. This is a **race condition**: the result depends on the timing of two things running at once.

### The fix: claim the ID before doing the work

Don't *ask* whether the message has been processed. *Claim* it, in one statement the database has to referee. Put a uniqueness constraint on `message_id`, and only one of two simultaneous inserts can succeed:

```python
def on_message(id, action):
    # one atomic claim; the database picks a winner
    rows = db.execute("""
        INSERT INTO processed (message_id)
        VALUES (%s)
        ON CONFLICT (message_id) DO NOTHING
    """, [id]).rowcount

    if rows == 0:      # lost the race
        return         # the winner is handling it

    do(action)         # only the winner gets here
```

Why this works: the check and the write are now one operation, so there's no gap between them for another consumer to slip into.

<Race a="Consumer 1" b="Consumer 2" result="Result: one charge of $50" tone="good" steps={[
  { a: "INSERT #7847 into processed: 1 row added. I own it" },
  { b: "INSERT #7847 into processed: conflict, 0 rows added" },
  { b: "Lost the race. Acks and stops", tone: "good" },
  { a: "Charges $50", tone: "good" }
]} />

This isn't a Postgres detail. Any store with a uniqueness constraint or a conditional write will do: a unique index, DynamoDB's `attribute_not_exists`, Redis `SET NX`. What you need is one operation that both tests and takes.

### What this still doesn't solve: the crash after the claim

The winner can crash between claiming and finishing. Now the ID is marked and the work never happened. Every redelivery bounces off a claim that belongs to a process that no longer exists, and the message is lost for good, while looking from outside exactly like one that was processed.

So the claim row shouldn't be a bare marker. Give it a **status** (`claimed` or `done`) and a **lease**: a claim time plus an expiry, so a claim that has gone stale can be taken over instead of blocking the message forever. Then "already claimed" and "claimed by a process that died" stop being the same state.

The truly robust version needs no lease at all, because it puts the claim and the work in the *same transaction*: insert the claim row and write the business change together, and commit once. Either both land or neither does, and a crash rolls back the claim along with everything else. Do this whenever the side effect lives in the same database as the claim, and notice how often it does.

<Note type="warn" label="When the work isn't in your database">

Charging a card breaks the pattern: you can't put someone else's payment API inside your transaction. So push idempotency across the boundary. Send an **idempotency key** (your message ID, or something derived from it) with the charge request, and the provider spots the repeat and returns the original result instead of charging again.

That's exactly what Stripe's, and every other payment provider's, idempotency keys are for. When you can't make the operation idempotent, make the *API call* idempotent, and let the system that owns the money enforce it.

</Note>

<Note label="The table you'll forget about">

A `processed` table grows by one row per message forever, and nobody notices until it's the biggest table in the database and its unique index no longer fits in memory. Give it a retention policy from day one: delete rows older than the longest time the queue could plausibly resend a message (hours or days, not years), using a partitioned table or a scheduled purge.

</Note>

</Collapse>

<Collapse id="visibility" title="3. Visibility timeouts: the bug that duplicates your work">

A job runs three times. The logs show no errors and no retries. Nothing in your code is wrong, and this is still the most common queue bug in production.

### How a broker decides you've died

When a consumer takes a message, the broker doesn't delete it. It hides it from other consumers for N seconds. SQS calls this the **visibility timeout**; other brokers call it an ack deadline or ack timeout. If your ack arrives within N seconds, the message is removed. If it doesn't, the broker assumes you died and hands the message to another consumer. It has no way to tell "crashed" from "still working".

So if a job takes longer than N, the broker gives it to someone else *while the first consumer is still running it*:

<Race a="Consumer 1" b="Consumer 2" result="Result: the same job runs twice at once, with no error anywhere" steps={[
  { a: "Takes the export job. Timeout is 30 s; this one needs 45 s" },
  { a: "Still working at 30 s. No ack yet", note: true },
  { b: "Broker assumes Consumer 1 died and hands it the same job" },
  { a: "Finishes at 45 s and acks", tone: "bad" },
  { b: "Runs the whole job again", tone: "bad" }
]} />

That's not a stray duplicate from a lost ack. It's guaranteed, simultaneous processing of the same message, which is exactly the race the claim in [section 2](#idem) was built for.

It gets worse. If the job is slow for *every* consumer, every redelivery also times out, and the message loops forever: redelivered, reprocessed, never completed, burning capacity the rest of the queue needed. A backlog that grows while your consumers are visibly busy is usually this.

### Three settings that fix it

- **Set the timeout above your real p99 processing time**, with headroom. Not above the average: that's the common mistake, because it's the slow tail that times out. (p99 is the time 99% of jobs finish within.)

- **Extend the deadline for long jobs.** SQS lets a consumer push its own timeout back while it works with `ChangeMessageVisibility`, so a job of unpredictable length extends its lease as it goes. That beats one huge fixed timeout, which means a real crash also goes unnoticed for that long. Other brokers have a limit instead of a lease: RabbitMQ's `consumer_timeout` (30 minutes by default) and Kafka's `max.poll.interval.ms`, the longest a consumer may go between fetches before its partitions are given to another consumer. Size those limits for your slowest job.

- **Cap redelivery.** A maximum receive count turns the infinite loop into an entry in a **dead-letter queue** (DLQ), a separate queue for messages that keep failing. That's a problem you can see.

<Note type="key" label="What to remember">

- Real queues deliver at least once. Plan for every message to arrive twice.
- Check-then-act is a race. Claim the message ID with one atomic insert, and only the winner does the work; better still, claim and work in one transaction.
- If a job can outlast the visibility timeout, it will run twice at once. Size the timeout from p99, extend it for long jobs, and cap redelivery.

</Note>

</Collapse>

<Collapse id="check" title="Check your understanding">

<Quiz q="You add a processed-IDs table and the double charges stop. A month later, a handful of payments silently never happen at all. What did the fix introduce?" options={["A claim that never expires: a consumer marked the ID, crashed before charging, and every redelivery now skips it", "The processed table's unique index outgrew memory and began rejecting inserts", "The payment provider started deduplicating on its own idempotency keys"]} answer={0}>

The consumer inserted the ID, then crashed before charging, so the row now says "handled" for work that never ran. Every redelivery bounces off it and acks. You traded a loud failure for a silent one.

Give the claim a status and a lease so a stale claim can be taken over, or commit the claim and the work in one transaction. When the work is an external call, send the provider an idempotency key so you can retry safely instead of guessing.

</Quiz>

<Quiz q="The same job runs three times. The logs show no errors and no retries. What's the first setting you check?" options={["The dead-letter queue's maximum receive count", "The consumer's retry policy", "The visibility timeout (or ack deadline) against your real p99 processing time"]} answer={2}>

No errors is the clue. Nothing failed: the broker simply assumed the consumer had died because no ack arrived in time, and gave the message to someone else, twice. Three runs of a job that takes just over the timeout is the classic signature.

Raise the timeout above your p99, have long jobs extend their own deadline, and check the message's receive count to confirm. It's the number nobody thinks to look at.

</Quiz>
