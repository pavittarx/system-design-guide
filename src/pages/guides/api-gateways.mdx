<div class="coldopen">
<span class="tag">◇ the field that was always there</span>
<p>The change is one line. An optional field in a response — <code>legacy_id</code>, unused, deprecated for two years, nobody has asked about it since — gets deleted. It ships on a Tuesday afternoon. Within four minutes, a mobile client on a version released eighteen months ago starts crashing on parse, because a developer long since departed wrote a decoder that treats every declared field as required. That client is on 340,000 phones. You cannot patch them. The rollback takes six minutes and the field is now permanent, in every response, forever, doing nothing. This is the API tax: the code is trivially deletable and the <em>promise</em> is not.</p>
</div>

<Collapse id="promise" title="1. The API is the product">
<p>Every other guide in this series is about things you can change. You can swap the database, replace the cache, re-shard, move to a different queue — the users never know. The API is the one layer where that stops being true, because the moment a third party writes code against it, its shape is no longer yours.</p>
<p>This produces a specific and consistent engineering error: teams design APIs the way they design internal function signatures, optimising for what's convenient to implement today. Then the API survives three rewrites of the thing behind it, and every one of those rewrites is made harder by a contract that was never designed to outlive its first implementation.</p>
<div class="note key">
<span class="label">The test that catches most of it</span>
    Before shipping an endpoint, ask: <em>if we replaced the entire backend next year, would this contract still make sense?</em> An endpoint called <code>/v1/get-user-from-cache</code> fails immediately. So does one whose response mirrors your table columns, whose pagination exposes your database offsets, or whose error codes are the ORM's exception names. Each of those has welded a caller's code to an implementation detail you were planning to change.
</div>
<p>The other thing worth internalising early: an API has at least two audiences with conflicting interests. The client developer wants exactly the data they need in one round trip. The API owner wants a small number of stable, cacheable, well-understood endpoints. Every API style below is a different resolution of that tension, and none of them dissolves it.</p>

</Collapse>
<Collapse id="styles" title="2. REST, RPC and GraphQL">
<p>Three dominant styles, each optimising something different, each with a bill that arrives later.</p>
<p><strong>REST</strong> models the world as resources with a fixed set of verbs. <code>GET /orders/88213</code>. Its real advantage is not elegance but that it inherits the entire HTTP ecosystem for free: intermediary caches understand a GET, load balancers understand idempotency, browsers understand status codes, and every CDN on earth can serve a cacheable response without knowing anything about your domain. That's a large amount of infrastructure you don't have to build (see <a href="cdn-edge.html">CDNs &amp; the Edge</a>).</p>
<p>Its cost is round trips. Rendering a single screen may need an order, its line items, the customer, and shipping status — four requests, four latencies, and on a mobile connection with 120 ms of round-trip time that's half a second of nothing but waiting.</p>
<p><strong>RPC</strong> (gRPC, Thrift, and the plain JSON-over-POST that most "REST" APIs actually are) models the world as procedures. <code>SubmitOrder(request) → response</code>. It maps cleanly to how the code is actually organised, generates typed clients from a schema, and over gRPC gets HTTP/2 multiplexing, binary encoding and streaming. Its cost is opacity: to a cache, a proxy, or a browser, every call is an opaque POST. You have given up the free ecosystem in exchange for efficiency and type safety, which is often a good trade for service-to-service traffic and a poor one for a public API.</p>
<p><strong>GraphQL</strong> hands the client a query language and lets it ask for exactly the fields it wants in one round trip. This genuinely solves the mobile over-fetching problem, and it solves the "we need a new endpoint for the new screen" problem that produces API sprawl.</p>
<div class="note warn">
<span class="label">GraphQL moves the cost, it does not remove it</span>
    Now every client can compose an arbitrary query, and some of those queries are expensive in ways nobody anticipated. A nested query walking users → orders → items → recommendations can fan out into thousands of database calls from a single HTTP request. Three defences are effectively mandatory: <strong>query depth limiting</strong>, <strong>query cost analysis</strong> (assign a cost to each field, reject anything over a budget), and <strong>batching</strong> at the data-loading layer so the N+1 becomes one query per level. Caching is also substantially harder, because every distinct query string is a distinct response — <strong>persisted queries</strong>, where clients send a hash of a pre-registered query, restore most of what you lost.
</div>

<p>Most large systems end up with all three: gRPC internally, REST at the public edge, and GraphQL for first-party apps. That is not indecision; it's each style being used where its trade-off is favourable.</p>

<Collapse id="versioning" title="3. Versioning and the promise you can't take back">
<p>The useful frame is not "how do we version" but "which changes are safe." Most changes are, and teams that understand which ones almost never need a v2.</p>
<div class="table-scroll">
<table>
<thead><tr><th>Change</th><th>Safe?</th><th>Why</th></tr></thead>
<tbody>
<tr><td>Add an optional request field</td><td class="good">Safe</td><td>Old clients omit it; server defaults</td></tr>
<tr><td>Add a response field</td><td class="good">Usually safe</td><td>Unless a client validates strictly — see the cold open</td></tr>
<tr><td>Add a new endpoint</td><td class="good">Safe</td><td>Nobody calls it yet</td></tr>
<tr><td>Add a new enum value</td><td class="bad">Breaking</td><td>Clients switch exhaustively and fall through to an error branch</td></tr>
<tr><td>Make an optional field required</td><td class="bad">Breaking</td><td>Every existing caller starts failing validation</td></tr>
<tr><td>Remove or rename a field</td><td class="bad">Breaking</td><td>Callers dereference it</td></tr>
<tr><td>Tighten validation</td><td class="bad">Breaking, invisibly</td><td>Requests that worked yesterday now 400</td></tr>
<tr><td>Change a default</td><td class="bad">Breaking, silently</td><td>Behaviour changes with no error to notice</td></tr>
</tbody>
</table>
</div>
<p>The last two are the dangerous ones, because they don't look like API changes in a code review. Somebody adds a length check to a validator or flips a default from <code>false</code> to <code>true</code>, and a partner's integration starts behaving differently with no version bump and no announcement.</p>
<p>When you genuinely must break, the options in increasing order of cost: a <strong>new field alongside the old one</strong> (both populated during a transition), a <strong>new endpoint</strong>, a <strong>version in the URL</strong> (<code>/v2/</code>), or a <strong>version negotiated by header</strong>. URL versioning is the most common because it's visible and debuggable, and its true cost is not the routing — it's that you now run two implementations, and the old one still needs security patches long after everyone has stopped caring about it.</p>
<div class="note">
<span class="label">Deprecation that actually works</span>
    Announce, then instrument, then chase, then remove. The instrumentation is the step people skip and the only one that matters: log every call to the deprecated path with the caller's identity, so that when you propose removal you can say "eleven integrations still call this, here they are" instead of guessing. HTTP has standard headers for the announcement — <code>Deprecation</code> and <code>Sunset</code> — and essentially no client reads them, so send email as well.
</div>
<p>Write clients to be <strong>tolerant readers</strong>: ignore unknown fields, treat unknown enum values as a defined "other" case, and never assume field order. This is the same discipline as schema evolution in <a href="message-queues.html">Message Queues &amp; Async</a>, and for the same reason — producer and consumer are never upgraded at the same instant.</p>


<Question q="Check yourself: You add a new field to a request body. Optional, defaulted, backwards compatible. Two weeks later a partner's integration breaks. What happened?">
Almost certainly a strict-validation client: many generated clients and API-contract-testing tools reject payloads containing unknown fields, so the field being optional on your side is irrelevant — its mere presence in a response, or a schema that now permits it, fails their validator. The related trap is enums, where adding a new value is technically additive but breaks every client that switches exhaustively over the old set. Both are why the tolerant-reader discipline matters: ignore unknown fields, map unknown enum values to a defined "unrecognised" case, and never assume ordering. You cannot make your clients tolerant, but you can document the expectation loudly, ship reference clients that behave that way, and treat "we added a field" as a change worth announcing rather than one worth assuming is invisible.
</Question>

</Collapse>
<Collapse id="pagination" title="4. Collections: pagination and filtering">
<p>Every collection endpoint eventually returns more rows than anyone wants, and the way you paginate determines whether that's a small problem or a permanent one.</p>
<p><strong>Offset pagination</strong> — <code>?page=5&amp;limit=20</code> — is what everyone builds first. It has two defects. The first is performance: <code>OFFSET 100000</code> makes the database walk and discard a hundred thousand rows before returning anything, so page 5,000 is thousands of times more expensive than page 1. The second is correctness, and it's worse: if a row is inserted while a user is paging, every subsequent page shifts by one, and they will see one item twice and never see another at all.</p>
<p><strong>Cursor (keyset) pagination</strong> — <code>?after=eyJpZCI6ODgyMTN9</code> — sends back an opaque token encoding the sort position of the last row. The next query becomes <code>WHERE (created_at, id) &lt; (:ts, :id) ORDER BY created_at DESC, id DESC LIMIT 20</code>, which uses the index and costs the same on page 5,000 as on page 1. Inserts don't shift anything, because position is defined by value rather than by count. The trade-off you accept is no "jump to page 47" — which almost no real client needs, and which the ones that do can get from a search index instead.</p>
<div class="note warn">
<span class="label">The tiebreaker is not optional</span>
    Sorting by a non-unique column alone — <code>ORDER BY created_at</code> where thousands of rows share a timestamp — makes the ordering undefined among ties, and any pagination built on it will duplicate and skip rows nondeterministically. Always append a unique tiebreaker to the sort, and include it in the cursor. This is the single most common pagination bug in production and it presents as an intermittent, unreproducible "sometimes a record is missing." <a href="database-scaling.html">Scaling Databases</a> has the query-plan side of this.
</div>
<p>Keep the cursor opaque — base64 an internal structure — so that clients cannot construct one by hand and you retain the freedom to change what's inside it. The moment a customer discovers your cursor is <code>base64("id:88213")</code>, someone will generate cursors, and your encoding becomes part of the contract you didn't mean to make.</p>
<p>Two more collection rules worth adopting: always impose a <strong>maximum page size</strong> the server enforces regardless of what was asked for, and never let filters be arbitrary — every filterable field is a query pattern you have promised to serve efficiently, which means an index you have promised to maintain.</p>

<Question q="Check yourself: Users report that paging through a list occasionally skips a record. The query is <code>ORDER BY created_at DESC LIMIT 20 OFFSET n</code>. What's wrong?">
Two independent bugs, and both need fixing. First, offset pagination is positional: if a row is inserted near the top between page requests, everything shifts down by one, so the record that was last on page one becomes first on page two — the user sees it twice — and the reverse happens on deletion, where a record is skipped entirely. Second, <code>created_at</code> is almost certainly not unique, and rows sharing a timestamp have no defined relative order, so the database is free to return them differently between two executions of the same query; that alone produces duplicates and omissions even with no concurrent writes at all. The fix for both is keyset pagination with a unique tiebreaker: sort by <code>(created_at, id)</code>, and have each page request carry the last row's values as a cursor rather than a count. This is also faster, because the database seeks into the index instead of counting past n rows it will discard.
</Question>

</Collapse>
<Collapse id="errors" title="5. Errors a client can act on">
<p>An error response has exactly one job: tell the caller what to do next. There are only four possible answers — fix your request, authenticate, retry later, or give up — and a good error makes it obvious which one applies.</p>
<p>Status codes carry the first, coarsest signal, and getting the 4xx/5xx split right matters more than any individual code. <strong>4xx means the client did something wrong; retrying an identical request will fail identically.</strong> <strong>5xx means the server failed; the same request might succeed later.</strong> That distinction is what lets a client library decide, without understanding your domain at all, whether to retry. Returning a 500 for a validation failure produces clients that retry a request that can never succeed — and at scale that's a self-inflicted traffic multiplier, the retry storm described in <a href="reliability-toolkit.html">The Reliability Toolkit</a>.</p>
<div class="note warn">
<span class="label">The 200-with-an-error-body anti-pattern</span>
<code>{`HTTP 200 {"success": false, "error": "insufficient funds"}`}</code> is popular and wrong. Every intermediary between you and the client — load balancers, CDNs, monitoring, the client's own HTTP library — reads the status code and nothing else. A 200 gets cached, counted as a success in your SLI, and silently swallowed by generic error handling. Your error rate dashboard will show a flat 0% during a total functional outage.
</div>
<p>The body carries the actionable detail. RFC 7807 (updated by RFC 9457) defines a standard shape — <code>type</code>, <code>title</code>, <code>status</code>, <code>detail</code>, <code>instance</code> — and whether or not you adopt it literally, adopt its properties: a <strong>stable machine-readable code</strong> that clients can branch on (<code>insufficient_funds</code>, not a human sentence that will get reworded), a human-readable message for logs, and for validation failures, <em>which field</em> was wrong. Include your request ID in every error body; it turns a support ticket from an archaeology exercise into a lookup.</p>
<p>Finally, distinguish retryable from non-retryable inside the 5xx range. A 503 with a <code>Retry-After</code> is an instruction. A 500 is an unknown. A 504 means the request may well have been processed even though you didn't hear back — which is the case that makes <strong>idempotency keys</strong> essential on any endpoint that moves money or creates records: the client sends a unique key, the server records the outcome against it, and a retry with the same key returns the original result instead of doing the work twice.</p>
<div class="note wild">
<span class="label">◈ In the wild · Stripe</span>
    Stripe lets a client attach an <code>Idempotency-Key</code> header to any POST, and records the outcome of that request against the key. So when a client retries after a timeout — never certain whether the first charge actually went through — the retry returns the original result rather than charging the card a second time. Keys are honoured for roughly 24 hours, which makes this the canonical production answer to "the request may have succeeded even though I didn't hear back." See <a href="https://docs.stripe.com/api/idempotent_requests">Stripe's idempotent-requests documentation</a>.
</div>

</Collapse>
<Collapse id="gateway" title="6. What a gateway does — and what it shouldn't">
<p>An API gateway is the single front door: one place that terminates TLS, authenticates the caller, enforces limits, routes to the right service, and emits a consistent access log. The argument for it is that these concerns are identical for every service, and implementing them forty times produces forty subtly different implementations, thirty-nine of which have a bug.</p>
<pre class="trace">
{"\n"}
<b>{"POST /v1/orders"}</b>{"   client → gateway → service        "}<b>{"total 84 ms"}</b>{"\n"}
{"  "}<b>{"1."}</b>{"  TLS terminate                       "}<span class="good">{"reused session"}</span>{"\n"}
{"  "}<b>{"2."}</b>{"  parse + normalise                          0.2 ms"}{"\n"}
{"  "}<b>{"3."}</b>{"  authenticate token (cached JWKS)           0.4 ms   "}<span class="good">{"sub=acct_9f21"}</span>{"\n"}
{"  "}<b>{"4."}</b>{"  rate limit check (token bucket)            0.9 ms   "}<span class="good">{"83/100 left"}</span>{"\n"}
{"  "}<b>{"5."}</b>{"  route: /v1/orders → orders-svc             0.1 ms"}{"\n"}
{"  "}<b>{"6."}</b>{"  forward, upstream work                    81.0 ms"}{"\n"}
{"  "}<b>{"7."}</b>{"  add X-RateLimit-* + request-id             0.1 ms"}{"\n"}
{"  "}<b>{"8."}</b>{"  emit access log + metrics                  0.2 ms"}{"\n"}
{"\n"}
</pre>
<p>Steps 2–5 and 7–8 total under two milliseconds. That number is the gateway's entire budget, and it is worth guarding jealously, because the gateway sits in front of <em>everything</em> — a gateway that adds 20 ms adds it to every request in the company.</p>
<p>What a gateway should refuse to do is business logic. The gravitational pull is real: it already sees every request, so it's tempting to put "just one" transformation there, then a fan-out to two services, then a conditional based on account type. Do that consistently for two years and you have rebuilt the enterprise service bus — a single deployable that every team must coordinate on, that nobody fully understands, and whose blast radius is the entire product. Orchestration belongs in a service that owns it. The gateway does cross-cutting concerns, and the test for whether something is cross-cutting is whether it would be identical for a service you haven't written yet.</p>
<div class="note">
<span class="label">Backend-for-frontend</span>
    When a specific client genuinely needs aggregation — the mobile app wants one call that returns four things — the pattern that survives is a <strong>BFF</strong>: a thin service owned by the client team, sitting behind the gateway, that does exactly that aggregation for exactly that client. It keeps client-specific logic out of the shared gateway and out of the domain services, and it can be deleted when the client is.
</div>

</Collapse>
<Collapse id="algorithms" title="7. Five ways to count">
<p>Rate limiting is one question — "has this caller had too much?" — with five standard answers that differ in memory, burst behaviour, and how badly they fail at the edges.</p>
<p><strong>Fixed window.</strong> Count requests per calendar minute; reset at the boundary. One counter per key, trivially cheap. It has a well-known defect:</p>
<div class="note key">
<span class="label">The boundary burst</span>
    Limit: 100 requests per minute. A client sends 100 at <b>11:59:59.9</b> and 100 more at <b>12:00:00.1</b>. Both windows are within limit. The server just absorbed <strong>200 requests in 0.2 seconds</strong> — double the rate you thought you'd guaranteed, delivered as a spike, at a boundary that every client's cron job is aligned to.
</div>
<p><strong>Sliding window log.</strong> Store a timestamp for every request; on each new one, discard entries older than the window and count what's left. Exactly correct, no boundary artefact. The cost is memory proportional to the limit times the number of keys: at 100 requests per key and 8 bytes per timestamp, ten million active keys is roughly <strong>8 GB</strong> — for a limiter.</p>
<p><strong>Sliding window counter.</strong> The pragmatic compromise. Keep the current window's count and the previous window's, and estimate by weighting the previous one by how much of it still overlaps. Fifteen seconds into a 60-second window, with 80 requests in the previous window and 30 so far in this one: <code>80 × 0.75 + 30 = 90</code>. Two integers per key — roughly <strong>160 MB</strong> for the same ten million keys — and the boundary burst is gone. It's an approximation that assumes the previous window's traffic was evenly spread, which is wrong and almost never matters.</p>
<p><strong>Token bucket.</strong> A bucket of capacity C refills at R tokens per second; each request takes one; empty bucket means rejection. Store two numbers — token count and last-refill timestamp — and compute the refill lazily on read, so there's no background job. Its defining property is that it <em>permits controlled bursts</em>: with C = 100 and R = 10/s, a client idle for a minute can fire 100 requests immediately and then settle to 10/s. That's usually what you want, because real clients are bursty and a limiter that punishes bursts punishes normal behaviour.</p>
<p><strong>Leaky bucket.</strong> Requests queue and drain at a fixed rate. Output is perfectly smooth — which is its purpose, when the thing you're protecting cannot tolerate spikes at all — at the cost of added latency and a queue that can itself become a problem. This is load-levelling, the same shape as a queue in front of a slow consumer; <a href="message-queues.html">Message Queues &amp; Async</a> covers when smoothing beats rejecting.</p>

<div class="note key">
<span class="label">🛠️ Hands-On Lab: Build an API Rate Limiter in Redis</span>
<p>Build this mini-project to implement custom token-bucket limits via shared cache:</p>
    
      

* <strong>The Server:</strong> Write an API server in Node.js or Python. Create a single endpoint <code>GET /api/data</code>.


      

* <strong>Redis Lua Script:</strong> Write a Lua script for Redis that checks and decrements client tokens. The script should receive keys: <code>ratelimit:client_ip</code>, and arguments: <code>bucket_capacity</code>, <code>refill_rate</code>, and <code>now_timestamp</code>. By performing the calculations inside Redis in Lua, you ensure atomicity without lock churn:
```lua
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local refill_rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local state = redis.call('HMGET', key, 'tokens', 'last_refill')
local tokens = tonumber(state[1]) or capacity
local last_refill = tonumber(state[2]) or now
local elapsed = math.max(0, now - last_refill)
tokens = math.min(capacity, tokens + elapsed * refill_rate)
if tokens >= 1 then
tokens = tokens - 1
redis.call('HMSET', key, 'tokens', tokens, 'last_refill', now)
return {1, tokens}
else
return {0, tokens}
end
```


      

* <strong>Send Rate Limit Headers:</strong> Run the Lua script in your middleware on every request. If returned status is <code>1</code>, allow the request and set headers: <code>X-RateLimit-Limit</code>, <code>X-RateLimit-Remaining</code>. If status is <code>0</code>, reject with <code>429 Too Many Requests</code> and a <code>Retry-After</code> header.


      

* <strong>Test Bursts:</strong> Run a load test using <code>k6</code> and verify that bursts up to capacity are allowed, after which traffic flatlines perfectly to the refill rate.


    
<p style="margin-top: 10px; font-size: 0.85rem; color: var(--accent-2);">💡 Include this atomic Redis Lua rate limiter in your portfolio as a benchmark of low-overhead distributed traffic policing.</p>
</div>


<Question q="Check yourself: Your limit is 100 requests per minute, fixed window. A client legitimately gets 200 through in under a second. How?">
They straddled a window boundary — 100 requests at 11:59:59 and 100 more at 12:00:00, each within its own window, both counters satisfied. The effective peak rate of a fixed-window limiter is twice its nominal rate over any interval spanning a reset, which matters because boundaries are exactly where bursts cluster: every cron job in the world starts on a round minute. A sliding-window counter fixes it by weighting the previous window's count by how much of it still overlaps the current instant, at a cost of one extra integer per key, and a token bucket avoids it entirely by making the allowance continuous rather than resetting. If your fixed-window limiter appears to be holding but the thing behind it keeps getting spiky load, this is the first place to look.
</Question>

<Collapse id="distributed" title="8. Rate limiting when there are twenty of you">
<p>Everything above assumes one counter. You have twenty gateway instances behind a load balancer, and the counter is now shared state — which makes this a distributed systems problem wearing an infrastructure problem's clothes.</p>
<p><strong>Option one: divide the limit.</strong> Twenty instances, limit 1000/min, so each allows 50. No coordination, no latency. It's also wrong in both directions: a client whose connections land unevenly gets throttled at well under 1000, and during a deploy the instance count changes and every effective limit silently moves with it. Fine for crude abuse prevention, unacceptable for a documented quota a customer is paying for.</p>
<p><strong>Option two: a shared counter.</strong> Redis, one atomic increment-and-check per request, executed as a script so the read and write cannot interleave. Accurate and simple, and the cost is a network round trip on every single request. At 50,000 requests per second with a 1 ms round trip, Little's Law says you're holding about 50 requests in flight waiting on the limiter continuously — plus you have created a hard dependency in front of your entire API.</p>
<div class="note warn">
<span class="label">The limiter is now a single point of failure — decide in advance</span>
    Redis goes down. Do you <strong>fail open</strong> (serve everything unlimited, and hope the thing you were protecting survives) or <strong>fail closed</strong> (reject everything, and turn a limiter outage into a total outage)? Fail open is the usual answer for protection-oriented limits and the wrong one for limits enforcing paid quotas or preventing abuse. Whichever you choose, choose it deliberately and alert on it, because a limiter that has been silently failing open for three weeks is indistinguishable from one that is working right up until the day it isn't.
</div>
<p><strong>Option three: local buckets with async reconciliation.</strong> Each instance keeps a local token bucket and periodically syncs its consumption to a shared store, adjusting its local allowance based on what the fleet has spent. Approximate, briefly over-permissive after a burst, and requires no round trip on the hot path. This is broadly the shape large providers converge on, because the alternative — perfect accuracy — costs a synchronous coordination step per request and is rarely worth it. If the limit genuinely must be exact, you are asking for consensus, and <a href="coordination-consensus.html">Coordination &amp; Consensus</a> explains what that costs.</p>


<Question q="Check yourself: Your rate limiter's Redis goes down. Fail open or fail closed?">
It depends entirely on what the limit is <em>for</em>, which is why this must be decided per limit rather than globally. A limit protecting a fragile downstream from overload should probably fail closed or degrade to a conservative local limit, because failing open removes the protection precisely when you have already lost a component and are least able to absorb a surge. A limit enforcing a paid quota should usually fail open, because turning a limiter outage into a billing-enforcement outage that rejects paying customers is a much worse commercial outcome than briefly letting someone exceed their plan. The middle path most large systems take is to fall back to a per-instance local bucket sized at the fleet limit divided by the instance count — approximate, unfair at the margins, but bounded — and to alert loudly on entering that state, because the genuinely dangerous case is a limiter that has been silently failing open for weeks.
</Question>

<Question q="Check yourself: Twenty gateway instances, a documented limit of 1,000 requests/minute per customer. How do you enforce it without adding a Redis round trip to every request?">
You accept approximation and push the coordination off the hot path. Each instance keeps a local token bucket and reports its consumption to a shared store every few hundred milliseconds, receiving back the fleet's total spend and adjusting its local allowance accordingly — so an instance seeing heavy traffic from one customer learns within a fraction of a second that the fleet-wide budget is nearly gone and tightens up, without ever blocking a request on a network call. The error is bounded by what the fleet can consume in one sync interval, which you can make as small as your tolerance requires, and it degrades gracefully because an instance that loses contact with the shared store simply falls back to its local share. The alternative worth considering first is whether the limit needs to be exact at all: if it exists to protect infrastructure, approximate is fine and much cheaper, and it's only when the number is a contractual commitment that anyone is going to audit that precision starts earning its cost.
</Question>

</Collapse>
<Collapse id="keys" title="9. What are you limiting, exactly?">
<p>The algorithm is the easy part. The key — the thing you count <em>per</em> — determines whether the limiter protects you or just annoys your customers.</p>
<p><strong>Per API key or account</strong> is the right default for authenticated traffic: it maps to a customer, a plan, and a bill, and it's forgeable only by stealing a credential. <strong>Per IP</strong> is what you're left with for unauthenticated traffic, and it's a blunt instrument — a corporate NAT or a mobile carrier gateway can put thousands of legitimate users behind one address, so any per-IP limit strict enough to stop an attacker will lock out an entire office. Meanwhile a determined attacker rotates through a residential proxy pool and never trips it. Per-IP limits are a speed bump, not a wall.</p>
<p><strong>Per endpoint</strong> matters because costs differ by orders of magnitude. A limit that's generous for <code>GET /health</code> is reckless for <code>POST /reports/generate</code>. The refinement is to charge by <em>cost</em> rather than by request: a cheap read deducts one token, an expensive aggregation deducts fifty. This is the only sane way to limit a GraphQL endpoint, where "1,000 requests per hour" is meaningless because one request can be a thousand times more expensive than another — compute the query's cost from its shape and deduct that.</p>
<div class="note">
<span class="label">Layer the limits</span>
    Real systems run several simultaneously: a global limit protecting the platform, a per-tenant limit enforcing the plan, a per-endpoint limit protecting expensive paths, and a per-IP limit on the unauthenticated surface. A request must pass all of them. Return a response that says <em>which</em> one it hit — otherwise a customer well within their documented quota gets a 429 and no way to understand why.
</div>
<p>One more distinction that saves arguments: <strong>rate limits</strong> smooth traffic over seconds and are about protecting infrastructure. <strong>Quotas</strong> cap consumption over a month and are about billing. They look identical in implementation and behave completely differently in incidents — you can safely relax a rate limit at 3 a.m. to get a customer moving; relaxing a quota is a commercial decision.</p>


<Question q="Check yourself: Why is &quot;1,000 requests per hour&quot; a meaningless limit for a GraphQL endpoint?">
Because request count has no relationship to cost when the client writes the query. One request can fetch a single field by primary key, and the next can walk users to orders to line items to recommendations and fan out into thousands of database round trips — the same one unit against your counter. A limiter counting requests will happily admit a thousand of the second kind. The workable approach is to compute a static cost for the query before executing it, by assigning weights to fields and multiplying through the pagination arguments at each level, and to deduct that cost from a token bucket; requests exceeding a per-query ceiling get rejected outright rather than deducted. Persisted queries make this dramatically easier, because you can compute and cache the cost of each registered query once instead of analysing arbitrary strings on the hot path, and they close the door on adversarial queries you never approved.
</Question>

</Collapse>
<Collapse id="429" title="10. 429, Retry-After, and the well-behaved client">
<p>Rejecting a request is the easy half. The hard half is that the client's reaction determines whether your limiter reduced load or multiplied it.</p>
<p>Return <strong>429 Too Many Requests</strong> — never 503, which means "server broken" and invites indiscriminate retries. Include <strong><code>Retry-After</code></strong> with the number of seconds until capacity exists; it converts a guess into an instruction. And expose the limit state on <em>successful</em> responses too, via <code>X-RateLimit-Limit</code>, <code>X-RateLimit-Remaining</code> and <code>X-RateLimit-Reset</code> headers, so a well-written client can slow down before it hits the wall rather than after.</p>
<div class="note warn">
<span class="label">Retry-After without jitter is a scheduling weapon</span>
    Ten thousand clients get a 429 saying <code>Retry-After: 60</code>. Ten thousand clients retry at exactly the same second. You have not spread the load — you have <em>synchronised</em> it, and built yourself a metronome that will keep ringing every sixty seconds. Clients must add random jitter; servers should help by varying the advertised value slightly per response. This is the same failure as synchronised cache expiry in <a href="understanding-caching.html">Understanding Caching</a> and the same fix.
</div>
<p>A 429 must also be <em>cheap</em>. If rejecting costs a database lookup to resolve the account and its plan, then an attacker sending a hundred thousand requests a second is still doing a hundred thousand database lookups a second, and your limiter has become the load. Resolve identity from a cached credential, check the counter, reject. Nothing else.</p>
<p>The two ends of this are the same contract seen from opposite sides. Stripe's rate-limiter design and GitHub's REST quotas are both worth reading as worked examples of a provider making its limits legible enough that clients can behave; the corresponding client-side discipline — exponential backoff with jitter, a retry budget, and a circuit breaker for the case where backing off isn't working — is in <a href="reliability-toolkit.html">The Reliability Toolkit</a>.</p>

</Collapse>
<Collapse id="auth" title="11. Auth at the edge">
<p>Two questions, routinely conflated. <strong>Authentication</strong> is "who is this?" — it's uniform, cacheable, and belongs at the gateway. <strong>Authorization</strong> is "may they do this to that?" — it depends on the resource, and it belongs in the service that owns the resource.</p>
<p>The reason the split matters is that gateway-side authorization requires the gateway to know your domain model. "Can this user edit this document?" depends on ownership, sharing rules, and organisational hierarchy, all of which live in the document service. A gateway that answers it has either duplicated that logic — where it will drift — or is calling back into the service anyway, which is the round trip you were trying to avoid.</p>
<p>Practically: the gateway validates the token's signature and expiry, rejects anything malformed before it touches a service, and forwards a verified identity downstream. Validating a JWT locally against a cached public key set costs microseconds and no network call, which is the entire appeal — and also the entire drawback, since a locally-validated token cannot be revoked. Short expiry (minutes, not days) plus refresh tokens is the standard mitigation; a revocation list checked at the gateway is the belt-and-braces version, at the cost of a lookup.</p>
<div class="note warn">
<span class="label">The forwarded-identity trap</span>
    Once the gateway injects <code>X-User-Id</code>, every internal service trusts that header. If any service is reachable without going through the gateway — a debug port, an internal load balancer, a pod someone can reach from a neighbouring namespace — then anyone who can reach it can set that header and become any user. Either strip and re-inject those headers at the boundary <em>and</em> make it impossible to reach services directly, or authenticate service-to-service calls independently with mTLS. The same reasoning applies to <code>X-Forwarded-For</code>, which is why <a href="load-balancing.html">Load Balancing</a> spends time on trusting the right hop.
</div>

</Collapse>
<Collapse id="gotchas" title="12. The gotchas that actually bite">
<p><strong>Nested timeouts that disagree.</strong> Gateway timeout 30 s, service timeout 60 s. At 45 seconds the gateway gives up and returns 504 while the service happily continues, finishes the work, and writes to the database. The client sees a failure, retries, and the work happens twice. Timeouts must decrease as you go inward, and the remaining deadline should be propagated with the request.</p>
<p><strong>Body buffering at the gateway.</strong> Many gateways buffer the full request body before forwarding, so they can retry or inspect it. A hundred concurrent 200 MB uploads is 20 GB of gateway memory. Stream large bodies, or route uploads past the gateway entirely to pre-signed storage URLs.</p>
<p><strong>Rate-limiting the health check.</strong> Health probes come from a small set of IPs at a steady rate. Put them behind a per-IP limiter and one day the limiter trips, probes fail, the load balancer marks every instance unhealthy, and the fleet removes itself from service. Exempt probes explicitly.</p>
<p><strong>Limit headers as an oracle.</strong> Returning different limits for valid and invalid API keys tells an attacker which keys are real. Returning 401 for "wrong password" and 404 for "no such user" enumerates your customer list. Be uniform about what you leak.</p>
<p><strong>The unauthenticated endpoint nobody rate-limited.</strong> Login, password reset, signup, and search are the four that get missed, and each is expensive in a different way — bcrypt burns CPU by design, password reset sends email that costs money and reputation, and search hits the most expensive index you own. Rate-limit them by IP <em>and</em> by target account, so an attacker cannot spread an attack on one account across many addresses.</p>
<p><strong>Version drift between the gateway config and the services.</strong> Routing rules, timeouts and limits usually live in gateway config, deployed on a different cadence from the services. Ship the two together or the config eventually references an endpoint that no longer exists — and gateway config changes have the widest blast radius of anything in your system, so they deserve canaries as much as code does.</p>
<p><strong>Assuming clients read your documentation.</strong> They read your errors. A 400 that says "invalid request" produces a support ticket; one that says <code>{`{"code":"invalid_currency","detail":"expected ISO 4217, got 'dollars'","field":"currency"}`}</code> produces a fix. Error messages are the most-read documentation you will ever write.</p>


<Question q="Check yourself: Gateway timeout is 30 s, the order service's own timeout is 60 s. A request takes 45 s. What does the customer experience?">
The gateway returns 504 at thirty seconds and the client sees a failure — while the order service, entirely unaware, keeps working and successfully creates the order at forty-five seconds. The customer believes it failed, retries, and gets a second order. Timeouts must strictly decrease as you move inward so that an inner call can never outlive the outer one that is waiting for it, and the robust version of this is deadline propagation: the gateway computes an absolute deadline, passes it downstream, and each hop budgets against the time actually remaining rather than against a fixed local value. Where the work is genuinely long-running, the correct shape is not a longer timeout but a different contract — accept the request, return 202 with a status URL, and let the client poll or receive a webhook. And on anything that creates or moves money, an idempotency key makes the duplicate-on-retry case harmless regardless.
</Question>

</Collapse>
<Collapse id="recap" title="13. Recap in 60 seconds">
<div class="recap">
    
      

* <strong>The API outlives the implementation.</strong> Design the contract so a full backend rewrite wouldn't change it.


      

* <strong>REST buys the HTTP ecosystem; RPC buys efficiency; GraphQL buys one round trip</strong> — and each hands you a different bill. GraphQL's is unbounded query cost, so depth limits, cost analysis and batching are mandatory.


      

* <strong>Additive changes are safe; removals, new enum values, tightened validation and changed defaults are not.</strong> The last two break silently.


      

* <strong>Cursor pagination over offset,</strong> always with a unique tiebreaker in the sort, or you will duplicate and skip rows.


      

* <strong>4xx means don't retry; 5xx means you might.</strong> Never 200 with an error body — it poisons caches, metrics and client error handling at once.


      

* <strong>Gateways do cross-cutting concerns only.</strong> Authentication at the edge, authorization in the service that owns the resource. Business logic in the gateway becomes an ESB.


      

* <strong>Token bucket or sliding-window counter</strong> for almost everything; fixed windows let clients get 2× the limit across a boundary.


      

* <strong>Distributed limits are a coordination problem.</strong> Divide-the-limit is cheap and wrong; a shared counter is accurate and adds a round trip plus a dependency. Decide fail-open vs fail-closed before it fails.


      

* <strong>Return 429 with Retry-After — and make sure clients jitter it,</strong> or you've synchronised your traffic instead of spreading it.


    
</div>
