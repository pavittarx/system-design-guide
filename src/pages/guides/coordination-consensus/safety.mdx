<Collapse id="split" title="1. Two leaders, and how fencing stops the old one">

Two data centres, one primary database. The link between them drops. Each side runs the same failover logic, and each reaches a sensible conclusion from what it can see:

<Race a="East (old primary)" b="West (replica)" result="Result: two primaries, two histories, no automatic way to merge them" steps={[
  { a: "Link drops. Still primary; keeps taking writes" },
  { b: "Primary unreachable, so it must be dead. Promotes itself" },
  { a: "A few seconds of writes that never reach the West", tone: "bad" },

  { b: "Holds writes the East doesn't have" }

Both sides believing they're in charge is called **split brain**, and it's what happened to GitHub in the [overview](/guides/coordination-consensus/). Notably, GitHub's failover tool, Orchestrator, itself ran on Raft, and its quorum worked as designed. The consensus algorithms from [Part 1](/guides/coordination-consensus/raft/) prevent split brain *inside* their own cluster, by majority rule. The danger is at the edge, where some other system *acts on* what the cluster told it.

### The paused lock holder

Here's the classic version at that edge, subtle enough that it has broken production systems built by careful people. Two workers use a lock service so that only one at a time writes to a shared file. The lock has a lease: it expires after 10 seconds unless renewed.

<Race a="Client A" b="Client B" result="Result: two writers, and B's write is overwritten" steps={[
  { a: "Gets the lock. It's the writer", tone: "good" },
  { a: "Stops dead: a 17-second garbage-collection pause", note: true },
  { b: "A's lease expires at the lock service. B gets the lock" },
  { b: "Writes to storage", tone: "good" },
  { a: "Wakes up, still sure it holds the lock" },
  { a: "Writes to storage, overwriting B's data", tone: "bad" }
]} />

Nothing failed here. The lock service was correct and the network was fine. Client A simply stopped running for longer than its lease, which a stop-the-world garbage collection, a VM being moved between hosts, or a heavily overloaded machine can all cause. When it resumed, its picture of the world was out of date, and it had no way to know.

### Fix: make the storage check a number

Every time the lock service grants the lock, it hands out a number one higher than the last. The client must send that number with every write, and the storage must **reject any write whose number is lower than the highest it has already seen**. That number is called a **fencing token**.

<Race a="Client A" b="Client B" result="Result: A's late write is refused, however long it slept" tone="good" steps={[
  { a: "Gets the lock with token 33" },
  { a: "Paused for 17 seconds", note: true },
  { b: "Lease expired. B gets the lock with token 34" },
  { b: "Writes with token 34. Storage records 34", tone: "good" },
  { a: "Wakes up. Writes with token 33" },
  { a: "Storage: 33 is lower than 34. Rejected", tone: "good" }
]} />

<Note type="key" label="Why fencing works when nothing else does">

Fencing doesn't need the client to be right. It needs the *storage* to check. Any scheme that relies on the paused process noticing it was paused can't work, because not noticing is the whole problem.

This is the same fencing idea introduced in [Consistency & the CAP Theorem](/guides/consistency-cap/), and it's the single most important idea in this guide.

</Note>

### The heavy-handed alternative

The other family of fixes is **STONITH**, "shoot the other node in the head". Before taking over, the new leader forcibly powers off or cuts the network of the old one, through a management interface or by blocking its access to storage. It needs infrastructure most teams don't have. But where it exists, it turns "probably dead" into "definitely dead", which is a genuinely stronger thing to know.

<Collapse id="locks" title="2. What a distributed lock can and can't promise">

A lock inside one program is real: there's one memory location and one CPU enforcing it, so taking the lock genuinely keeps everyone else out. A lock across machines is something else. It's a message saying "you may go ahead", sent over a network that can delay it, to a process that can pause right after receiving it. It's advice, not enforcement.

### First: what breaks if two holders slip through?

The answers fall into two sharply different groups:

<CardGrid>
  <Card pill="Efficiency locks" tone="mid">
    "Only one worker should rebuild this cache entry." If two do, you waste some CPU and nothing is wrong. A cheap Redis lock is fine. Failure costs money, not correctness.
  </Card>
  <Card pill="Correctness locks" tone="bad">
    "Only one process may write this file / charge this card / advance this counter." If two do, you get corrupted data or a double charge. Nothing short of consensus plus fencing tokens will do.
  </Card>
</CardGrid>

Most locks people reach for are efficiency locks dressed up as correctness locks. Classify yours honestly and most of the arguments about lock implementations disappear.

### The common Redis lock, and its two traps

The usual Redis pattern is `SET key value NX PX 30000`: set the key only if it doesn't exist, with a 30-second expiry. Each client stores its own unique value, and releases the lock with a small Lua script that deletes the key only if the value is still its own. That last detail matters:

<Race a="Client A" b="Client B" result="Result: B's lock is gone, so a third client can take it while B is still working" steps={[
  { a: "Takes the lock. Work runs long; the 30 s expiry passes" },
  { b: "Takes the now-free lock" },
  { a: "Finishes and runs a plain DEL on the key", tone: "bad" },
  { b: "Still working, but the lock it holds is gone", tone: "bad" }
]} />

Even done correctly, it's a lock on a single Redis node. If that node fails over to a replica that hadn't received the write yet, the lock vanishes:

<Race a="Client A" b="Client B" result="Result: two clients hold the same lock" steps={[
  { a: "Takes the lock on the Redis primary", tone: "good" },
  { a: "Primary crashes before copying the key to its replica", note: true },
  { b: "Replica is promoted. The key isn't there" },
  { b: "Takes the same lock on the new primary", tone: "bad" }
]} />

### Redlock, and why fencing settles the argument

**Redlock** takes the lock on several independent Redis nodes at once to get around this. Martin Kleppmann published a well-known critique: its safety depends on clocks drifting only a little and processes pausing only briefly, and you can assume neither.

The practical conclusion isn't so much "Redlock is broken" as this: if you need the guarantee Redlock is arguing about, you need fencing tokens anyway, and once you have fencing tokens, the argument stops mattering.

For correctness locks, use a real consensus store (etcd, ZooKeeper, Consul) and use the sequence number it gives you as the fencing token at the storage. That combination is sound. Anything else means deciding, hopefully on purpose, that the work occasionally running twice is acceptable.

<Lab
  title="Build a Distributed Lock with Fencing Tokens"
  tip="Add this fenced lock simulation to your portfolio to show deep understanding of distributed consistency boundary enforcement."
>

Build this mini-project to implement safe lease-based mutual exclusion using Redis and PostgreSQL/SQLite:

- **Acquire Lock & Token:** Write a script that acquires a 5-second lease in Redis for a resource name, returning a token generated by an atomic counter (`INCR lock_version:resource_id`).

- **Database Schema:** Create a mock table in SQLite or PostgreSQL:

  ```sql
  CREATE TABLE resource_state (
    id INT PRIMARY KEY,
    data TEXT,
    last_fencing_token INT DEFAULT 0
  );
  ```

- **Enforce Fencing:** Write a function to update the database state that verifies the fencing token. The database must reject the update if the incoming token is smaller than `last_fencing_token`:

  ```python
  def write_with_fencing(db_conn, resource_id, new_data, token):
      cursor = db_conn.cursor()
      # Atomic conditional update
      cursor.execute("""
          UPDATE resource_state
          SET data = ?, last_fencing_token = ?
          WHERE id = ? AND ? > last_fencing_token
      """, (new_data, token, resource_id, token))
      if cursor.rowcount == 0:
          raise Exception("Write rejected: Outdated fencing token!")
  ```

- **Simulate the GC Pause:** Spawn Client A (Token 1). Sleep A for 6 seconds to simulate a GC pause. Meanwhile, lease expires and Client B acquires lock (Token 2), writing to database successfully. Client A wakes up, tries to write, and verify that the database throws the fencing error!

<Collapse id="leases" title="3. Leases: locks that expire on their own">

A worker takes a lock, then its machine loses power. Nobody will ever release that lock, so it's held forever, and everyone else waits forever. That's why almost every practical distributed lock is really a **lease**: a lock with a time limit, which the holder must keep renewing or lose.

Why this helps: "detect that the holder died" is impossible, as [the overview](/guides/coordination-consensus/#why) showed. "Wait for the lease to run out" is easy. You've swapped an unanswerable question for a timer. The price is that the timer is a guess, which brings back the paused-process problem from [section 1](#split). Hence: leases *and* fencing tokens, always together.

### Whose clock times the lease?

Suppose the client decides for itself when its 10-second lease ends, and its clock runs slow:

<Race a="Client (clock runs slow)" b="Lock store" result="Result: the client writes after its lease was given to someone else" steps={[
  { b: "Grants a 10-second lease at 12:00:00" },
  { a: "Counts 10 seconds on its own clock" },
  { b: "12:00:10. Lease expired; grants it to another client" },
  { a: "Its clock says only 8 seconds have passed. Keeps writing", tone: "bad" }
]} />

<Note type="warn" label="Whose clock?">

The lease must be timed by the **store**, not the client.

Even at the store, measure elapsed time with a **monotonic clock**, one that only counts forward, never with the time of day. Time-of-day clocks get moved: NTP corrections, leap-second smearing and restoring a VM snapshot can all set them backwards, and a clock that jumps backwards silently extends every lease it's timing.

</Note>

### How long should a lease be?

It's the usual timeout trade-off in a new costume. A short lease (1–2 s) means fast recovery after a crash, but frequent renewals, more load on the store, and a real risk that a short GC pause loses you a lease you still needed. A long lease (30–60 s) is cheap and stable, but a crashed leader blocks progress for up to a minute.

Kubernetes' built-in leader election uses a 15-second lease. The leader tries to renew it every 2 seconds, and steps down if it hasn't managed to renew within 10. That's a reasonable middle for control-plane work, where a 15-second gap is survivable.

### A Raft leader is a lease holder

A lease is what a Raft leader has, made explicit. The heartbeat is the renewal; the election timeout is the lease length. Once you see that, "leader election" and "distributed locking" stop looking like two topics. The difference is that Raft's correctness never depends on the timer, because an old leader can't commit without a majority. Your lock-protected storage needs fencing tokens to get the same property.

<Note type="key" label="What to remember">

- A process can pause for any length of time and wake up believing it still holds a lock. Only the storage, by checking fencing tokens, can stop its late write.
- Decide whether a lock protects efficiency or correctness. Correctness needs a consensus store plus fencing; a cheap Redis lock is fine for efficiency.
- Use leases, timed by the store on a monotonic clock, so a crashed holder can't block everyone forever.

[Part 3](/guides/coordination-consensus/practice/) covers the real tools: etcd, ZooKeeper and Consul.

</Note>

</Collapse>

<Collapse id="check" title="Check your understanding">

<Quiz q="A client acquires a lease, gets paused by garbage collection, and resumes. How do fencing tokens protect the backend store from corruption?" options={["The client checks its token with the lock store before each write and aborts if it has been superseded", "The lock store closes the paused client's session, so its late write never reaches storage", "The storage resource rejects any write whose token is lower than the highest it has already seen"]} answer={2}>

The lock service hands out a higher number every time it grants the lock. Client A gets token 33. While A is paused, its lease expires and Client B gets token 34. B writes, and the storage records 34 as the highest token seen.

When A wakes and writes with token 33, the storage compares it with 34, sees it's lower, and rejects it. A can't overwrite B's data. The check has moved from the client, which can't detect its own pauses, to the storage, which can.

</Quiz>

<Quiz q="What's the difference between an efficiency lock and a correctness lock, and why does this distinction change the implementation?" options={["If an efficiency lock fails you waste some work; if a correctness lock fails you corrupt data, so only the latter needs consensus plus fencing tokens", "Efficiency locks are held briefly and correctness locks for a long time, so only the latter needs a lease", "Efficiency locks live in the application and correctness locks in the database, so only the latter survives a process pause"]} answer={0}>

An efficiency lock exists to avoid duplicate work. If it fails and two nodes hold it, you burn some CPU. The right implementation is the cheap one: a Redis `SET NX PX`, no consensus, no fencing, and an accepted small rate of doing the work twice.

A correctness lock protects a rule: one writer to a file, one charge to a card. If it fails, you get corrupted data or an angry customer. It needs a consensus-backed store *and* fencing tokens checked by the storage, because the lock alone can't survive a process pause.

The distinction matters because people argue about lock implementations in the abstract, use heavy machinery for efficiency locks, and ship correctness locks with none. Decide which kind you have first; the implementation follows.

</Quiz>
