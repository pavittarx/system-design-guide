<Collapse id="stores" title="1. etcd, ZooKeeper, Consul: what you actually get">

You will almost never implement Raft. You will run something that has, and use it as a small, strongly consistent, low-throughput key-value store with a few extra powers.

<Table numeric>

| | etcd | ZooKeeper | Consul |
| --- | ---- | --------- | ------ |
| Protocol | Raft | ZAB (Paxos-like) | Raft |
| Interface | gRPC key-value | Hierarchical znodes | HTTP/DNS key-value |
| Change notification | Watch (streaming) | Watch (one-shot) | Blocking queries |
| Ephemerality | Leases on keys | Ephemeral znodes | Sessions + health checks |
| Best known for | Kubernetes' entire state | Kafka, HBase, Hadoop | Service discovery, service mesh |

</Table>

The primitives they all provide are the same three, and they are enough to build everything in the next section: an **atomic compare-and-swap** (write only if the current version is what I think it is), a **lease or session** that expires unless renewed, and a **watch** that notifies you when a key changes so you are not polling.

<Note type="warn" label="These are not databases">

Every write goes through consensus, so throughput is in the low thousands of writes per second — for the entire cluster, not per node — and total data size should stay in the tens or low hundreds of megabytes. etcd's default database size limit is **2 GB** and you do not want to be near it.

Store *decisions*, not data: who is the leader, what is the current config, which shard lives where, which nodes are members. If you find yourself writing per-user or per-request records into etcd, you have chosen the wrong tool with unusual confidence.

</Note>

The other thing to internalise is that the coordination store becomes a dependency of everything that uses it, which makes it a single point of failure with unusually broad blast radius. When etcd is unhealthy, Kubernetes cannot schedule, scale, or reconcile anything. Design so that a coordination outage degrades you to "cannot change" rather than "cannot serve" — running workloads should keep running on their last-known-good configuration, exactly as a service should keep serving from a stale config cache rather than crash-looping.

</Collapse>

<Collapse id="patterns" title="2. Patterns built on top">

Given compare-and-swap, leases and watches, the standard patterns fall out.

<Stack>
  <Layer idx="A">**Leader election.** Everyone tries to create the same key with a lease, using create-if-absent. Exactly one succeeds and renews it; the rest watch the key and retry when it disappears. Kubernetes controllers do precisely this.</Layer>
  <Layer idx="B">**Service discovery.** Each instance registers itself under a prefix with a lease and heartbeats. Consumers watch the prefix and get the live membership. A crashed instance's lease expires and it vanishes from the set without anyone deregistering it.</Layer>
  <Layer idx="C">**Dynamic configuration.** Config lives in a key; services watch it and reload on change. Add a version number and you get instant, ordered, auditable rollouts — with the Cloudflare lesson from [CDNs & the Edge](/guides/cdn-edge/) firmly in mind, roll changes out gradually rather than to everyone at once.</Layer>
  <Layer idx="D">**Membership and sharding.** The current member list lives in the store; a leader assigns shards to members and writes the assignment back. When membership changes, the leader recomputes and everyone watches for their new assignment — combine with consistent hashing from [Load Balancing](/guides/load-balancing/) so a membership change moves 1/*n* of the keys rather than all of them.</Layer>
  <Layer idx="E">**Barriers and queues.** Ordered keys under a prefix give you a fair queue; a counter plus a watch gives you a barrier that releases when the last participant arrives. Useful for batch coordination, rarely worth it for anything on a request path.</Layer>
</Stack>

Notice what these have in common: the store holds a small amount of slowly-changing truth, and everything else *watches*. The data plane never asks the store a question per request. If your request path contains a synchronous call to etcd, you have made a 2,000-writes-per-second component into the ceiling for your entire system.

</Collapse>

<Collapse id="avoid" title="3. How to need less of this">

Every technique here has a cost in latency, operational complexity, and new failure modes. The best coordination is the coordination you designed away, and there are four reliable ways to do it.

<CardGrid>
  <Card pill="Partition the problem" tone="good">
    If each key is owned by exactly one shard and each shard by one process, there is nothing to agree about. Consistent hashing plus stable ownership eliminates most locks outright. Coordination is only needed at the boundary — when ownership changes.
  </Card>
  <Card pill="Make operations idempotent" tone="good">
    If running twice is the same as running once, you no longer need to guarantee it runs once. Idempotency keys, upserts, and conditional writes convert an exclusion problem into a deduplication problem, which is far easier — see [Message Queues & Async](/guides/message-queues/).
  </Card>
  <Card pill="Push it into the database" tone="good">
    A single-row conditional update, a unique constraint, or a `SELECT … FOR UPDATE` gives you real mutual exclusion using a transaction manager you already run and already monitor. One less system to lose quorum.
  </Card>
  <Card pill="Use commutative operations" tone="good">
    If the operations commute, order stops mattering and so does agreement about it. Counters, sets and CRDTs from [Consistency & the CAP Theorem](/guides/consistency-cap/) converge without any coordination at all.
  </Card>
</CardGrid>

The general principle is worth stating plainly: coordination is a *tax on every operation that requires it*, so make the set of such operations as small as you can. Most systems need strong agreement about a handful of things — who owns what, what the config is, who is primary — and need nothing at all about the millions of operations that follow from those answers. Keep the two categories separate and the expensive one small.

</Collapse>

<Collapse id="gotchas" title="4. The gotchas that actually bite">

<Note label="1 · Two-node clusters">
A two-node cluster tolerates zero failures and has twice the hardware to fail. It is strictly worse than one node. This mistake is usually made by a team that thinks "redundancy" and hears "two".
</Note>

<Note label="2 · Locks without fencing tokens">
The GC-pause trace in [Part 2](/guides/coordination-consensus/safety/#split) is not exotic; it is a Tuesday on an oversubscribed host. If a lock protects correctness and the resource does not reject stale tokens, you have a corruption waiting for a slow enough garbage collection.
</Note>

<Note label="3 · Wall-clock leases">
NTP corrections, leap-second smearing, and VM snapshot restores all move wall clocks. A clock that jumps backwards silently extends every lease it times. Use monotonic clocks for durations, always.
</Note>

<Note label="4 · The store on the request path">
A consensus store does low thousands of writes per second, cluster-wide. Reading it once per request makes it your throughput ceiling and your availability floor. Watch and cache; never poll per request.
</Note>

<Note label="5 · Stretching the cluster across regions">
Every write waits for a majority. Spread the majority across oceans and every write pays 150 ms+ forever. Keep the quorum local; replicate its decisions outward asynchronously.
</Note>

<Note label="6 · Automatic failover with no witness">
Automatic promotion on a partition is what produced GitHub's 24-hour incident. Either give the decision to a majority that spans the partition boundary (an odd number of sites, or a lightweight witness in a third), or require a human. Two sites and automatic promotion is a split brain generator.
</Note>

<Note label="7 · Watches you assume are reliable">
Watch streams disconnect. ZooKeeper watches fire once and must be re-registered, and events between disconnect and re-registration are simply missed. Always reconcile against the full current state after reconnecting rather than trusting that you saw every event.
</Note>

</Collapse>

<Collapse id="check" title="Check your understanding">

<Quiz q="Your service reads its feature flags from etcd on every request. What's wrong and how do you fix it?" options={["etcd's linearizable reads are slow; switch those reads to serializable mode and keep reading per request", "etcd becomes your throughput ceiling and availability floor; load the flags once, watch for changes, and serve from memory", "Nothing, as long as the cluster has five nodes; add nodes if read latency grows"]} answer={1}>

You have coupled your request throughput and availability to a component designed for neither. etcd handles low thousands of operations per second cluster-wide, so it becomes your ceiling; and when it is unavailable — during a rolling upgrade, a leader election, a partition — your service stops serving rather than merely stopping updating.

The fix is to invert it: read the flags once at startup, hold them in memory, and register a *watch* so etcd pushes changes to you. Request handling then touches only local memory. Keep serving the last known values if the watch disconnects, reconcile against the full current state on reconnect (watches miss events across disconnects), and persist a copy to local disk so a restart during an etcd outage still comes up with sane configuration.

The general rule: a coordination outage should degrade you to "cannot change" rather than "cannot serve".

</Quiz>

</Collapse>
