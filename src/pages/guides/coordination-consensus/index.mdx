<ColdOpen tag="◇ 21 October 2018, GitHub">

Routine work replacing failing optical equipment cuts the link between GitHub's East Coast network hub and its primary East Coast data centre. The link is back in **43 seconds**. In those 43 seconds, the failover system does exactly what it was built to do: the primary database can't be reached, so it promotes the databases on the West Coast to primary and sends writes there.

But the East Coast primary had taken a few seconds of writes that never reached the West. Now each site holds writes the other doesn't have, and there's no automatic way to merge them. GitHub spends **24 hours and 11 minutes** degraded, much of it restoring terabytes of backups and re-syncing replicas, and the leftover writes are reconciled by hand afterwards. The fibre wasn't the failure. The failure was that a system decided the old leader was dead when it was only out of reach.

</ColdOpen>

<Collapse id="why" title="1. Why you can't tell slow from dead">

Ask one process what `x` is and you get an answer. Ask five, and you've created a research problem. That's because the network between them can do three things to any message: deliver it, lose it, or deliver it much later than you expected. And the sender can't tell which one happened.

### Two machines, one missing reply

Here's the smallest version of the problem: a monitor checking on a database primary.

<Race a="Monitor" b="Primary" result="Result: the monitor has to guess, and either guess can be wrong" steps={[
  { a: "Sends \"are you alive?\"" },
  { b: "Busy: a 12-second garbage-collection pause", note: true },
  { a: "No reply after 5 s. Dead? Or the reply was lost? Or just slow?" },
  { a: "Gives up waiting and declares it dead. Promotes a replica", tone: "bad" },
  { b: "Pause ends. Carries on as primary, unaware", tone: "bad" }
]} />

From the monitor's side, "the message never arrived", "the reply got lost", "the machine crashed" and "the machine is just busy" all look the same: silence. Nothing it can measure tells them apart.

<Note type="key" label="The one fact underneath everything in this guide">

In a network with no limit on how long a message can take, **you cannot tell a slow node from a dead one.** Not with a better timeout, not with a better heartbeat, not with a smarter algorithm. The information needed to tell them apart doesn't exist at the observer.

</Note>

### Every failure detector is a timeout, and every timeout is a guess

This is the direct cause of the GitHub incident above and of most outages in this guide. Every way of detecting a failure comes down to "no answer within N seconds". Set N short and you declare healthy nodes dead, triggering failovers you didn't need. Set it long and real failures go unnoticed while requests pile up behind a dead machine. There's no correct value, only a trade-off you're making, usually without writing it down.

### There's a proof that it can't be perfect

The formal version is the **FLP impossibility result** (Fischer, Lynch and Paterson, 1985). In a system where messages can take any amount of time, and even one node might crash, no step-by-step (deterministic) algorithm is guaranteed to get the nodes to agree on a value. Not "no fast algorithm": none. Any algorithm can be kept undecided forever by unlucky message timing.

### How real systems get around it

They make a weaker promise. Raft and Paxos, the algorithms you'll meet in [Part 1](/guides/coordination-consensus/raft/), are always **safe**: they never make two conflicting decisions. But they're only guaranteed to make *progress*, called **liveness**, when the network behaves for long enough. If messages keep arriving late at exactly the wrong moments, a Raft cluster can hold election after election and never pick anyone. It won't be wrong; it'll just be stuck.

In practice, random timeouts make that vanishingly unlikely. That's engineering's usual answer to an impossibility proof: make the bad case rare rather than absent.

</Collapse>

<Collapse id="leader" title="2. Why systems pick one leader">

Two database nodes both accept writes. At the same moment, a user changes their email to `a@x.com` on one node and, from another tab, to `b@x.com` on the other:

  { a: "Accepts: email = a@x.com" },
  { b: "Accepts: email = b@x.com" },
  { a: "Sends its change to Node 2" },
  { b: "Sends its change to Node 1" },
  { a: "Now holds b@x.com", tone: "bad" },
  { b: "Now holds a@x.com", tone: "bad" }
]} />

Each node applied the other's change last, so they swapped answers instead of agreeing. With *n* nodes all making decisions, every pair can disagree like this. The most effective simplification in distributed systems is to pick one node, the **leader**, and send every decision through it. Picking it is called **leader election**. Now the system is one machine making decisions in order, which you already know how to reason about.

### Leaders are everywhere once you look

The primary in a replicated database orders all writes. The controller in a Kafka cluster assigns partitions. The Kubernetes scheduler decides where pods run. The coordinator of a sharded system decides who owns which range. In each case the leader isn't there to be faster. It's there because having exactly one writer removes a whole category of conflicts.

<Note type="wild" label="◈ In the wild · Google Chubby">

Much of this pattern traces back to Google's [Chubby](https://research.google/pubs/the-chubby-lock-service-for-loosely-coupled-distributed-systems/), a small, strongly consistent lock service built on Paxos. Its main use turned out to be not locking but leader election and naming: GFS and Bigtable pick their primary by racing to grab one Chubby lock, and the winner leads. It directly inspired ZooKeeper.

</Note>

<CardGrid>
  <Card pill="What a leader buys you" tone="good">
    One order for all events. No conflicting writes to merge. Simple rules ("only the leader may do X"). One place for caches, rate limits and admission control. Straightforward reasoning during incidents.
  </Card>
  <Card pill="What it costs you" tone="bad">
    A throughput ceiling of one machine. A gap in service every time the leader dies. A new way to fail, two leaders, that's worse than having none. Extra latency for anyone far from the leader.
  </Card>
</CardGrid>

### The gap when a leader dies

That gap, the **failover window**, is the part people underestimate. Between "leader dies" and "new leader is serving", nobody can write. The gap is at least three things added together:

- the time to notice, which is your failure-detection timeout;
- the election itself;
- the new leader catching up on any writes it was missing.

A well-tuned etcd cluster does this in a second or two. A database with a 30-second detection timeout and a large replication backlog can take minutes. Your availability budget from [The Reliability Toolkit](/guides/reliability-toolkit/) has to pay for every one of those gaps.

<Note type="key" label="What to remember">

- A missing reply looks the same whether the other machine is dead, slow, or cut off. Every failure detector is a timeout, and every timeout is a guess.
- No algorithm can guarantee agreement in every timing. Real ones never decide two conflicting things, and accept that they're occasionally stuck.
- One leader removes whole classes of conflict, at the cost of a failover gap and the risk of two leaders.

</Note>

</Collapse>

<Collapse id="check" title="Check your understanding">

<Quiz q="Why is a perfect failure detector impossible in an asynchronous network?" options={["Heartbeats cannot be sent often enough to catch every failure in time", "Network delay is unbounded, so to the observer a slow node and a dead node look identical", "Clocks on different machines drift, so no two nodes measure a timeout the same way"]} answer={1}>

Because you can't tell a slow node from a dead one. In an asynchronous network there's no upper limit on how long a message can take, so a heartbeat might be delayed for any amount of time. Whatever timeout you choose, a healthy but slow node, or one cut off by a network partition, can exceed it and be wrongly declared dead.

This limit, formalised in the FLP impossibility result, is why failure detection always trades false alarms (failovers you didn't need) against slow reactions (noticing real failures late).

</Quiz>
